## 2. Причина (установлена экспериментально)

**Кука сессии ставится с флагом `Secure` (backend/app/auth.py:103), а вход Заказчика происходит не по trustworthy-origin.** Эксперимент: тот же стенд, но origin `http://wiki-local.test:8931` (имитация «http поверх не-localhost», как у пользователя НЕ на машине сервера) — при логине:

- ответ `POST /api/auth/login` — **200**, тело `{"ok":true}` — сервер сессию создал и куку отправил;
- браузер куку **молча не сохранил** (`context.cookies() → []`): Secure-кука по http принимается только с localhost/127.0.0.1 (trustworthy origin по RFC 6265bis / Secure-cookies spec);
- login.js делает `window.location.href="/board"` — URL меняется, но при любом следующем переходе middleware не находит куки → **302 на /login** (страница рендерится заново как «Вход»);
- в итоге Заказчик «находится» на /search по URL без авторизации; `loadSuggestions()` получает **401** и по своему дизайну молча оставляет datalist пустым (`if (!response.ok) return null`, search.js:518) — **значения не появляются, ошибок в консоли нет**.

Это в точности симптом жалобы: «эндпоинт отвечает (401 без сессии подтвержден), в UI значения не появляются» и никакой JS-ошибки. На http-стенде localhost (тесты, разработка) дефект не воспроизводится — потому ворота (веб-сьют) зеленые.

Важно (ОБНОВЛЕНИЕ от 2026-09-27, задача DEV 5.2): гипотеза «Заказчик входит по http» СНЯТА. Заказчик подтвердил дословно: «я вхожу по https//ip:port и принимаю ошибку сертификата» — вход по **https** с self-signed исключением (проверено: сертификат прод-сервера CN=issuer=194.58.34.122). Такой origin — trustworthy, браузер **сохраняет** Secure-куку. Воспроизведение прод-сценария на стенде (см. §3-бис) подтвердило: **на текущем коде дефект НЕ воспроизводится** — вся цепочка зеленая (9 подсказок в datalist, селект из справочника, 0 ошибок консоли). Возможные объяснения исходной жалобы: (а) дефект устранен попутно другими правками после снятия жалобы (кеш-бастинг `?v=static_v` DEF-003 — застарелая статика без привязки данных была в кеше браузера Заказчика); (б) у Заказчика в момент жалобы был http-набор адреса/другой браузер без принятого исключения. Закрытие — за задачей 5.3 (подтверждение в реальной сессии на проде).

## 3. Что чинить (предложение фикса 5.1 → реализовано в 5.2)

**Первичный фикс — среда, не код:** убедиться, что Заказчик входит строго через `https://194.58.34.122:10443` (схема https!). nginx на 80-м порту отсутствует в конфигах deploy — стоит добавить `listen 80 → 301 https://...` редирект, чтобы http-набор IP:10443/80 не оставлял пользователя в «полу-авторизованном» состоянии (сейчас опечатка в схеме дает именно немую потерю сессии).

**Кодовой фикс (реализован в 5.2, защита от немого отказа; малый и безопасный):**
1. `frontend/static/js/login.js`: после успешного `POST /api/auth/login` (200) — контрольный `GET /api/auth/me`; при 401 (кука Secure молча не сохранилась — не-trustworthy origin) вместо немого редиректа на /board показывается сообщение «Сессия не сохранена. Откройте сайт по адресу https://194.58.34.122:10443 …» и пользователь остается на странице входа. При 200 — прежний редирект на /board.
2. `frontend/static/js/search.js` (`loadSuggestions`): при 401 `GET /api/suggestions` — неблокирующее предупреждение в `#search-error` («Подсказки недоступны: сессия не активна. Откройте сайт по адресу https://…») вместо прежней тишины (именно тишина `if (!response.ok) return null` замаскировала дефект). Поиск при этом работает: подсказки необязательны (режимы поиска не блокируются, страница не покидается).
3. Secure-кука НЕ ослаблена (`backend/app/auth.py:136` — `secure=True` без изменений, NFR-7); backend-правок нет.

Проверка сценариев фикса (playwright, https-стенд): S1 happy-path без регресса (логин → /board, 9 подсказок, предупреждение скрыто); S2 логин 200 + контрольный me=401 (мок) → сообщение показано, на /board НЕТ редиректа; S3 /search с suggestions=401 (мок) → предупреждение видно, страница на месте, 0 pageerror.

Опционально (механизм, требующий решения архитектора): ослаблять Secure на проде нельзя (NFR-7), поэтому только схема https + явный редирект + внятное сообщение пользователю.
