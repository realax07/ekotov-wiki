## Ревью №1 — 2026-10-19, роль: архитектор (СА), Флоу 1, волна 2 (VALID_GATE)

**Предмет:** пакет weather-service @ 827f26a (proposal, дельта
specs/weather-service — 14 Requirements / 23 сценария — счетчики сверены
подсчетом, design r1, tasks.md; мокап design/p18-weather/variant-a.html
утвержден 2026-10-19). `openspec validate weather-service --type change
--strict` — green (прогон этого прохода).
**Метод:** прицельные проверки по 6 точкам мандата: границы сайдкара без БД,
nginx auth_request против прод-паттерна видео, отказные сценарии провайдера,
Open-Meteo без секретов, static_v/R7-урок, реалистичность NFR.

### Прицельные проверки

1. **Сайдкар weather:8381 без БД — границы выведены корректно.** Единственное
   состояние — кэш-файл в named volume `weather-cache` (атомарная запись
   tmp + `os.replace`, design §2/§4), переживает down/up (сценарий «Кэш в
   томе переживает пересоздание контейнера»); RW-маунт ровно один, миграций
   нет и MUST NOT (сценарий «Миграций у пакета нет», `MIGRATE_MODULE` не
   трогается). Отклонение альтернатив (БД-кэш, память процесса) обосновано
   в design §8; том против «памяти» — верный выбор (первый запрос после
   рестарта не бьет в провайдера). Логика чтения §4 (свежий кэш → без вызова
   провайдера; истек → провайдер; отказ → stale-кэш без перезаписи; пустой
   кэш + отказ → 503, файл не создается) согласована со сценариями спеки
   1:1, противоречий спека↔дизайн по отказам провайдера не найдено
   (таймаут 5 с × 2 + пауза 1 с = ~11 с потолок — spec Req «Таймауты…»,
   NFR «Отзывчивость…», design §3 — числа сходятся). Замечаний нет, кроме
   O1/O2 (наблюдения ниже).
2. **nginx auth_request — отклонение от прод-паттерна видео (находка F1).**
   В проде паттерн video разделяет два случая: API-локации (`= /api/videos`,
   `^~ /api/videos/`) НЕ имеют auth_request — сессию проверяет сессионный
   middleware сервиса (401 JSON); auth_request → `/_video_auth` стоит ТОЛЬКО
   там, где nginx сам отдает контент (`/videos/` alias), т.е. где проверять
   некому (services/frontend/nginx/videos-proxy.inc, ekotov-wiki.conf §5/§6).
   Design §5 weather ставит `auth_request /_weather_auth` на ОБЕ API-локации
   при том, что у weather есть свой middleware (spec Req «API погоды…»):
   каждый запрос `/api/weather` = два похода в сервис (subrequest authcheck
   + основной прокси) с двойной валидацией одной сессии — дублирование,
   которого у прецедента нет. Дополнительно сниппет §5 не переносит два
   урока прод-инсов видео: (а) `proxy_pass http://weather:8381` статическим
   именем без переменной резолвится один раз на старте — nginx не стартует
   без контейнера weather и держит мертвый IP после пересоздания (прямо
   написано в шапке videos-proxy.inc; сам design §5 текстом заявляет
   «старт nginx без weather безопасен», а сниппет этого не обеспечивает);
   (б) не решена семантика `proxy_intercept_errors`: у видео он включен,
   но у weather сервис СА отвечает управляемым 503 `weather_unavailable`
   (spec «Пустой кэш…») — слепое копирование intercept on под
   `error_page 503 = @weather_down` подменит честную JSON-ошибку сервиса
   общей деградацией nginx.
3. **Отказные сценарии провайдера — согласованы** (см. п.1). Битый
   JSON/неполный ответ = недоступность, кэш не затирается (spec «Битый
   ответ…» ↔ design §3/§4) — противоречий нет. Единственный содержательный
   пробел провайдера — единицы измерения (находка F2).
4. **Open-Meteo без секретов — скрытых зависимостей по rate-limit нет.**
   Бесплатный тариф: ~600 запросов/мин, ~5 000/час, ~10 000/сутки на IP —
   при TTL 60 мин и 2–3 пользователях это ≤ 24 обновления/сутки плюс
   единичные повторы: запас > 2 порядков. Ключ не нужен, секретов нет
   (User-Agent в конфиге — правильно). НО: у Open-Meteo `wind_speed_10m`
   по умолчанию в **км/ч**, а спека требует ветер в **м/с** (сценарий
   «Полная карточка…»: «румб по русским румбам, м/с»; контракт §6
   `"speed": 5`) — ни параметр `wind_speed_unit=ms`, ни конверсия
   (×0.2778) в design §3 «Преобразования» не названы (там только давление
   и румбы) — F2. Вторая мелочь того же шва: в current запрошено поле
   `precipitation` (это **мм** осадков), а карточка показывает «осадки
   (%)» и контракт `"precipitation": 80` — по design §3 это
   `precipitation_probability_max` из daily[0]; поле current при этом не
   используется нигде — либо убрать из запроса, либо зафиксировать смысл
   поля контракта.
5. **static_v / R7-урок — обязанность ПМ зафиксирована, но шов поставки
   страницы недоопределен (находка F3).** Релизный бамп как дисциплина
   присутствует: tasks 5.1 [pm] (прецедент P11), design §7, AGENTS-урок
   «пропущенный бамп = фикс не работает» учтен процессно. Однако
   `static_v` — Jinja-глобал (backend/app/pages.py:44) и попадает ТОЛЬКО
   в страницы, отрендеренные ядром; все страницы стека рендерятся ядром
   из frontend/templates (в образ nginx статика копируется, шаблоны —
   нет, services/frontend/Dockerfile: «templates НЕ копируются»). Страница
   /weather же отдается nginx'ом как статика (design §5/§8): ее ссылки на
   CSS/JS заморожены на момент сборки образа, бамп static_v в pages.py
   (волна 5) эту страницу не инвалидирует — механизм кеш-бастинга для
   собственного HTML/CSS/JS страницы в пакете не назван. И второе: каркас
   сайдбара «дословно из base.html» в статическом HTML — вторая копия
   шаблона, который живет в app-образе: правка сайдбара (а она ОБЯЗАТЕЛЬНА
   — spec «Пункт сайдбара виден авторизованным»: «открыл ЛЮБУЮ страницу» →
   правится base.html в ядре) требует ручной синхронизации двух копий в
   двух образах — дрейф, которого паттерн /video (Jinja-рендер ядра,
   middleware дает 401-редирект бесплатно) не имеет. Аргумент §8 «не грузит
   ядро» при 2–3 пользователях и одном статичном route несущественен.
6. **NFR-числа реалистичны.** mem_limit 128m для FastAPI+httpx без БД и без
   ffmpeg — с запасом (прецедент: netdata 256m, nginx 64m); резерв хосту
   ≥ 2 GB — проверка задачей 4.2/5.2; потолок ~11 с при 1 воркере для
   2–3 пользователей приемлем при async-клиенте (см. O3).

### Находки

- **F1 (Must, до старта dev):** design §5 — nginx-сниппет отклоняется от
  прод-паттерна видео в трех местах: (а) auth_request на API-локациях
  дублирует сессионный middleware сервиса — по прецеденту video
  auth_request нужен только на статической странице `/weather` (там nginx
  сам отдает контент), API-локации — middleware 401 JSON (заодно отпадает
  exempt-контракт authcheck на servisном маршруте — он остается нужен
  только для `/_weather_auth`); (б) `proxy_pass` статическим именем без
  переменной + resolver — не обеспечивает заявленный в тексте §5 и в спеке
  («старт nginx без weather безопасен») анти-stale-DNS; нужен паттерн
  `$upstream_weather` из videos-proxy.inc; (в) семантика
  `proxy_intercept_errors` не решена: для `/api/weather*` должен быть off
  (сервис сам отвечает управляемым 503 — иначе сценарий «Честное
  сообщение…» деградирует до общей @weather_down). Правки: design §5
  (+ текст спеки Req «nginx-маршрутизация…», который канонизирует
  auth_request на «обеих локациях» — формулировку сузить до страницы).
- **F2 (Should, до старта dev):** единицы ветра и семантика осадков:
  design §3 — добавить `wind_speed_unit=ms` в запрос (или конверсию
  км/ч → м/с в «Преобразования»), иначе спека «ветер … м/с» не
  обеспечивается; зафиксировать, что контрактное `precipitation` карточки
  «Сегодня» = probability (%) из daily[0], а `current=precipitation` (мм)
  либо исключить из запроса, либо описать его назначение. Правки: design
  §3/§6, сценарий «Запрос к провайдеру…» (перечень полей).
- **F3 (Should, до старта dev):** шов поставки страницы /weather: либо
  перевести страницу на рендер ядром (паритет /video: Jinja-шелл из
  base.html, active_page='weather', middleware-редирект бесплатно,
  static_v работает из коробки) — тогда §5 упрощается до одной
  API-семейства и статического auth_request не требуется вовсе; либо
  оставить nginx-статику, но явно зафиксировать: (а) механизм
  кеш-бастинга собственных ассетов страницы (собственный ?v= маркер
  страницы, бампимый тем же релизным проходом, что и static_v — задача
  5.1), (б) обязанность синхронизации сайдбар-копии с base.html при любой
  его правке (RUNBOOK/задача 3.3). Текущая формулировка «поставка
  static_v-бампом» для статического HTML не работает.

### Наблюдения (не блокеры, без правки пакета)

- **O1:** гонка обновления кэша: при истекшем TTL два одновременных запроса
  могут оба пойти в провайдера (in-process lock не назван). При 2–3
  пользователях и квотах Open-Meteo — безвредно; можно закрыть простым
  asyncio.Lock в задаче 3.2 без изменения спеки.
- **O2:** поведение при невозможности ЗАПИСАТЬ кэш (том переполнен/ro) не
  описано: ожидаемо — лог + ответ пользователю как при успехе получения
  (или деградация), кэш прежний. Стоит одной строки в design §4 при
  следующей правке.
- **O3:** при отказе провайдера worst-case ~11 с на 1 uvicorn-воркере:
  чтобы `/api/health` не флапал в этот window (timeout healthcheck ~5 с в
  шаблоне video), клиент провайдера должен быть async (spec «воркер
  сервиса не блокируется» это подразумевает — зафиксировать в задаче 3.1).
- **O4:** активное состояние пункта сайдбара на статической странице
  (`{% if active_page %}` в base.html не исполнится) — решается вместе с
  F3 (при рендере ядром — бесплатно).

### Вердикт

**RETURN.** Границы сайдкара (кэш-файл в томе, без БД, атомарная запись,
переживание down/up) и отказные сценарии провайдера согласованы спека↔дизайн
без противоречий; rate-limit Open-Meteo при 60-мин кэше и 2–3 пользователях
не является зависимостью. Но до старта dev (волна 3) требуются правки:
F1 (Must) — nginx-сниппет §5 к прод-паттерну видео (auth_request только на
странице, переменная+resolver, intercept off) + сужение формулировки Req
«nginx-маршрутизация…»; F2 (Should) — единицы ветра/семантика осадков
(design §3/§6 + сценарий параметров запроса); F3 (Should) — шов поставки
страницы (рендер ядром паритет /video — предпочтительно, либо явный
кеш-бастинг + синхронизация сайдбара). Правки — автору пакета (СА), затем
контрольный проход архитектора по Fixes; validate --strict сохранять green
на каждой правке.
