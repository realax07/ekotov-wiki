# Design: video-hosting

Версия: r2 (2026-10-17; r1 — базовый пакет, r2 — кусок D + превью в B по
утвержденным мокапам). Источники: requirements.md пакета (ОВ-1…ОВ-4 —
PLAN-video-hosting.md), прецеденты: `services/images` (Dockerfile, compose,
nginx include-паттерн, сессионный middleware, лимит до записи),
master-spec `gallery` (деградация 503, отдача из тома, комментарии/лайки/
категории — образец социального слоя D), `/avatars/` ядра
(том вне репо/БД). СА дизайн НЕ рисует — мокапы исполняет ui_designer (§0).

## §0. Дизайн-фаза (Д-паттерн Р4/Р5; этап 1 плана)

Видео — крупная видимая UI-дельта: **ui_designer** готовит мокапы в
`design/` (standalone HTML, токены V3 «Бумага», без внешних
библиотек/CDN — ОГР-8): страница `/video` — список карточек (превью,
имя, статус, размер, дата; плейсхолдер несконвертированного; индикатор
конвертации), форма загрузки (индикация прогресса/ошибки лимита 500 МБ),
встроенный плеер `<video>`, подтверждение удаления; пункт сайдбара
«Видео» (после «Галерея», иконка в едином стиле). **Утверждение
Заказчиком — развилка до dev-задач куска A**; после dev —
design_validator против мокапов. Статус r2: мокапы (`design/video-hosting/`)
**утверждены Заказчиком 2026-10-17, включая блоки куска D** — комментарии,
лайки/дизлайки, выбор/фильтр категории; dev-задачи всех кусков идут по
утвержденным мокапам.

## §1. Целевая топология

```
Браузер (owner/PE) ── https://…:10443 ── nginx [frontend]
   ├── /video                  → app:8377 (страница, сессия ядра; паритет /gallery)
   ├── = /api/videos           → video:8380 (пара = + ^~, паттерн images)
   ├── ^~ /api/videos/         → video:8380 (API: upload/list/delete/file/preview/health)
   ├── /videos/                → alias том videos-data (ro) + auth_request → video (§5)
   └── остальное               → как сейчас (app, search, images, backup, netdata)

app:8377     — ядро: страница /video + миграция таблицы video_videos (one-shot)
video:8380   — FastAPI (uvicorn 1 воркер): API видео, фоновая конвертация (§3),
               RW-профиль БД (своя таблица video_videos), том videos-data RW
```

- Наружу открыт только nginx :10443 (FR-65-преемственность) — `video`
  порты НЕ публикует (паритет app/search/images).
- При отказе `video` nginx отвечает на `/api/videos*` и `/videos/`
  быстрым управляемым 503 (JSON + Retry-After, паттерн `@images_down`);
  остальные маршруты работают.

## §2. Контейнер и образ: services/video (по образцу images)

`services/video/Dockerfile` — копия схемы `services/images/Dockerfile`
(python:3.12-slim, deps слоями с пинами fastapi/uvicorn/python-multipart,
код в `/srv/app`, USER 10001, EXPOSE 8380, healthcheck через urllib без
curl, CMD uvicorn 1 воркер) с двумя отличиями:

1. **ffmpeg — статический бинарь в образе, НЕ apt** (ограничение ТЗ;
   slim-база + apt-ffmpeg тянет десятки пакетов и непредсказуемые версии).
   На этапе сборки скачивается pinned-релиз статической сборки
   (johnvansickle/ffmpeg-release-amd64-static; версия и SHA256 фиксируются
   в Dockerfile — воспроизводимость, паритет пинам pip-слоя), checksum
   проверяется в RUN, бинарь кладется в `/usr/local/bin/ffmpeg`
   (плюс `ffprobe` из того же tarball — определение длительности/кадров).
   При недоступности внешнего источника на сборке — fail fast (сборка
   ломается, тихой подмены на apt нет).
2. Данные в образе НЕТ: БД томом `wiki-data:/data:rw`, файлы видео томом
   `videos-data:/data/videos` (env: `EKOTOV_WIKI_DB_PATH`,
   `EKOTOV_WIKI_VIDEOS_DIR` — дефолты кода `/data/wiki.db`, `/data/videos`).

compose-сервис `video` в `deploy/compose.yaml` (паритет images):
`restart: unless-stopped`, `mem_limit: 512m` (ffmpeg-буферы при 500 МБ
исходнике больше, чем у Pillow; факт — замер NFR-35 на стенде, стабильное
превышение = эскалация до прод), healthcheck тот же шаблон (:8380),
`depends_on: [app]` (схему БД создает миграция ядра), ротация логов
json-file 10m×3, порты не публикуются. Суммарный резерв хосту ≥ 2 GB —
проверка в задаче deploy (NFR-35/прецедент NFR-20).

## §3. Фоновая конвертация: subprocess + статус в БД, без брокера

**Решение:** внутрипроцессная фоновая задача сервиса (thread + FIFO-очередь
в памяти, `queue.Queue`, 1 поток-воркер) + `subprocess.run(ffmpeg …)`;
статус — колонка в БД. Очередь-брокер (RabbitMQ/Redis/celery) НЕ вводится:
2 пользователя, конвертация ≤ 1 одновременно, жизненный цикл пакета —
один контейнер; брокер — вне скоупа Уровня 1 (PLAN) и нарушает ОГР-масштаб
(YAGNI, прецедент отказа от выделения auth).

Механика:

- **Серийность:** ровно одна конвертация одновременно (поток-воркер берет
  из очереди по одному) — предсказуемый профиль RAM/CPU для NFR-35 и p95
  NFR-37; загрузка/список/удаление живут в основном потоке uvicorn и не
  ждут воркер.
- **Команда:** `nice -n 10 ffmpeg -i <orig> -c:v libx264 -preset veryfast
  -movflags +faststart <out.mp4>` (faststart — прогрессальная отдача
  `<video>`), превью: `ffmpeg -i <orig> -frames:v 1 preview.jpg`. Запуск
  через subprocess с `preexec_fn=lambda: os.nice(10)` — пониженный
  приоритет CPU против запросов API.
- **Превью-кадр — вместе с конвертацией (кусок B; перенос из C, решение
  Заказчика 2026-10-17):** воркер снимает первый кадр тем же проходом
  обслуживания файла и кладет `preview.jpg` в том рядом с mp4
  (`<id>/preview.jpg`, storage §5). Для файла, уже являющегося mp4
  (вырожденная конвертация), кадр тоже снимается — быстрым дешевым
  проходом `ffmpeg -frames:v 1` (без перекодирования). До готовности кадра
  список показывает плейсхолдер по макету; кадр не является условием
  статуса `ready` только в том смысле, что ставится тем же шагом воркера —
  при неудаче снятия кадра фиксируется неудача попытки (ветка ретрая).
- **Timeout:** `subprocess` с жестким wall-clock-таймаутом 30 мин (500 МБ
  worst-case; истечение = kill процесса = неудача попытки → ветка ретрая).
  Зависший ffmpeg не может заблокировать очередь дольше таймаута.
- **Статусы:** `uploaded` → `converting` → `ready`; `error` после
  исчерпания повторов («загружено»/«конвертируется»/
  «готово»/«ошибка»). Пишет статус ТОЛЬКО поток-воркер (один писатель
  статуса — нет гонок с API; API читает).
- **Ретрай:** при неудаче попытки (non-zero exit / timeout / отсутствия
  выходного файла) — ровно один автоматический повтор; после второй
  неудачи — `error`, оригинал сохраняется (требование ТЗ).
- **Успех:** mp4 + preview кладутся в том (storage-модуль), оригинал
  удаляется, статус `ready`, размер в метаданных обновляется.
- **Крэш-восстановление:** на старте контейнера записи в статусах
  `converting` (контейнер умер посреди конвертации; файл оригинала на
  месте, частичный mp4-артефакт удаляется перед повтором) И `uploaded`
  (поставлена в очередь до сбоя, но воркер не начал: очередь в памяти
  потеряна — без re-enqueue запись навсегда застревает в «загружено»)
  переводятся в очередь заново. Инвариант: после старта воркера в БД
  нет записей `uploaded`/`converting`, которых нет в очереди.
- **Удаление во время конвертации:** DELETE ставит флаг отмены (in-memory,
  по id); воркер перед записью результата проверяет флаг/статус записи —
  при отмене артефакты отбрасываются, ничего не пишется. Ровно один
  владелец очереди — модуль `converter.py` (шов — sdd §3).

## §4. Лимиты: 500 МБ до записи, ресурсы конвертации

- **Сервис:** размер загрузки проверяется ДО записи файла на диск — по
  `Content-Length` (ответ 422 «файл больше 500 МБ» еще до чтения тела;
  паритет images/NFR-21-паттерн) + потоковое чтение с накопленным
  счетчиком как страховка от отсутствия/лжи Content-Length (обрыв чтения
  = 422, диск не расходуется сверх лимита).
- **nginx:** `client_max_body_size 520m` ТОЛЬКО в локациях `/api/videos`
  (+ multipart-обвязка ~20 МБ) — включается images-стилем из
  `videos-proxy.inc` (урок images: server-лимит 2m перебивается локацией,
  иначе 413 раньше сервиса).
- **CPU/RAM конвертации:** nice 10 + серийность (§3) + mem_limit 512m
  контейнера; `cpus`-квота НЕ вводится до замеров стенда (NFR-35 решает по
  факту; резерв решения зафиксирован).
- **p95 NFR-37:** серийный воркер + 1 поток означает: API-запросы
  обслуживаются событийным циклом независимо; upload большого файла
  читается потоково (без чтения 500 МБ в память). Замер: 20 списков +
  5 малых загрузок при идущей конвертации ~300 МБ — p95 < 500 мс.

## §5. Хранение: том videos-data, аутентифицированная отдача (отличие от images)

Том `videos-data` (named volume, по образцу `images-data`/аватаров):
вне репозитория и БД, переживает пересоздание контейнеров. Структура:
`videos-data/<id>/original.<ext>`, `videos-data/<id>/video.mp4`,
`videos-data/<id>/preview.jpg` — каталог на id, а не плоские имена
(атомарное удаление = rmtree каталога; нет коллизий имен).

**Ключевое отличие от images:** `/images/` отдается nginx-alias'ом
публично — для видео это запрещено NFR-36/ОВ-2 (public links MUST NOT).
Отдача `/videos/` делается nginx'ом из ro-маунта тома (позиция «файл из
тома, отдается через nginx» — паритет производительности и незагрузки
сервиса), но с проверкой сессии через **`auth_request`**:

```
location /videos/ {
    auth_request /_video_auth;            # subrequest → video:8380
    error_page 401 = @login_redirect;     # страницы: редирект на /login
    error_page 502 503 504 = @videos_down; # video недоступен: управляемая 503,
                                          # НЕ голый 500 от упавшего subrequest
    alias /data/videos/;                  # ro-маунт тома (паритет images)
}
location = /_video_auth {
    internal;
    proxy_pass http://video:8380/api/videos/authcheck;  # 200/401 по cookie
    proxy_pass_request_body off;
    proxy_set_header Content-Length "";
}
```

Контракт на стыке (шов nginx↔video, §3 сквозных процессов
service-decomposition): `/api/videos/authcheck` — exempt от JSON-обвязки,
возвращает 200 при валидной сессии (cookie пересылается subrequest'ом) и
401 иначе; эндпоинт не читает БД тяжелее проверки сессии (O(мс)).
API-отдача `/api/videos/{id}/file|preview` тоже существует (middleware,
паритет 401) — но основной поток файлов идет через nginx (Range-запросы
`<video>` и кеш обрабатывает nginx).

## §6. nginx-маршрутизация и деградация

Паттерн search/images-семейства в `services/frontend/nginx/`:

- `videos-proxy.inc`: `set $upstream_videos http://video:8380;` (resolver
  127.0.0.11 valid=10s — анти-stale-DNS, старт nginx без video безопасен),
  proxy-заголовки, `client_max_body_size 520m` (только upload-локации),
  `error_page 502 503 504 = @videos_down` (быстрый JSON 503 +
  Retry-After, паритет `@images_down`); тот же error_page — и в локации
  `/videos/` (§5): отказ authcheck-subrequest (video down) отвечает
  управляемой 503, а не голым 500.
- Локации в `ekotov-wiki.conf`: `= /api/videos` + `^~ /api/videos/`
  (пара точный+префикс, URI не переписывается), `/videos/` с auth_request
  (§5), `/_video_auth` internal.
- Файлы `videos-data` появляются в конфиге только ro-маунтом frontend
  (`videos-data:/data/videos:ro` — паритет images).

## §7. БД: владение схемой (service-decomposition §2)

- Таблица **`video_videos`** — владелец ровно один: сервис `video`.
  Ядро НЕ пишет в нее (первичное создание — миграцией ядра one-shot по
  запросу владельца, паттерн migrate_gallery; накат/изменения схемы —
  в контейнере владельца). r2: туда же относятся таблицы социального
  слоя `video_comments`/`video_reactions` (кусок D, sdd §4) — владелец
  тот же.
- Профиль доступа: **RW-своей-схемы** (паритет images): RW только
  `video_videos` + `video_comments` + `video_reactions`, SELECT `users`
  (имя загрузившего/автора комментария) и `image_categories` (справочник
  категорий куска D). Гарантии профиля — кодом сервиса (short
  transactions, busy_timeout, только свои таблицы).
- Схема: `id`, `filename` (исходное имя), `status`
  (uploaded/converting/ready/error), `size_bytes` (актуальные файлы),
  `mime` (исходный), `uploaded_by` (FK users), `created_at`,
  `convert_attempts` (0/1/2), `category_id` (NULL = «Без категории»;
  FK → `image_categories` — **существующий справочник галереи**, r2:
  НОВЫЙ справочник НЕ создается; запись в него сервис video НЕ пишет —
  только SELECT; создание/переименование категорий остается у галереи).
  Файлов в БД НЕТ (том — §5).
- Социальный слой (кусок D): `video_comments` (id, video_id CASCADE,
  user_id → users, text NOT NULL, created_at) и `video_reactions`
  (PK(video_id, user_id) — уникальность голоса; value CHECK IN (1,-1);
  CASCADE) — паттерн image_comments/image_reactions галереи (FR-81/82);
  удаление видео каскадно чистит комментарии и реакции.
- Сортировка/поиск куска C: `ORDER BY filename COLLATE NOCASE
  ASC/DESC` + `WHERE filename LIKE '%'||?||'%'` с `lower()`-нормализацией
  обоих сторон — без новых таблиц и индексов сверх объема данных; фильтр
  категории (D): `WHERE category_id = ?` либо `WHERE category_id IS NULL`
  («Без категории») — не отдельный параметр-таблица.

## §8. Безопасность (NFR-36) и изоляция (ОВ-3)

- Все `/api/videos*` — за сессионным middleware сервиса (копия
  images/search: без права писать в sessions; без сессии — 401
  `{"error": "unauthorized"}`). Страница `/video` — ядро, редирект на
  `/login` без сессии. Отдача файлов — auth_request (§5). r2: все операции
  социального слоя (комментарии/реакции/категории, NFR-38) наследуют тот
  же middleware — отдельных exempt-ов у D-эндпоинтов нет.
- Публичные ссылки/токены не проектируются (вне скоупа).
- Вставка в статьи: фронтенд-инструменты редактора не расширяются;
  сервис не предоставляет embed-эндпоинтов (ОВ-3 изоляция — спека, не
  только договоренность кода).
- Путь из имени файла НЕ конструируется (имена пользователя — только
  метаданные; файловые пути — только `<id>/...` из uuid сервиса) —
  защита от path traversal по умолчанию.

## §9. Отвергнутые альтернативы

| Альтернатива | Почему нет |
|---|---|
| apt-get ffmpeg в образе | ограничение ТЗ + нестабильная версия/поверхность; статический бинарь с пином и checksum — воспроизводимо |
| Очередь-брокер (Redis/RabbitMQ/celery) | вне скоупа Уровня 1 (PLAN), масштаб 2 пользователей, +1 контейнер в лимит-бюджете стека без эксплуатационной нужды; внутрипроцессный воркер закрывает серийность/ретрай/статусы |
| Отдача `/videos/` plain alias (как /images/) | нарушает NFR-36/ОВ-2 — публичная ссылка на файл; auth_request сохраняет nginx-отдачу за сессией |
| Отдача файлов самим FastAPI (SendFile) | держит воркер uvicorn на длинных стримах + Range-логика вручную; nginx из тома дешевле и с кешем; API-маршрут оставлен как fallback/паритет 401 |
| Конвертация on-demand (при первом playback) | непредсказуемая задержка первого просмотра, сложнее статусы; ТЗ фиксирует конвертацию при загрузке |
| HLS/несколько разрешений | Уровень 2+, вне скоупа (PLAN) |
| Отдельный справочник категорий для видео (video_categories) | решение Заказчика r2: справочник общий с галереей; дубль справочника плодит рассинхронизацию значений (категория галереи не появилась бы в видео) — только FK на существующий `image_categories` |
| Таблицы комментариев/реакций в ядре | нарушает владение схемой сервиса; таблицы владельца video по паттерну image_comments/image_reactions |

## §10. Замеры на стенде (NFR-35/37 — до прод-выкатки)

Сценарий замера: конвертация ~200–300 МБ файла; фиксировать: RSS контейнера
(пик и плато), CPU (docker stats), healthcheck, p95 20 списков + 5 малых
загрузок. Итог — REPORT пакета; стабильное превышение mem_limit — стоп и
эскалация до Заказчика (лимиты/`cpus`-квота — из §4 резерва).
