## Ревью №1 — 2026-10-17, роль: архитектор (СА), Флоу 1

**Предмет:** пакет video-hosting @ 50ebff3 (proposal, requirements DRAFT r1,
design r1, sdd, дельта specs/video-service — 12 Requirements / 23 сценария).
**Метод:** чек-лист СА перед нарезкой (skill service-decomposition §5) +
прицельная проверка: отказ video:8380, ffmpeg-ресурсы/таймауты/крэш,
безопасность пути `/videos/` (auth_request).

### Чек-лист §5 (service-decomposition)

- [x] «Сервис?» — критерии §1 выполнены и названы: свой том вне БД ядра
  (`videos-data`), независимая деградация (nginx 503, ядро живо), независимый
  деплой по тегам — sdd §1; брокер не вводится (YAGNI, 2 пользователя) —
  design §3/§9. Замечаний нет.
- [x] Владелец каждой новой сущности назван явно: таблица `video_videos` —
  сервис `video` (RW-своей-схемы + SELECT users; ядро НЕ пишет, первичное
  создание — one-shot миграция ядра по запросу владельца, паттерн
  migrate_gallery) — design §7, sdd §4; том `videos-data` — сервис `video`
  (RW), frontend — ro-маунт для alias-отдачи — design §5/§6.
- [x] Сквозные процессы перечислены с владельцем, контрактом стыка,
  деградацией и смоуком: загрузка+конвертация, playback, отказ сервиса —
  sdd §5; лимит 500 МБ согласован на стыке nginx (520m) ↔ сервис (до записи,
  422) — design §4.
- [x] Зоны задач не пересекаются — проверено `seam_checker.py` по zones из
  tasks.md (см. ниже); [P]-параллель допущена только для непересекающихся зон.
- [x] Порядок миграций на межсервисном шве: `MIGRATE_MODULE=migrate_video`
  строго до up, `depends_on: [app]` у контейнера video — design §2; задача
  5.1 tasks.md.
- [x] «Рекомендации к нарезке» заполнены: швы/НЕЛЬЗЯ делить/[P] — sdd §2
  («Правила швов»).

### Прицельные проверки

1. **video:8380 down не роняет wiki** — OK. Порты не публикуются; resolver
   127.0.0.11 (старт nginx без video безопасен); `error_page 502 503 504 =
   @videos_down` → быстрый JSON 503 + Retry-After на `/api/videos*` и
   `/videos/`; сценарий деградации в спеке (specs/video-service/spec.md,
   «Маршрутизация и деградация»).
2. **ffmpeg: ресурсы/таймауты/крэш-восстановление** — OK после устранения
   F1. nice 10 + серийный воркер (1 одновременно) + mem_limit 512m +
   wall-clock timeout 30 мин (kill = неудача попытки → ветка ретрая);
   ровно 1 авторетрай, потом `error` с сохраненным оригиналом; отмена при
   DELETE через флаг; замеры NFR-35/37 на стенде до прода (design §10).
3. **nginx auth_request на `/videos/`** — OK после устранения F2.
   Subrequest на внутренний `/api/videos/authcheck` (200/401 по cookie,
   без тяжелых БД-чтений — контракт стыка в design §5); 401 → редирект на
   `/login`; alias из ro-маунта; пути файлов — только `<id>/…` из uuid
   сервиса, имена пользователя в путях не участвуют (path traversal —
   design §8); публичных ссылок нет (NFR-36/ОВ-2 — отличие от `/images/`
   зафиксировано как ключевое, design §5/§9).

### Находки

- **F1 (Must, устранено в этом же проходе):** design §3 «Крэш-восстановление»
  re-enqueue'ил только статус `converting`. Запись, поставленная в очередь до
  сбоя контейнера, но не начатая воркером (статус `uploaded`), навсегда
  застревала в «загружено»: очередь в памяти потеряна, пути re-enqueue у
  `uploaded` не было. Исправлено: design §3 + sdd §2 (converter) — на старте
  re-enqueue статусов `uploaded` И `converting`; инвариант «в БД нет
  uploaded/converting вне очереди». Покрытие задачей 2.1 tasks.md и
  тест-критерием 2.2.
- **F2 (Should, устранено в этом же проходе):** сниппет auth_request в
  design §5 не задавал обработку отказа subrequest: при остановленном
  `video` authcheck отвечает 502, и без `error_page` в локации `/videos/`
  пользователь получал голый 500 вместо управляемой 503 (нарушение сценария
  «Маршрутизация и деградация» для файлового пути). Исправлено: design §5
  (сниппет) + §6 (текст) — `error_page 502 503 504 = @videos_down` в
  локации `/videos/`. Покрытие задачей 1.4 tasks.md.

### Наблюдения (не блокеры, без правки пакета)

- **O1:** том `videos-data` не входит в контур backup-sidecar (сейчас:
  wiki.db + avatars). Пакет этого не требует (ОВ-4 — экономия диска, оригиналы
  удаляются), решение о бэкапе видео — за Заказчиком отдельно; зафиксировать
  в map.md и при приемке упомянуть.
- **O2:** конкурентность RW (app + images + video) в одной SQLite WAL —
  наследует риск Д-б карты; профиль video ограничен своей таблицей
  (короткие транзакции, busy_timeout), наблюдаемость — через замеры стенда.

### Вердикт

**APPROVE.** Пакет структурно полный (openspec validate --strict — change
green; 12/12 Requirements, 23 сценария 1:1), границы сервиса/владение/швы/
деградация по чек-листу §5 выполнены; две находки F1/F2 устранены правкой
design.md/sdd.md автором пакета в этом же проходе (до нарезки tasks.md,
реализация еще не начата). Нарезка — tasks.md этого прохода; QA-контур
включен полностью (J39); сквозной смоук — в плане прогонов (решение
2026-10-12).

## Ревью №2 — 2026-10-17, роль: архитектор (СА), Флоу 1

**Предмет:** контрольный проход по дельте куска D @ 5ce47a0 (requirements r2,
spec r2, design r2, sdd r2, tasks r2; proposal синхронизирован). Фокус —
4 точки мандата: таблицы социального слоя, категории через RO, порядок
волн A → D → B → C, превью в B для уже-mp4.

### Прицельные проверки

1. **Таблицы `video_comments`/`video_reactions`** — OK. `video_comments`
   (id TEXT PK, video_id FK ON DELETE CASCADE, user_id FK users, text NOT
   NULL, created_at); `video_reactions` — PK(video_id, user_id) = ровно
   один голос на пользователя (toggle = DELETE строки, перенос = UPDATE
   value), `value CHECK IN (1, -1)`, CASCADE — design §7, sdd §4. Владелец
   обоих таблиц — сервис `video` (RW-своей-схемы), ядро НЕ пишет; паттерн
   сверен с реализацией галереи: `backend/app/migrate_gallery.py`
   (image_reactions PK(image_id, user_id) + CHECK, image_comments
   image_id CASCADE, автосверка по PRAGMA foreign_key_list) и
   `services/images/app/db.py` (PRAGMA foreign_keys=ON на соединении —
   CASCADE реально работает в рантайме); паритет video/db.py прямо
   назван швом в sdd §2 и задачей 2.2. Удаление видео каскадно чистит
   комментарии/реакции (sdd §3 DELETE-контракт) — покрыто тест-критерием
   2.5. Замечаний нет.
2. **Категории — существующий `image_categories` через RO** — OK. Новый
   справочник НЕ создается: `video_videos.category_id INTEGER NULL`
   (NULL = «Без категории») FK → `image_categories` — только SELECT;
   создание/переименование категорий остается у галереи (design §7, sdd
   §4/§7); `GET /api/videos/categories` — чистый SELECT (sdd §3); задача
   2.2(в) фиксирует «без записи в чужой справочник». Профиль доступа
   video расширен ровно на SELECT `image_categories` поверх RW своих
   трех таблиц — выхода в чужую схему на запись нет. Отклонение
   альтернативы `video_categories` задокументировано (design §9).
   `ALTER TABLE ADD COLUMN category_id` (задача 2.1) в SQLite допустим
   (REFERENCES-колонка с NULL-default) и идемпотентен (проверка наличия
   колонки). Замечаний нет.
3. **Порядок волн A → D → B → C** — OK. Цепочка в tasks.md «Зависимости и
   порядок»: 1.1 → 1.7 → 2.1 → (2.2 → 2.3) → 2.4 ∥ 2.5 → 2.6 → 3.1–3.3 →
   4.1–4.2 → QA 5.x → deploy 6.x. Зоны не пересекаются: 2.1 — общая зона
   с 1.1 (`migrate_video.py`, строго после), 2.2 — общая с 1.2/1.3
   (`db.py`), 2.3 — общая с 1.3 (`videos.py`), 2.4 — общая с 1.5
   (фронтенд) — все [P]-запрещены; единственный [P] волны 2 — 2.4 ∥ 2.5
   (frontend/templates+js против services/video/tests — зоны
   непересекающиеся). Шов D не ломает A: D живет в отдельном модуле
   `social.py` (sdd §2 — «зона не пересекается с videos.py»; videos.py
   в list отдаст готовые агрегаты из db), D-эндпоинты НЕ exempt от
   сессионного middleware (NFR-38, sdd §2/§8) — 401-инварианты волны A
   сохранены; трассировка 17/17, сценарии 37/37 в requirements и спеке
   1:1 (проверено подсчетом), `openspec validate video-hosting
   --type change --strict` — green (прогон этого прохода). Замечаний нет.
4. **Превью в B для уже-mp4** — OK. Кадр снимается тем же проходом
   воркера: `ffmpeg -frames:v 1` без перекодирования (design §3, задача
   3.1(б), спека «Для уже-mp4 кадр тоже снимается») — быстрый дешевый
   проход, НЕ полная переконвертация. Неудача снятия кадра = неудача
   попытки в существующую ветку ретрая (ровно 1), без нового контура;
   до готовности — плейсхолдер по макету. Из C превью убрано (4.1 —
   только сортировка/поиск), нумерация волн сдвинута с явной таблицей
   соответствия ссылок ревью №1 в шапке tasks.md. Замечаний нет.

### Наблюдения (не блокеры, без правки пакета)

- **O3:** `video_videos.category_id` ссылается на чужой справочник без
  ON DELETE-поведения; у галереи сейчас НЕТ эндпоинтов удаления/переименования
  категорий (master-spec gallery: только создание именем при загрузке и
  фильтрация), поэтому риск отсутствует. Если у галереи когда-нибудь
  появится DELETE категорий — ее «проверка использования» обязана
  учитывать и `video_videos` (межсервисная согласованность по FK);
  зафиксировать в map.md при архивации (6.3).
- **O4:** неудача снятия превью при успешной конвертации приводит к
  повторному полному проходу ffmpeg (кадр и конвертация — один шаг
  попытки). Для worst-case 500 МБ это допустимо (тот же 30-мин таймаут),
  упрощение сознательное — менять не требуется.

### Вердикт

**APPROVE.** Дельта куска D эволюционирует утвержденное техрешение №1
(паттерн галереи, тот же воркер, тот же middleware), не создавая новых
архитектурных сущностей: владение таблицами, RO-чужой справочник, швы и
порядок волн, перенос превью в B — согласованы в requirements/spec/design/
sdd/tasks без расхождений. Наблюдения O3/O4 — в журнал, правок пакета не
требуют. Ревью №1 остается в силе.
