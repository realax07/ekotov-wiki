### Точки фокуса

1. **Хранение HTML+data vs markdown — решение обосновано.** Поле content —
   санитизированный HTML с релиза add-wiki (sanitize_html на записи,
   wiki.py:239/308/397 — сверено с кодом), «markdown-поле» в брифе —
   фактическая ошибка делегации, СА зафиксировал расхождение до решения
   (design §1) — правильно. Отказ от markdown (§10.1) существенен: конверсия
   = миграция всех страниц (в пакете миграций НЕТ осознанно) + двойной
   md/html-парсер в редакторе и рендере. innerHTML-сохранение безопасно:
   серверная санитизация на записи закрывает инъекции; остаточный риск
   сериализации editor-артефактов — F1 (устранен).
2. **Sanitize** — enum-словарь data-атрибутов с валидацией значений
   (`_safe_block_attr`, невалидное → снять → деградация), `data-title` и
   текст кода — экранированные текстовые узлы, эмит экранированный
   (`html.escape(quote=True)` в _render_start — сверено), on*/style/id
   снимаются прежним whitelist'ом, script/style с содержимым, URL-фильтр
   без изменений (§2/§8). Вектор через подсветку снят архитектурно: спанов
   в БД нет, лексер работает над декодированным текстом. Найденная дыра
   paste-пути (table-in-table мимо кнопок) — F3 (устранен); paste-time
   `onerror` в contenteditable до сохранения — O2 (предсуществующее, вне
   скоупа).
3. **Матрица §6** — полна по вставляемому (спойлер/код/табы/таблица ×
   спойлер/ячейка/вкладка/код-блок): запрещены ровно table-in-table и
   любые блоки внутри кода; опасные комбинации прикрыты лимитом глубины 5
   на санитайзере + ограничением кнопок. Дыра paste-пути для таблиц — F3.
4. **Самописный лексер** — решение легитимно (ОГР-8, кастомная палитра,
   ~6 КБ против 80–120 КБ вендоринга), fail-safe «не распознал — текст»
   исключает потерю символов. Риск регрессий/перфа прикрыт бюджетом NFR-40;
   отсутствовавшее требование линейности regex (ReDoS на пользовательском
   коде) — F5 (устранен).
5. **impact.md vs дифф-реальность** — согласована: SA-дифф = 6 файлов
   openspec/** (git show bdac735), карта это отражает; openapi.json не
   трогается корректно (сохранение существующим PUT /api/wiki/pages/{id});
   `tests/api/test_sanitize.py` существует (расширение), имена новых сьютов
   свободны; нумерация FR-118…122/NFR-39…40 не занята (максимум фактический —
   FR-117/NFR-38, сверено grep по openspec). Противоречие по static_v — F2
   (устранен).
6. **static_v по волнам (R7-урок)** — исходная формулировка impact.md
   («на промежуточных dev-PR без статики правила молчат») противоречила
   собственной волновой нарезке: волны 2.5/3.4/4.5/5.3 трогают
   `frontend/static/**`, а гейт считает дифф накопительно
   (pr_validate.py `main...HEAD`) → DENY промежуточного PR. Устранено (F2):
   каждый dev-PR со статикой несет бамп, волна 6.3 — финальный.
7. **Старый контент** — не ломается: whitelist не сужается, div/span без
   data-атрибутов проходят как раньше (идемпотентность санитайзера на
   уже-санитизированном контенте — регресс-тест байт-в-байт, волна 1.2);
   старый голый `<pre>` продолжает рендериться прежними стилями
   (impact.md §Миграции); сценарий NFR-40 «Статья без блоков не меняет
   поведение» покрывает рендер-путь. Замечание O3 о формулировке.

### Находки

- **F1 (Must, устранено в этом же проходе):** «сериализация DOM как есть»
  (design §3) несовместима с inline-панелями: таб-бар с «+»/«×», панель
  таблицы, input переименования шапки лежат внутри contenteditable-зон,
  попали бы в PUT и срезались санитайзером (button/span+class вне
  whitelist) — сохраняемое расходилось бы с редактируемым DOM, тот же
  класс бага, что «потеря контента rich-v1». Исправлено: design §3 —
  editor-only узлы помечаются `data-editor` + `contenteditable="false"` и
  вырезаются детерминированно при сериализации; инвариант уточнен
  («сохраняемое ≡ DOM минус data-editor»); тест — в tasks 1.3.
- **F2 (Must, устранено в этом же проходе):** static_v по волнам — impact.md
  §Статика утверждала, что промежуточные dev-PR «без статики» и бамп нужен
  один раз релизным диффом; фактически стилевые волны 2–5 сами меняют
  `frontend/static/**`, гейт (IR-03) прогоняется на накопительном
  `main...HEAD` → каждый такой PR = DENY (риск ровно урока R7 video-1.1).
  Исправлено: impact.md §Статика — каждый dev-PR со статикой несет бамп
  (идемпотентный), 6.3 — финальный бамп `p12-rich-1` + проверка
  накопительного диффа; tasks 5.3/6.3 синхронизированы.
- **F3 (Should, устранено в этом же проходе):** запрет table-in-table держался
  только на кнопках редактора (§6); paste вставляет вложенную таблицу мимо
  кнопок, санитайзер ее пропускает (table в ALLOWED_TAGS, счетчика таблиц
  нет), и с сохраненной страницы она возвращается в редактор — воспроизводство
  источника потери контента rich-v1. Исправлено: design §2 — unwrap вложенной
  таблицы на санитайзере с сохранением текста ячеек (`<br>`-разделитель);
  тест — в tasks 1.2.
- **F4 (Should, устранено в этом же проходе):** H-toggle планировал ручную
  замену тега (h→p, h_x→h_y) — она выпадает из нативного undo-стека
  contenteditable: Ctrl+Z после toggle не откатывает или ломает стек, при
  том что в дельте specs/wiki остался сценарий Undo/redo и tasks 5.5
  требует регресс undo/redo. Исправлено: design §3 — сама замена выполняется
  `execCommand('formatBlock')` после управляемого определения блока
  (undo-стек жив), ручная DOM-замена — только fallback; тест «undo после
  снятия/замены H» — в tasks 5.4.
- **F5 (Should, устранено в этом же проходе):** самописный лексер (§5) не
  имел требования к линейности regex: вход — произвольный пользовательский
  код, правило с вложенным квантификатором = катастрофический бэктрекинг
  (заморозка вкладки, нарушение NFR-40), замер «20 блоков ≤150 мс»
  патологический вход не ловит. Исправлено: design §5 — правила без вложенных
  квантификаторов/обратных ссылок, блок >64 КБ — plain, тест на
  патологическом входе в волне 3; tasks 3.1 дополнен.

### Наблюдения (не блокеры, без правки пакета)

- **O1:** `data-block-part` валидируется по enum, но не по контексту
  (`data-block-part="tab"` внутри спойлера пройдет санитайзер). Безвредно:
  активация игнорирует неузнанные части, контент виден (NFR-39). Можно
  усилить в волне 1 без изменения контракта.
- **O2:** paste HTML в contenteditable исполняет `<img onerror>` до
  сохранения (серверная санитизация срабатывает только на записи) —
  предсуществующее поведение базового редактора (FR-110), P12 не ухудшает.
  Отдельный пакет, если Заказчик сочтет риском.
- **O3:** формулировка «страницы без блоков проходят байт-в-байт» точна
  только для уже-санитизированного контента из БД (свойство идемпотентности
  санитайзера); фиксура старого контента в тесте волны 1.2 должна браться
  из реальных сохраненных страниц, не из рукописного HTML.
- **O4:** сценарии spec'а 9 Requirements / 36 сценариев пересчитаны —
  сходятся с мандатом; решений ОВ-1…ОВ-5 в spec/мокапах — поименно
  (вся шапка, 6 языков + нумерация, скролл, отдельная кнопка удаления
  таблицы, Backspace).
