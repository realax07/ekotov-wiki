# Proposal: add-r2-categories-settings

## Change ID

`add-r2-categories-settings`

## Why

Релиз 2 «Категории + настройки + форма» проекта ekotov-wiki. Источник требований — утвержденное Заказчиком ТЗ `test-model/requirements-r2.md` (УТВЕРЖДЕН r1 пост-фактум, решения Заказчика получены дословно 2026-09-21, 0 открытых вопросов): FR-19…FR-30, NFR-8, ограничения ОГР-7…ОГР-11, дефолты Д-1…Д-5.

Цель релиза: категории перестают быть свободным текстом (справочник + жесткая валидация), появляются общие для обоих пользователей настройки, форма задачи получает выбор категории из списка, автодополнение тегов, priority-lock для fast-задач и улучшенный визуал; закрывается дефект DEF-001 (селект-поля не тянут значения из данных).

Дословные решения Заказчика (2026-09-21), зафиксированные в шапке ТЗ:
1. Валидация категории — «1. Жесткая» (нельзя сохранить задачу с категорией вне справочника).
2. Настройки — «2. Общие» (видят и меняют оба пользователя).
3. Миграция — «3. Мапь в справочник» (существующие тексты категорий маппятся в справочник).
4. Саджест — set() из уже заведенных тегов и категорий.

## What Changes

Дельты по доменам (все — в `specs/` этого пакета):

| Домен | Тип дельты | Требования | Содержание |
|---|---|---|---|
| `categories` (новый) | ADDED | FR-19, FR-20, FR-21, FR-22, NFR-8 | Справочник категорий: CRUD в настройках, жесткая валидация на создание/редактирование (UI + API), миграция текстовых значений 1:1 без потерь |
| `settings` (новый) | ADDED | FR-23, FR-24, FR-25 | Страница настроек (только для авторизованных), настройки общие для обоих пользователей; состав первого релиза — управление справочником категорий |

## Scope

### In scope

- FR-19 (Must): справочник категорий; категория задачи — значение из справочника во всех местах ввода.
- FR-20 (Must): CRUD категорий в настройках; переименование применяется ко всем задачам; удаление используемой категории блокируется (Д-1).
- FR-21 (Must): жесткая валидация — задачу нельзя сохранить с категорией вне справочника (UI и API/хранение, обход невозможен).
- FR-22 (Must): миграция существующих текстовых категорий в справочник, маппинг 1:1 (Д-2).
- FR-23 (Must): раздел «Настройки» внизу слева рядом с выходом; страница настроек для авторизованных.
- FR-24 (Must): настройки общие — оба пользователя видят и меняют.
- FR-25 (Must): состав настроек первого релиза — управление справочником категорий.
- FR-26 (Should): автодополнение тегов в форме — объединение заведенных тегов и категорий, право создать новое значение (Д-3).
- FR-27 (Must): fast → priority=high, lock в UI, серверная валидация; дельта спеки fastline.
- FR-28 (Should): крестик закрытия модального окна формы в правом верхнем углу.
- FR-29 (Should): приоритеты цветом и иконкой (inline SVG, ОГР-8/Д-4), состояния ошибок формы; стиль — по выбору Заказчика из вариантов до задачи 2.5 (Д-5).
- FR-30 (Must): селект-поля из уникальных значений данных хранилища (DEF-001).
- NFR-8 (Must): миграция без потерь — 0 задач с потерянным/измененным без переименования значением; число категорий = числу уникальных непустых значений до миграции; автоматическая сверка до/после.
- Задачи плана Релиза 2: 2.1…2.6 (2.6 — QA-цикл).

### Out of scope

- Управление тегами как справочник в настройках (Won't ТЗ: теги живут на задачах).
- Настройки профиля / смена пароля (бэклог P3 — вне релизов).
- Advanced-подсказки синтаксиса поиска (отложено).
- Мягкая валидация категории — отвергнута решением Заказчика «1. Жесткая».
- Подсказки поиска как таковые (FR-15…FR-18 реализованы и заархивированы; переиспользуется только механизм, Д-3).
- Разграничение прав на настройки (ОГР-11: FR-24 — общие для обоих).

## Approach

Brownfield-дельты поверх master-спек Релиза 1 (8 доменов) без перезаписи существующих Requirements. Новый домен `categories` — справочник и валидация; `settings` — страница и общность настроек. Поведение fastline меняется точечно: MODIFIED единственного Requirement («Назначение задачи на fast line вручную при создании») — fast и priority более не независимы; инвариант «≤1 активной fast-задачи» не меняется. Технические решения (таблица справочника, REST-контракты, механика миграции и серверной валидации) — в `design.md` и `sdd.md` пакета.

Миграция (FR-22, ОГР-9) — одноразовая, при внедрении справочника: каждое уникальное непустое значение `category` задач становится категорией справочника 1:1; пустые значения записей не создают; ручное слияние синонимов при миграции не делается — корректировка потом средствами переименования (FR-20). Проверка NFR-8 — автоматической сверкой до/после.

## Assumptions (дефолты Д-1…Д-5 — данность, право возражения Заказчика)

- Д-1: удаление используемой категории блокируется, пока на ней есть задачи (перевести задачи → удалить). Основание: согласуется с «Жесткая» (каскадное обнуление оставило бы задачу с невалидной категорией).
- Д-2: миграция 1:1, без ручной чистки синонимов на этапе миграции.
- Д-3: автодополнение тегов в форме использует механизм подсказок поиска (FR-15…FR-17), расширенный правом создания нового значения в форме.
- Д-4: иконки приоритетов — inline SVG, без внешних библиотек.
- Д-5: визуальный стиль формы (FR-29) выбирается Заказчиком из 2–3 вариантов до старта задачи 2.5; без выбора — текущий стиль + обязательный минимум (FR-28, цвета/иконки приоритетов, состояния ошибок).

Дополнительное уточнение в границах ТЗ (зафиксировано в спеке и design): пустая категория (не указана) жесткой валидацией не запрещается — из Д-2 (пустые значения при миграции не создают записей, задачи остаются без категории) и действующей модели `category` nullable; требование FR-21 действует на непустые значения. Возражение Заказчика распространяется на весь пакет до старта задачи 2.1.
