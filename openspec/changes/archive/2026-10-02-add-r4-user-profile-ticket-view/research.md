# Research: add-r4-user-profile-ticket-view

Альтернативы ключевых техрешений до design. Источники: requirements-r4 (утв. 2026-09-29), answers_round4 (ОВ-21…26), PLAN-R4, PRODUCT_BACKLOG (P3, P9, DEF-002…005), sdd.md r8, карточка Р3-пакета (образец).

## 1. Аватар: библиотека автосжатия (FR-42, Д-8)

| Вариант | Оценка |
|---|---|
| **Pillow (PIL) — серверное сжатие** — принят | Де-факто стандарт обработки изображений в Python; center-crop + resize до ≤256px — несколько строк; зависимости: один pip-пакет (без системных библиотек), не «тяжелая» — несоразмерности с легковесностью (ОГР-1) нет: обработка только при загрузке (2 пользователя), не в горячем пути |
| Самописный парсер png/jpg + сжатие | Отклонено: повторная реализация декодирования JPEG — большой объем и риск дефектов; нет готовых преимуществ |
| Клиентское сжатие (canvas в браузере) | Отклонено: ОГР-16 прямо требует сжатие **на сервере** («сжатие выполняется на сервере, пользователь не обрабатывает файл сам»); клиентская валидация типа/размера — только UX-улучшение поверх серверной, не замена |
| ImageMagick / внешние CLI-утилиты | Отклонено: системная зависимость на VPS вне pip-окружения — усложнение деплоя; Pillow покрывает то же |
| Динамическое сжатие при отдаче | Отклонено: сжимать достаточно один раз при загрузке; отдача — статика nginx (ОГР-16), горячий путь не трогаем |

## 2. Квадрат ≤256px: обрезка или вписывание (Д-8)

| Вариант | Оценка |
|---|---|
| **Center-crop до квадрата + resize до 256×256** — принят | Детерминированный результат: любой исходник → ровно квадрат ≤256px (Д-8 «квадрат ≤256px»); лица/логотипы в центре в большинстве случаев; аватар отображается в кружке — квадрат обязателен версткой (кружок с первой буквой — тот же формат) |
| Вписывание с сохранением пропорций (letterbox) | Отклонено: прямоугольный результат или поля-прокладки — не квадрат; расходится с Д-8 и круглым отображением |

## 3. Хранение аватара (ОГР-16)

| Вариант | Оценка |
|---|---|
| **Файл в `/var/lib/ekotov-wiki/avatars/` (вне rsync-корня прода), путь в users.avatar_path, отдача nginx `location /avatars/`** — принят (пересмотрено по ревью review-001, blocker C-1) | ОГР-16 по смыслу: «статика (nginx), отдача с кеш-бастингом» — соблюдается (отдача мимо Python, `?v=<avatar_updated_at>`); нулевая новая инфраструктура. Первоначальный вариант «подкаталог frontend/static/» отклонен после сверки с deploy-механизмом: `deploy.sh` делает `rsync -a --delete` клона в `/opt/ekotov-wiki` — пользовательские файлы в статике прода гарантированно стирались бы следующим деплоем. `/var/lib/ekotov-wiki/` — уже домен данных прода (БД), владелец wiki, та же бэкап-дисциплина; один новый `location` в nginx-конфиге (правка — явный шаг деплоя с `nginx -t` + reload, RUNBOOK синхронно) |
| Подкаталог `frontend/static/avatars/` (исходный вариант) | Отклонен (C-1): rsync `--delete` вычищает всё, чего нет в клоне-источнике, — данные не переживают третий деплой; exclude-вариант хуже (рассинхрон exclude-списка при будущих правках deploy.sh) |
| Блоб в SQLite (BLOB) | Отклонено: раздача бинарей через Python-роут — лишний горячий путь; конфликт с ОГР-16 (статика nginx) |
| Внешнее хранилище (S3-совместимое) | Отклонено: новая инфраструктура на VPS ради двух пользователей — несоразмерно |

Инвалидация кеша конкретного пользователя: URL аватара отдается с версией `?v=<avatar_updated_at>` (dedicated-колонка users, B-3 ревью) + глобальный бамп `static_v` для разметки. Бэкап каталога аватаров включен в deploy-заметку (ОГР-19, C-3 ревью).

## 4. Tooltip: технология (FR-43/44, ОГР-17)

| Вариант | Оценка |
|---|---|
| **Единый CSS/JS-механизм в статике проекта (общий модуль)** — принят | ОГР-17 прямо требует единый механизм для профиля и карточек; JS-модуль (позиционирование у нижнего края, закрытие по mouseleave/blur) + CSS по токенам V3; `prefers-reduced-motion` — отключение анимаций на уровне CSS (TC-vis-105); ноль зависимостей (ОГР-1) |
| Атрибут `title` | Отклонено: нативный tooltip нестилизуем под V3, неуправляем (задержки/позиция браузера), не дает состав из аватара/роли/bio — FR-43 требует разметку |
| CSS-only (`:hover` + absolute) | Отклонено частично: не решает позиционирование у краев экрана (профиль внизу слева — всплывашка обязана не вылезать за вьюпорт) и доступность (focus/keyboard); гибрид — CSS для вида, JS для позиционирования и переиспользования |
| Библиотека (Popper/Tippy) | Отклонено: новая фронтенд-зависимость несоразмерна одной всплывашке двух типов |

## 5. View-модалка: отдельное окно vs переиспользование формы (FR-47, Д-9, ОГР-18)

| Вариант | Оценка |
|---|---|
| **Отдельный read-only рендер + кнопка «Редактировать», открывающая существующую task-form** — принят | FR-47 прямо требует окно, **отличное от форм**; переиспользуется существующая форма редактирования (не копия) — Д-9 закрывается без дублирования логики; read-only рендер проще и безопаснее: нет риска случайного сохранения |
| Та же форма в режиме disabled | Отклонено: «отличное от форм» не выполняется (визуально то же окно); disabled-поля ввода — против духу read-only (FR-47: «без полей ввода») |
| Отдельная страница (не модалка) | Отклонено: решение Заказчика — «модальным окном» (дословно, решение [3]) |

## 6. Миграция: механизм (FR-36…38, NFR-9)

| Вариант | Оценка |
|---|---|
| **Одноразовый идемпотентный скрипт с автосверкой до/после (образец migrate_categories.py)** — принят | Прецедент Релиза 2 (NFR-8): снимок «до» → ALTER/UPDATE в одной транзакции → сверка «после» → exit 1 при расхождении; NFR-9 требует автоматической сверки; бэкап прода до накатки — deploy-заметка (ОГР-19) |
| Фоновая миграция при старте приложения | Отклонено: сверка и остановка при расхождении — не то, что должно происходить молча при рестарте сервиса; явный шаг деплоя контролируемее |
| Пересоздание БД + перенос данных | Отклонено: риск потерь на живых данных против ALTER+UPDATE; NFR-9 — 0 потерь |

Бэкфилл: creator = owner — из решения PLAN-R4 («существующие задачи созданы владельцем», FR-38); assigned = owner — дословное решение ОВ-23; роли owner → PM, wife → PE — ОВ-21 (естественное соответствие, подтверждено в answers).

## 7. Смена пароля: сессии (FR-41, Д-11)

| Вариант | Оценка |
|---|---|
| **Текущая сессия сохраняется, прочие сессии пользователя не затрагиваются** — принят | Д-11 дословно («текущая сессия сохраняется, без принудительного re-login»); механика: bcrypt-хеш нового пароля в users; sessions не трогаются. Проверка текущего пароля обязательна (Д-11) — защита от смены в оставленной сессии |
| Инвалидация всех сессий при смене | Отклонено: противоречит Д-11 (текущая сессия обязана сохраниться); в модели «общая доска» на 2 пользователей прочие сессии — свои же устройства |

## 8. Поиск: подсказки и advanced для assigned/creator (FR-46)

| Вариант | Оценка |
|---|---|
| **Расширение действующего механизма «уникальные значения столбцов БД» (FR-35/DEF-001)** — принят | FR-46: «тот же механизм, что FR-35/DEF-001»; источник — `SELECT DISTINCT` по join tasks→users; для assigned — дополнительно виртуальное значение «без исполнителя» (ОВ-24); advanced-парсер получает два новых поля (assigned, creator) с операторами `=` и `IS NULL` — расширение грамматики без смены синтаксиса |
| Отдельный справочник пользователей для подсказок | Отклонено: подсказки должны отражать фактические данные задач (механизм FR-35), а не состав учеток; для 2 пользователей совпадает, но механизм другой |
| Свободный текстовый ввод логина в фильтре | Отклонено: подсказки из БД — требование FR-46; свободный ввод — источник опечаток и пустых результатов |

## 9. Валидация роли: справочник (ОВ-21)

Справочник фиксированный — решение Заказчика дословно («справочник, значения Product manager, Product engineer. На права и ни на что не влияет»). Альтернативы «редактируемый справочник» (вариант «б») и «свободное поле» (вариант «в») отклонены Заказчиком в раунде ОВ — в design не рассматриваются. Хранение: TEXT в users.role с серверной валидацией по списку (CHECK-констрейнт не нужен — список фиксирован на уровне кода, миграция проставляет дефолты; отдельная таблица ролей не требуется для двух фиксированных значений).
