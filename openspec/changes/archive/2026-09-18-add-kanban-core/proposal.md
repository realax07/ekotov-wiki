# Proposal: add-kanban-core

## Change ID

`add-kanban-core`

## Why

Репозиторий `ekotov-wiki` не содержит реализации: система отсутствует целиком (greenfield). Утвержденное Заказчиком ТЗ (`requirements.md`, r3, 0 открытых вопросов) требует создать с нуля личную канбан-доску для двух пользователей с доступом из интернета: доска с тремя столбцами и fast line, архив, поиск по старым задачам (фильтр-конструктор + advanced SQL-like), сайдбар, веб-авторизация логин/пароль с сессиями и куки. Данный change-пакет — первый и единственный для релиза 1: он добавляет всю функциональность.

## What Changes

Все дельты — **ADDED** (система создается с нуля, никакого предыдущего поведения нет):

- `specs/auth/spec.md` — ADDED: вход по логину/паролю, сессии/куки, обязательная авторизация для страниц и API, 2 пользователя, пароли не в открытом виде.
- `specs/board/spec.md` — ADDED: доска, три фиксированных столбца, перемещение задач.
- `specs/fastline/spec.md` — ADDED: выделенная линия, ручное назначение при создании, правило ≤1 fast-задачи в активных статусах, освобождение после «Выполнено», приоритетный порядок.
- `specs/tasks/spec.md` — ADDED: создание/редактирование/удаление задач, признаки задачи, комментарии, API-доступ, сохранность данных при рестарте.
- `specs/archive/spec.md` — ADDED: уход задачи в архив после «Выполнено», доступ к архиву через поиск.
- `specs/search/spec.md` — ADDED: вкладка поиска, фильтр-конструктор, режим advanced SQL-like, поиск через API.
- `specs/navigation/spec.md` — ADDED: сайдбар, пустой раздел «Wiki» с todo.
- `specs/regression/spec.md` — ADDED (распоряжение Заказчика, 2026-09-18): автотест-сьют `tests/` (82 теста по 80 кейсам) — регрессионный набор, обязательный этап воркфлоу; каждый следующий change проходит полный зеленый прогон до архивации; новые кейсы пополняют набор.

После утверждения и реализации пакет архивируется целиком в master-spec (`openspec/specs/`) — все дельты appended (контракт 7).

## Scope

### In scope (Must — по ТЗ, раздел 5)

FR-1…FR-7, FR-9…FR-14; NFR-3, NFR-4, NFR-6, NFR-7.

### In scope (Should)

FR-8 (API-доступ; реализуем — заказан в вводных п. В-3, при этом обязан требовать авторизацию по NFR-7); NFR-1 (2 с), NFR-2 (1 000 задач), NFR-5 (БД вне репозитория).

### Out of scope (Won't — этот релиз)

- Wiki-функции: создание/редактирование wiki-страниц, поиск по статьям ([ОВ-11], [ОВ-17]). В сайдбаре — пустой раздел «Wiki» с пометкой todo (это часть FR-13/Must, входит в дельту navigation).
- 2FA, роли и разграничение прав между пользователями ([ОВ-12]: «сильно не заморачиваемся пока») — оба пользователя имеют равный доступ ко всем задачам.
- Настраиваемость столбцов доски (ОГР-3: столбцы фиксированы).
- Массовые операции над задачами, Drag-n-drop между устройствами в реальном времени, уведомления — в ТЗ не заявлены.

### Предложения Заказчику (не входят в пакет)

- Возможность вернуть архивную задачу обратно на доску (unarchive) — в ТЗ не заявлена (FR-6 говорит «и обратно» только о столбцах); если нужно — отдельный change.
- Полнотекстовый поиск по подстроке названия/описания без фильтра-конструктора — в ТЗ поиск определен через признаки; может быть добавлен позже.

## Approach

1. Разбить функциональность на 7 доменов (auth, board, fastline, tasks, archive, search, navigation) — по файлу дельты на домен.
2. Специфицировать наблюдаемое поведение с трассировкой каждого Requirement → FR-N/NFR-N; негативные сценарии — обязательно для правил с валидацией (fast line ≤1, вход без авторизации, неверный логин, некорректный фильтр).
3. Технические решения — в `design.md` и `sdd.md` (стек, компоненты, REST-контракты, модель SQLite, матрица трассировки); в спеках реализации нет.
4. Порядок реализации — в `tasks.md`: каркас + auth раньше фич (доска/задачи/fast line → архив → поиск → навигация/полировка).

## Assumptions

- Пользователи заводаются администратором при развертывании (seed), саморегистрация не нужна (NFR-4: ровно 2 пользователя, ОГР-6).
- Оба пользователя видят все задачи (общая доска супругов); «свои задачи» в ТЗ трактуется как «задачи этой системы», а не с ограничением по владельцу — из ТЗ не следует разделение задач по пользователям.
- Сессии хранятся на сервере с TTL; переживание рестарта сервера сессиями не требуется (NFR-3 покрывает данные, сессия — не данные).
