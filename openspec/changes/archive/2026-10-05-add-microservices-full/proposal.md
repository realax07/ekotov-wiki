# Proposal: add-microservices-full

## Change ID

`add-microservices-full`

## Why

Директива Заказчика (Telegram 2026-10-03, 23:1x): «Не будем ждать, следующий релиз — полный переход на микросервисы (в контейнерах)». Это пересмотр ОВ-1 (а) плана P11 — пауза эксплуатации 1–2 недели после контейнеризации отменяется, ЭТАП 2 (выделение сервисов) запускается сразу и в полном составе, не «сервис за сервисом по мере надобности».

Контекст: контейнеризация (add-containerization) закрыта, прод работает на compose (app + nginx, том `wiki-data`), e2e-job в CI, миграции/бэкап/откат — deploy.sh v2. Фундамент для сервисного разбиения готов: OpenAPI-контракт зафиксирован (FR-68), стенд и прод на одних образах (FR-67).

**Рамка решения — план P11 (`docs/ba/architecture-services-plan.md`), раздел 1.2 «Честная оценка»:** при общей SQLite каждый сервис с RW-доступом — отказ от атомарности инвариантов (прецедент fast line), синхронизация миграций между N процессами, деградация WAL-конкурентности. Поэтому «полный переход» трактуется как **полный набор сервисов из таблицы 1.2 плана с безопасными профилями данных**, а не механический разрез монолита на N частей с общим RW:

| Сервис | Профиль данных | Входит в переход |
|---|---|---|
| `app` (ядро: auth, tasks, board, categories, comments, profile, users, страницы) | SQLite RW (том `wiki-data`) | да (база, уже есть) |
| `frontend` (nginx) | без томов | да (уже есть) |
| `search` (+`suggestions`) | SQLite **RO** | да (первый выделяемый — код изолирован: search.py 805 стр., 18 функций, свои роутеры `/api/search*`; suggestions.py 154 стр., `/api/suggestions`) |
| `backup` (sidecar/cron) | том RO + каталог бэкапов | да (снимает ручной шаг из deploy.sh) |
| `auth` | RW (sessions) | **нет** — план прямо не рекомендует (сетевой хоп на каждый запрос, выигрыша при 2 пользователях нет); остается в ядре |

Ограничение ресурса: VPS 3.9 GB, лимиты app 512m + nginx 64m + search 512m + backup ~64m → резерв хосту ≥ 2.6 GB — укладывается (FR-73 паритет).

Событийной шины нет (план §1.3): интеграция — синхронный HTTP через nginx-маршрутизацию; для браузера URL не меняются.

## What Changes

Дельта — **новая capability `services`** (профиль сервисной топологии: маршрутизация, контракты, профили данных) + **MODIFIED** в capability `deploy` (deploy.sh: раздельная сборка/деплой тегов сервисов, healthcheck-матрица, миграционный порядок «ядро до читателей»).

| Группа | Requirement | Тип | Источник |
|---|---|---|---|
| Выделение search-service | «Поиск работает отдельным сервисом с RO-доступом к данным» | ADDED | план §1.2 search |
| Контракт до кода | «Контракт /api/search* и /api/suggestions заморожен в OpenAPI до выделения» | ADDED | план §3 |
| Маршрутизация | «nginx маршрутизирует /api/search*, /api/suggestions на search-сервис; остальное — на app; для браузера URL не меняются» | ADDED | план §1.2 |
| Профиль данных search | «search читает тот же том, mount ro; не пишет» | ADDED | план §1.2 «только RO» |
| Backup-service | «Бэкап тома — sidecar по расписанию; deploy.sh перестает дублировать шаг» | ADDED | план §1.2 exporter |
| Деплой N сервисов | «deploy.sh собирает/катит теги каждого сервиса; healthcheck-матрица до смоука; порядок: миграция ядра до подъема читателей» | MODIFIED | deploy «Миграции…» |
| Наблюдаемость границ | «Схема OpenAPI search-сервиса зафиксирована в contracts/, CI проверяет экспорт=файл» | ADDED | FR-68 паритет |
| Ресурсы | «Лимиты памяти полного стека с резервом хосту ≥ 2 GB» | MODIFIED | FR-73 |

## Impact

- **Код:** `services/search/` (новый: Dockerfile + app-код search+suggestions, RO-подключение), `services/backup/` (новый: cron-sidecar), `deploy/compose.yaml` (+2 сервиса, маршрутизация), `deploy/deploy.sh` (матрица сервисов, порядок миграций), `backend/app/main.py` (−search_router, −suggestions_router), nginx-конфиг образа frontend (+location маршрутизация).
- **Контракты:** `contracts/openapi-search.json` (новый, экспорт из search-сервиса), существующий `contracts/openapi.json` сужается на маршруты поиска.
- **Тесты:** api-сьют: search/suggestions-тесты переезжают против search-сервиса (URL те же через nginx — прогоняется тот же набор); e2e без изменений (браузер не знает о сервисах).
- **Данные:** том `wiki-data` общий, search — ro-маунт. Схема БД не меняется (никаких миграций search).
- **RUNBOOK:** раздел деплоя — матрица сервисов; откат — по тегам каждого сервиса.
- **Не трогается:** auth (в ядре, решение плана), страницы Jinja2 (рендерит app), существующие инварианты fast line (профиль записи не дробится).

## Risks

- WAL-конкурентность: 2 процесса-читателя (app, search) + 1 писатель (app) — SQLite выдерживает (readers не блокируют writer, writer — readers в WAL); контролируемый риск, откат — объединенный образ app (маршруты возвращаются одним тегом, план §8 п.3).
- Дрейф контракта: search-сервис и ядро читают одни строки TASK_COLUMNS — фиксация через общий импорт задачи заморожена контрактом OpenAPI + CI-проверка экспорт=файл.
- 4 контейнера на 3.9 GB — контролируется mem_limit и наблюдением паузы эксплуатации (уже начатой).
