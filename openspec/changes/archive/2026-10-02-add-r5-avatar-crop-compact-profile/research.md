# Research: add-r5-avatar-crop-compact-profile

Альтернативы ключевых техрешений до design. Источники: `docs/ba/requirements-r5.md` (черновик 2026-09-30, вводные Заказчика дословно), код Р4 (`backend/app/avatar.py`, `frontend/static/js/profile-settings.js`), design-токены V3 (`design/form-style-v3.html`), уроки Р4 (research/design пакета add-r4-user-profile-ticket-view).

## 1. ОВ-СА-1: вариант передачи результата кропа — А (фронт-кроп) vs Б (координаты)

Критерии оценки по ТЗ: тестируемость (СЦ-3 требует попиксельного соответствия превью и итога), безопасность (недоверие клиенту), EXIF-поворот, размер payload (NFR-11), соответствие вводной Заказчика «чисто логика фронта» (ОГР-24 — предпочтение, не жесткое ограничение).

| Критерий | А: фронт-кроп (canvas → готовый квадрат) | Б: координаты кропа (сервер режет исходник) |
|---|---|---|
| Тестируемость | Автотест API проверяет только серверную нормализацию (валидация/resize) — тривиально. Попиксельная сверка «превью = итог» (СЦ-3) — web-тест, и в варианте Б тоже ложилась бы на фронт (координаты рисует клиент) | Автотест детерминирован: координаты → известный пиксельный результат на фиксированном исходнике. Сильная сторона Б |
| Безопасность | Сервер в любом случае не доверяет клиенту: повторная Pillow-валидация + безусловный resize 256×256 (Р4-конвейер сохраняется целиком). Плохой/подмененный blob отбраковывается тем же кодом, что и битый файл Р4 (422) | Параметры x/y/scale — новый вектор атак (нужна валидация диапазонов относительно уже развернутого по EXIF изображения); поверхность проверки шире |
| EXIF | Критично, но решаемо стандартно: браузеры применяют EXIF-ориентацию при декодировании в `<img>`/`createImageBitmap` (per spec, все вечнозеленые браузеры); canvas-рендер уже работает с повернутым изображением. Риск: старые браузеры — но они попадают в fallback NFR-14 (без виджета), где сервер режет center-crop по-Р4 | Сервер обязан сам применять `ImageOps.exif_transpose` до наложения координат — иначе координаты клиента (посчитанные по превью с ориентацией) не совпадут с серверным исходником; плюс протокол передачи координат должен фиксировать систему отсчета |
| Payload (NFR-11) | ~10–150 КБ (256×256 PNG) — трафик не зависит от размера исходника; NFR-11 исполняется автоматически | Полноразмерный исходник ≤2 МБ гоняется по сети каждый раз — прямое противоречие NFR-11, требует «осознанного исключения» |
| Вводная Заказчика | Дословно «чисто логика фронта» — полное соответствие (ОГР-24) | Частичное противоречие |
| Стоимость | Новый фронт-модуль (виджет и так Must — FR-49…51) + 0 изменений контракта | Виджет (тот же Must) + расширение API + серверная геометрия + валидация параметров |

**Вердикт: вариант А.** Решающие аргументы: (1) NFR-11 — единственный критерий, где Б требует осознанного исключения, а А исполняет требование бесплатно; (2) кроп-виджет обязателен в обоих вариантах, поэтому Б добавляет к обязательному объему серверную геометрию + расширение контракта + валидацию координат без выгоды для пользователя; (3) вводная Заказчика совпадает с А (ОГР-24). Слабости А (попиксельная тестируемость, зависимость качества от клиента) закрываются: серверная нормализация детерминирована и тестируется автотестами; web-тест СЦ-3 сверяет превью с отданным файлом; fallback NFR-14 сохраняет работоспособность без canvas. Сценарии «портрет 2 МБ с телефона» (главный кейс двух пользователей) работают одинаково, но А не переливает 2 МБ по мобильной сети.

## 2. ОВ-СА-2 (следствие А): серверная обработка пришедшего квадрата

| Вариант | Оценка |
|---|---|
| **Повторная Pillow-валидация + безусловный resize до 256×256 LANCZOS (недоверие клиенту)** — принят | Весь существующий конвейер Р4 сохраняется (валидация типа/размера до декодирования, Pillow-декодирование как проверка содержимого, resize, PNG-приведение, атомарная запись, `avatar_updated_at`). Битый/подмененный blob → 422 тем же кодом. Пришедший не-квадрат (злонамеренный или старый клиент) все равно приводится к 256×256 — наблюдаемое поведение системы не зависит от честности клиента |
| Доверять клиенту: сохранять blob как есть, если он «квадратный png ≤256» | Отклонено: пиксельное содержимое/форматы не проверяемы без декодирования; исключение из конвейера Р4 = новая ветка в безопасности ради экономии одного resize |

## 3. ОВ-СА-3: API-контракт

| Вариант | Оценка |
|---|---|
| **`POST /api/profile/avatar` как есть (multipart `file`, png/jpg ≤2 МБ), без поля параметров кропа** — принят | При варианте А параметров не нужно: сервер получает готовый итог. Контракт, коды ошибок, `avatar_updated_at`, кеш-бастинг, ТС-ava-001…007 — без изменений (ОГР-23). Ноль backend-работы сверх уже существующей |
| Расширение multipart полем crop-параметров | Отклонено: не нужно при А; при Б потребовало бы версионирования контракта и миграции ТС |

## 4. ОВ-СА-4: пределы зума и мелкие исходники

| Вариант | Оценка |
|---|---|
| **min = cover (сторона изображения ≥ диаметр маски, «дыр» нет — FR-50), max = ×3 от cover; исходник меньше маски — принудительный апскейл до cover + ненавязчивое предупреждение о возможной потере четкости** — принят | min-граница аналитически выводится из FR-50 (запрет «дыр»); ×3 — практический потолок полезного зума для 256px-итога (дальше — только мыло). Апскейл гарантирует работоспособность крошечных файлов (например, 64×64 иконки) без запрета — отказ ломал бы сценарий «загрузить старый мелкий файл», которого ТЗ не запрещает |
| Запрещать файлы меньше маски | Отклонено: отсутствие запрета в ТЗ (СЦ-10 отклоняет только тип/размер); потеря качества — информируем, не блокируем |
| max без ограничения | Отклонено: бесполезный зум (пикселизация) + усложняет предсказуемость жестов |

## 5. ОВ-СА-5: тач-зум и клавиатура

| Вариант | Оценка |
|---|---|
| **Тач: touch-drag + pinch-to-zoom + слайдер (обязателен на таче); клавиатура: слайдер — фокус + стрелки (нативный input range); виджет-контейнер — tabindex=0, стрелки двигают фото (шаг 5% или 1 пиксель маски), +/- зум шагом 10%; aria: role="application"/group с aria-label «Выбор области аватара», слайдер aria-valuenow=% зума** — принят | NFR-13: pinch — ожидаемый жест, слайдер дублирует (NFR-13 требует его обязательно). NFR-15: нативный input range дает клавиатуру бесплатно; стрелки-движение — прямой аналог drag; aria-значение зума озвучивается. Reduced-motion (ОГР-17 Р4): без плавных анимаций трансформаций — инstant-перекладка |
| Только слайдер+кнопки на таче (без pinch) | Отклонено: хуже ожиданиям пользователя; pinch при это несложен (touch-события, расстояние между двумя точками) |

## 6. ОВ-СА-6: смена пароля в единой карточке

| Вариант | Оценка |
|---|---|
| **Блок смены пароля внутри единой карточки, ниже полей профиля; подтверждение — только явной кнопкой «Сменить пароль» (не по blur); после успеха поля очищаются, показывается подтверждение** — принят | Проверка по blur — сюрприз-запросы и риск блокировки формы; кнопка — предсказуемо и совпадает с механикой Р4 (`POST /api/profile/password`). Визуальная иерархия (подзаголовки секций внутри одной карточки) — на живой макет J25 (ОГР-25) |
| Подтверждение нового пароля повторным вводом | Отклонено как расширение состава полей Р4: FR-55 фиксирует «состав полей не меняется» |

## 7. Компактная карточка: переверстка или новая страница

| Вариант | Оценка |
|---|---|
| **Переверстка существующей `GET /settings/profile` в единую карточку V3 (шаблон/JS/CSS профиля правятся на месте)** — принят | ОГР-23 прямо: «переработка верстки существующей страницы, а не новая сущность»; марщрут, редирект без сессии, состав полей Р4 и три независимые операции сохранения (профиль/пароль/аватар) сохраняются |
| Отдельный роут/страница | Отклонено: против ОГР-23 |
