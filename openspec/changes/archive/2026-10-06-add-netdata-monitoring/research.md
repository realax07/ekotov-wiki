# Research: add-netdata-monitoring

Альтернативы ключевых техрешений (полный разбор — design.md):

1. **Инструмент мониторинга**: Netdata (один контейнер, встроенный UI,
   ~150–300 MB) vs Grafana+Prometheus+exporters (3+ контейнера, ~0.5–1 GB) vs
   хостовой Netdata вне compose. Выбор — **контейнерный Netdata** (ОВ-1 = «в»,
   легкий стек; управляется тем же compose; изоляция маунтов ro).
2. **Метрики контейнеров**: docker.sock ro (штатный docker-коллектор Netdata,
   полные метрики cgroups + имена контейнеров) vs ручные cgroup-маунты
   (без docker-сокета, но имена/перечень контейнеров неполные). Выбор —
   **docker.sock :ro** (урок R6/PLAN-R7: ro, только чтение метрик).
3. **Авторизация**: nginx basic auth на локации /netdata/ vs auth_request к
   wiki-сессии vs проверка сессии внутри Netdata. Выбор — **basic auth**
   (design §2: auth_request не умеет проверять роль из JSON-ответа без njs;
   Netdata без обвязки сессии wiki не поднимет).
4. **Точка входа**: subpath /netdata/ за существующим nginx (один TLS-порт,
   одна наружная точка — преемственность FR-65) vs отдельный публикуемый порт
   Netdata vs поддомен. Выбор — **subpath** (паттерн search-локаций; новых
   наружных портов нет; ссылка из UI простая).
5. **Рендер ссылки в сайдбаре**: JS-рендер по `/api/auth/me` (механика блока
   профиля уже такая) vs серверный контекст Jinja2 (роль надо прокидывать во
   все страницы). Выбор — **JS по роли из /api/auth/me** (design §3).
