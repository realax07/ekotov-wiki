# Design: add-wiki

Версия: r1 (2026-10-10). Источники: requirements.md пакета (FR-107…FR-116,
NFR-30…NFR-34), решения Заказчика 1–7 + дефолты ОВ-1…ОВ-4
(`docs/ba/answers_round1.md`), действующий код `backend/app/`
(migrate_gallery.py, board.py, pages.py), токены V3 `frontend/static/css/app.css`.

## §0. Дизайн-фаза (обязательна — директива Заказчика)

P15 — крупная видимая UI-дельта: мокапы рисует **ui_designer** (зона
`design/**`, файлы `design/wiki-*.html`, продукт-код не пишет), Заказчик
утверждает ДО dev-волн (развилка, approval_ref оркестратора; прецедент
Д-5, add-gallery-service 1.1 → 1.5), после dev **design_validator** сверяет
фактический вид с мокапами
(`test-model/reviews/add-wiki/review-NNN-design.md`). Мокапы — standalone
HTML по токенам V3 «Бумага» (`app.css :root`: paper/ink/clay, радиусы,
focus-ring, 8px-сетка), без внешних библиотек (ОГР-8), контраст AA. Состав:

1. **wiki-tree**: `/wiki` — список корневых страниц с поддеревьями, узлы
   раскрыть/свернуть, пустое состояние с кнопкой «Создать первую страницу»,
   поле поиска раздела с выдачей (заголовок, путь, подсветка фрагмента);
2. **wiki-page**: страница статьи — breadcrumb, отрендеренный контент,
   действия (Редактировать, История, Удалить для листа);
3. **wiki-editor**: WYSIWYG-редактор — тулбар (H1–H3, B/I/U, ul/ol, цитата,
   код-блок, ссылка, таблица, изображение, undo/redo), форма заголовка,
   выбор родителя, сохранение/отмена;
4. **wiki-history**: список версий (автор, дата-время, от новых к старым),
   просмотр версии read-only, действие «Откатить» с подтверждением;
   подтверждение удаления — тоже здесь (диалог).

Развилка Заказчика: утверждение мокапов — волны dev НЕ стартуют до
зафиксированного утверждения. СА/dev мокапы не рисуют (J10: приемка мокапа —
утверждение Заказчика).

## §1. Схема БД (таблицы в общей wiki.db; владелец — монолит)

```sql
CREATE TABLE IF NOT EXISTS pages (
  id         INTEGER PRIMARY KEY,
  parent_id  INTEGER REFERENCES pages(id) ON DELETE RESTRICT,  -- NULL = корневая
  title      TEXT NOT NULL,
  content    TEXT NOT NULL DEFAULT '',       -- HTML после санитизации
  author_id  INTEGER NOT NULL REFERENCES users(id),
  created_at TEXT NOT NULL,                  -- ISO (паттерн board.py msk/utc)
  updated_at TEXT NOT NULL
);

CREATE TABLE IF NOT EXISTS page_versions (
  id         INTEGER PRIMARY KEY,
  page_id    INTEGER NOT NULL REFERENCES pages(id) ON DELETE CASCADE,
  content    TEXT NOT NULL,                  -- HTML после санитизации
  author_id  INTEGER NOT NULL REFERENCES users(id),
  created_at TEXT NOT NULL
);

CREATE INDEX IF NOT EXISTS idx_pages_parent   ON pages(parent_id);
CREATE INDEX IF NOT EXISTS idx_pages_title    ON pages(title);
CREATE INDEX IF NOT EXISTS idx_page_versions_page ON page_versions(page_id, id);
```

Решения по схеме:

- `parent_id` — `ON DELETE RESTRICT` + прикладная проверка: удаление с
  дочерними запрещено на уровне API (FR-116, ОВ-2); RESTRICT — страховка от
  каскадного сноса поддерева на уровне БД.
- `pages.title` NOT NULL — непустота заголовка валидируется на API (FR-108);
  CHECK в DDL не дублирует прикладную валидацию (единое место ошибки).
- Версия хранит **контент** (заголовок не версионируется — FR-112/113
  говорят о контенте правки; ОВ не требуют историю заголовков).
- `updated_at` обновляется при каждом сохранении; `created_at` версии —
  время сохранения правки (FR-112).
- Таблицы в общей `wiki.db` (решение 1): монолит — единственный владелец
  (RW), других сервисов у wiki нет.

Индексы под сценарии: `idx_pages_parent` — выборка дерева (дети по
parent_id); `idx_pages_title` — LIKE-префикс по заголовку; составной
`idx_page_versions_page(page_id, id)` — история страницы от новых к старым
(ORDER BY id DESC) без сортировки по created_at.

## §2. Миграция (NFR-32; паттерн backend/app/migrate_gallery.py)

Новый one-shot скрипт `backend/app/migrate_wiki.py` по образцу
`migrate_gallery.py`: запуск `DB_PATH=… SECRET_KEY=… python -m app.migrate_wiki`
из каталога `backend/`.

- Идемпотентность: `CREATE TABLE/INDEX IF NOT EXISTS` — повторный запуск на
  смигрированной БД — no-op, снова проходит сверку.
- Атомарность: все DDL в ОДНОЙ явной транзакции `BEGIN IMMEDIATE` (паттерн
  migrate_gallery, урок ревью 001) — краш не оставляет частично
  смигрированной БД.
- Автосверка после DDL (exit 1 при расхождении, печать в stdout):
  (а) обе таблицы существуют; (б) наборы колонок = §1; (в) FK `parent_id →
  pages(id)` и `page_id → pages(id)` с ожидаемыми ON DELETE
  (PRAGMA foreign_key_list); (г) NOT NULL обязательных колонок; (д) все 3
  индекса на своих таблицах/колонках.
- **Репетиция обязательна**: прогон на свежей копии прод-БД до боевой
  накатки (правило deploy-спеки, урок Р4; прецедент REPORT-2.1-gallery-
  migration-rehearsal) — шаг deploy-задачи.

## §3. API-контракты (REST монолита, префикс /api/wiki; auth — middleware 401)

Все методы требуют сессию (аноним — 401 middleware'ом, паттерн board.py);
права не проверяются по ролям — общий доступ (FR-115). Ошибки формы — 422
(паттерн FastAPI + валидация), не найдено — 404.

| Метод и путь | Назначение | Ответы |
|---|---|---|
| `GET /api/wiki/pages` | Список всех страниц (id, parent_id, title, updated_at) — клиент строит дерево; без контента (легкий ответ дерева) | 200 |
| `POST /api/wiki/pages` | Создание страницы: `{parent_id?: int|null, title: str (непустой), content?: str}`; санитизация контента до записи | 200 `{id}`; 422 (пустой title / несуществующий parent_id) |
| `GET /api/wiki/pages/{id}` | Страница: поля + `breadcrumb: [{id, title}]` от корня (сервер считает цепочку) + `can_delete: bool` (нет дочерних — для UI) | 200; 404 |
| `PUT /api/wiki/pages/{id}` | Сохранение правки `{title?, content?}`; каждое сохранение = запись в page_versions (автор сессии, контент ПОСЛЕ санитизации) + updated_at | 200; 404; 422 (пустой title) |
| `GET /api/wiki/pages/{id}/versions` | Список версий: `{id, author_login, created_at}` — от новых к старым | 200; 404 |
| `GET /api/wiki/pages/{id}/versions/{vid}` | Контент версии (read-only источник для просмотра) | 200; 404 (чужая страница/нет версии) |
| `POST /api/wiki/pages/{id}/revert/{vid}` | Откат: контент версии становится текущим контентом, создается НОВАЯ версия (автор — исполнитель отката); история не переписывается | 200 `{new_version_id}`; 404 |
| `GET /api/wiki/search?q=` | LIKE-поиск: `%q%` по title и content текущих страниц; результаты `{id, title, path, snippet}` — до N=20, путь = breadcrumb строкой | 200; 422 (пустой q) |
| `DELETE /api/wiki/pages/{id}` | Удаление листа (Should, FR-116): запрещено при наличии дочерних | 200; 404; 409 (есть дочерние) |

Контент в ответах `GET` — уже просанитированный (санитизация на записи; §4).
`POST /api/images` НЕ дублируется — редактор вызывает существующий эндпоинт
images-сервиса (§5).

## §4. Санитизация HTML (NFR-31; ОГР-8)

Собственный серверный sanitizer на `html.parser` stdlib (`HTMLParser`),
БЕЗ внешних библиотек (bleach/lxml запрещены принципом продукта). Модуль
`backend/app/sanitize.py`:

- **Whitelist тегов** = тулбар редактора (FR-110): `h1 h2 h3 p br b strong i
  em u ul ol li blockquote pre code a img table thead tbody tr th td` +
  структурные `div span` (перенос из contenteditable).
- **Whitelist атрибутов**: `a[href, title]`, `img[src, alt]`, `td/th[colspan,
  rowspan]`; все прочие атрибуты снимаются — в т.ч. любые `on*`, `style`,
  `class`, `id`.
- **URL-фильтр**: `a[href]`, `img[src]` — только схемы `http:`, `https:`,
  относительные `/...`; `javascript:`, `data:` (кроме `data:image/` для img —
  ЗАПРЕЩЕН тоже: контент хранит только ссылки `/images/{id}`, FR-111) и
  прочие схемы вырезаются вместе с атрибутом.
- **Запрещенные теги** (`script, iframe, object, embed, form, ...`):
  вырезаются С СОДЕРЖИМЫМ у `script/style`; остальные — разворачиваются
  (содержимое остается, тег нет).
- Место применения — **на записи** (POST/PUT/revert): в БД лежит только
  чистый HTML; отображение дополнительно страховочно прогоняет тот же
  sanitizer при рендере страницы (дешево, защита от «грязных» данных из
  прошлых версий/ручных правок БД).
- Тесты sanitizer: обязательный негативный набор — `<script>`, `onclick`,
  `javascript:`-ссылка, `iframe`, вложенная мутация (`<scr<script>ipt>`);
  позитивный — вся разметка тулбара проходит без искажений.

## §5. Интеграция с images-сервисом (FR-111, NFR-34)

- Загрузка с диска: JS редактора вызывает **существующий** `POST /api/images`
  (multipart) — wiki ничего не добавляет к images-сервису; лимиты (≤ 10 МБ,
  JPEG/PNG/GIF/WebP, 422) — существующие, NFR-21 (NFR-34).
- Выбор из галереи: JS запрашивает существующий `GET /api/images` (список) и
  вставляет выбранное.
- В контент вставляется `<img src="/images/{id}" alt="…">`; раздача —
  существующая nginx-локация `/images/`; в БД wiki файлы НЕ дублируются.
- Санитизация пропускает `img` c `src` на `/images/...` (§4 URL-фильтр).

## §6. Рендер дерева и breadcrumb (FR-107…FR-109)

- **Дерево**: страница `/wiki` отдает каркас + `GET /api/wiki/pages`
  (плоский список); JS (vanilla) строит вложенный UL рекурсивно по parent_id
  (O(n), без рекурсивных запросов сервера — дерево целиком за один запрос,
  NFR-30). Узлы с детьми — кнопка раскрыть/свернуть (состояние в памяти
  страницы, без сохранения на сервер — не требуется ОВ). Пустое состояние —
  по мокапу. Ссылки узлов — на `/wiki/{id}` (ОВ-1).
- **Breadcrumb**: сервер считает цепочку предков запросом `parent_id`-lace
  (цикл по уровням; защита от цикла — лимит глубины, например 100) и
  отдает в `GET /api/wiki/pages/{id}` (§3) — клиент рендерит цепочку
  ссылок; текущая страница — без ссылки (FR-109).
- **Поиск**: `q` → SQL `WHERE title LIKE ? ESCAPE '\' OR content LIKE ?`
  с паттерном `%q%` и экранированием `%_\` в q (escape-функция на сервере);
  ORDER BY updated_at DESC, LIMIT 20. Сниппет: первое вхождение подстроки в
  контенте, окно ±60 символов, совпадение оборачивается `<mark>` при рендере
  (клиентом, по позиции из ответа — сервер отдает оффсет и длину, чтобы не
  вставлять HTML в API-ответ). Путь в иерархии — строка breadcrumb из §6.
- **Страница статьи** `/wiki/{id}`: тот же шаблон, что просмотр из дерева;
  действие «Редактировать» переводит статью в редактор; «История» —
  панель версий; «Удалить» — только для листа (can_delete), с подтверждением.

## §7. Фронтенд (NFR-33; токены V3; ОГР-8)

- `frontend/static/js/wiki/` — ванильные модули: `tree.js` (дерево),
  `editor.js` (contenteditable + тулбар на `document.execCommand`/Selection
  API: H1–H3, B/I/U, ul/ol, blockquote, pre/code, ссылка (prompt-диалог по
  мокапу), таблица (вставка минимальной разметки), изображение (диалог
  «из галереи / с диска»), undo/redo — нативный + кнопки), `history.js`
  (версии/просмотр/откат), `search.js` (поиск раздела), `page.js` (клей).
  БЕЗ внешних CDN/сборщиков (ОГР-8).
- `frontend/static/css/wiki.css` — только токены из `app.css :root`
  (никакого хардкода цветов); кеш-бастинг `?v=` бамп при выкатке.
- Тулбар: содержание по мокапу (утверждает Заказчик); состояния
  hover/focus-visible по токенам; доступность — кнопки с aria-label.
- Кроссбраузерность: Chrome + Firefox актуальные — ручной чек + playwright
  на chromium (NFR-33).
- Правки существующих файлов: `base.html` — не меняется (пункт сайдбара уже
  ведет на `/wiki`); шаблон `wiki.html` переписывается из заглушки; точечно
  `pages.py` (роуты страниц `/wiki`, `/wiki/{id}`).

## §8. Права и сессии (FR-115)

- Паттерн `board.py`: сессионные куки, существующий middleware отдает 401
  на `/api/wiki/*` без сессии и редиректит на `/login` страницы — серверный
  код wiki проверку не дублирует, но 401-ветки покрываются тестами.
- Разделения по ролям НЕТ: owner и wife паритетно (решение 7).

## §9. Производительность (NFR-30)

- Дерево одним запросом (`SELECT id, parent_id, title, updated_at FROM
  pages`), сборка на клиенте — масштабируется до 1000 страниц без вложенных
  запросов.
- Breadcrumb — цепочка точечных SELECT по PK (глубинаTyp ≤ 10–20); поиск
  пути в выдаче — batch одним запросом IN (…).
- Версии: список по составному индексу (page_id, id DESC) LIMIT с пагинацией
  не требуется (10 000 версий на все страницы; на страницу — десятки).
- Пороговая проверка — на стенде с засеянным корпусом (1000 страниц /
  10 000 версий): скрипт-сеялка + замер p95 (pytest-марка perf, задача QA).

## §10. Осознанные не-цели

- Индексация в search-сервис, глобальный поиск со страницы «Поиск» (Won't).
- Slug-URL (ОВ-1), home page wiki (ОВ-4), история заголовков, каскадное
  удаление поддерева (ОВ-2 дефолт), переименование/слияние, экспорт.
- Изменения compose/nginx/топологии: новых маршрутов нет — `/api/wiki/*`
  и `/wiki*` идут в app по существующим `location /`, раздача изображений —
  существующая `/images/`.
- WYSIWYG-редактирование таблиц сложной структуры (merge-ячейки) —
  вставка/правка простой таблицы (тулбар FR-110).
