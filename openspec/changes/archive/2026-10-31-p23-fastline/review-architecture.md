### Главная ставка пакета: «бэкенд не трогается» — ПОДТВЕРЖДЕНА по швам

Все серверные ограничения, нужные зоне, уже существуют и покрыты транзакционно:

| Шов | Код | Покрывает зону? |
|---|---|---|
| ≤1 при создании | `_fast_line_busy` :482 + BEGIN IMMEDIATE (гонка закрыта, докстринг :151) | ДА — 409 «fast line occupied» |
| ≤1 при включении fast у обычной (PATCH FR-89) | tasks.py :568+, `_fast_line_busy(exclude_task_id)` в той же транзакции | ДА — идемпотент-включение, 409 второй |
| Возврат fast из done | move :735–753, счетчик `id != ?` в BEGIN IMMEDIATE | ДА — 409, «новая не вставляется, пока не выполнена» |
| Priority-lock | create :458–467, PATCH :593–607 (включая BUG-002 явный null) | ДА — 422 «fast requires high» |
| «Выполнена» + слот | move→done, done_at=msk_now_iso; ленивая autoarchive по МСК-дню (board.py :114–127, лексикографическое сравнение, blocker review-6.1-001 закрыт форматом) | ДА — карточка в «Выполнено» зоны до границы дня |
| is_fast при move | move не трогает is_fast (докстринг) | ДА |

Дыры, требующей правки tasks.py/board.py, не найдено. Держать запрет правок
бэка в dev-диффе (impact §2: расхождение = DENY J58) — корректно.

### Этапы = существующий status: конфликтов с канбаном нет

Источник правды один: `status` + флаг `is_fast`; отдельного fastline_stage нет
(§2, отвергнутая альтернатива обоснована — второй источник правды). Канбан и
зона читают одно поле: fast-карта в status=todo рендерится клиентом
исключительно в зоне, канбан-колонка «Ожидает» ее не получает — конфликта
«где truth» нет, пока разделение по is_fast сделано в cards.js ДО раскладки по
колонкам (tasks 1.3). Серверный `ORDER BY is_fast DESC` (board.py :69)
сохраняется — безвреден. Решение засчитано.

### static_v (IR-03) — требование корректно

Правило IR-03 (impact_rules.json): when `^frontend/.*(static|templates)` →
require `backend/app/pages.py`. Дифф пакета трогает board.html + board.css +
js → бамп обязан быть; tasks 4.2 (маркер `p23-fastline-1`) и impact §4 это
фиксируют, оговорка про накопительный `main...HEAD` соответствует уроку R7.
Текущее значение static_v «p12-rich-2» (pages.py :54) — бамп реален.

### Эскалации Э1–Э3 — разумны

Э1 (выполненная остается в «Выполнено» зоны до автоархивации) согласован и с
move-семантикой (archived_at НЕ трогается), и с инвариантом ≤1 (считает только
todo/in_progress) — против мокапов не бьет. Э2 (DnD обычной в пустую зону
запрещен) последователен с ОГР-5. Э3 (текст чипа — за ревью дизайна волны 2)
— корректный уровень делегации.

### Находки

- **F1 (Must):** impact.md §2, строка «DnD-обходы: is_fast назначается ТОЛЬКО
  при создании (ОГР-5)… обычная задача не может попасть в зону ни одним
  путем» — фактическая ошибка карты. В tasks.py существует и покрыт путь
  PATCH FR-89: `TaskUpdate.is_fast` (:214), включение fast обычной задачи
  (:568–668, 409/422 переиспользуются), и UI-редактор УЖЕ показывает чекбокс
  fast в режиме редактирования (task-form.js :41–45, :431, :918 — «PATCH несет
  is_fast всегда, полное переключение, решение Заказчика п.7»). Слот ≤1 сервер
  держит — дыры безопасности нет, но: (а) строка карты ложная; (б) третья
  вставка в зону через редактирование нигде в пакете не решена — противоречит
  spec-требованию «Вставка… MUST выполняться кнопкой» и дизайну §4/Э2.
  Требуется решение в этом же PR: либо чекбокс в редактировании сохраняется —
  тогда правка формулировки spec (сценарий PATCH-вставки + строка §2 карты),
  либо скрывается в edit-режиме — тогда это изменение поведения FR-89 и
  эскалация к Заказчику (его решение п.7). Молча оставить нельзя.
- **F2 (Must):** impact §6 «существующие board… без изменений, должны остаться
  зелеными» — неверно, регресс-радиус шире. Минимум два сьюта завязаны на
  СТАРОЕ поведение (fast-карта в колонках канбана) и сломаются после
  MODIFIED fastline: `tests/web/test_fastline_ui.py` TC-UI-010 (fast-карта
  первая в колонке todo, подсветка task-card-fast в канбане) и
  `tests/web/test_r3_dnd_ui.py` TC-dnd-103 (drag fast-карты МЕЖДУ колонками
  канбана done→todo, локаторы `_column(page, 'done')`). Оба сьюта требуют
  переноса на зону — это правки существующих файлов, которых нет ни в §1
  таблице карты, ни в §6. Внести в impact (иначе расхождение дифф↔карта на
  dev-PR = DENY J58 уже по факту правок тестов).
- **F3 (Should):** design §5 «DnD ВНУТРИ зоны — разрешен всегда: ≤1 нарушить
  невозможно» — неверен на одном ребре: выполненная fast-карта в «Выполнено»
  зоны + новая fast (слот свободен, кнопка активна) → drag выполненной назад
  в «Ожидает» = возврат из done при занятой линии → серверный 409
  (tasks.py :735–753). Клиентски закрыто общим 4xx-путем (#board-error +
  refreshBoard), но формулировку в design поправить и в spec добавить
  негативный сценарий «возврат выполненной в этап при новой активной — 409,
  карточка возвращается» (наследник TC-dnd-103 — см. F2).
- **O1 (наблюдение):** XSS/рендер — новая разметка переиспользует renderCard/el
  (текстовые узлы, существующее экранирование), новых innerHTML-путей в
  tasks/design нет — чисто. DnD-квирки p12/r8 (гонки dnd_helpers) учтены
  архитектурно: единый refreshBoard как источник правды, сервер 409-путь уже
  обкатан (TC-dnd-103). Рекомендация в tasks 3.1: ассерт «ровно один POST move
  на drop» (двойной dragend/fire — классический квирк HTML5 DnD).
- **O2 (наблюдение):** состояние «занято» вычисляется из последнего GET
  /api/board (tasks 2.2) — при двух вкладках кнопка может быть активна на
  устаревших данных; это допустимо (серверный 409 + чип по api.js, tasks 2.3),
  но в tasks 2.3 явно упомянуть сценарий «гонка двух вкладок».

### Вердикт

**RETURN.** Ядро пакета здорово: бэкенд-нуль-правка подтверждена по всем швам
(≤1, priority-lock, возврат из done, автоархивация МСК), этапы=status без
двойного источника правды, IR-03 корректен, эскалации разумны. Возврат по двум
Must-находкам: F1 — ложная строка «ни одним путем» в impact §2 + нерешенный
patch-путь вставки через чекбокс редактирования (FR-89), F2 — неполная
тест-карта (test_fastline_ui, test_r3_dnd_ui переводятся на зону). После
точечных правок impact.md/design.md/spec в том же PR — повторное ревью не
требуется, достаточно фикс-коммита с отметкой в этом журнале.

### F1 — закрыт корректно

Edit-форма — третий путь вставки, согласован по всем четырем артефактам:
design §4.2 (гейт: чекбокс обычной задачи disabled при занятой зоне с
причиной чипа; на самой fast-задаче доступен всегда — выключение освобождает
слот, повторное включение идемпотентно по exclude_task_id) ↔ spec
(требование «Вставка…» перечисляет кнопку + чекбокс edit-формы + paste-запрет;
сценарии FR-89-вставки и «Чекбокс fast в edit-форме заблокирован при занятой
зоне») ↔ impact §1 (task-form.js: гейт чекбокса, design §4.2) и §2 (строка
PATCH FR-89: `_fast_line_busy(exclude_task_id)` в транзакции, 409/422
переиспользуются) ↔ tasks 2.5 (гейт, волна 2) и 4.1 (чек-лист включает гейт).
Ложная строка «ни одним путем» из impact §2 убрана: строка «DnD-обходы»
теперь корректно опирается на «move не меняет is_fast» и перечисляет оба
легальных пути назначения (POST + PATCH FR-89). Эскалация FR-89 снята
обоснованно: поведение не меняется (решение Заказчика п.7).

### F2 — закрыт, противоречий в карте нет

impact §6: test_fastline_ui (TC-UI-010) и test_r3_dnd_ui (TC-dnd-103/106)
помечены «**правится** — без правки упадет»; формулировка «зелеными без
изменений» осталась только для бэкенд-сьютов (корректно — бэкенд не меняется)
и для «прочих существующих board» (корректно — они fast не касаются). Оба
файла внесены в карту §1 (защита от DENY J58 на dev-PR по факту правок
тестов). tasks 4.4 (волна 4) переводит оба сьюта + добавляет негатив 409.
Сверка с файлами: TC-UI-010 действительно ассертит fast-карту первой в
колонке todo + task-card-fast в канбане (сломается); TC-dnd-103 — drag

Дублирования 3.3↔4.4 по негативу 409 нет: 3.3 — jsdom-уровень, 4.4 —
playwright-сьют, уровни разные.
