## 2. Бэкенд: семантика fastline — правки НЕ нужны (проверено по швам)

Постановка требовала проверить `board.py` + `tasks.py`. Проверка всех швов
показала: серверные правила уже покрывают поведение зоны в новой редакции.

| Шов | Текущее поведение (код) | Покрывает зону? |
|---|---|---|
| Создание второй fast-задачи | 409 `{"error": "fast line occupied"}` при активной (todo/in_progress) fast-задаче (`tasks.py` `_fast_line_busy`) | ДА — ограничение «1 задача до выполнения» |
| Возврат fast-задачи из done в todo/in_progress | тот же инвариант ≤1, 409 (`tasks.py`, расширение 5.1) | ДА — «новая не вставляется, пока предыдущая не выполнена» |
| Priority-lock | fast ⇒ priority=high, 422 `fast requires high` (`tasks.py`) | ДА — без изменений |
| Включение fast при редактировании (PATCH FR-89) | `TaskUpdate.is_fast` (:214), включение :572+ — `_fast_line_busy(exclude_task_id)` в той же транзакции: идемпотент для самой fast-задачи, 409 для второй; priority-lock 422 переиспользуется | ДА — третий путь вставки закрыт тем же инвариантом; клиентский гейт — чекбокс edit-формы (§1 task-form.js, design §4.2) |
| Перемещение между этапами | POST `/api/tasks/{id}/move {status}` — этапы зоны = статусы | ДА — ОВ-5 без нового эндпоинта |
| «Выполнена» | status=done, done_at=msk_now_iso; ленивая автоархивация через МСК-день (`board.py`) | ДА — слот освобождается, карточка исчезает из зоны на границе дня |
| Выборка доски | GET `/api/board` → `{"columns": {todo, in_progress, done}}`, fast первыми (`board.py`) | ДА — разделение по `is_fast` клиентское; ответ и сортировка не меняются |
| DnD-обходы | move не меняет is_fast (докстринг move, tasks.py); DnD обычной в зону — клиентский запрет (красный пунктир, запрос не отправляется) | ДА — DnD не может назначить is_fast ни в каком направлении; назначение — только кнопка (POST) и edit-форма (PATCH FR-89, строка выше), оба под инвариантом ≤1 |

Правки `board.py`/`tasks.py` в dev-диффе = расхождение с картой → DENY J58.
Если ревью найдет дыру — правка проходит только с одновременным обновлением
этой карты в том же PR.

## 3. Контракты

- `contracts/openapi.json` — **НЕ меняется**: новых/измененных эндпоинтов нет.
  Вставка — существующий POST `/api/tasks` (is_fast=true), перемещение между
  этапами — существующий POST `/api/tasks/{id}/move`, чтение — существующий
  GET `/api/board`. Правило IR-01 НЕ срабатывает: дифф не трогает
  `services/*/openapi` и `contracts/`.
- Этап зоны — существующее поле `status` (задача «где хранить этап» решена
  БЕЗ нового поля `fastline_stage`: design.md §2); новые поля Task не вводятся.

## 4. Статика (static_v)

- Меняется кешируемая статика: `frontend/templates/board.html`,
  `frontend/static/**` → правило **IR-03 срабатывает**: в диффе ОБЯЗАН быть
  `backend/app/pages.py` — бамп `static_v` (предлагаемый маркер:
  `p23-fastline-1`), иначе DENY ворот.
- SA-дифф (только `openspec/**`) статику не трогает — правила молчат.
- Гейт считает дифф накопительно (`git diff --name-status main...HEAD`):
  каждый dev-PR волны, трогающий статику, несет бамп сам (бамп дешевый и
  идемпотентный — урок R7 video-1.1).

## 5. Deploy-матрица, RUNBOOK, миграции

- **Deploy/RUNBOOK — НЕ трогаются**: новых сервисов нет (IR-02 молчит),
  миграций нет (IR-04 молчит). Релиз — существующий деплой монолита по
  `deploy/deploy.sh` без изменений матрицы.
- **Миграция НЕ нужна**: флаг `is_fast`, `status`, `done_at`, `archived_at`
  существуют; схема tasks не меняется. Существующие данные совместимы:
  активная fast-задача (если есть) просто окажется в зоне после деплоя.
