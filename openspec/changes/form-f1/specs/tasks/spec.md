## MODIFIED Requirements

### Requirement: Формы создания и редактирования по дизайну V3

Формы создания и редактирования задачи MUST быть выполнены по эталону F1 «Быстрый поток» (`design-forge/extra/form-v1/` create.html + edit.html), построенному на токенах канона A — токены полей V3 (радиус, рамки, фокус-кольцо) сохранены (FR-34, FR-48, преемственность DEF-005): поля — боксы на `--color-raised`, десктоп-модалка 720px, приоритет — сегмент из 3 кнопок поверх сохраненного нативного select (см. ADDED «Сегмент приоритета»), срок — quick-чипы поверх нативного date-инпута (см. ADDED «Quick-чипы срока»), категория + исполнитель в одну строку, фастлайн — тумблер-карточка, ошибки — инлайн под полями, липкий футер (см. MODIFIED «Единая зона действий задачи»). Все интерактивные элементы форм MUST быть покрыты стилями (урок DEF-004). Соответствие не вводит новых функций и не меняет валидацию — только визуал и UX-раскладку. На узких экранах ≤760px форма MUST перестраиваться в bottom-sheet: грейб, поля стёком, липкий футер, категория+исполнитель столбиком (FR-62, эталон form-v1/mobile); на ≤480px — одна колонка без горизонтальной прокрутки, все поля доступны; дропдаун подсказок позиционируется корректно. На ≤480px поля формы (input, textarea, select) MUST иметь font-size ≥16px — без авто-зума iOS при фокусе (NFR-24); интерактивные элементы формы MUST иметь тач-таргет ≥44×44px (NFR-23). Тач-логика модалки подчиняется требованию board «Просмотр карточки задачи» в мобильной fullscreen-оболочке (ОВ-4).

#### Scenario: Форма редактирования соответствует мокапу V3

- **GIVEN** пользователь открыл форму редактирования существующей задачи
- **WHEN** форма сверяется с эталоном form-v1/edit.html по токенам
- **THEN** цвета, радиусы, типографика и состояния формы соответствуют эталону F1 на токенах канона A (токены полей V3 сохранены), включая поле исполнителя (select, ОВ-26); заголовок режима — «Редактирование» (FR-48)

#### Scenario: Поля ввода оформлены по токенам полей V3

- **GIVEN** пользователь авторизован и открыл форму создания задачи
- **WHEN** пользователь осматривает поля ввода (input/textarea) и фокусируется на поле
- **THEN** поля оформлены по токенам полей V3 — радиус, рамки, фокус-кольцо; фокус отображается фокус-кольцом

#### Scenario: Выбранные теги отображаются по дизайну V3

- **GIVEN** пользователь открыл форму задачи и выбрал в поле «Теги» значения
- **WHEN** пользователь осматривает выбранные теги
- **THEN** выбранные теги отображаются по дизайну V3 (оформление выбранных значений — одна из зон расхождения DEF-005 устранена)

#### Scenario: Выбранный приоритет отображается по дизайну V3

- **GIVEN** пользователь открыл форму задачи
- **WHEN** пользователь выбирает приоритет (low/medium/high)
- **THEN** выбор отображается сегментом F1 поверх нативного select (см. ADDED «Сегмент приоритета поверх нативного select (F1)») — различимость по-прежнему не только цветом (FR-29)

#### Scenario: Негативный: все интерактивные элементы покрыты стилями

- **GIVEN** открыта форма создания или редактирования задачи
- **WHEN** пользователь осматривает все интерактивные элементы формы (поля, кнопки, крестики, селекты, сегмент, чипы)
- **THEN** ни один интерактивный элемент не остался с дефолтным браузерным оформлением без стилей (урок DEF-004)

#### Scenario: Полиш не меняет логику и валидацию

- **GIVEN** визуальный проход по форме выполнен (FR-60, Д-15)
- **WHEN** пользователь выполняет обычные операции формы — создание, редактирование, валидацию ошибок (422), fast line, комментарии
- **THEN** логика, состав полей и валидация работают как прежде — изменился только визуал и UX-раскладка; регресс формы зеленый (FR-60, DEF-005, СЦ-7)

#### Scenario: Escape закрывает чистую форму сразу

- **GIVEN** открыта форма задачи (создание или редактирование), поля не тронуты
- **WHEN** пользователь нажимает Escape
- **THEN** форма закрывается сразу, без вопроса; данные на сервере не изменились (FR-61, ОВ-3, СЦ-8)

#### Scenario: Escape на грязной форме требует подтверждения

- **GIVEN** открыта форма задачи с несохраненными изменениями (поля отличаются от состояния на момент открытия)
- **WHEN** пользователь нажимает Escape
- **THEN** показывается подтверждение «Закрыть без сохранения?» (паттерн `window.confirm` существующих модалок); отмена → форма осталась с введенными значениями; подтверждение → форма закрыта без сохранения; данные на сервере не изменились (FR-61, СЦ-8)

#### Scenario: Адаптив одной колонкой на узких экранах

- **GIVEN** пользователь открыл форму задачи
- **WHEN** форма просматривается на экране шириной ≤760px (проверка ~390px)
- **THEN** форма перестроена в bottom-sheet по эталону form-v1/mobile: грейб, поля стёком, липкий футер, категория+исполнитель столбиком; ≤480px — одна колонка, все поля full-width, модалка без горизонтальной прокрутки, все поля доступны; дропдаун подсказок позиционируется корректно (FR-62, ОВ-3, СЦ-9)

#### Scenario: Поля без авто-зума на мобильном

- **GIVEN** открыта форма задачи на экране шириной ≤480px (проверка 375×812, device-эмуляция)
- **WHEN** пользователь фокусирует любое поле (input, textarea, select)
- **THEN** поле имеет font-size ≥16px — авто-зум iOS не включается (NFR-24)

#### Scenario: Тач-таргеты элементов формы

- **GIVEN** открыта форма задачи на экране шириной ≤480px
- **WHEN** пользователь осматривает интерактивные элементы (поля, кнопки, крестики, селекты, чипы тегов, сегмент, quick-чипы)
- **THEN** эффективная тач-область каждого элемента ≥44×44px (NFR-23)

### Requirement: Единая зона действий задачи

В режиме редактирования задачи всё управление задачей MUST быть собрано в одну визуальную зону внизу формы — липкий футер (position: sticky, FR-63, ОВ-4): слева `[Столбец ▾] [Удалить]` (режимная часть `#task-actions`), справа `[Отмена] [Сохранить]`. Деструктивное действие «Удалить» MUST быть визуально отделено от «безопасных» действий (левая сторона футера против правой); подтверждение удаления сохраняется (`window.confirm`, FR-7). В режиме создания зоны `#task-actions` нет — блок скрыт (как сейчас), футер — `[Создать] [Отмена]`. Идентификаторы элементов (`#task-form-submit`, `#task-form-cancel`, `#task-delete-button`, `#task-move-select`, `#task-actions`) MUST НЕ переименовываться — меняется разметка/раскладка, не контракт DOM (ОГР-28; e2e и unit-тесты цепляются по id).

#### Scenario: Состав и порядок зоны действий в редактировании

- **GIVEN** пользователь открыл форму редактирования задачи
- **WHEN** пользователь осматривает нижнюю часть формы
- **THEN** селект «Столбец», «Удалить», «Отмена» и «Сохранить» находятся в одном визуальном блоке — липком футере: `[Столбец ▾] [Удалить]` слева, `[Отмена] [Сохранить]` справа; кнопки управления задачей не разнесены по форме (FR-63, ОВ-4, СЦ-11)

#### Scenario: «Удалить» отделен отступом от безопасных действий

- **GIVEN** открыта форма редактирования с зоной действий
- **WHEN** пользователь осматривает кнопку «Удалить»
- **THEN** «Удалить» визуально отделена от «Сохранить»/«Отмена»/селекта столбца — расположена на левой стороне футера, безопасные действия на правой (destructive отдельно) (FR-63, СЦ-11)

#### Scenario: Подтверждение удаления сохранено

- **GIVEN** открыта форма редактирования задачи
- **WHEN** пользователь нажимает «Удалить» и подтверждает удаление
- **THEN** задача удаляется после подтверждения `window.confirm` — механика удаления не изменилась (FR-7, FR-63, СЦ-11)

#### Scenario: Действия зоны работают

- **GIVEN** открыта форма редактирования задачи
- **WHEN** пользователь переключает столбец селектом, сохраняет задачу и отменяет правки
- **THEN** перенос столбца, сохранение и отмена работают как прежде — обработчики не переписывались, перенесена разметка (FR-63, ОГР-28, СЦ-11)

#### Scenario: В режиме создания зоны нет

- **GIVEN** пользователь открыл форму создания задачи
- **WHEN** пользователь осматривает форму
- **THEN** блок `#task-actions` скрыт; ряд действий — `[Создать] [Отмена]` (FR-63)

#### Scenario: Идентификаторы элементов не изменились

- **GIVEN** форма задачи открыта в любом режиме
- **WHEN** e2e и unit-тесты обращаются к элементам по id `#task-form-submit`, `#task-form-cancel`, `#task-delete-button`, `#task-move-select`, `#task-actions`
- **THEN** все элементы найдены по прежним id — контракт DOM не изменен (ОГР-28, преемственность FR-47, СЦ-11)

## ADDED Requirements

### Requirement: Сегмент приоритета поверх нативного select (F1)

Форма задачи MUST отображать приоритет сегментом из 3 кнопок (Низкий/Средний/Высокий) поверх СОХРАНЕННОГО нативного select `#task-priority` (PLAN-FORM-F1; эталон form-v1/create.html `.segment`). Нативный select MUST остаться в DOM без изменения контракта (value/name/коллект/e2e `select_option`) — сегмент является только отображением и синхронизирует селект в обе стороны: клик по кнопке записывает value в select, изменение value любым способом подсвечивает соответствующую кнопку (`.is-checked` + `aria-pressed`). Пустой value («—», создание) — ни одна кнопка не подсвечена. Disabled-селект (fast line закрепила приоритет, FR-27) MUST дизаблить кнопки сегмента.

#### Scenario: Клик по кнопке сегмента синхронизирует select

- **GIVEN** открыта форма задачи, select `#task-priority` активен
- **WHEN** пользователь нажимает кнопку сегмента «Высокий» (`.seg[data-priority-value="high"]`)
- **THEN** value селекта `#task-priority` становится `high`, кнопка получает `.is-checked` и `aria-pressed="true"`, остальные кнопки сняты; payload формы собирается из селекта как прежде

#### Scenario: Select — источник истины (e2e select_option)

- **GIVEN** открыта форма задачи
- **WHEN** значение `#task-priority` меняется программно (Playwright `select_option`, заполнение формы)
- **THEN** сегмент перерисовывается: подсвечена кнопка, соответствующая новому value; контракт-тесты нативного select остаются зелеными без правок локаторов

#### Scenario: Пустой приоритет — ничего не подсвечено

- **GIVEN** открыта форма создания (value селекта пуст — «—»)
- **WHEN** пользователь осматривает сегмент
- **THEN** ни одна кнопка не подсвечена (`.is-checked` нет) — мокап-дефолт «средний» не переносится: payload `priority: null` легален

#### Scenario: Disabled-инвариант FR-27

- **GIVEN** включен фастлайн-тумблер (приоритет закреплен high, селект disabled)
- **WHEN** пользователь пытается нажать кнопку сегмента
- **THEN** все кнопки сегмента disabled, клик не меняет значение селекта; после выключения тумблера кнопки разблокируются

### Requirement: Quick-чипы срока (F1)

Форма задачи MUST отображать под полем срока quick-чипы «Сегодня», «Завтра», «+7 дней» (`.qchip[data-due-quick]`) поверх СОХРАНЕННОГО нативного date-инпута `#task-due-date` (PLAN-FORM-F1; эталон form-v1/create.html). Чип MUST записывать соответствующую дату (сегодня / завтра / +7 календарных дней, ISO `YYYY-MM-DD`) в date-инпут — инпут остается источником истины: ручной ввод/календарь перерисовывают подсветку чипов (`.is-checked` по совпадению даты), дата вне быстрых значений — ни один чип не подсвечен. Коллект и формат payload не меняются.

#### Scenario: Чип пишет дату в инпут

- **GIVEN** открыта форма задачи, поле срока пусто
- **WHEN** пользователь нажимает чип «Завтра»
- **THEN** `#task-due-date` получает завтрашнюю дату в формате ISO, чип подсвечен (`.is-checked`)

#### Scenario: Ручной ввод — источник истины

- **GIVEN** открыта форма задачи
- **WHEN** пользователь вводит в `#task-due-date` дату вручную (или через календарь), совпадающую/не совпадающую с быстрым значением
- **THEN** подсветка чипов перерисовывается: совпадение — подсвечен соответствующий чип; произвольная дата — ни один чип не подсвечен; payload собирается из инпута как прежде

### Requirement: Счётчик длины заголовка (F1)

Поле названия задачи (`#task-title`, maxlength=500) MUST иметь счётчик `#title-counter` вида `N/500` (PLAN-FORM-F1; эталон form-v1/create.html `.counter`), обновляющийся при вводе и при заполнении формы. Счётчик — только отображение: maxlength не меняется, валидация и payload не затрагиваются. Подсказка под названием — нейтральный (не сигнальный) цвет — правка дефекта мокапа.

#### Scenario: Счётчик обновляется при вводе

- **GIVEN** открыта форма создания задачи, поле названия пусто
- **WHEN** пользователь вводит «Покупки» (8 символов)
- **THEN** счётчик показывает `8/500`; при очистке поля — `0/500`

#### Scenario: Счётчик при заполнении формы

- **GIVEN** задача с названием 12 символов открывается в редактировании
- **WHEN** форма заполняется значениями задачи
- **THEN** счётчик показывает `12/500` — синхронно с предзаполненным полем
