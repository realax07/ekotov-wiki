# Design: add-r4-user-profile-ticket-view

Технические решения Релиза 4. Наблюдаемое поведение — в дельтах `specs/`; здесь — как оно достигается. Стек не меняется (sdd.md §1: FastAPI + SQLite + Jinja2/ванильный JS + nginx). Новая python-зависимость одна — Pillow (аватар, research §1); новых фронтенд-зависимостей нет (ОГР-1).

## 1. Миграция схемы users/tasks (FR-36, FR-37, FR-38, NFR-9, ОВ-21/23)

- Одноразовый идемпотентный скрипт `backend/app/migrate_r4.py` (запуск: `python -m app.migrate_r4` из `backend/`) — по образцу `migrate_categories.py` (Релиз 2, NFR-8). Колонки также добавляются в `SCHEMA_SQL` (db.py) для свежих БД; ALTER — только при их отсутствии (PRAGMA table_info), как сделано для done_at.
- Схема users: `+ display_name TEXT`, `+ role TEXT`, `+ bio TEXT`, `+ avatar_path TEXT` (все nullable; Д-10/FR-42 — дефолты отображения при NULL). Схема tasks: `+ creator_id INTEGER REFERENCES users(id)` (nullable в схеме, заполняется всем), `+ assigned_to_id INTEGER REFERENCES users(id)` (nullable — FR-37).
- Индексы: `tasks(creator_id)`, `tasks(assigned_to_id)` — фильтры поиска FR-46.
- Бэкфилл (одна транзакция с ALTER): `creator_id = owner` для ВСЕХ задач (FR-38); `assigned_to_id = owner` для всех существующих задач (ОВ-23 — не null); `users.role`: owner → 'Product manager', wife → 'Product engineer' (ОВ-21, дефолт существующих записей; новые пользователи не заводятся — NFR-4).
- Автосверка до/после (NFR-9): снимок «до» (все поля всех задач + хеши паролей/логины) → миграция → сверка: прежние поля задач не изменились, `COUNT(tasks) WHERE creator_id IS NULL = 0`, `COUNT(tasks) WHERE assigned_to_id IS NULL` = числу задач, созданных ПОСЛЕ миграции (0 на момент накатки), логины/пароли работают. Расхождение → exit 1.
- **Deploy-заметка (ОГР-19):** миграция прода — строго после бэкапа (путь резервного копирования — из RUNBOOK; бэкап = копия файла БД, sdd §1). Откат при неудаче — восстановление из бэкапа. Порядок шага деплоя: остановка uvicorn (или пауза трафика) → бэкап → `python -m app.migrate_r4` → сверка exit 0 → старт → смоук `/api/health` + вход обоих пользователей. Бамп `static_v` — отдельным шагом (§7).

## 2. API профиля и аватара (FR-36/40/41/42, NFR-10, Д-11)

| Метод/путь | Описание | Ответы |
|---|---|---|
| `GET /api/profile` | Профиль текущего пользователя | 200 `{"login", "display_name", "role", "bio", "avatar_url"}` |
| `PUT /api/profile` | Сохранить display_name, role, bio | 200 (обновленный профиль); 422 — role вне справочника, display_name/bio неверного типа; 401 |
| `POST /api/profile/password` | Смена пароля: `{"current_password", "new_password"}` | 200 `{"ok": true}`; 401 (нет сессии); 422 `{"error": "invalid current password"}` (единый текст — не раскрывать лишнее, по духу NFR-7); 422 — пустой новый пароль |
| `POST /api/profile/avatar` | Загрузка аватара (multipart/form-data, поле `file`) | 200 `{"ok": true, "avatar_url": "..."}`; 422 `{"error": "invalid file type"}` — не png/jpg; 422 `{"error": "file too large"}` — >2 МБ; 401 |

- Все — вне exempt-списка (401 без сессии, middleware). Оперируют только пользователем сессии (JOIN sessions→users) — «свой профиль» (FR-39).
- Роль: серверная валидация по фиксированному списку `['Product manager', 'Product engineer']` (ОВ-21); прав/поведения не влияет — поле только читается (NFR-4 не затронута).
- Смена пароля (Д-11): проверка `bcrypt.checkpw(current)` → новый `bcrypt.hashpw`; sessions не трогаются (текущая сессия живет). Ошибка текущего пароля — 422, пароль не меняется.
- Аватар: проверка Content-Type/расширения (png/jpg) и размера (≤2 МБ, NFR-10/ОВ-22) → Pillow: декодирование, center-crop до квадрата, resize до 256×256 (Д-8; LANCZOS) → сохранение в `frontend/static/avatars/<user_id>.png` (формат содержимого приводится к png независимо от исходника — упрощает отдачу; WebP не требуется) → `avatar_path` в users. Ошибка декодирования (битый файл с png-расширением) → 422 invalid file type. Путь в `avatar_path` — относительный; `avatar_url` в ответах — с версией `?v=<updated_at>` для инвалидации кеша (§7).

## 3. `/api/auth/me` — расширение (FR-33/36/43)

Ответ 200 расширяется до `{"user", "display_name", "role", "bio", "avatar_url"}` (пустые значения — null при незаполненном профиле; Д-10 решается на клиенте: подпись = display_name или логин). JOIN по сессии уже есть (auth.py `me`) — расширяется выборка колонок. Обратная совместимость: ключ `user` сохранен.

## 4. Страница настроек пользователя (FR-39/40/41/42, ОГР-20)

- Новая страница `GET /settings/profile` (pages.py, редирект на /login без сессии — как /settings). Шаблон `frontend/templates/profile-settings.html` + `static/js/profile-settings.js` (модуль) + `static/css/profile-settings.css`. Названия страниц/путей — внутренние, в спеке не нормируются (контракт — поведение).
- Состав: форма профиля (display_name — текст; role — select c ровно двумя значениями ОВ-21; bio — textarea), блок смены пароля (текущий + новый), загрузка аватара (file input, показ ошибки «файл слишком большой»/«неверный тип» из ответа API). Кнопки сохранения — отдельные на каждый блок (независимые операции).
- Общий раздел «Настройки» (`/settings`, справочник категорий) не изменяется (ОГР-20); клик по профилю ведет на настройки пользователя, не на `/settings`.

## 5. Tooltip — единый механизм (FR-43/44, ОГР-17, ОВ-25)

- Общий модуль `frontend/static/js/tooltip.js` + CSS в app.css (токены V3): JS-инициализация на элементах с `data-tooltip` (профиль внизу сайдбара; карточки задач доски и выдачи поиска), позиционирование у нижнего левого края (не вылезает за вьюпорт), показ по hover/focus, скрытие по blur/mouseleave. Содержимое — готовая разметка, отрендеренная карточкой/профилем из уже загруженных данных (без отдельных запросов — данные assigned/creator и профиль приходят в ответах API, §6).
- Состав tooltip профиля (ОВ-25): аватар (или кружок-фоллбек), display_name (или логин, Д-10), логин, роль, bio. Состав tooltip карточки (FR-44, ОВ-25): assigned + creator — имена (display_name или логин; «Unassigned» курсивом при пустом assigned, ОВ-24); мини-аватары в tooltip карточки — на усмотрение dev/дизайна (не нормируются).
- Доступность: при `prefers-reduced-motion: reduce` анимации появления/скрытия всплывашек отключены (CSS media query, TC-vis-105) — содержимое появляется мгновенно (ОГР-17).

## 6. Assigned/creator: данные и отображение (FR-37/44/45, ОВ-23/24/26)

- Контракты задач (sdd §9): `POST /api/tasks` — опциональное `assigned_to_id` (существующий user или null; ОВ-26), `creator_id` ставит сервер = пользователю сессии (не принимается от клиента); `PATCH /api/tasks/{id}` — допускает `assigned_to_id` (select из пользователей, ОВ-26), `creator_id` не входит в контракт (изменение игнорируется/отклоняется — см. дельту tasks, сценарий «Creator задачи неизменяем»: отклонение выбирается реализацией как невходящее поле pydantic-схемы; наблюдаемо — creator не меняется). `GET /api/tasks/{id}`, `GET /api/board`, ответы поиска — содержат `creator` и `assigned` (имена; null → «Unassigned» на клиенте).
- Select исполнителя: источники значений — пользователи системы (`GET /api/auth/me` не дает списка; заведенных двое, NFR-4). Допустимо: маленький эндпоинт `GET /api/users` (id+display_name+login, вне exempt) ЛИБО статические два значения из известного состава — выбирается dev-задачей; требование спеки — «select из пользователей системы» (ОВ-26). Если вводится `GET /api/users` — включить в sdd-контракты и чеклист QA (I3).
- Карточки (cards.js): строка assigned/creator добавляется в шаблон карточки; при пустом assigned — курсивом «Unassigned», строка отображается всегда (ОВ-24). На карточках fast line и всех столбцов — одинаково (FR-45).
- View-модалка: отдельный рендер read-only — все признаки, assigned/creator, комментарии; кнопка «Редактировать» открывает существующую task-form в режиме редактирования (Д-9); визуальное отличие от форм — оформление по токенам V3 без полей ввода (ОГР-18); открытие — клик по карточке (существующий openTaskDetail переосмысляется: текущее окно деталей с полями редактирования разделяется на view-модалку и вызов task-form).

## 7. Поиск: фильтры и advanced (FR-46, ОВ-24)

- Конструктор: два новых поля фильтра — assigned (значения из БД + «без исполнителя») и creator (значения из БД); подсказки — из уникальных значений столбцов (join tasks→users) — тот же механизм «значения из данных», что `GET /api/suggestions`/категории (FR-35/DEF-001). Виртуальное значение «без исполнителя» маппится в `assigned IS NULL`.
- `GET /api/search` — новые query-параметры `assigned` (login | «none») и `creator` (login); `POST /api/search/advanced` — расширение грамматики полями `assigned`/`creator` с операторами `=` и `IS NULL` (парсер уже параметризованный — SQL-инъекции исключены, sdd NFR-7). `normalized_query` синхронно отражает новые условия.
- Выдача (UI и API) — assigned/creator в каждой строке; «Unassigned» курсивом (ОВ-24).

## 8. DEF-005: формы по мокапу V3 (FR-48)

- Вход: визуальный аудит форм создания/редактирования против мокапа V3 по четырем зонам DEF-005 (выбранные теги; поля ввода — токены полей; отображение приоритета; форма редактирования целиком). Правки — CSS + разметка; логика/валидация не меняются. Поле assigned (новое, ОВ-26) проектируется сразу по мокапу V3 — не создает нового расхождения.
- Чеклист «все интерактивные элементы покрыты стилями» (урок DEF-004) — в задачи QA. Ревью визуала — design_validator (E13).

## 9. Кеш-бастинг и отдача аватара (урок DEF-002/003, ОГР-16)

- Бамп `static_v` в pages.py при релизе со статикой (CSS/JS/шаблоны меняются в §3–8) — обязательный шаг деплоя, иначе Заказчик не увидит обновлений до 7 дней (DEF-002).
- Аватар раздается nginx из статики; инверсия кеша конкретного пользователя — версия в URL `?v=` (из updated_at аватара); глобальный бамп static_v страхует разметку.

## 11. Риски

- Pillow недоступен в окружении (зависимость не ставится) — эскалация: без него автосжатие нереализуемо (FR-42 Must); запасной вариант — stdlib-валидация без сжатия НЕ проходит ТЗ, решение только через установку Pillow.
- Миграция на проде: расхождение сверки → exit 1 → откат из бэкапа (ОГР-19); репетиция на копии прода перед накаткой — в задачу 1.1.
- Tooltip у нижнего края вьюпорта (профиль) — обязательный подбор позиции вверх; проверка web-тестом.
- Расширение `GET /api/auth/me` — потребители (profile.js) обновляются в том же релизе; обратная совместимость по ключу `user`.
- Клик по карточке теперь открывает view-модалку, а не форму редактирования — риск регрессии сценариев FR-7 закрывается сценарием Д-9 (кнопка «Редактировать») и web-тестами.
