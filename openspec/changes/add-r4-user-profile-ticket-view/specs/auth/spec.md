# Delta: auth

## MODIFIED Requirements

### Requirement: API текущего пользователя

Система MUST предоставлять API-эндпоинт `GET /api/auth/me`, возвращающий данные текущего авторизованного пользователя: логин, display_name, роль, «о себе» (bio) и URL аватара (FR-33, FR-36; расширение состава ответа в Релизе 4 — источник блока профиля и tooltip'а, FR-43). Эндпоинт MUST требовать действующую сессию: без сессии — отказ 401, как для всех API вне exempt-списка (NFR-7; exempt-список авторизации не расширяется). Эндпоинт MUST быть read-only: состояние не изменяет (редактирование профиля — отдельные эндпоинты профиля, FR-40). При незаполненном профиле поля display_name, роль, bio, URL аватара возвращаются пустыми (null) — логин заполнен всегда (Д-10: отображаемое имя заменяется логином, пока не задано).

#### Scenario: Текущий пользователь определен по сессии — полный состав

- **GIVEN** пользователь авторизован (действующая сессия; логин, например, «owner») и его профиль заполнен (display_name, роль, bio, аватар)
- **WHEN** вызывающий отправляет `GET /api/auth/me`
- **THEN** API отвечает 200 с логином, display_name, ролью, bio и URL аватара текущего пользователя, соответствующим сессии

#### Scenario: Текущий пользователь определен по сессии

- **GIVEN** пользователь авторизован (действующая сессия; логин, например, «owner»)
- **WHEN** вызывающий отправляет `GET /api/auth/me`
- **THEN** API отвечает 200 с логином текущего пользователя, соответствующим сессии (ключ `user` присутствует в ответе всегда — обратная совместимость)

#### Scenario: Дефолты при незаполненном профиле

- **GIVEN** пользователь авторизован, но никогда не заполнял профиль (нет display_name, роли, bio, аватара)
- **WHEN** вызывающий отправляет `GET /api/auth/me`
- **THEN** API отвечает 200: логин заполнен, display_name, роль, bio и URL аватара — пустые (null)

#### Scenario: Негативный: без сессии — 401

- **GIVEN** вызывающий не имеет действующей сессии
- **WHEN** вызывающий отправляет `GET /api/auth/me`
- **THEN** API отвечает 401 `{"error": "unauthorized"}` — эндпоинт не входит в exempt-список авторизации (NFR-7)

#### Scenario: Второй пользователь получает свои данные

- **GIVEN** второй пользователь (жена владельца) авторизована в своей сессии
- **WHEN** вызывающий в этой сессии отправляет `GET /api/auth/me`
- **THEN** API отвечает 200 с данными (логин, display_name, роль, bio, аватар) второго пользователя — каждый пользователь получает данные своей сессии

#### Scenario: Второй пользователь получает свой логин

- **GIVEN** второй пользователь (жена владельца) авторизована в своей сессии
- **WHEN** вызывающий в этой сессии отправляет `GET /api/auth/me`
- **THEN** API отвечает 200 с логином второго пользователя — каждый пользователь получает логин своей сессии

## ADDED Requirements

### Requirement: Профиль пользователя — просмотр и редактирование

Система MUST предоставлять API профиля текущего пользователя (FR-36, FR-40): `GET /api/profile` возвращает логин, display_name, роль, bio и URL аватара; `PUT /api/profile` сохраняет display_name, роль и bio. Роль MUST приниматься только из фиксированного справочника значений «Product manager» и «Product engineer» (ОВ-21); роль — чисто отображаемое поле: не влияет на права, авторизацию и поведение системы (ОВ-21, NFR-4). Редактирование доступно только своего профиля: эндпоинты operate исключительно над пользователем сессии (FR-39). Оба эндпоинта MUST требовать действующую сессию (401, NFR-7). Сохранение пустого display_name допустимо — при этом везде, где показывается имя, отображается логин (Д-10).

#### Scenario: Просмотр своего профиля

- **GIVEN** пользователь авторизован
- **WHEN** вызывающий отправляет `GET /api/profile`
- **THEN** API отвечает 200 с логином, display_name, ролью, bio и URL аватара пользователя сессии

#### Scenario: Сохранение профиля

- **GIVEN** пользователь авторизован
- **WHEN** вызывающий отправляет `PUT /api/profile` с display_name, ролью «Product engineer» и текстом bio
- **THEN** API отвечает 200; повторный `GET /api/profile` возвращает сохраненные значения; блок профиля и tooltip после обновления страницы отображают новые значения (FR-40, FR-43)

#### Scenario: Негативный: роль вне справочника отклоняется

- **GIVEN** пользователь авторизован
- **WHEN** вызывающий отправляет `PUT /api/profile` с ролью, отличной от «Product manager» и «Product engineer» (например, «Admin»)
- **THEN** API отвечает ошибкой валидации (422); профиль не изменяется — прежние значения сохраняются (ОВ-21)

#### Scenario: Негативный: без сессии — 401

- **GIVEN** вызывающий не имеет действующей сессии
- **WHEN** вызывающий отправляет `GET /api/profile` или `PUT /api/profile`
- **THEN** API отвечает 401 `{"error": "unauthorized"}` — эндпоинты не входят в exempt-список (NFR-7)

### Requirement: Смена пароля

Система MUST предоставлять текущему пользователю смену своего пароля: вводится текущий пароль и новый пароль (FR-41; ОГР-13 отменено решением Заказчика, ОГР-15). Смена MUST требовать корректный текущий пароль (Д-11); после успешной смены текущая сессия пользователя MUST сохраняться — принудительный повторный вход не требуется (Д-11). Новый пароль MUST храниться только в необратимом виде (NFR-7). Эндпоинт MUST требовать действующую сессию.

#### Scenario: Успешная смена пароля

- **GIVEN** пользователь авторизован и знает свой текущий пароль
- **WHEN** пользователь вводит корректный текущий пароль и новый пароль и подтверждает смену
- **THEN** пароль изменен; текущая сессия сохраняется без повторного входа (Д-11); вход со старым паролем после выхода отклоняется, вход с новым паролем выполняется успешно

#### Scenario: Негативный: неверный текущий пароль

- **GIVEN** пользователь авторизован
- **WHEN** пользователь вводит неверный текущий пароль и любой новый пароль
- **THEN** смена отклоняется с понятным сообщением об ошибке; пароль не изменен — вход со старым паролем продолжает работать (Д-11)

#### Scenario: Негативный: без сессии — 401

- **GIVEN** вызывающий не имеет действующей сессии
- **WHEN** вызывающий отправляет запрос смены пароля
- **THEN** API отвечает 401 `{"error": "unauthorized"}` (NFR-7)

### Requirement: Загрузка аватара

Пользователь MUST иметь возможность загрузить файл аватара в своем профиле (FR-42). Принимаются ТОЛЬКО файлы png/jpg: файл иного типа MUST отклоняться с понятной ошибкой, аватар не изменяется (FR-42). Исходный файл размером более 2 МБ MUST отклоняться с понятной ошибкой «файл слишком большой» — не молча и не падением (NFR-10, ОВ-22). Сервер MUST выполнять автосжатие: загруженное изображение приводится сервером к квадрату размером не более 256px (Д-8, ОГР-16) — пользователь не обрабатывает файл сам. Хранение и отдача аватара — статика с кеш-бастингом (ОГР-16). Эндпоинт загрузки MUST требовать действующую сессию; аватар загружается только свой. При отсутствии аватара отображается кружок с первой буквой логина (fallback, FR-33/FR-42).

#### Scenario: Успешная загрузка png

- **GIVEN** пользователь авторизован и находится в форме профиля
- **WHEN** пользователь загружает файл формата png размером не более 2 МБ
- **THEN** загрузка выполняется успешно; аватар отображается в блоке профиля внизу сайдбара и в tooltip'е профиля вместо кружка с буквой (FR-42, FR-43)

#### Scenario: Успешная загрузка jpg

- **GIVEN** пользователь авторизован
- **WHEN** пользователь загружает файл формата jpg размером не более 2 МБ
- **THEN** загрузка выполняется успешно, аватар отображается в блоке профиля и в tooltip'е (FR-42)

#### Scenario: Серверное автосжатие в квадрат ≤256px

- **GIVEN** пользователь авторизован
- **WHEN** пользователь загружает корректный png/jpg с размерами, превышающими 256px по любой стороне (например, 1000×800)
- **THEN** сервер сохраняет и отдает изображение, приведенное к квадрату не более 256px (Д-8, ОГР-16); от пользователя никаких действий по обработке файла не требуется

#### Scenario: Негативный: тип файла не png/jpg

- **GIVEN** пользователь авторизован, у него установлен действующий аватар
- **WHEN** пользователь загружает файл иного типа (например, gif или bmp)
- **THEN** загрузка отклоняется с понятной ошибкой о недопустимом типе файла; ранее установленный аватар не изменяется (FR-42)

#### Scenario: Негативный: исходник больше 2 МБ

- **GIVEN** пользователь авторизован
- **WHEN** пользователь загружает корректный png/jpg размером более 2 МБ
- **THEN** загрузка отклоняется с понятной ошибкой «файл слишком большой» (NFR-10, ОВ-22); аватар не изменяется, ошибок приложения нет

#### Scenario: Негативный: без сессии — 401

- **GIVEN** вызывающий не имеет действующей сессии
- **WHEN** вызывающий отправляет файл аватара на эндпоинт загрузки
- **THEN** API отвечает 401 `{"error": "unauthorized"}`; файл не сохраняется (NFR-7)

## ADDED Requirements

### Requirement: Миграция пользователей и задач без потери данных

Миграция схемы (users: display_name, role, bio, avatar — FR-36; tasks: creator_id, assigned_to_id — FR-37) MUST выполняться без потери данных (NFR-9): после миграции каждый пользователь сохраняет логин и пароль (вход работает), каждая задача сохраняет все прежние значения полей; creator_id заполнен у 100% задач (бэкфилл = owner, FR-38); assigned_to_id заполнен = owner у всех существующих задач (ОВ-23). Роли существующих пользователей проставляются по умолчанию: owner → «Product manager», wife → «Product engineer» (ОВ-21, значение по умолчанию для существующих записей). Миграция прода выполняется только после бэкапа (ОГР-19). Повторный запуск миграции MUST не дублировать данные и не менять значений (по образцу NFR-8).

#### Scenario: Вход работает после миграции

- **GIVEN** до миграции в системе заведены пользователи «owner» и «wife» с действующими паролями
- **WHEN** миграция выполнена и пользователь входит со своими прежними логином и паролем
- **THEN** вход выполняется успешно — учетные данные не потеряны (NFR-9)

#### Scenario: Значения задач сохранены

- **GIVEN** до миграции существует задача с известными значениями всех полей (название, описание, приоритет, категория, статус, теги, комментарии)
- **WHEN** миграция выполнена и пользователь открывает эту задачу
- **THEN** все прежние значения отображаются без изменений и потерь (NFR-9)

#### Scenario: Бэкфилл creator = owner у всех задач

- **GIVEN** до миграции в системе есть задачи (созданные владельцем)
- **WHEN** миграция выполнена
- **THEN** у каждой задачи (100%) creator = «owner» — включая архивные и fast-задачи (FR-38)

#### Scenario: Бэкфилл assigned = owner у всех существующих задач

- **GIVEN** до миграции в системе есть задачи без поля исполнителя
- **WHEN** миграция выполнена
- **THEN** у каждой существующей задачи assigned = «owner» (ОВ-23; ни одна существующая задача не остается без исполнителя после миграции)

#### Scenario: Роли по умолчанию после миграции

- **GIVEN** до миграции пользователи «owner» и «wife» не имели ролей
- **WHEN** миграция выполнена
- **THEN** роль «owner» = «Product manager», роль «wife» = «Product engineer» (ОВ-21, значение по умолчанию для существующих записей)

#### Scenario: Идемпотентность миграции

- **GIVEN** миграция уже выполнена один раз
- **WHEN** миграционный скрипт запускается повторно
- **THEN** повторный запуск не дублирует данные и не меняет значений — creator/assigned остаются = owner, значения задач не искажаются (по образцу миграции категорий Релиза 2, NFR-8)
