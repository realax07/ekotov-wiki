# Design: add-r3-visual-foundation

Технические решения Релиза 3. Наблюдаемое поведение — в дельтах `specs/`; здесь — как оно достигается. Стек не меняется (sdd.md r8 §1: FastAPI + SQLite + Jinja2/ванильный JS + nginx). Новых фронтенд/бэкенд-зависимостей нет (легковестность ОГР-1); прод-топология, сессии, схема БД — без изменений.

## 1. Drag-and-drop карточек (FR-31, ОГР-14, Д-6)

- Технология: нативный HTML5 Drag and Drop API (research §1). Плитка — `draggable=true`; события: `dragstart` (создание drag-образа: `setDragImage` с клоном; скрытие оригинала — opacity/display: дословное «прикрепляется к курсору и исчезает с доски»), `dragover` на колонках (`preventDefault` + подсветка зоны-приемника), `dragleave` (снятие подсветки), `drop` (перевод), `dragend` (сброс состояния).
- Эквивалентность прежнему способу (ОГР-14): drop вызывает тот же путь, что существующий элемент перевода — `POST /api/tasks/{id}/move` с целевым статусом. Серверные проверки, fast line (инвариант ≤1 fast в активных статусах, 409), done_at/автоархивация — без изменений; серверная часть вообще не меняется.
- Исходная позиция карточки сохраняется клиентом до подтверждения ответа: успех → перерисовка доски; ошибка (409 fast line занят или 4xx) → показ ошибки и возврат плитки на исходное место (Д-6); drop вне зон-приемников → обработчик не вызывается, HTML5 DnD сам возвращает визуал, статус не отправляется.
- Touch: обработчики не вешаются на touch — на сенсорных устройствах перенос прежним способом (ОВ-19).
- Место: ES-модуль `frontend/static/js/board/` (cards.js или выделенный dragdrop.js — по объему, research §3); зона приема — контейнер столбца.

## 2. Визуальные эффекты доски (FR-32, ОГР-12)

- База — действующие токены V3 «Бумага» (переменные темы `frontend/static/css/app.css :root`); эффекты — надстройка: новые CSS-правила используют токены, тема не меняется.
- Технология: чистый CSS — transitions (hover, плавный move), keyframes (появление карточек), тени/глубина (box-shadow по токенам), пустой state (оформление пустого контейнера столбца). Доступность: `prefers-reduced-motion: reduce` — анимации отключаются (обязательное условие FR-32). Производительность: анимации только transform/opacity, без layout-thrashing (PRODUCT_BACKLOG P8).
- Плавное перемещение между столбцами (связка с FR-31): при подтвержденном drop карточка анимированно занимает новую позицию в целевом столбце (FLIP-техника или эквивалент на transform — решение dev-задачи); требование наблюдаемое — «не телепортируется».
- Пресеты (ОВ-20): ПМ готовит 2–3 пресета (мокапы или живые пресеты) до dev-задачи; Заказчик выбирает один. До утверждения действует обязательный минимум: hover-переходы карточек + пустой state (уходят в код независимо от выбора). Ревью визуального результата — design_validator (E13).
- Точка внедрения статики: изменения CSS → бамп `static_v` (см. §5).

## 3. Профиль: GET /api/auth/me + блок сайдбара (FR-33, ОГР-13, Д-7)

- Backend: новый read-only роутер `GET /api/auth/me` в auth-роутере. Ответ 200: `{"user": "<login>"}` — login берется из проверенной сессии (middleware уже резолвит user_id → login). Без сессии — стандартный 401 `{"error": "unauthorized"}` (middleware; эндпоинт не добавляется в exempt-список). Изменений схемы, PATCH/паролей нет (ОГР-13).
- Frontend: на страницах функционала JS запрашивает `/api/auth/me` и заполняет блок внизу сайдбара: цветной кружок (цвет — по токенам V3; детерминированно по логину или один акцентный цвет — решение dev-задачи) с первой буквой логина (верхний регистр) + подпись с логином целиком (Д-7). Пока `/api/auth/me` отвечает 401 (сессия истекла), блок не отображается — middleware и так перенаправит на /login.
- Существующие разделы сайдбара (доска, поиск, Wiki, настройки, выход) не вытесняются: блок добавляется в layout ниже существующих элементов.

## 4. Формы V3 (FR-34, DEF-005)

- Вход: визуальный аудит форм создания/редактирования против мокапа V3 (`design/`) и токенов `app.css` — по четырем зонам расхождения DEF-005: (1) вид выбранных тегов; (2) поля ввода input/textarea (токены полей: радиус `--radius-field`, рамки, фокус-кольцо); (3) отображение выбранного приоритета (селект/иконки/цвет — иконки приоритетов уже inline SVG после Релиза 2, приводится оформление); (4) форма редактирования целиком.
- Правки — CSS + разметка шаблонов; логика форм, валидация, API — не меняются. Обязательная проверка «все интерактивные элементы покрыты стилями» (урок DEF-004) — чеклист задачи QA.
- Кеш-бастинг: бамп `static_v` в `pages.py` (урок DEF-002/DEF-003) — иначе Заказчик не увидит новых стилей до 7 дней.

## 5. Подсказки/селекты из БД — доведение DEF-001 (FR-35)

- Порядок (фиксирован ТЗ): **диагностика на проде с сессией Заказчика → установление причины → фикс**. Кандидаты-причины (PRODUCT_BACKLOG DEF-001): (а) JS-ошибка при загрузке /search не дает заполнить datalist; (б) select категории не привязан к данным (статические option); (в) несоответствие формата ответа ожиданиям клиента. Эндпоинт `GET /api/suggestions` отвечает (401 без сессии подтвержден) — дефект в клиентском потреблении.
- Общий механизм (задел под будущие справочники): все динамические списки — селекты (категория в форме и в фильтре) и подсказки (datalist тегов/категорий поиска) — заполняются из одного источника фактических данных: уникальные значения соответствующих столбцов БД; категории — из справочника `GET /api/categories`, теги/подсказки — `GET /api/suggestions` (set() теги∪категории). Допустимо предвычислять и хранить множество значений (FR-35); на объеме 2 пользователей/1000 задач прямые запросы достаточны, кэш (если вводится) инвалидируется при изменении данных.
- Статические/захардкоженные option-списки удаляются (уже сделано для категории в Релизе 2 — проверяется полнота: все селекты и оба datalist'а). Жесткая/мягкая валидация значений не затрагивается.
- Подтверждение закрытия: сценарий в реальной сессии на проде (дельта search) — значения видны в UI, не только в ответе API.

## 7. Риски

- HTML5 DnD имеет особенности поведения между браузерами (drag-образ, dragleave-мерцание) — закрывается тестом web-сьюта на целевом браузере Заказчика и деградацией: при недоступности DnD перенос работает прежним способом (действие равнозначно, ОГР-14).
- Плавный move-анимации при drop синхронизируется с перерисовкой доски после ответа API — флэш/скачок карточки недопустим по FR-32; проверяется web-тестом.
- Диагностика DEF-001 требует прод-сессии Заказчика — задача помечена как требующая участия Заказчика (эскалация ПМ по расписанию сессии).
