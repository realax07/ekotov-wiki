# Proposal: add-r3-visual-foundation

## Change ID

`add-r3-visual-foundation`

## Why

Релиз 3 «Визуальный фундамент» проекта ekotov-wiki. Источник требований — утвержденное Заказчиком `requirements.md` r4 (УТВЕРЖДЕН 2026-09-27; вводные Заказчика 2026-09-26 + ответы раунда 3 `docs/ba/answers_round3.md`): FR-31…FR-35, ограничения ОГР-12/13/14, дефолты Д-6/Д-7 (приняты без возражений), 0 открытых вопросов (ОВ-19 «принимаю», ОВ-20 «подтверждаю» — дословно).

Цель релиза: доска получает перетаскивание карточек (P7) и визуальные эффекты на токенах V3 (P8), пользователь видит свой профиль внизу сайдбара (P3-минимум), формы доводятся до дизайна V3 (DEF-005), а подсказки/селект-поля доводятся до фактического исполнения — значения из БД в реальной сессии на проде (DEF-001, расхождение «спека закрыта — Заказчик не видит значений»).

## Scope

### In scope

- FR-31 (Must): drag-and-drop карточек между столбцами мышью на десктопе; при зажатии карточка прикрепляется к курсору и исчезает с исходного места; отпускание над столбцом — перевод в него; отпускание вне зоны столбца — возврат на место без изменения статуса. Результат равнозначен переводу прежним способом — тот же API `POST /api/tasks/{id}/move`, серверные проверки, fast line (ОГР-5) и архивация без изменений (ОГР-14). Конфликт fast line при drop в активную фазу — 409, ошибка в UI, плитка возвращается (Д-6). На touch-устройствах перенос — прежним способом (ОВ-19: «принимаю»).
- FR-32 (Must): визуальные эффекты доски поверх действующих токенов V3 «Бумага» — hover-переходы карточек; плавное перемещение карточки между столбцами (связано с FR-31, без «телепортации»); анимация появления карточек; тени/глубина; оформленный пустой state пустого столбца. При системной настройке уменьшения движения анимации отключаются. Обязательный минимум до утверждения пресета: hover-переходы + пустой state; полный состав Заказчик утверждает из 2–3 пресетов ПМ до dev-задачи (ОВ-20: «подтверждаю»).
- FR-33 (Must, P3-минимум): профиль внизу сайдбара — цветной кружок с первой буквой логина; текущий пользователь через `GET /api/auth/me` (авторизация обязательна). Рядом с кружком — логин целиком (Д-7).
- FR-34 (Must, DEF-005): формы создания/редактирования по дизайну V3 по всем зонам расхождения; критерий приемки — соответствие мокапу V3 по токенам (цвета, радиусы, типографика, состояния), все интерактивные элементы покрыты стилями.
- FR-35 (Must, DEF-001): подсказки поиска и селект-поля показывают уникальные значения соответствующих столбцов БД (предвычисление допустимо); статические/пустые списки не допускаются; механизм общий для селект-полей; закрытие подтверждается диагностикой на проде с сессией Заказчика. Жесткая/мягкая валидация не затрагивается.

### Out of scope

- Аватарки-файлы и смена пароля в профиле — дословное исключение Заказчика (ОГР-13, Won't).
- Настройка профиля (display_name и прочее) — за границей P3-минимум (Won't).
- Touch-перетаскивание — отклонено Заказчиком (ОВ-19).
- Новая тема/смена дизайн-направления — база остается V3 «Бумага», эффекты — надстройка (ОГР-12).
- Новая валидация значений подсказок (жесткая/мягкая) — FR-35 багфикс исполнения FR-30, валидация не меняется.
- P1/P9-функциональные улучшения формы вне зон расхождения DEF-005 — остаются в бэклоге.

## Approach

Brownfield-дельты поверх master-спек (10 доменов) без перезаписи существующих Requirements. DnD — новое UI-средство существующего перевода: серверная часть не меняется, вся дельта — клиентское поведение доски (board, FR-31) с сохранением серверных инвариантов (ОГР-14, Д-6). Визуал FR-32 — чистый CSS (transitions/keyframes) поверх переменных темы app.css, без новых зависимостей; состав — по пресету Заказчика, до утверждения действует обязательный минимум. Профиль FR-33 — один новый read-only эндпоинт `GET /api/auth/me` (login из сессии) + блок в сайдбаре; изменений схемы нет. FR-34 — визуальный аудит форм против мокапа V3 (`design/`) и токенов app.css, правки CSS/разметки, бамп `static_v` (урок DEF-002/DEF-004). FR-35 — сначала диагностика на проде с сессией Заказчика (эндпоинт отвечает, значения в UI не появляются), затем фикс по установленной причине; механика — общий «источник значений из данных» для селектов и подсказок. Технические решения — в `design.md`, контракты — в `sdd.md` (r8).

Примечание о существующих маршрутах (I3): пакет не изменяет серверные контракты — все действующие маршруты (`GET /api/board`, `GET /api/search`, `POST /api/search/advanced`, `POST /api/auth/logout`, `GET /wiki` и прочие из sdd.md §3) сохраняются без изменений; из них пакет затрагивает только потребление `GET /api/search`/`POST /api/search/advanced` клиентом поиска (FR-35 — клиентское исполнение подсказок) и создает один новый маршрут `GET /api/auth/me` (FR-33, sdd §3.1-бис).

## Assumptions (дефолты Д-6/Д-7 — приняты Заказчиком без возражений 2026-09-27)

- Д-6: отпускание fast-карточки в активную фазу («Ожидает»/«В работе») при занятой fast line — сервер отклоняет перевод (409), UI показывает ошибку, плитка возвращается на исходное место; инвариант «≤1 fast в активных статусах» сохраняется при любом способе переноса.
- Д-7: рядом с кружком профиля отображается логин пользователя целиком (owner/wife) — кружок с буквой плюс текстовая подпись.
