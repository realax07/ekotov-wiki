# Дельта specs: wiki — НОВЫЙ домен (P15)

## Purpose

Wiki-функционал в монолите: иерархия страниц (дерево по parent_id,
вложенность неограниченная), WYSIWYG-редактор на contenteditable (vanilla
JS, ОГР-8), изображения через существующий images-сервис, LIKE-поиск,
полная история версий с откатом, общий доступ для обеих учеток. Данные —
таблицы `pages` + `page_versions` в общей `wiki.db` (миграция по паттерну
migrate_gallery). Поиск по wiki — только внутри раздела Wiki (глобальный
поиск и search-сервис не затрагиваются). Индексация wiki в search-сервис —
отдельное будущее решение (Won't).

## ADDED Requirements

### Requirement: Дерево страниц Wiki

Раздел Wiki MUST отображать авторизованному пользователю дерево всех
страниц, построенное по иерархии `parent_id`, с неограниченной вложенностью
(FR-107). Страница `/wiki` без параметров MUST показывать список корневых
страниц (`parent_id = NULL`) с раскрывающимися поддеревьями; узлы дерева
MUST раскрываться и сворачиваться. При отсутствии страниц MUST показываться
пустое состояние с кнопкой создания первой страницы. Отдельная «главная
страница» wiki НЕ вводится (ОВ-4): точка входа раздела — дерево от корневых.

#### Scenario: Открытие /wiki со страницами

- **GIVEN** пользователь авторизован и в wiki есть корневые и вложенные
  страницы
- **WHEN** пользователь открывает `/wiki` без параметров
- **THEN** отображается список корневых страниц (`parent_id = NULL`) с
  поддеревьями; вложенность раскрывается на любую глубину без ограничения
  (FR-107)

#### Scenario: Раскрытие и сворачивание узлов

- **GIVEN** пользователь видит дерево с вложенными страницами
- **WHEN** пользователь кликает по узлу с дочерними страницами
- **THEN** поддерево раскрывается; повторный клик сворачивает его (FR-107)

#### Scenario: Пустое состояние

- **GIVEN** пользователь авторизован и в wiki нет ни одной страницы
- **WHEN** пользователь открывает `/wiki`
- **THEN** отображается пустое состояние с кнопкой создания первой страницы
  (FR-107)

### Requirement: Создание страницы Wiki

Авторизованный пользователь MUST иметь возможность создать страницу:
заголовок (непустой) и контент, с указанием родительской страницы или
«без родителя» (корневая) (FR-108). Созданная страница MUST появиться в
дереве на выбранном месте. Пустой заголовок MUST отклоняться (ошибка формы,
без создания страницы).

#### Scenario: Создание корневой страницы

- **GIVEN** пользователь авторизован
- **WHEN** пользователь создает страницу с непустым заголовком и контентом,
  выбрав «без родителя»
- **THEN** страница создается корневой и появляется в дереве на верхнем
  уровне (FR-108)

#### Scenario: Создание вложенной страницы

- **GIVEN** пользователь авторизован и в дереве есть страница-родитель
- **WHEN** пользователь создает страницу, указав родителя
- **THEN** страница создается дочерней к выбранной и появляется в дереве
  внутри её поддерева (FR-108)

#### Scenario: Пустой заголовок отклоняется

- **GIVEN** пользователь авторизован и открыл форму создания страницы
- **WHEN** пользователь отправляет форму с пустым заголовком
- **THEN** создание отклоняется с ошибкой формы; страница не создается
  (FR-108)

### Requirement: Breadcrumb на странице статьи

На странице статьи MUST отображаться цепочка предков от корня до текущей
страницы (FR-109). Каждый элемент цепочки MUST быть кликабельным и вести на
соответствующую страницу. Текущая страница в цепочке не ссылается на себя.

#### Scenario: Полная цепочка предков

- **GIVEN** существует страница третьего уровня вложенности (корень →
  раздел → статья)
- **WHEN** пользователь открывает страницу статьи
- **THEN** breadcrumb показывает цепочку «корень → раздел → статья»; каждый
  элемент — кликабельная ссылка на соответствующую страницу (FR-109)

#### Scenario: Breadcrumb корневой страницы

- **GIVEN** пользователь открыл корневую страницу wiki
- **WHEN** пользователь просматривает breadcrumb
- **THEN** цепочка состоит из одного элемента — текущей страницы (без
  ссылки на саму себя) (FR-109)

### Requirement: WYSIWYG-редактор страниц

Редактирование контента MUST выполняться в WYSIWYG-редакторе на
contenteditable: vanilla JS, БЕЗ внешних CDN, библиотек и сборщиков (ОГР-8,
решение 2) (FR-110). Тулбар MUST содержать: заголовки H1–H3, жирный,
курсив, подчеркивание, нумерованный и маркированный списки, цитату,
код-блок, ссылку, таблицу, изображение (FR-110, FR-111), отмену/повтор
(undo/redo). Отредактированный вид MUST соответствовать сохраненному
(WYSIWYG). Работа редактора MUST проверяться в актуальных Chrome и Firefox
(NFR-33).

#### Scenario: Тулбар применяет форматирование

- **GIVEN** пользователь авторизован и редактирует страницу в WYSIWYG-редакторе
- **WHEN** пользователь применяет инструменты тулбара (H1–H3, B/I/U,
  нумерованный/маркированный списки, цитата, код-блок, ссылка, таблица)
- **THEN** форматирование применяется к выделению в поле редактирования;
  сохраненная страница отображает тот же вид без расхождений (FR-110)

#### Scenario: Undo/redo

- **GIVEN** пользователь внес правки в редакторе
- **WHEN** пользователь нажимает отмену/повтор тулбара
- **THEN** правка отменяется / повторно применяется (FR-110)

#### Scenario: Редактор без внешних зависимостей

- **GIVEN** страница редактора открыта в браузере
- **WHEN** проверяются сетевые запросы страницы
- **THEN** запросов к внешним CDN/доменам нет — редактор работает целиком на
  локальной статике (vanilla JS, ОГР-8; NFR-33)

### Requirement: Изображения в контенте через images-сервис

Вставка изображения в контент MUST выполняться (а) выбором из существующей
галереи или (б) загрузкой с диска через существующий `POST /api/images`
(решение 3) (FR-111). В контенте MUST храниться ссылка на раздачу
`/images/{id}`; файлы изображений MUST NOT дублироваться в БД wiki. Лимиты
загрузки переиспользуются от images-сервиса (≤ 10 МБ, JPEG/PNG/GIF/WebP,
422 при нарушении — NFR-21 через NFR-34): новые лимиты и хранение в wiki НЕ
вводятся (NFR-34).

#### Scenario: Вставка изображения из галереи

- **GIVEN** пользователь редактирует страницу и в галерее есть изображения
- **WHEN** пользователь выбирает изображение из существующей галереи
- **THEN** в контент вставляется ссылка на `/images/{id}` этого изображения;
  файл в БД wiki не дублируется (FR-111)

#### Scenario: Загрузка изображения с диска

- **GIVEN** пользователь редактирует страницу
- **WHEN** пользователь загружает файл с диска (валидный: ≤ 10 МБ,
  JPEG/PNG/GIF/WebP)
- **THEN** файл загружается через существующий `POST /api/images` и в
  контент вставляется ссылка на `/images/{id}` (FR-111, NFR-34)

#### Scenario: Нарушение лимитов загрузки

- **GIVEN** пользователь загружает файл с диска при вставке изображения
- **WHEN** файл больше 10 МБ или неподдерживаемого типа
- **THEN** images-сервис отвечает 422 и в контент ничего не вставляется —
  пользователь видит ошибку (NFR-34, лимиты NFR-21)

### Requirement: Редактирование страницы с записью версии

Авторизованный пользователь MUST иметь возможность редактировать заголовок
и контент страницы (FR-112). Каждое сохранение правки MUST создавать запись
в `page_versions` (автор, время, контент) — история полная, правки НЕ
теряются. Запись версии создается и при изменении только заголовка, и при
изменении только контента.

#### Scenario: Сохранение правки создает версию

- **GIVEN** пользователь авторизован и редактирует существующую страницу
- **WHEN** пользователь сохраняет правку
- **THEN** страница обновляется и в `page_versions` появляется новая запись:
  контент, автор (текущая сессия), время сохранения (FR-112)

#### Scenario: История полная

- **GIVEN** страницу последовательно правили разные пользователи
- **WHEN** пользователь открывает историю страницы
- **THEN** видны все правки с авторами и временем — ни одна правка не
  потеряна (FR-112)

### Requirement: История версий и откат

Пользователь MUST иметь возможность открыть список версий страницы: автор,
дата-время, порядок — от новых к старым (FR-113). Просмотр содержимого любой
версии MUST быть доступен read-only. Откат к версии MUST возвращать её
контент как СНОВА последнюю версию: создается НОВАЯ запись в
`page_versions`; история НЕ переписывается и НЕ удаляется (решение 6).

#### Scenario: Список версий от новых к старым

- **GIVEN** страница имеет несколько версий от разных авторов
- **WHEN** пользователь открывает историю страницы
- **THEN** версии отображаются списком: автор, дата-время, от новых к старым
  (FR-113)

#### Scenario: Просмотр версии read-only

- **GIVEN** пользователь открыл историю страницы
- **WHEN** пользователь выбирает любую версию для просмотра
- **THEN** содержимое версии отображается read-only — без возможности
  правки в этом просмотре (FR-113)

#### Scenario: Откат создает новую версию

- **GIVEN** страница имеет версии V1, V2, V3 (V3 — последняя)
- **WHEN** пользователь откатывается к V1
- **THEN** контент страницы становится содержимым V1, и в `page_versions`
  создается НОВАЯ запись V4 с этим контентом; версии V1–V3 остаются в
  истории без изменений (FR-113)

### Requirement: Поиск по wiki

Авторизованный пользователь MUST иметь возможность искать по wiki подстрокой
по заголовку И тексту страниц (SQL LIKE через API монолита, решение 4)
(FR-114). Результаты MUST отображаться списком: заголовок страницы, путь в
иерархии, фрагмент контента с подсветкой совпадения. Поиск НЕ по версиям —
только по текущему контенту (ОВ-3). Поиск доступен только внутри раздела
Wiki; глобальный поиск по wiki со страницы «Поиск» и индексация в
search-сервис — вне скоупа (Won't, решение 4).

#### Scenario: Поиск находит по заголовку и тексту

- **GIVEN** существуют страницы, содержащие подстроку запроса в заголовке,
  и страницы — только в контенте
- **WHEN** пользователь вводит подстроку в поиск раздела Wiki
- **THEN** в результатах присутствуют оба типа страниц, каждая — с
  заголовком, путем в иерархии и фрагментом с подсветкой совпадения (FR-114)

#### Scenario: Поиск не затрагивает версии

- **GIVEN** подстрока встречается только в старой версии страницы (в текущем
  контенте её нет)
- **WHEN** пользователь ищет эту подстроку
- **THEN** страница в результатах отсутствует — поиск только по текущему
  контенту (ОВ-3, FR-114)

#### Scenario: Поиск без совпадений

- **GIVEN** пользователь открыл поиск раздела Wiki
- **WHEN** пользователь вводит подстроку, которой нет ни в одной странице
- **THEN** отображается пустой результат без ошибок (FR-114)

### Requirement: Права доступа к wiki

Любая авторизованная сессия (owner, wife) MUST читать и редактировать все
страницы wiki и версии — без разделения прав (решение 7, FR-115). Анонимный
запрос страницы wiki MUST выполнять редирект на `/login`; анонимный вызов
wiki-API MUST отвечать 401 (паттерн `board.py`, сессионные куки, middleware).

#### Scenario: Паритет owner и wife

- **GIVEN** owner и wife авторизованы в своих сессиях
- **WHEN** каждый читает, создает, редактирует страницы и работает с
  версиями
- **THEN** оба выполняют все операции одинаково успешно — разделения прав
  нет (FR-115)

#### Scenario: Анонимный доступ к странице

- **GIVEN** сессия отсутствует
- **WHEN** запрашивается любая страница wiki (включая `/wiki/{id}`)
- **THEN** выполняется редирект на `/login` (FR-115)

#### Scenario: Анонимный вызов API

- **GIVEN** сессия отсутствует
- **WHEN** вызывается любой метод wiki-API
- **THEN** ответ — 401 (FR-115)

### Requirement: Удаление страницы

Авторизованный пользователь ДОЛЖЕН иметь возможность удалить страницу после
подтверждения (FR-116, Should). Удаление страницы, у которой есть дочерние,
MUST БЫТЬ ЗАПРЕЩЕНО до их переноса или удаления (дефолт ОВ-2): попытка
возвращает ошибку без удаления. Удаление страницы MUST NOT удалять файлы
изображений в галерее (в контенте — только ссылки `/images/{id}`).

#### Scenario: Удаление листовой страницы

- **GIVEN** пользователь авторизован и страница не имеет дочерних
- **WHEN** пользователь подтверждает удаление
- **THEN** страница удаляется и исчезает из дерева; файлы изображений в
  галерее остаются (FR-116)

#### Scenario: Удаление страницы с дочерними запрещено

- **GIVEN** страница имеет хотя бы одну дочернюю
- **WHEN** пользователь пытается её удалить
- **THEN** удаление отклоняется с ошибкой; страница и поддерево остаются
  (ОВ-2, FR-116)

### Requirement: Производительность wiki-API

Ответы wiki-API MUST укладываться в p95 < 300 мс (открытие страницы, дерево,
список версий) и поиск — p95 < 500 мс на корпусе до 1000 страниц /
10 000 версий (NFR-30; эталон порога поиска — формулировка FR-спеки поиска).

#### Scenario: Пороги на эталонном корпусе

- **GIVEN** на стенде корпус до 1000 страниц и до 10 000 версий
- **WHEN** выполняется серия запросов открытия страницы, дерева, списка
  версий и поиска
- **THEN** p95 открытия/дерева/версий < 300 мс, p95 поиска < 500 мс (NFR-30)

### Requirement: Санитизация HTML контента

Контент страниц — HTML из редактора; при отображении MUST применяться
серверная санитизация по whitelist тегов/атрибутов редактора (FR-110)
(NFR-31). Скрипты (`script`), обработчики `on*`, `javascript:`-URL и внешние
embed НЕ проходят санитизацию. Сессии — как у доски: сессионные куки, Secure
в проде (паттерн `board.py`).

#### Scenario: Скрипт вырезается при отображении

- **GIVEN** в контент страницы вставлен `<script>` или атрибут `onclick`
  (например, через вставку HTML)
- **WHEN** страница отображается
- **THEN** скрипт/обработчик в отдаваемом HTML отсутствует — санитизация по
  whitelist удаляет их до рендера (NFR-31)

#### Scenario: Разрешенные теги проходят

- **GIVEN** контент содержит только теги whitelist редактора (H1–H3, B/I/U,
  списки, цитата, код-блок, ссылки, таблицы, изображения)
- **WHEN** страница отображается
- **THEN** разметка сохраняется без искажений (NFR-31)

### Requirement: Миграция таблиц pages и page_versions

Миграция `pages` + `page_versions` MUST выполняться по паттерну
`app.migrate_gallery`: идемпотентно (CREATE TABLE/INDEX IF NOT EXISTS), все
DDL в одной явной транзакции BEGIN IMMEDIATE, автосверка схемы (exit 1 при
расхождении), обязательная репетиция на копии прод-БД до боевой накатки
(NFR-32; правило deploy-спеки, урок Р4).

#### Scenario: Повторный запуск миграции

- **GIVEN** миграция уже применена к БД
- **WHEN** скрипт миграции запускается повторно
- **THEN** он завершается успешно как no-op (ничего не создает) и снова
  проходит автосверку (NFR-32)

#### Scenario: Репетиция на копии прод-БД

- **GIVEN** подготовлена свежая копия прод-БД
- **WHEN** миграция прогоняется на копии до боевой накатки
- **THEN** сверка зеленая, боевые данные не тронуты; только после этого
  выполняется накатка на прод (NFR-32)

### Requirement: Фронтенд wiki без внешних зависимостей

Фронтенд wiki (редактор, дерево, история) MUST быть vanilla JS без внешних
зависимостей (ОГР-8); вид MUST строиться на дизайн-токенах V3 «Бумага»
(`app.css :root`, без хардкода цветов) (NFR-33). Работа редактора MUST
проверяться в актуальных Chrome и Firefox.

#### Scenario: Токены вместо хардкода

- **GIVEN** страницы wiki сверстаны
- **WHEN** проверяются CSS wiki-страниц
- **THEN** цвета/отступы берутся из переменных `app.css :root` (V3
  «Бумага»); хардкода цветов нет (NFR-33)

#### Scenario: Кроссбраузерность редактора

- **GIVEN** актуальные Chrome и Firefox
- **WHEN** выполняются базовые операции редактора (ввод, тулбар, undo/redo,
  сохранение)
- **THEN** редактор работает в обоих браузерах (NFR-33)
