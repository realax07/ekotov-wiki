## 1. Общее описание

Мониторинг прод-стека ekotov-wiki (compose-проект `ekotov-wiki-par`: app +
frontend/nginx + search + backup, TLS :10443): легкий стек **Netdata**
(ОВ-1 = вариант «в») одним контейнером — метрики железа хоста (CPU, RAM,
HDD), контейнеров и сервисов; дашборд доступен по под-пути `/netdata/`
единственной наружной точки (nginx :10443), доступ — **только учетка owner**
(ОВ-2). В UI — ссылка «Мониторинг» внизу слева сайдбара, видна только owner,
открывает дашборд в новой вкладке. БД wiki и поведение существующих
маршрутов не меняются.

Нумерация продолжает сквозную: последние использованные — FR-74
(add-containerization), NFR-18 (r6).

## 2. Аудитория

Пользователь мониторинга — владелец (учетка `owner`, роль «Product manager»,
бэкфилл ОВ-21). Пользователь PE (учетка `wife`) мониторинга не видит и не
получает. Исполнители пакета: ui_designer (мокапы, зона design/**), dev
(фронтенд + devops-активности), QA (в т.ч. design_validator), Заказчик
(утверждение мокапа + прод-приемка).

## 3. Функциональные требования (FR)

- **FR-75** (Must): Метрики собираются контейнером `netdata`
  (образ `netdata/netdata`) в составе compose (прод и стенд — паритет
  топологии): хостовые источники `/proc`, `/sys` — маунты строго read-only;
  метрики контейнеров — через `/var/run/docker.sock` строго read-only
  (только чтение метрик, управление контейнерами не выполняется; урок R6).
  Порт netdata наружу не публикуется; доступ — только через nginx-локацию
  `/netdata/` на существующем порте 10443 (преемственность: наружу открыт
  только nginx).
- **FR-76** (Must): Доступ к `/netdata/` — HTTP Basic-аутентификация на
  уровне nginx (проверка ДО проксирования; пары локаций точная + префиксная
  по образцу search-семейства). Креды — owner; файл htpasswd вне репозитория
  (bind-mount ro), пароль basic auth отдельный от пароля wiki. Без валидных
  кредов — 401 (в т.ч. PE и неавторизованным). Скрытие ссылки в сайдбаре —
  удобство, не граница доступа.
- **FR-77** (Must): Дашборд вживую показывает: CPU, RAM, диски (HDD) хоста;
  показатели каждого контейнера прод-стека (app, frontend, search, backup,
  netdata) по именам. Без дополнительных компонентов мониторинга
  (cAdvisor/exporters/Prometheus — не нужны, ОВ-1 легкий стек). Критерий
  приемки Заказчика: дашборд с этими показателями вживую на проде.
- **FR-78** (Must): Ссылка «Мониторинг» в сайдбаре: нижний левый блок
  (`sidebar-footer`), рядом с «Настройки»/«Выйти»; ведет на `/netdata/`,
  открывает в новой вкладке (`target="_blank"`); рендер по роли из
  `GET /api/auth/me` — только owner («Product manager»); до ответа/при 401
  ссылка не отображается (паттерн блока профиля). Вид ссылки (место, иконка,
  состояния) — по мокапу ui_designer, утвержденному Заказчиком ДО dev;
  после dev соответствие мокапу проверяет design_validator (дополнение
  Заказчика: «Дизайн не забудь», «У нас есть дизайнер»).

## 4. Нефункциональные требования (NFR)

- **NFR-19** (Must): Ресурсы мониторинга: `mem_limit` netdata 256m;
  healthcheck; ротация логов json-file 10m×3 (паритет стеку). Суммарные
  лимиты стека с netdata — 1.41 GB, резерв хосту (VPS 3.9 GB) ≥ 2.4 GB
  (требование ≥ 2 GB из deploy-спеки сохраняется). Фактическое потребление
  RAM netdata замеряется на стенде до прод-выкатки (урок PLAN-R7: вес меряем
  по факту); стабильное превышение лимита блокирует выкатку до решения
  Заказчика.

## 6. Ограничения

- VPS: 3.9 GB total / 2.7 GB available — +256m лимит укладывается (deploy:
  резерв ≥ 2 GB сохраняется).
- Только `docker compose`; без k8s (ограничение проекта).
- Внешние библиотеки в UI запрещены (ОГР-8): иконка — inline-SVG, стили —
  токены V3 «Бумага» (app.css :root).
- docker.sock — только ro (урок R6/PLAN-R7).
- Дизайн-фаза: мокапы — ui_designer (зона design/**), утверждение —
  Заказчик, ревью вида — design_validator (паттерн Р4/Р5).
