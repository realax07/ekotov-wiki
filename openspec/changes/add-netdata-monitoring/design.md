## §1. Целевая топология

```
Браузер (owner) ── https://194.58.34.122:10443 ── nginx [frontend]
   ├── /netdata        → 301 /netdata/
   ├── = /netdata/     → basic auth (htpasswd owner) → proxy http://netdata:19999/
   └── ^~ /netdata/    → то же (assets/API дашборда)
   └── остальное       → как сейчас (app:8377, search:8378)

netdata [контейнер netdata/netdata, :19999 ВНУТРИ compose-сети, не публикуется]
   ├── /proc, /sys  → маунты с хоста :ro (CPU/RAM/диски хоста)
   └── /var/run/docker.sock :ro (контейнеры: cgroups + имена)
```

- Единственная наружная точка остается nginx :10443 (преемственность
  deploy: «Наружу открыт только nginx», FR-65) — порт 19999 netdata НЕ
  публикуется (паритет app/search).
- resolver 127.0.0.11 + переменная в proxy_pass — анти-stale-DNS, тот же
  паттерн, что app/search (design add-containerization §1).
- Пара `= /netdata/` (точный) + `^~ /netdata/` (префикс, отключает regex) —
  по образцу search-семейства; плюс `= /netdata` → 301 на `/netdata/`
  (официальный паттерн Netdata: дашборд требует trailing slash).
- URI НЕ переписывается на assets: официальный паттерн — `proxy_pass
  http://netdata/$ndpath$is_args$args` с вырезанием префикса через named
  capture; Netdata сам отдает корректные пути (его UI поддерживает запуск из
  subpath). Проверяется смоуком стенда (задача 1.3); при пробелах —
  запасной вариант с `proxy_redirect`/rewrite фиксируется в tasks до
  приемки (эскалация в REPORT).

## §2. Авторизация — basic auth на nginx-локации (ОВ-2)

Выбор: **nginx basic auth (htpasswd)** на обеих локациях `/netdata`.

| Вариант | Оценка |
|---|---|
| **basic auth на nginx** (принято) | + одна директива на локации; + работает ДО прокси (Netdata не получает ни одного запроса без кредов); + креды знает только nginx ( образ frontend не пересобирается при смене пароля — файл маунтом); + штатный механизм, документирован Netdata |
| auth_request к wiki-сессии | − `/api/auth/me` отвечает 200/401, но не различает роль в статус-коде — роль «owner» из JSON nginx без njs/lua не проверит; − циклическая зависимость (доступ к мониторингу зависит от ядра app) |
| Сессии wiki внутри Netdata | − Netdata не знает механизм сессий wiki; − доработка чужого стека |

- **htpasswd-файл** (bcrypt/apr1-хеш логина owner и ОТДЕЛЬНОГО пароля) —
  bind-mount ro в контейнер frontend (`/etc/nginx/netdata.htpasswd`);
  генерация — шаг задачи [ops]/RUNBOOK (`printf "owner:$(openssl passwd
  -apr1)"`), в репозиторий НЕ попадает (`.gitignore`).
- Пароль basic auth — отдельный от пароля wiki-owner (осознанное ограничение:
  смена пароля в wiki не меняет доступ к /netdata/; Заказчику выдается/задается
  при [ops]-задаче; фиксируется в RUNBOOK).
- **Ссылка в сайдбаре — рендер по роли**: `GET /api/auth/me` уже отдает
  `role` (`'Product manager'` = owner-логин, бэкфилл ОВ-21; проверка по
  факту `me.role === 'Product manager'`, до ответа/401 — пункт скрыт, как и
  блок профиля). ВАЖНО: скрытие ссылки — удобство, НЕ защита; граница
  доступа — basic auth на nginx (серверная). PE/анон: пункт не виден,
  прямой заход на `/netdata/` — 401 basic auth.
- Браузер кеширует basic-креды на сессию — повторный ввод не требуется.

## §4. Метрики: что соберет Netdata (покрытие требований Заказчика)

Требование Заказчика: «показатели контейнеров, сервисов и железа (cpu, RAM,
HDD)». Стоковый образ `netdata/netdata` из коробки:

| Показатель | Источник в Netdata | Маунт |
|---|---|---|
| CPU, RAM, диски (HDD), сеть хоста | core-коллекторы (proc/sys) | `/host/proc:/proc:ro`, `/host/sys:/sys:ro` |
| Контейнеры (5 шт. стека): CPU/RAM/сеть/IO каждого, имена | docker/cgroups-коллектор | `/var/run/docker.sock:/var/run/docker.sock:ro` |
| Сервисы = контейнеры стека (app, frontend, search, backup, netdata) | те же cgroups + приложения | — |

- **docker.sock строго :ro** — только чтение метрик (урок R6/PLAN-R7);
  netdata НЕ управляет контейнерами.
- cAdvisor НЕ нужен: docker-коллектор Netdata дает те же cgroups-метрики с
  именами контейнеров (ОВ-1 = легкий стек, без лишней инфры).
- Безопасность скоупа метрик: docker.sock дает видимость всех контейнеров
  хоста — на этом VPS других контейнеров нет (факт RUNBOOK §1), риск принят
  и смягчен basic auth + непубликуемым портом.

## §5. Ресурсы (VPS 3.9 GB)

| Сервис | mem_limit | Было |
|---|---|---|
| app | 512m | 512m |
| frontend | 64m | 64m |
| search | 512m | 512m |
| backup | 64m | 64m |
| **netdata** | **256m** (вводные Заказчика; стоковый образ ~150–300 MB) | — |
| **сумма** | **1.41 GB** | 1.15 GB |
| **резерв хосту** | **≥ 2.4 GB** (требование deploy-спеки ≥ 2 GB выполняется) | ≥ 2.7 GB |

- healthcheck netdata: `wget` по `/api/v1/info` внутри контейнера (curl в
  образе нет; wget в netdata-образе есть) — или curl из frontend к
  `http://netdata:19999` (в nginx-unprivileged wget есть). Решение: wget
  внутри самого контейнера (паритет самодостаточных healthcheck app/search).
- Ротация логов json-file 10m×3 — паритет всех сервисов (NFR-11).
- Замер фактического RAM после подъема стенда — задача 1.1 (урок PLAN-R7);
  стабильное превышение 256m → эскалация Заказчику до прод-выкатки.
- Стенд (`compose.test.yaml`) — тот же сервис netdata (паритет топологии
  NFR-10): docker.sock стенда — тот же хост-сокет (метрики реальные, данные
  БД стенда не затрагиваются).

## §6. Деплой (паритет порядку матрицы)

- Новых миграций и образов ядра НЕТ: пересборка только frontend (nginx-конфиг)
  + новый контейнер netdata (pull готового образа).
- Порядок: бэкап (стандартный шаг deploy.sh) → build frontend → up netdata →
  up frontend (пересоздание с новой локацией) → healthy → смоук-матрица
  (существующая + `/netdata/` чеки: без кредов 401; с кредами 200 и признак
  дашборда; app/search не затронуты).
- Откат: `docker compose up -d` предыдущим тегом frontend + `docker compose
  stop netdata` (пара «код+конфиг», БД не затронута) — по общему правилу
  deploy: «Откат одним действием».
- htpasswd на VPS: создается до пересоздания frontend (шаг [ops]-задачи,
  RUNBOOK §7-подобный раздел) — иначе nginx упадет на `auth_basic_user_file`
  при старте (файл проверяется `nginx -t` до reload).

## §7. Осознанные не-цели

- Grafana/Prometheus/cAdvisor/exporters — ОВ-1 (Netdata, легкий стек).
- Netdata Cloud, алертинг, репликация метрик, long-term storage — не
  запрашивалось; встроенная история Netdata (RAM-bound ring buffer в лимите
  256m) достаточна.
- Метрики бизнес-уровня (задачи/поиск) — не запрашивалось.
- SSO wiki → Netdata — ограничение §2 (basic auth отдельными кредами);
  унификация — потенциальное предложение Заказчику на будущее, не в этом
  пакете.
