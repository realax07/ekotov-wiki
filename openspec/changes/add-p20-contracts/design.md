# Design: add-p20-contracts

Рамки решений — §7a ТЗ (ОВ-1…ОВ-9 закрыты Заказчиком). Инварианты пакета:
ОГР-29 (контракты — снимок фактического поведения, ноль правок кода),
ОГР-30 (сервер-сервер вызовов нет — ограничение, не дефект), ОГР-31
(контракт меняется только вместе с кодом одним PR).

## §1. Формат контрактов и экспорт-скрипты (ОВ-2)

Единица контракта — пара файлов:

- `contracts/openapi-<svc>.json` — источник истины, OpenAPI 3.x JSON,
  стабильный дифф-формат: `json.dumps(sort_keys=True, indent=2,
  ensure_ascii=False) + "\n"` (как search);
- `services/<svc>/openapi.yaml` — навигационный якорь 10–14 строк по
  образцу `services/search/openapi.yaml`: комментарий «источник истины —
  JSON, экспорт scripts/export_openapi_<svc>.py» + точный список путей.

Экспорт — живое приложение, не `app.openapi()` в процессе: middleware
auth регистрируется через http-слой, и контракт должен быть зафиксирован
ровно такой, какой его отдает живой сервис (урок export_openapi_search.py,
дизайн add-microservices-full §3). Механика каждого нового скрипта
`scripts/export_openapi_{video,images,weather}.py` — по образцу
`export_openapi_search.py`, отличия:

| Сервис | App | Env для старта | Auth-контроль |
|---|---|---|---|
| video | `services/video/app/main.py` | tmpdir-том файлов, БД общая структура (метаданные) | вход seed-юзером; `anon /openapi.json` → 401 |
| images | `services/images/app/main.py` | tmpdir-том картинок + БД | тот же паттерн |
| weather | `services/weather/app/main.py` | tmpdir кэш-файла, без БД; провайдер не вызывается (нужен только `/openapi.json`) | тот же паттерн |

Фильтрация путей НЕ нужна (у сервиса своя схема целиком), но контроль
полноты набора — каждый скрипт после записи печатает список путей и
ассертит ожидаемое множество (video: 15, images: 11 + `/api/health`,
weather: `/api/weather` + `/api/health`); расхождение = RuntimeError.
Ветер search: `export_openapi_search.py` не меняется, задача волны 1 —
прогон на HEAD и пустой `git diff` (FR-133); если дифф непуст или формат
расходится с единым (например сортировка/дубль-ключи) — переэкспорт и
приведение в том же PR (условная задача 1.2 tasks.md).

Ядро: `scripts/export_openapi.py` существует; в пакет входит только
проверка «экспорт = файл» (волна 7, негативный тест гейта) — новый
механизм сверки не нужен.

## §2. Единая error-схема через $ref (ОВ-7)

В каждой из 5 спек — `components.schemas.Error`:

```json
{"type": "object", "required": ["error"],
 "properties": {"error": {"type": "string"}}}
```

Все описанные в спеке ответы 4xx/5xx (`{"error": …}` — фактический
стандарт сервисов и ядра, §2 ТЗ) ссылаются на неё через
`{"$ref": "#/components/schemas/Error"}`. Без `additionalProperties: false`
(ОВ-1б: не ломаем гибкость ответов). Схема вписывается в экспортированные
файлы экспорт-скриптом (post-export шаг: аннотирование error-ответов `$ref`-ом
если FastAPI их отдал как `{"error": …}`-схемы) либо — если живая схема уже
несет совместимые схемы ошибок — оставляется как отдана; критерий:
`$ref`/схема Error присутствует в файле, контрактный тест 401-ответа
валидируется по ней (сценарий ОВ-7 спеки). Ручная правка замороженного
JSON вне экспорт-скрипта запрещена (FR-137).

## §3. Схемная валидация сервисных тестов (ОВ-1б, FR-138)

- Зависимость: `jsonschema` (draft-07+) — добавляется в test-deps сервисов
  (requirements тестов/services-образы не меняются: валидация — только в
  тестах, не в рантайме сервисов).
- Helper: `services/<svc>/tests/contract_helpers.py` — читает
  `contracts/openapi-<svc>.json` из корня репо (путь через
  `Path(__file__).resolve().parents[2]/..`), строит `Draft7Validator` с
  резолвером `$ref` на корень замороженного файла; функции
  `validate_response(path, method, status, payload)` — берет схему ответа
  из спеки и валидирует payload; отсутствие маршрута/статуса в спеке =
  ошибка теста (это и есть ловушка дрейфа на уровне тестов).
- Покрытие: минимум happy-path 200 каждого маршрута (где маршрут требует
  тела/файла — минимальный валидный запрос существующими fixtures тестов)
  + типовая ошибка: 401 без сессии и/или 422 на невалидный запрос —
  для каждого сервиса хотя бы один негативный ответ.
- Существующие ассерты множеств путей (TC-openapi-201…210, test_openapi_paths
  и «куски A+D») сохраняются как первый дешевый уровень; добавляются только
  новые схемные проверки (NFR-45: правок существующих ассертов нет).
- Замедление ≤ 20% (NFR-46): замер `time pytest` до/после в задаче 5.5 —
  валидация словаря по схеме — микросекунды на ответ, риск только в
  резолвере `$ref` (строится один раз на модуль).

## §4. Карта «Контракты и зависимости» (FR-139, ОГР-30, Д-17, ОВ-9)

Новый раздел в существующем `architecture/map.md` (не новый файл). Структура
на каждый сервис (search, video, images, weather):

- nginx-маршруты: пары «`= точный` + `^~` префикс-слэш» и порт
  (search 8378, images 8379, video 8380, weather 8381, app 8377);
- потребители: браузерные JS-файлы (`search.js`, галерея, `video.js`,
  inline weather.html); для video — внутренний стык `auth_request` →
  `/_video_auth` → `GET /api/videos/authcheck` (единственный
  сервер-сервер-потребитель — nginx, не код ядра);
- деградации: named-локации `@search_down/@images_down/@videos_down/@weather_down`
  → 503 JSON + `Retry-After: 5`;
- контракт-файл: `contracts/openapi-<svc>.json` + якорь + экспорт-скрипт;
- внешние зависимости: weather → Open-Meteo (таймауты 5с×2, кэш 60м,
  User-Agent из env — по provider.py, без спеки чужого API); games —
  standalone-контейнер, строка-зависимость (ОВ-9).

Плюс правило уровня карты: «ядро (backend/app) не ходит в сервисы по HTTP
(ОГР-30)» — инвариант теста TC-openapi-202, распространяемый на все
сервисы. Ссылки на файлы контрактов в карте — относительные пути
(проверяемые `test -f`, сценарий спеки).

## §5. Механика гейта дрейфа (FR-140, ОВ-5/ОВ-6, ОГР-31)

Гейт = декларативные правила в `scripts/impact_rules.json`, исполняются
СУЩЕСТВУЮЩИМ CI-шагом `pr_validate` (flow.yml шаг «pr_validate», строка
~110: `python3 pr_validate.py . --id …` → `check_impact_rules`). Новый
workflow-шаг НЕ добавляется — правило и есть реализация (ТЗ: «правило в
impact_rules.json + шаг в flow.yml/preflight»: шаг уже исполняет правила
IR-01…IR-07, расширение списка = включение гейта). Стоимость ~0 мс на PR
(NFR-46 ≤30 c). Локальный preflight — тот же `pr_validate.py` вызывается
flow_preflight в точке диспетчеризации (существующее поведение).

Новые правила (номера свободны, IR-01…IR-07 заняты):

| ID | when | content_when | require |
|---|---|---|---|
| IR-08 (video) | `^services/video/app/` | `\+\s*@(router\|app)\.(get\|post\|put\|patch\|delete\|api_route)` | `^contracts/openapi-video\.json$` |
| IR-09 (images) | `^services/images/app/` | тот же | `^contracts/openapi-images\.json$` |
| IR-10 (weather) | `^services/weather/app/` | тот же | `^contracts/openapi-weather\.json$` |
| IR-11 (search) | `^services/search/app/` | тот же | `^contracts/openapi-search\.json$` |
| IR-12 (ядро) | `^backend/app/` | тот же | `^contracts/openapi\.json$` |

`content_when` (штатный механизм схемы, АУД-4/Н25; читается и воротами
по git-патчу, и flow_preflight) точит триггер до «в диффе появилась
строка декоратора маршрута»: правки логики handler'а внутри маршрута без
нового декоратора НЕ триггерят правило — контракт меняется только когда
меняется сам контракт поверхности (путь/метод/статус/схема = тело
`/openapi.json`). Это осознанное сужение: дрейф полей схемы ответа без
изменения декораторов ловит ВТОРОЙ уровень — схемная валидация §3
(сервисные тесты краснеют на PR без правки контракта) — двухслойная
защита: гейт = поверхность, тесты = payloads. Ветка IR-12 исключает
ложные DENY на static_v-бампах (`pages.py`) и миграциях: они не добавляют
декораторов маршрутов.

Правка IR-01 (обязательное сопутствующее изменение): текущий триггер
`^services/[^/]+/openapi` матчит НОВЫЕ yaml-якоря `services/<svc>/openapi.yaml`
→ правка якоря в ОГР-31-PR (код+контракт+якорь) давала бы ложный DENY
(require — `contracts/openapi.json` ядра, которого в диффе нет). Сужение:
`when.path` → `^services/[^/]+/openapi\.json$` (машиночитаемая спека у
сервиса — таких файлов нет, правило консервируется как guard на будущее).
IR-07 (`^contracts/` → require `contracts/openapi.json`) сохраняется:
правка чужого контракта-файла по-прежнему требует ядерный переген.

Негативный тест гейта (задача 7.3): фиктивный коммит-дифф «новый маршрут в
services/video/app без контракта» → `PR_CHANGED_FILES`/`PR_BODY`-конвенция
локального прогона `pr_validate.py` → ожидаемый DENY-текст с id IR-08 и
hint «перегенерируй контракт»; позитив: тот же дифф + строка в
`contracts/openapi-video.json` → green. Тест кладется рядом с существующими
прогонами ворот (tests/ репо-конвейера), маркер TC-FLOW-NNN по правилу 6.

## §6. nginx-тест (FR-141, ОВ-8)

`tests/api/test_nginx_routes_contract.py`: парсинг
`services/frontend/nginx/ekotov-wiki.conf` регэкспом по строкам
`location`-директив; ассерт: ровно ожидаемые семейства для каждого
сервиса — search: `= /api/search` + `^~ /api/search/` + `= /api/suggestions`
+ `^~ /api/suggestions/`; images: `= /api/images` + `^~ /api/images/`;
video: `= /api/videos` + `^~ /api/videos/` (+ внутренние `/_video_auth`,
`/videos/`, `@videos_down` — по спеке требований, точный список в тесте);
weather: `= /api/weather` + `^~ /api/weather/`; named-локации деградаций
присутствуют. Правка маршрутизации без одновременной правки теста/спеки/карты
= красный тест. Прокси-цели (порты/имена контейнеров) ассертятся по
`proxy_pass`-переменным тех же локаций.

## §7. Порядок волн (ОВ-4: Д-16 с заменой)

search → video → images → weather → (схемная валидация, карта+nginx-тест)
→ гейт последней волной (ТЗ §10.3: гейт включается, когда все 4 контракта
заморожены и зеленые). Распределение по tasks.md: волны 1–4 — контракты
(S каждая), волна 5 — схемная валидация (M), волна 6 — карта + nginx-тест
(S+S), волна 7 — гейт (M). Итого S×6 + M×2 — сходится с §9 ТЗ.

## Impact

- **Сервисы**: behavior-neutral; код сервисов и ядра НЕ меняется
  (ОГР-29); правятся только тесты services/*/tests (добавление проверок).
- **Контракты**: `contracts/openapi-{search,video,images,weather}.json` +
  `contracts/openapi.json` (ядро — без изменений контента, входит в гейт);
  yaml-якоря services/{video,images,weather}/openapi.yaml — новые.
- **Статика (static_v)**: НЕ бампится — frontend/templates/static не
  трогаются (IR-03 не срабатывает).
- **deploy-матрица + RUNBOOK**: не меняются (новых сервисов/образов нет;
  IR-02 не срабатывает).
- **Миграции**: нет.
- **Ворота**: `scripts/impact_rules.json` — новые IR-08…IR-12 + сужение
  IR-01; сам код ворот (`pr_validate.py`) НЕ меняется.
- **CI**: `.github/workflows/flow.yml` НЕ меняется (правила исполняются
  существующим шагом pr_validate); тесты: новый
  `tests/api/test_nginx_routes_contract.py`, тест гейта, обновления
  services/*/tests.
- **Тесты**: существующие сьюты остаются зелеными без правок ассертов
  (NFR-45); замедление ≤20% (NFR-46), гейт ≤30 c.
