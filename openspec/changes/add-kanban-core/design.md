# Design: add-kanban-core

Технические решения change-пакета. Детали кода — не здесь (см. sdd.md для контрактов и модели данных; tasks.md — для шагов реализации).

## 1. Общий подход

Тонкий серверный слой (API + раздача статики веб-морды) перед nginx, SQLite как единственное хранилище, серверные сессии в куках. Приложение — один процесс; состояния в памяти минимумы (только сессии и Prepared statements). Достигается легковесность (ОГР-1): нет брокеров, кэшей, ORM-магии — типовой стек «nginx → app → SQLite» покрывает NFR-1/NFR-2 с запасом (2 пользователя, 1 000 задач).

## 2. Сессии и куки (FR-14, NFR-7)

- **Механика:** сессия = случайный токен (криптостойкий, ≥128 бит энтропии), выдаваемый сервером после успешного логина. Токен кладется в куку `HttpOnly` + `SameSite=Lax` (+ `Secure` — NFR-6, доступ по HTTPS). Сервер хранит соответствие «токен → пользователь, время выдачи, TTL». Каждая страница и каждый API-запрос проходит middleware-проверку: есть валидная сессия — пропустить; нет — редирект на /login (страницы) или 401 (API).
- **TTL и продление:** срок жизни сессии — скользящий (например, 30 дней бездействия); продление — обновлением TTL при каждом запросе. Истечение = удаление записи сессии, кука становится невалидной.
- **Хранение сессий:** в таблице БД (или в памяти с записью в БД) — чтобы штатный рестарт не ломал входы пользователей сильнее необходимости; NFR-3 гарантирует только данные, сессии могут инвалидируются при рестарте (зафиксировано в спеке tasks как допустимое).
- **Logout:** явное действие пользователя удаляет серверную запись сессии и куку.
- **Почему так:** без фреймворковых «магических» сессий — явный механизм легко проверить на безопасность и протестировать; соответствует «сильно не заморачиваемся пока» и при этом закрывает NFR-7 (защита кук: HttpOnly против XSS-кражи, SameSite против CSRF-базового, Secure против перехвата в сети).

## 3. Пароли (NFR-7)

Хранится только хеш с солью по адаптивному алгоритму (bcrypt/argon2 — что даст выбранный фреймворк из коробки). Проверка пароля — константное время. Заведение 2 пользователей — seed-скриптом при развертывании, пароли не попадают в репозиторий (вводятся интерактивно или из env).

## 4. Правило fast line ≤1 (FR-3, ОГР-5)

- **Инвариант:** в статусах «Ожидает» и «В работе» одновременно не более одной задачи с признаком fast.
- **Место проверки:** сервер, при создании задачи с флагом fast (и при любых попытках перевода в fast). Проверка = запрос количества fast-задач в активных статусах; если ≥1 — отказ.
- **Гонки:** SQLite с однойWriter-моделью + транзакция «проверка + вставка» атомарна; при 2 пользователях вероятность гонки пренебрежима, но транзакция делает поведение детерминированным. Отказ = HTTP 409 с человекочитаемой причиной.
- **Освобождение:** как только fast-задача уходит в «Выполнено» (и в архив), инвариант выполняется автоматически — отдельного «освобождения» не нужно. Проверка снова пропускает новую fast-задачу.
- **Порядок на линии:** внутри fast line задача отображается выделенно; сортировка по приоритету (признак задачи) — ОГР-5 «порядок прохождения — по приоритету».

## 5. Архив (FR-4, новая редакция Заказчика: архивация через день, календарно по МСК)

Задача при переводе в «Выполнено» НЕ архивируется мгновенно: move ставит `done_at` (момент перевода) и оставляет задачу на доске в столбце «Выполнено» до конца текущего календарного дня по МСК (UTC+3).

- **Ленивая автоархивация (без фонового процесса):** при каждом `GET /api/board` перед формированием ответа выполняется один UPDATE:
  `UPDATE tasks SET archived_at = <now> WHERE status = 'done' AND archived_at IS NULL AND done_at < <начало текущего календарного дня МСК>`.
  Задачи, выполненные вчера по МСК или ранее, получают `archived_at` и исчезают с доски. Для 2 пользователей фоновый планировщик (cron/daemon) избыточен — доска читается часто, задержка архивации до первого чтения после полуночи МСК неотличима от требуемой календарной границы (FR-4).
- **Почему done_at, а не сравнение по updated_at:** граница считается относительно момента перевода в done, а не последнего редактирования задачи; обратный move из done снимает `done_at` (и `archived_at` на случай ручного возврата), инвариант модели — sdd.md §4.
- **Часовой пояс:** «начало текущего дня» вычисляется в фиксированном UTC+3 (МСК) независимо от локального TZ сервера/контейнера (зафиксировано в sdd.md §3.3/§5).
- **Дальнейшая судьба задачи не меняется:** архив не удаляется, доска фильтрует только не-архивные; поиск видит все (с различимым признаком архивности, FR-10). Удаление задачи (FR-7) — единственный путь полного исчезновения данных.

## 6. Поиск (FR-10…FR-12)

- **Фильтр-конструктор (mode: builder):** пользователь выбирает значения признаков (приоритет, категория, тег, срок, архивность). Каждый выбранный признак = условие; условия объединяются по И. Пустой конструктор = без условий = все задачи.
- **Режим advanced (FR-12):** конструктор сериализует свои условия в SQL-подобный текст (например, `priority = "high" AND tag IN ("home", "car")`). Пользователь правит текст; парсер переводит его обратно во внутренний фильтр.
- **Конструктор фильтра → SQL-подобный фильтр:** внутреннее представление фильтра — список предикатов над полями задачи. Конструктор build() генерирует текст; парсер parse() строит список предикатов из текста; исполнитель превращает предикаты в параметризованный SQL WHERE над SQLite (тэги — через связующую таблицу). Параметризация обязательна — пользовательский текст фильтра не конкатенируется в SQL напрямую (защита от инъекций, NFR-7).
- **Ошибки фильтра:** синтаксическая ошибка в advanced = человекочитаемое сообщение, без выполнения запроса (негативный сценарий спеки search).

## 7. API-слой (ОГР-2, FR-8, NFR-7)

REST JSON под префиксом `/api/*`. Каждый запрос (кроме `POST /api/auth/login`) проходит авторизационную проверку сессии — иначе 401. Полные контракты (метод/путь/схема/коды) — в `sdd.md`. Веб-морда — клиентом этого же API (ОГР-2: веб не «прибит» к БД).

## 8. Развертывание (NFR-6, ОГР-1)

VPS: nginx как reverse-proxy и терминатор TLS (сертификат Let's Encrypt), проксирующий на application-сервер (uvicorn/gunicorn или встроенный сервер фреймворка). Процесс приложения — systemd-юнит. Файл БД — вне репозитория (NFR-5, `.gitignore` `*.db`, `*.sqlite*`), путь задается конфигурацией развертывания.
