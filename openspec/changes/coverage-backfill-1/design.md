# design.md — coverage-backfill-1

## §0. Подход

Автотесты пишутся по дословным шагам утвержденных кейсов
(`test-model/approved/…`), без пересмотра диспозиций. Прецеденты: web/e2e —
Playwright-сьют `tests/web/` (фикстуры conftest, маркер TC-ID в docstring —
как `tests/web/test_board_fastline.py` для p23-101…108); api/services —
pytest `tests/api/` и `services/*/tests/` (паритет
`services/weather/tests/test_weather_service.py`).

## §1. Ключевые решения

1. **Один кейс = один чек-бокс = один тест-файл** (имя
   `test_<домен>_backfill[_NN].py` с функциями по сценариям кейса) —
   чек-бокс tasks.md прямо трассируется в файл; ревью и прогон
   атомарны по кейсу.
2. **Маркер TC-ID обязателен в docstring** — единственный механизм
   трассировки qa-инвентаризации (маркер = покрытие); без маркера кейс
   числится разрывом.
3. **Стенд** — существующий механизм `scripts/qa_stand_up.sh` / RUNBOOK
   (изолированный venv, tmp-БД, свой порт); новых инфра-механизмов нет.
4. **Прод-код заморожен**: если кейс невоспроизводим из-за дефекта
   продукта — баг-репорт `test-model/bugs/` и чек-бокс закрывается с
   ссылкой на баг (тест пишется после фикса отдельным change).
5. **Should-решение**: кейсы Should, неправматоматизируемые по классификации
   (TC-p23-116 визуальный ОВ-4), получают документированное Should-решение
   в coverage-отчете F.2 (прецедент qa-cleanup-1026) вместо теста.

## §2. Критерии приема

- Все новые тесты green на чистом стенде (F.1); flake-квалификация —
  прецедент Д2 (solo-rerun).
- grep маркеров всех 85 TC-ID по `tests/` + `services/*/tests/` находит
  каждый (или Should-решение в отчете F.2).
- `openspec validate --changes --strict` + `scripts/flow_check.py` — green.
- Диф коммита — только `tests/**`, `services/*/tests/**`,
  `test-model/reports/coverage-backfill-1/**`, `openspec/changes/
  coverage-backfill-1/**`.

## §3. Альтернативы

Инкремент тривиален, альтернативы не рассматривались: добивка покрытия
существующими механизмами (сьюты/фикстуры/стенд) без новых решений.
