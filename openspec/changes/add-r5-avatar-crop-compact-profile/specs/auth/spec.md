# Delta: auth — загрузка аватара (вариант А: фронт-кроп + серверная нормализация)

## MODIFIED Requirements

### Requirement: Загрузка аватара

Пользователь MUST иметь возможность загрузить файл аватара в своем профиле (FR-42). Принимаются ТОЛЬКО файлы png/jpg: файл иного типа MUST отклоняться с понятной ошибкой, аватар не изменяется (FR-42, NFR-12). Исходный файл размером более 2 МБ MUST отклоняться с понятной ошибкой «файл слишком большой» — не молча и не падением (NFR-10, NFR-12, ОВ-22). Контракт загрузки MUST сохраняться: `POST /api/profile/avatar` (multipart/form-data, поле `file`) — путь, поле, коды ошибок и тела ответов без изменений (ОВ-СА-3); параметров кропа в контракте нет (ОВ-СА-1: принят вариант А — фронт-кроп, FR-54).

**Изменение (r5, вариант А):** при доступности кроп-виджета на сервер передается только итоговый обрезанный квадрат 256×256, сформированный клиентом (canvas), — исходник остается в браузере: трафик загрузки НЕ зависит от размера исходника (NFR-11, FR-54). Сервер MUST НЕ доверять клиенту: содержимое запроса в любом случае проходит полную серверную проверку (тип png/jpg по декларации И по декодированию, размер ≤2 МБ до декодирования) и MUST безусловно приводиться сервером к квадрату 256×256 PNG (Д-8, Д-13) — даже если присланный файл не квадратный. Итоговое хранимое изображение всегда 256×256 PNG независимо от честности клиента.

**Fallback (NFR-14):** при недоступности canvas/JS (старый браузер, отключен JS) загрузка аватара остается работоспособной как в Релизе 4 — простая отправка исходного файла, сервер выполняет автосжатие center-crop до квадрата 256×256; ошибки клиентского виджета MUST NOT нарушать работоспособность страницы профиля.

Хранение и отдача аватара — статика с кеш-бастингом `?v=<avatar_updated_at>` (ОГР-16, ОГР-23); существующие аватары, сохраненные до этого изменения, MUST NOT перекраиваться и мигрировать — серверная нормализация применяется только к новым загрузкам (ОГР-21). Эндпоинт загрузки MUST требовать действующую сессию; аватар загружается только свой. При отсутствии аватара отображается кружок с первой буквой логина (fallback, FR-33/FR-42).

#### Scenario: Вариант А — на сервер уходит только итоговый квадрат

- **GIVEN** пользователь авторизован, у браузера есть canvas/JS (кроп-виджет доступен)
- **WHEN** пользователь загружает png/jpg ≤2 МБ, выбирает область в кроп-виджете и подтверждает («Применить»)
- **THEN** на сервер отправляется один запрос `POST /api/profile/avatar` с итоговым квадратом 256×256 (исходный файл на сервер не передается: размер тела запроса не зависит от размера исходника — NFR-11); аватар заменен выбранной областью (FR-52)

#### Scenario: Серверная нормализация не доверяет клиенту

- **GIVEN** пользователь авторизован
- **WHEN** на `POST /api/profile/avatar` приходит валидный png, геометрия которого НЕ квадрат 256×256 (например, 512×300 — подмененный или устаревший клиент)
- **THEN** сервер сохраняет изображение, приведенное к ровно 256×256 PNG (безусловная серверная нормализация, Д-8/Д-13); ответ 200, аватар отображается корректно (ОВ-СА-2)

#### Scenario: Серверная валидация пришедшего содержимого сохранена

- **GIVEN** пользователь авторизован
- **WHEN** на `POST /api/profile/avatar` приходит файл неподдерживаемого содержимого (не png/jpg по декодированию) или размером более 2 МБ
- **THEN** загрузка отклоняется (422 «invalid file type» / 422 «file too large» соответственно) с теми же телами ответов, что в Релизе 4; аватар не изменяется (NFR-12, ОВ-СА-3)

#### Scenario: Контракт загрузки не расширялся

- **GIVEN** пользователь авторизован
- **WHEN** аватар загружается корректным multipart-запросом с полем `file` (png/jpg ≤2 МБ)
- **THEN** запрос обрабатывается успешно без дополнительных полей/параметров кропа; ответ 200 содержит `avatar_url`, версия `?v=` в URL изменилась (ОВ-СА-3, ОГР-23)

#### Scenario: Fallback без canvas — загрузка как в Релизе 4

- **GIVEN** пользователь авторизован, окружение без canvas/JS (кроп-виджет недоступен, NFR-14)
- **WHEN** пользователь загружает png/jpg ≤2 МБ простым выбором файла
- **THEN** загрузка выполняется успешно: сервер сам приводит изображение к квадрату 256×256 (center-crop, как в Релизе 4); страница профиля функциональна, ошибок JS нет (СЦ-11)

#### Scenario: Успешная загрузка png
- **GIVEN** пользователь авторизован и находится в форме профиля
- **WHEN** пользователь загружает файл формата png размером не более 2 МБ
- **THEN** загрузка выполняется успешно; аватар отображается в блоке профиля внизу сайдбара и в tooltip'е профиля вместо кружка с буквой (FR-42, FR-43)

#### Scenario: Негативный: исходник больше 2 МБ
- **GIVEN** пользователь авторизован
- **WHEN** пользователь выбирает корректный png/jpg размером более 2 МБ
- **THEN** файл отклоняется с понятной ошибкой «файл слишком большой» ДО отправки на сервер (клиентская проверка теми же правилами) и/или на сервере (NFR-10, NFR-12); аватар не изменяется

#### Scenario: Негативный: тип файла не png/jpg
- **GIVEN** пользователь авторизован, у него установлен действующий аватар
- **WHEN** пользователь загружает файл иного типа (например, gif или bmp)
- **THEN** загрузка отклоняется с понятной ошибкой о недопустимом типе файла; ранее установленный аватар не изменяется (FR-42, NFR-12)

#### Scenario: Backward-compat существующих аватаров
- **GIVEN** у пользователя есть аватар, сохраненный до этого изменения (center-crop Релиза 4)
- **WHEN** пользователь открывает профиль, не загружая новый файл
- **THEN** аватар отображается как был (не перекроен); серверный файл не изменяется (ОГР-21, СЦ-13)

#### Scenario: Негативный: без сессии — 401
- **GIVEN** вызывающий не имеет действующей сессии
- **WHEN** вызывающий отправляет файл аватара на эндпоинт загрузки
- **THEN** API отвечает 401 `{"error": "unauthorized"}`; файл не сохраняется (NFR-7)
