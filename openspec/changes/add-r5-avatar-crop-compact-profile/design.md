# Design: add-r5-avatar-crop-compact-profile

Технические решения пакета «Аватар 2.0». Наблюдаемое поведение — в дельтах `specs/`; здесь — как оно достигается. Стек не меняется (sdd.md §1: FastAPI + SQLite + Jinja2/ванильный JS + nginx). **Новых зависимостей нет** (ОГР-1): backend — Pillow/python-multipart уже стоят с Р4 (пины в `backend/requirements.txt`); фронт — ванильный JS/Canvas 2D. Схема БД не меняется; API-контракты не меняются (ОВ-СА-3). Клиентские вычисления (геометрия кропа, мин-макс зума) — внутренние, в спеку не входят.

## 0. Резюме решений по ОВ-СА (полные обоснования — research.md)

| ОВ | Решение |
|---|---|
| ОВ-СА-1 | **Вариант А — фронт-кроп** (canvas → готовый квадрат на существующий `POST /api/profile/avatar`). Решающие критерии: NFR-11 исполняется автоматически (payload ~10–150 КБ, не зависит от исходника); вводная Заказчика «чисто логика фронта» соблюдена дословно (ОГР-24); кроп-виджет обязателен в обоих вариантах — Б добавляет серверную геометрию + расширение API + валидацию координат без выгоды пользователю. Слабости А (тестируемость, EXIF) закрыты: серверная нормализация детерминирована и тестируется (ОВ-СА-2), EXIF-поворот применяется браузером при декодировании в `<img>` (spec-поведение вечнозеленых браузеров), неспособные клиенты уходят в fallback NFR-14 |
| ОВ-СА-2 | (А-ветка) Сервер **не доверяет клиенту**: действующий конвейер Р4 сохраняется целиком — декларация png/jpg → размер ≤2 МБ до декодирования → Pillow-декодирование (формат PNG/JPEG по содержимому) → **безусловный resize 256×256 LANCZOS + сохранение PNG** (`avatar.py` меняется минимально: center-crop заменяется на «приведи к 256×256 как есть», см. §2) |
| ОВ-СА-3 | Контракт `POST /api/profile/avatar` — **как есть**: multipart `file`, png/jpg ≤2 МБ; 200/422-тела/401 — без изменений; `avatar_updated_at` и `?v=` не трогаются (ОГР-23). ТС-ava-001…007 остаются зелеными |
| ОВ-СА-4 | Зум: **min = cover** (min сторона изображения ≥ диаметр маски; «дыр» нет — FR-50), **max = ×3 от cover**; исходник меньше маски — **принудительный апскейл до cover** + предупреждение о возможной потере четкости (не блокируем: СЦ-10 отклоняет только тип/размер) |
| ОВ-СА-5 | Тач: **touch-drag + pinch-to-zoom**, слайдер зума работает на таче обязательно (NFR-13). Клавиатура (NFR-15): слайдер — нативный фокусируемый input (стрелки); контейнер виджета tabindex=0 — стрелки двигают фото (шаг = 5% видимой области), `+`/`-` — зум шагом 10%; aria-label «Выбор области аватара», слайдер отдает aria-valuenow (%) |
| ОВ-СА-6 | Смена пароля — внутри единой карточки ниже профиля; подтверждение **только кнопкой «Сменить пароль»** (не по blur); механика Р4 (`POST /api/profile/password`, Д-11) сохранена. Визуальная иерархия секций — на живой макет J25 (ОГР-25) |

Дефолты Д-12 (виджет открывается сразу после выбора файла в той же карточке; «Применить» завершает и кроп, и загрузку) и Д-13 (итог — 256×256 PNG) приняты и отражены ниже.

## 1. Кроп-виджет: модуль и геометрия (FR-49…FR-53, NFR-11/13/15, Д-12/Д-13)

- Новый фронт-модуль `frontend/static/js/avatar-crop.js` + стили в `frontend/static/css/profile-settings.css` (токены V3 из app.css; новых файлов темы нет — ОГР-25). Ноль фронт-зависимостей.
- Модель состояния: загруженное изображение (FileReader → `HTMLImageElement`; браузер применяет EXIF-ориентацию при декодировании — виджет работает с уже повернутым изображением), масштаб `s ∈ [s_min, s_max]`, смещение `(dx, dy)`. Ограничение «дыр нет»: `dx, dy` клэмпятся так, что изображение всегда покрывает квадрат маски (инвариант FR-50 — проверяется в задачах dev и QA).
- Рендер: `<canvas>` внутри круглой маски (CSS `border-radius: 50%` + overflow) — drag (Pointer Events: mouse/touch/pen единообразно), зум колесом (`wheel`, passive:false только внутри виджета — скролл страницы вне виджета не ломается, СЦ-9), слайдер `<input type="range">`, pinch (расстояние между двумя touch-точками → масштаб). Live-предпросмотр (FR-51) — сама маска и есть превью: то, что видно в кружке, попиксельно равно итогу (рендерится тем же кодом, что финальный кадр).
- «Применить» (FR-52, Д-12): offscreen canvas 256×256 → `drawImage` выбранной области → `canvas.toBlob('image/png')` → `FormData` → существующий `POST /api/profile/avatar`. После 200 — обновление `avatar_url` из ответа (`?v=` изменился сервером — ОГР-23), кружок сайдбара/tooltip/profile-refresh как в Р4.
- «Отмена»/закрытие/уход со страницы (FR-53): сброс state виджета, file input очищается, **никаких запросов на сервер**; прежний аватар не затронут (`?v=` не меняется — проверка в QA, СЦ-5).
- Пределы зума (ОВ-СА-4): `s_min` = сторона изображения = диаметр маски (cover); `s_max` = 3 × cover. Изображение меньше маски: `s_min > 1` (апскейл до cover) + подпись «исходник маленький — итог может быть нечетким».
- Fallback (NFR-14, Should): отсутствие `HTMLCanvasElement`/`FileReader`/Pointer Events → виджет не инициализируется, file input работает по-Р4 (простая отправка исходника, сервер сам center-crop); ошибки JS в модуле ловятся try/catch на init — страница профиля остается функциональной (СЦ-11).
- Доступность (NFR-15): контейнер `tabindex="0"` + `role="group"` + `aria-label="Выбор области аватара"`; стрелки двигают фото, `+`/`-` зумируют; слайдер — стандартный фокусируемый input (стрелки нативно), `aria-valuenow` = % зума; `prefers-reduced-motion` (ОГР-17 Р4) — трансформации без transition (мгновенная перерисовка).

## 2. Backend: минимальная правка `avatar.py` (ОВ-СА-2/3, NFR-12/14, Д-13)

- Контракт не меняется (research §3): `multipart/form-data`, поле `file`, 200 `{"ok": true, "avatar_url": ...}` / 422 `invalid file type` / 422 `file too large` / 401.
- Меняется ОДНА операция: вместо `center_crop_square` — безусловное приведение декодированного изображения к 256×256 LANCZOS (`img.resize((256, 256))`) **независимо от входной геометрии**: честный клиент присылает готовый квадрат 256×256 (resize — no-op по качеству), злонамеренный/старый клиент — что угодно (все равно получит 256×256 PNG). Проверки до декодирования (декларация png/jpg, ≤2 МБ) и Pillow-декодирование как проверка содержимого — без изменений (недоверие клиенту, NFR-12).
- Хранение/отдача: `/var/lib/ekotov-wiki/avatars/<user_id>.png`, атомарная запись, `avatar_updated_at`, nginx `location /avatars/`, `?v=` — все как в Р4 (ОГР-16/23). Миграций и правок nginx нет.

## 3. Единая карточка профиля V3 (FR-55, FR-56, ОВ-СА-6, ОГР-25)

- Переверстка существующей страницы `GET /settings/profile` (маршрут, редирект без сессии, шаблон/JS/CSS — те же файлы Р4, правятся на месте; ОГР-23: не новая сущность).
- Структура: ОДНА карточка (`--color-bg-surface`, `--radius-card`, `--shadow-soft`) с секциями внутри — единые отступы (`--space-*`, 8px-сетка), типографика, рамки, состояния фокуса (`--focus-ring`) и ошибок (`--status-error*`) по мокапу `design/form-style-v3.html`:
  1. Аватар: текущий кружок + кнопка выбора файла → кроп-виджет (§1) прямо в карточке (Д-12);
  2. Имя/роль/bio: display_name (текст), роль (select, ровно 2 значения — ОВ-21), bio (textarea);
  3. Смена пароля: текущий + новый, кнопка «Сменить пароль» (ОВ-СА-6: подтверждение только кнопкой, не по blur; механика Р4/Д-11 без изменений).
- Состав полей Р4 не меняется (FR-40/41/42 — bio, роль, пароль сохранены, функций не потеряли); три независимые операции сохранения остаются (профиль / пароль / аватар), но теперь визуально в одном блоке с подзаголовками секций.
- Адаптив (FR-56): ≤ ~768px — одна колонка, без горизонтальной прокрутки; кроп-виджет полнофункционален на таче (§1). Двухколоночная раскладка — только как опция широкого экрана на живом макете J25.
- Общий раздел «Настройки» (`/settings`, справочник категорий) не затрагивается (ОГР-20/ОГР-23).

## 4. Живой макет J25 (ОГР-25)

- Артефакт пакета: `design/avatar-crop-v3.html` — самодостаточная страница (токены V3 inline, как в `form-style-v3.html`): единая карточка (аватар-зона + кроп-виджет с маской/слайдером + поля + смена пароля) в двух состояниях (desktop / ≤768px) и состояниях (фокус, ошибка, превью). | НФТ | Решение |

## 7. Риски

- **EXIF-поворот на клиенте**: браузеры применяют ориентацию при декодировании `<img>` (спека image-direction), но фиксируется web-тестом на «портретном» jpg с телефона (главный кейс пользователей); регрессия — изображение в виджете повернуто → fallback-ветка не нужна, чинится `createImageBitmap(..., {imageOrientation: 'from-image'})` в задаче 2.1 (деталь реализации, контракт не меняет).
- **Попиксельность превью vs итога (СЦ-3)**: превью и финальный кадр рендерятся одной функцией с одинаковыми s/dx/dy — расхождение возможно только на субпиксельном сглаживании; допускается проверка «визуально идентично» + попиксельная сверка в web-тесте с допуском на антиалиасинг.
- **Старые браузеры без Pointer Events**: NFR-14 fallback покрывает (простая загрузка); Pointer Events поддерживаются всеми целевыми вечнозелеными браузерами.
- **Потеря качества апскейла мелких исходников**: предупреждение в UI (ОВ-СА-4); не блокируем.
- **Регресс Р4-тестов аватара (ТС-ava-001…007)**: контракт не меняется; единственное поведенческое отличие — сервер теперь приводит к 256×256 без center-crop; для ТС-ava-005 (сжатие) результат эквивалентен (256×256), что подтверждается прогоном регресса в задаче 4.3.
