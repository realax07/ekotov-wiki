# Design: add-rich-editor

> Статус: r1 (СА, 2026-10-16). Источник: requirements.md (УТВЕРЖДЕН Заказчиком;
> ОВ-1..4 решены). Директива Заказчика (обязательная): пакет L обязан быть
> ДЕКОМПОЗИРОВАН — большие модули на меньшие логические; НЕ один `editor.js`
> на фронте, sanitize rich-контента — отдельным backend-модулем, не дописка
> в существующий `sanitize.py` одним куском. Директива выполнена — §2, §3.

## 0. Контекст

Сейчас: страница wiki хранит HTML из contenteditable-редактора (vanilla JS,
ОГР-8) в `pages.content`/`page_versions.content`; санитизация — серверный
whitelist `backend/app/sanitize.py`; рендер — вставка просанитизированного
HTML на страницу статьи. Существующие страницы — plain text + HTML тулбара
FR-110/FR-111.

## 1. D1 — модель хранения: блочный markdown-диалект (гибрид с legacy-HTML)

**Решение:** блочный markdown-диалект (рекомендация ПМ принята), гибридно:
одна колонка `content` хранит смесь legacy-контента (существующий HTML из
редактора) и блоков диалекта; рендер/парсинг диспатчится по блокам.

Синтаксис диалекта:

- GFM-таблицы (`| a | b |` + разделитель `|---|`) — FR-117;
- `:::columns` … `:::` с разделителями колонок `<<<` — FR-118;
- `:::callout type=info|warn|success` … `:::` — FR-119;
- `:::aside` … `:::` — врезка (FR-120);
- `:::spoiler title="…"` … `:::` — FR-121;
- fenced code ` ```lang ` — код с подсветкой (FR-122);
- `![alt](/images/{id}){width=N}` — масштаб изображения в процентах
  доступной ширины (FR-123; атрибут `width` — единственное расширение,
  NFR-34/лимиты не меняются).

Внутри блоков инлайн-контент — текст + инлайн-markdown (`**b**`, `*i*`,
`` `code` ``, `[link](url)`); **сырой HTML внутри блоков диалекта не
поддерживается** (хранится и отображается как текст).

**Обоснование против альтернативы (расширенный HTML-белый список):**

1. **Sanitize.** Диалект структурно безопасен: парсер знает конечный набор
   конструкций, рендер строит DOM через `createElement`/`textContent` —
   пользовательский контент никогда не интерпретируется как HTML. HTML-путь
   требует расширения whitelist на каждый новый тип блока и каждый атрибут —
   именно там livedы XSS (прецедент BUG-AF-RECHECK-004).
2. **Обратная совместимость (FR-125/NFR-36).** Старый контент не содержит
   конструкций диалекта на позиции блока (`:::` в начале строки, GFM-шапка
   таблицы, fenced code) → парсер пропускает его через существующий legacy-путь
   (`sanitize.py` + текущий рендер) без единой правки. Миграция данных
   не нужна (Won't по requirements).
3. **Диффы читаемы:** версии/история (FR-112/FR-113) диффают текст — блочная
   разметка читаема в отличие от HTML с классами.
4. **Без миграций БД:** колонка `content` не меняет тип; таблицы `pages`,
   `page_versions` не трогаются.

Риск диалекта (частичный HTML + markdown в одном поле) закрывается
диспетчеризацией: строка вне блока диалекта — legacy-HTML-путь как сегодня;
строка внутри блока — только текст.

## 2. D2 — декомпозиция фронтенда (директива Заказчика)

Новые модули в `frontend/static/js/wiki/rich/` (vanilla ES-модули, ОГР-8,
без CDN/сборщиков); существующий `editor.js` НЕ раздувается — только тонкая
интеграция (§4):

| Модуль | Ответственность |
|---|---|
| `rich/block-parser.js` | парсер диалекта: текст → дерево блоков (и обратно — сериализатор) |
| `rich/renderer.js` | дерево блоков → DOM (createElement/textContent, без innerHTML для пользовательского контента) |
| `rich/toolbar.js` | расширение тулбара: кнопки вставки/правки блоков, состояния |
| `rich/blocks/tables.js` | FR-117: вставка/правка таблиц, GFM-сериализация |
| `rich/blocks/columns.js` | FR-118: колонки, `<<<`-разделители, вложенность (FR-127) |
| `rich/blocks/callout.js` | FR-119: типы info/warn/success, смена типа |
| `rich/blocks/aside.js` | FR-120: врезка — выделенное оформление, отличный от callout вид |
| `rich/blocks/spoiler.js` | FR-121: заголовок, раскрытие без перезагрузки |
| `rich/blocks/code.js` | FR-122: код-блок, choice языка, переносы/пробелы буквально |
| `rich/blocks/image-scale.js` | FR-123: контрол масштаба, `{width=N}` атрибут |
| `rich/highlight.js` | подсветка синтаксиса кода — собственный токенайзер (vanilla, ОГР-8; без внешних библиотек) |

Каждый block-модуль — единый контракт: `parse(node)`, `serialize(node)`,
`render(node)`, `toolbar(schema)` — регистрируется в реестре `block-parser.js`.
Новый тип блока = новый модуль + регистрация, без правки ядра.

## 3. D3 — декомпозиция бэкенда (директива Заказчика)

Rich-sanitize — **отдельный модуль**, `backend/app/sanitize.py` не
переписывается и не дополняется «одним куском»:

| Модуль | Ответственность |
|---|---|
| `backend/app/rich_blocks.py` | серверный парсер/валидатор/сериализатор диалекта (зеркалирует фронтовый grammar): 422 при структурной ошибке, нормализация |
| `backend/app/sanitize_rich.py` | санитизация rich-контента: фильтр URL-схем (`javascript:`/`data:` — вырезать), whitelist атрибутов диалекта (`width`, `title`, `type`), нейтрализация HTML-векторов в тексте блоков; переиспользует helpers `sanitize.py` через импорт (без правки самого `sanitize.py`) |
| `backend/app/wiki.py` | ТОЛЬКО тонкий шов: на сохранении вызов `rich_blocks.validate()` + `sanitize_rich.sanitize()`; логика — в новых модулях |

## 4. D4 — интеграция в редактор (единственная задача с зоной editor.js)

`editor.js`: при сохранении — сериализация rich-блоков в диалект; при
загрузке — блоки диалекта → интерактивное редактирование через модули §2;
legacy-HTML — существующее поведение без изменений (FR-125). WYSIWYG:
модули рендерят блок в редакторе тем же `renderer.js`, что и на просмотре
(FR-124 по построению).

## 5. D5 — разбиение: один пакет, две волны dev

Один change-пакет (не два): ядро диалекта (parser/serializer/санитизация)
неделимо — два пакета означали бы два независимых ядра и двойной sanitize-
риск. Волны внутри пакета (tasks.md):

- **Волна 1 — ядро + таблицы + колонки:** rich_blocks.py, sanitize_rich.py,
  block-parser/renderer/toolbar ядро, blocks/tables, blocks/columns,
  регресс-тест совместимости (эталон до волны 2).
- **Волна 2 — callout + графика + image-scale:** blocks/callout, spoiler,
  code, highlight, image-scale, вложенность (FR-127), perf-чек (NFR-37).

Разрез волн выбран по независимости блок-модулей от ядра (контракт §2):
волна 2 не правит файлы волны 1.

## 6. Деградация и безопасность

- Отказ JS-модулей рендера: страница отобразит сырой диалект как текст
  (безопасно — это текст), legacy-страницы не затронуты.
- XSS-defense-in-depth: (1) серверная `sanitize_rich.py` на сохранении,
  (2) DOM-построение без innerHTML на рендере, (3) серверная повторная
  санитизация при отдаче контента API (текущий путь сохранен).
- Наблюдаемость: 422-ошибки валидации диалекта логируются с page_id.
