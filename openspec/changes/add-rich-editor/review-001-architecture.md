## Фокус 1. Модель хранения (design §1) — D1 утверждается по существу

Гибрид «блочный markdown-диалект + legacy-HTML passthrough» архитектурно верен:

- Слои защиты rich-пути достаточны: (1) структурная безопасность парсера
  (конечная грамматика), (2) DOM только createElement/textContent —
  пользовательский контент никогда не интерпретируется как HTML, (3)
  `sanitize_rich.py` на записи. innerHTML для пользовательского контента
  запрещен и в design (§2 renderer), и в задаче 1.4, и в чек-листе ревью 4.1.
- Legacy-путь структурно не меняется (passthrough через существующий
  sanitize-на-записи путь) — но см. мажор A-2 и минор M-4.
- Альтернатива (расширенный HTML-whitelist) отклонена обоснованно: поверхность
  sanitize росла бы с каждым блоком (прецедент BUG-AF-RECHECK-004), диффы
  версий нечитаемы, миграция не нужна — все четыре аргумента design §1
  подтверждается картой (sanitize.py — whitelist на html.parser, НА ЗАПИСИ).

### A-1 MAJOR. Design §6 утверждает несуществующий слой: «серверная повторная санитизация при отдаче контента API (текущий путь сохранен)»

Проверено по коду и карте: `backend/app/wiki.py` санитизирует ТОЛЬКО на
записи — `sanitize_html` в POST (L239), PUT (L308), revert (L397); GET
(`/api/wiki/pages/{id}`) отдает сохраненный контент как есть (L280).
Архитектурная карта, Wiki-домен: «применяется НА ЗАПИСИ (POST/PUT/revert)».
Слоя «повторная санитизация при отдаче» в текущем коде НЕТ — design
приписывает пакету несуществующую защиту (класс ошибки DEF-002: допущение о
среде не проверено).

Следствие: сценарий дельты wiki-sanitize «Санитизация выполняется и на
сохранении, и на рендере» («независимо от того, каким путем контент попал в
хранилище») не обеспечен ни одной задачей: 1.3 — только шов сохранения.
Для rich-блоков рендер структурно безопасен (textContent) и сценарий
выполняется; для legacy-HTML части — нет: контент, попавший в хранилище
мимо sanitize (старые строки, прямой доступ к БД), отрендерится как есть.

Фикс (одно из двух, на выбор СА): (а) завести задачу/пункт 1.3 на
санитизацию при отдаче; (б) переформулировать сценарий спеки честно под
фактическую модель «sanitize-на-записи + структурная безопасность рендера»,
убрав ложный слой из design §6. Молча оставить как есть нельзя — QA 3.1
упрется в невыполнимый сценарий.

### A-2 MAJOR. Не определена политика неоднозначности legacy-контента → 422 при re-save старой страницы

Design §1 утверждает «старый контент не содержит конструкций диалекта на
позиции блока» как факт. Это непомеченное допущение: plain-text страницы
легитимно могут содержать строку, начинающуюся с `:::`, `| a | b |` +
`|---|`, ``` — задача 1.3 зовет `rich_blocks.validate(content)` на КАЖДОМ
сохранении и отвечает 422 при структурной ошибке. Итог: старую страницу с
таким текстом невозможно ОТРЕДАКТИРОВАТЬ И СОХРАНИТЬ (не только прочитать) —
прямое нарушение NFR-38 («существующее поведение wiki сохраняется») и FR-125
в редактировании. Регресс 1.7 на фиксированном наборе это не ловит: набор
не включает патологические страницы.

Фикс: (а) проверить реальные данные (запрос к БД стенда/прод-копии: строки
страниц с `^:::`, GFM-шапками, ``` на позиции блока) — допущение перевести
в факт с пометкой проверки; (б) зафиксировать в design §1 fallback-политику:
толерантный парс (кандидат в блок, не прошедший разбор → текст + лог,
без 422) и/или эскейп-механизм; (в) негативный тест в 1.1/1.7 на
«legacy-текст, похожий на диалект».

## Фокус 2. Декомпозиция (директива Заказчика) — не пережата

15 модулей (frontend 11 + backend 2 + шов) — это исполнение директивы, не
фрагментация: 11 frontend-модулей = ядро (block-parser/renderer/toolbar) +
7 block-модулей с ЕДИНЫМ контрактом `parse/serialize/render/toolbar` +
highlight как отдельная ответственность. Каждый block-модуль кохезивен по
типу блока; «новый тип блока = новый модуль + регистрация» — ось
расширения без правки ядра (NFR-38 по построению). Обратное (6 модулей
«по блоку на два») сделало бы renderer/toolbar точками постоянных правок.
Backend: rich_blocks.py / sanitize_rich.py отдельно, sanitize.py не
переписывается (запрет записи в швах) — директива выполнена дословно.

### M-3 MINOR. Design §5 «волна 2 не правит файлы волны 1» противоречит задаче 2.5

Зоны 2.5 — `editor.js` и `toolbar.js`, т.е. файлы волны 1 (задачи 1.6/1.4).
Для зон это корректно (последовательность объявлена в швах, п.4), но
формулировка design §5 неточна. Уточнить: «block-модули волны 2 не правят
файлы волны 1; 2.5 — единственный последовательный шов editor.js/toolbar.js».

### M-4 MINOR. Поведение sanitize_rich на legacy-части смешанного контента не зафиксировано

Задача 1.2 описывает только диалектную часть. Если sanitize_rich обработает
legacy-HTML иначе, чем sanitize_html, — re-save старой страницы изменит
контент (NFR-36/38). Дополнить 1.2: явное правило «legacy-часть —
passthrough к helpers sanitize.py без изменений» + тест
`sanitize_rich(legacy) == sanitize_html(legacy)`.
