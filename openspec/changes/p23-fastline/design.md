# Design: p23-fastline

Эталон вида — утвержденные мокапы `design/p23-fastline/v2-*.png` (вариант A,
шапка FASTLINE, ОВ-1…ОВ-5 + ограничение «1 задача») и README дизайн-фазы.
Стиль — V3 «Бумага», токены дословно из `frontend/static/css/app.css` +
`board.css` (голубые токены `--p-blue-*` — те же, что у существующих
`.task-card-fast` / `.fast-row` / `.badge-fast`); ОГР-8 — без внешних
зависимостей.

## §1. Зона: вид по мокапам (вариант A)

Горизонтальная зона НАД основным канбаном: подложка `--p-blue-050` («зона
собирает» цвет fast-карточек), тонкая рамка `--p-blue-200`, серифный заголовок
**FASTLINE** одним словом (правка ОВ-6 README v2), счетчика НЕТ (ОВ-2).
Внутри — 3 столбца-этапа. Пустая зона отображается ПОЛНОСТЬЮ (ОВ-3), подсказок
нет (заявка: «подсказки показывать не надо»). В шапке зоны — кнопка
«+ Fast-задача»: активна с голубой рамкой только при пустой зоне; при занятой
— disabled (cursor not-allowed) + чип-запрет в error-цветах сайта: «В
фастлайне уже есть задача — выполните текущую» (мокапы v2-empty / v2-blocked).

## §2. Хранение этапа: существующий `status`, БЕЗ поля fastline_stage

Решение: этап зоны = существующее поле `status`; отдельное поле
`fastline_stage` НЕ вводится. Маппинг 1:1:

| Столбец зоны | status | Пояснение |
|---|---|---|
| Ожидает | `todo` | как канбан |
| В работе | `in_progress` | как канбан |
| Выполнено | `done` | done_at = момент выполнения; автоархивация МСК-дня |

Отвергнутая альтернатива (новое поле `fastline_stage`): требует миграцию,
второй источник правды рядом со `status` (рассинхрон при любом move),
новые ветки в move-эндпоинте и в автоархивации — при том, что мокапы
провойтывают этапы как те же «Ожидает/В работе/Выполнено». Ноль пользы,
четыре новых шва. Названия столбцов — из утвержденных мокапов (нейтральные
«План/Готово» отвергнуты: расхождение с утвержденным видом и с канбаном).

Принадлежность зоне: `is_fast = 1 AND archived_at IS NULL` (выборка GET
/api/board уже содержит оба поля). Выполненная fast-задача остается видимой
в столбце «Выполнено» зоны до автоархивации (граница МСК-дня, существующее
правило) — симметрично столбцу «Выполнено» канбана; слот «1 задача» при этом
свободен (инвариант ≤1 считает только todo/in_progress). Аннотация мокапа
«выполненная покидает фастлайн» читается как «покидает активную часть зоны
и в итоге исчезает вместе с доской» — эскалация Э1 (design.md §7).

## §3. API: не меняется

Новых эндпоинтов и полей нет; `contracts/openapi.json` не перегенерируется.

- Чтение: GET `/api/board` — ответ не меняется; разделение fast/обычные —
  клиентское по `is_fast` (серверная сортировка `is_fast DESC` сохраняется,
  безвредна).
- Вставка: POST `/api/tasks` с `is_fast=true` — существующие 409
  «fast line occupied» (≤1) и 422 «fast requires high» (priority-lock).
- Перемещение между этапами (ОВ-5): существующий POST
  `/api/tasks/{id}/move {status}` — тот же путь, что DnD канбана и селект
  (ОГР-14); серверные правила не меняются.
- Быстрое выполнение: drop в «Выполнено» зоны = move в done — тот же
  эндпоинт, что quick-done канбана.

## §4. Ограничение «1 задача»: один инвариант, все пути вставки закрыты

Единственный источник правила — серверный инвариант ≤1 (`tasks.py`,
`_fast_line_busy`): создание и возврат из done дают 409. Клиент добавляет
только блокировки доступности (не новые правила):

1. Кнопка «+ Fast-задача» disabled + чип при наличии активной fast-задачи
   (состояние из последнего GET /api/board).
2. DnD обычной задачи в занятую зону: столбец-приемник отвечает красным
   пунктиром + знак запрета, cursor not-allowed, POST НЕ отправляется
   (мокап v2-dnd-blocked); в пустую зону DnD из канбана запрещен тоже —
   is_fast назначается только при создании (ОГР-5), сервер вернул бы
   обычную задачу в канбан (Э2).
3. Paste/селект-путь (селект «Столбец» в task-form): меняет только status,
   is_fast трогать не может — задача физически не может попасть в зону
   через него; вставка ВТОРОЙ fast-задачи через форму создания уже отклонена
   сервером (409, сообщение api.js у чипа).

DnD ВНУТРИ зоны (единственная fast-карта между 3 столбцами) — разрешен
всегда: ≤1 нарушить невозможно (мокап v2-dnd-move).

## §5. DnD-интеграция с существующим механизмом (cards.js)

Переиспользуется нативный HTML5 DnD канбана (drag-ghost, drop-target,
refreshBoard как единый источник правды), без новых зависимостей:

- Направления и цвета (ОВ-4): приемник столбца зоны — голубой пунктир
  (`--p-blue-*`), приемник канбана — терракотовый (как сейчас): направления
  не спутать.
- Drag обычной карты: зоны канбана активны (терракота), столбцы зоны —
  не-приемники (пустая — красный пунктир как «нельзя», занятая — красный
  пунктир + запрет, v2-dnd-blocked).
- Drag fast-карты: активны только столбцы зоны (голубой пунктир), канбан —
  не-приемник (fast-задача не покидает зону).
- Полет: карта полупрозрачная с тенью; исходная позиция — drag-ghost
  (наклон 3°, 35%) — как в существующих пресетах.
- Ошибка 4xx/сеть: сообщение в `#board-error`, refreshBoard из серверного
  состояния (карта возвращается) — существующее поведение.
- Touch не затрагивается (HTML5 DnD не срабатывает — перенос через карточку/
  селект, ОВ-19 как в канбане).

## §6. Мобильная раскладка (минимум, без нового дизайна)

Мокапы — только desktop 1440×900. На узких экранах зона: шапка + кнопка,
столбцы укладываются вертикально (stack) той же сеткой, что столбцы канбана
в существующем responsive-режиме (домен add-responsive-mobile). Поведение
(блокировки, DnD-замены через селект) — идентично desktop. Переработка
мобильного вида зоны — вне скоупа (при необходимости — новый пункт бэклога).

## §7. Эскалации (к ПМ/Заказчику, не блокируют реализацию)

- **Э1.** Аннотация мокапа v2-busy «выполненная покидает фастлайн» vs заявка
  «таски фастлайна только на нем». Решение СА (§2): выполненная fast-задача
  остается в столбце «Выполнено» зоны до автоархивации МСК-дня. Против
  мокапов не бьет (в них выполненных fast-карт нет); подтвердить формулировку.
- **Э2.** DnD обычной задачи в ПУСТУЮ зону в мокапах v2 не показан (в волне 1
  README допускал его как способ назначения fast). Решение СА (§4.2):
  запрещено — ОГР-5 (is_fast только при создании) выше; вставка fast-задачи —
  только кнопкой «+ Fast-задача». Подтвердить: запрет красным пунктиром и в
  пустой зоне.
- **Э3.** Текст чипа/сообщений («В фастлайне уже есть задача — выполните
  текущую») — из мокапа, финальная формулировка за ревью дизайна волны 2.

## §8. Волны реализации (см. tasks.md)

1. Фундамент: константы этапов + разделение задач + скелет зоны (пустая).
2. Состояния: занято (disabled+чип), вставка fast-задачи, Выполнено/409-пути.
3. DnD: перемещение внутри зоны, запреты, цвета.
4. Регресс + статик-бамп + финальная сверка вида с мокапами.
