# sdd.md — Системный дизайн: ekotov-wiki, Релиз 2 (change add-r2-categories-settings)

Источник требований: `test-model/requirements-r2.md` (УТВЕРЖДЕН r1, решения Заказчика 2026-09-21): FR-19…FR-30, NFR-8, ОГР-7…ОГР-11, дефолты Д-1…Д-5. Пакет: `openspec/changes/add-r2-categories-settings/`.

Файл дополняет корневой `sdd.md` (Релиз 1, r6), не заменяет его: стек, компоненты, авторизация и контракты Релиза 1 действуют без изменений. Здесь — только дельта Релиза 2. После архивации пакета разделы переносятся/сливаются в корневой sdd (контракт 7).

## 1. Стек и компоненты

Без изменений (корневой sdd §1–2: nginx + FastAPI + SQLite WAL + Jinja2/ванильный JS). Новых зависимостей нет (ОГР-8). Новый компонент — **модуль категорий** (API CRUD + валидация + миграционный скрипт) и **страница /settings**; сайдбар дополняется разделом «Настройки».

## 2. Модель данных (дельта)

```sql
categories (
  id   INTEGER PK,
  name TEXT UNIQUE NOT NULL           -- справочник един (ОГР-7); дубли по регистру возможны, слияние вручную (Д-2)
)
```

- `tasks.category` — без изменений (TEXT, nullable), ссылка по значению на `categories.name`. Переименование категории — атомарный UPDATE значения; FK не вводится (обоснование — design.md §1.1).
- Индекс: `tasks(category)` — для проверки использования при удалении (Д-1) и сверки миграции.
- Инвариант fast line (новый, FR-27): `is_fast = 1 ⇒ priority = 'high'`. Поддержан серверной валидацией + приведением данных при миграции (design.md §4).
- Ограничение целостности «непустая category существует в categories» — серверной валидацией API (§3), не схемой БД: nullable-поле и существующие данные до миграции.

## 3. API-контракты (дельта)

Общее: авторизация — как весь `/api/*` (401 `{"error": "unauthorized"}` без сессии); ошибки валидации — 422 `{"error": "validation", "details": {...}}`; конфликт — 409. Exempt-список не расширяется.

### 3.1 Категории (новый)

| Метод/путь | Описание | Ответы |
|---|---|---|
| `GET /api/categories` | Список справочника (источник select-полей формы и фильтра, FR-30) | 200 `{"categories": [{"id": 1, "name": "home"}, ...]}` (отсортировано по name); 401 |
| `POST /api/categories` | Создать | 201 `{"id": ..., "name": ...}`; 422 (пустое/пробельное имя); 409 (дубль имени) |
| `PATCH /api/categories/{id}` | Переименовать (применяется ко всем задачам со старым значением) | 200 `{"id": ..., "name": ...}`; 404; 409/422 (дубль/пустое имя) |
| `DELETE /api/categories/{id}` | Удалить (Д-1: блокируется, если категория используется задачами) | 200 `{"ok": true}`; 404; 409 `{"error": "category in use", "details": {"tasks": N}}` |

### 3.2 Изменения существующих контрактов

**POST /api/tasks** (корневой sdd §3.2):
- добавляется валидация: непустая `category` не из `categories` → **422** `{"error": "validation", "details": {"category": "not in categories"}}` (FR-21);
- добавляется priority-lock: `is_fast=true` с явным `priority != "high"` → **422** `{"error": "validation", "details": {"priority": "fast requires high"}}`; `is_fast=true` без priority → приоритет устанавливается `high` (FR-27).

**PATCH /api/tasks/{id}** — та же валидация категории (FR-21). Смена `is_fast` после создания — не входит в дельту (fast назначается только при создании, ОГР-5 — без изменений).

**GET /api/suggestions** — без изменений; переиспользуется формой задачи как источник подсказок тегов (Д-3, FR-26).

### 3.3 Страницы (дельта)

| Путь | Описание |
|---|---|
| `GET /settings` | Страница настроек (управление справочником категорий); без сессии — редирект на /login (NFR-7); настройки общие (FR-24, ОГР-11) |

## 4. Контракты фронтенда (внутренние решения — design.md)

- Форма задачи: поле категории — select из `GET /api/categories`; поле тегов — datalist из `GET /api/suggestions` с правом нового ввода; поле приоритета блокируется при отмеченном fast line; крестик закрытия — правый верхний угол; подсветка невалидных полей по `details` 422-ответов; иконки приоритетов — inline SVG (ОГР-8).
- Фильтр-конструктор: select категории — из `GET /api/categories` (DEF-001/FR-30).

## 5. Решения по НФТ (дельта)

| НФТ | Решение |
|---|---|
| NFR-8 (0 потерь миграции) | Скрипт миграции: снимок «до» → INSERT DISTINCT непустых category (1:1, пустые мимо) → автосверка «после» (значения всех задач в справочнике; COUNT категорий = COUNT уникальных непустых «до»); расхождение = провал, внедрение не завершено. Идемпотентен. Плюс приведение fast-задач к `priority='high'` |
| NFR-1/NFR-2 | Прямые запросы по индексам; кэш значений не требуется на объеме 2 пользователей / 1000+ задач (допустим по FR-30 «можно предвычислять», решение — не вводить) |
| NFR-7 | /settings и /api/categories/* за существующим middleware; exempt-список не меняется |
| ОГР-8/9/10/11 | Inline SVG, новых зависимостей нет; миграция одноразовая, слияние синонимов вручную потом (FR-20); fast×priority — серверная валидация, обход невозможен; права на настройки не проектируются |

## 7. Ограничения и допущения

- ОГР-7: справочник в общем SQLite рядом с задачами, един (без user_id).
- ОГР-9: миграция одноразовая; слияние синонимов — после, средствами FR-20.
- ОГР-10: дельта fastline — MODIFIED; серверная валидация обязательна.
- ОГР-11: пользователей 2; права на настройки не проектируются.
- Д-1…Д-5 — приняты как данность (право возражения Заказчика: Д-1/Д-2 до старта 2.1, Д-3 до 2.4, Д-4/Д-5 до 2.5).
- Зафиксированное уточнение (в границах ТЗ, см. proposal «Assumptions»): пустая категория жесткой валидацией не запрещается (FR-21 действует на непустые значения; из Д-2 и nullable-модели).
