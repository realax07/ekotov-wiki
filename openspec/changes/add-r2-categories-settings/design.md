# Design: add-r2-categories-settings

Технические решения Релиза 2. Наблюдаемое поведение — в дельтах `specs/`; здесь — как оно достигается. Стек не меняется (sdd.md §1: FastAPI + SQLite + Jinja2/ванильный JS + nginx; ОГР-8 запрещает новые фронтенд-зависимости).

## 1. Справочник категорий (FR-19…FR-22, NFR-8, ОГР-7, Д-1, Д-2)

### 1.1 Модель данных

Новая таблица в SQLite (структура БД — решение системного анализа, ОГР-7: справочник един, рядом с задачами, без пер-пользовательских списков):

```sql
categories (
  id   INTEGER PK,
  name TEXT UNIQUE NOT NULL
)
```

- Уникальность `name` — на уровне БД; дубликаты (включая различие регистра) технически возможны как разные записи — слияние «синонимов» не автоматизируется (Д-2: «home» и «Home» — разные категории; слияние вручную потом через переименование FR-20).
- Поле `tasks.category` остается TEXT (nullable): ссылка по значению на `categories.name`. Отдельный FK `category_id` не вводится — переименование категории (FR-20: «применяется ко всем задачам») при хранении по id потребовало бы отдельного маппинга старых значений; хранение по значению делает переименование атомарным `UPDATE categories SET name=? WHERE name=?`. Ограничение целостности «непустая category задачи существует в categories» обеспечивает серверная валидация (§1.3) — SQLite FK по TEXT-значению без NOT NULL не дает нужной семантики.
- Миграция: без переименования задач; значения задач не меняются — создаются записи справочника (§1.2).

### 1.2 Миграция (FR-22, ОГР-9, Д-2, NFR-8)

Одноразовый скрипт при внедрении (ОГР-9), идемпотентный (повторный запуск не создает дублей):

1. Снимок «до»: список уникальных непустых значений `tasks.category` + категории каждой задачи (для сверки NFR-8).
2. `INSERT INTO categories(name) SELECT DISTINCT category FROM tasks WHERE category IS NOT NULL AND category <> ''` — маппинг 1:1, пустые значения записей не создают.
3. Задачи не трогаются: их значения уже совпадают с созданными записями справочника — ни одна задача не теряет значение.
4. Сверка «после» (NFR-8): (а) каждое непустое значение category каждой задачи присутствует в categories; (b) `COUNT(categories)` = `COUNT(DISTINCT непустые category до)`. Расхождение → провал, внедрение не завершено (сценарий дельты categories).

Слияние синонимов при миграции не выполняется (Д-2, ОГР-9): корректировка после миграции — средствами переименования (FR-20), которое при хранении по значению обновляет все задачи атомарно.

### 1.3 Серверная валидация (FR-21, «Жесткая»)

- Точка проверки — API-слой (единая точка бизнес-логики, sdd.md §2): при POST /api/tasks и PATCH /api/tasks/{id} непустое значение `category` сверяется со справочником (`SELECT 1 FROM categories WHERE name = ?`). Отсутствует → **422** `{"error": "validation", "details": {"category": "not in categories"}}`. Валидация на сервере делает обход через API невозможным (FR-21, ОГР-10 по аналогии).
- Пустая категория (NULL/пустая строка) проходит валидацию — nullable-модель данных сохраняется, Д-2 (пустые значения валидны) зафиксирована в спеке.
- UI-часть: поле категории в форме — select/datalist из справочника (не свободный ввод), следовательно значение вне списка из формы отправить нельзя; серверная проверка остается страховкой.

### 1.4 CRUD категорий (FR-20, Д-1)

- Создание: проверка на непустое имя (после trim) — иначе 422; уникальность имени — БД (дубль → 409/422).
- Переименование: `UPDATE categories SET name=? WHERE id=?` — задачи, ссылающиеся по значению, обновляются автоматически (наблюдаемо: «применяется ко всем задачам»).
- Удаление (Д-1): предварительная проверка `SELECT COUNT(*) FROM tasks WHERE category = ?`; есть использующие → отказ с указанием, что категория используется задачами (перевести задачи → удалить). Порядок: проверить использование → удалить. Гонка с параллельной установкой категории пренебрежима (2 пользователя, NFR-4), но серверная валидация §1.3 закрывает окно: задача с удаленной категорией не сохранится.

## 2. Настройки (FR-23…FR-25, ОГР-11)

- Страница `GET /settings` (Jinja2), в exempt-логике страниц — как прочие защищенные: без сессии редирект на /login (sdd.md §3.6, следствие NFR-7).
- Раздел «Настройки» в сайдбаре — внизу слева, рядом с кнопкой выхода (шаблон базового layout).
- Настройки общие (FR-24): состояние настроек — общие таблицы БД (categories), без user_id; любой из двух пользователей читает и меняет. Разграничение прав не проектируется (ОГР-11).
- Состав настроек первого релиза — только управление справочником категорий (FR-25). Остальное — Won't.

## 3. API-контракты (детали в sdd.md §3.7, здесь — решения)

| Метод/путь | Назначение | Коды |
|---|---|---|
| `GET /api/categories` | Список справочника (для select-полей формы, фильтра, страницы настроек) | 200; 401 |
| `POST /api/categories` | Создать категорию | 201; 401; 422 (пустое имя); 409 (дубль имени) |
| `PATCH /api/categories/{id}` | Переименовать (применяется ко всем задачам) | 200; 401; 404; 409/422 (дубль) |
| `DELETE /api/categories/{id}` | Удалить (блокируется при использовании задачами, Д-1) | 200; 401; 404; 409 (используется) |

Подсказки формы (FR-26, Д-3): переиспользуется существующий `GET /api/suggestions` (set() из тегов+категорий существующих задач, FR-15…FR-17, архив add-suggestions) — механизм един, изменений эндпоинта подсказок не требуется; право создания нового значения реализуется клиентской логикой формы (принять произвольный ввод), сервер создаст тег как обычно (теги не справочник — Won't).

## 4. Priority-lock fast line (FR-27, ОГР-10)

- Признаки fast и priority более не независимы: инвариант `is_fast ⇒ priority='high'`.
- API: при POST /api/tasks с `is_fast=true` сервер принудительно устанавливает `priority='high'`; явно переданный приоритет ≠ high → 422 (отклонение, а не молчаливая правка — наблюдаемое поведение дельты: «fast-задача с приоритетом ≠ high отклоняется»).
- UI: отметка fast line блокирует поле приоритета значением «высокий» (FR-27).
- Существующие данные: разовая проверка/приведение при внедрении (UPDATE fast-задач с priority ≠ high → high) — сценарий дельты fastline; проверка входит в миграционный скрипт §1.2.
- Дельта спеки — MODIFIED Requirement «Назначение задачи на fast line вручную при создании» (единственный, упоминавший создание fast-задачи); инвариант «≤1 активной fast-задачи» (409) не меняется.

## 5. Форма задачи (FR-26, FR-28, FR-29, ОГР-8, Д-4, Д-5)

- Крестик закрытия — в правом верхнем углу модального окна; закрытие без сохранения.
- Иконки приоритетов — inline SVG (цвет + иконка на low/medium/high) в форме и на карточке; без внешних библиотек (ОГР-8, Д-4).
- Состояния ошибок: подсветка невалидных полей по 422-ответам API (включая категорию по FR-21); сетка полей, типографика, анимация открытия/закрытия.
- Конкретный стиль — выбор Заказчика из 2–3 мокапов/пресетов до старта задачи 2.5 (Д-5); без выбора — текущий стиль + обязательный минимум. Точка согласования — перед задачей 2.5 (эскалация ПМ → Заказчик, право возражения до старта 2.5).

## 6. DEF-001 / FR-30 — селект-поля из данных

Единый механизм: все динамические списки значений (select категории в форме и в фильтре, подсказки) заполняются запросами к фактическим данным: категории — `GET /api/categories` (справочник), теги/подсказки — `GET /api/suggestions` (заведенные значения). Никаких статических option-списков в шаблонах/JS. Допустимо предвычисление/кэширование множества значений (FR-30: «можно предвычислять и хранить») — на объеме 2 пользователей/1000 задач прямые запросы достаточны; кэш инвалидируется при изменении справочника. Дефект «select категории не привязан к данным» устраняется привязкой обоих селектов к `/api/categories`.
