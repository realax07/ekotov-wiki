# Delta: fastline

## MODIFIED Requirements

### Requirement: Назначение задачи на fast line вручную при создании

Задача MUST назначаться на fast line вручную пользователем в момент создания задачи (FR-3, ОГР-5). Система MUST НЕ назначать задачи на fast line автоматически. Fast-задача при создании MUST получать приоритет «высокий» (high) автоматически, и пользователь MUST НЕ иметь возможности назначить fast-задаче другой приоритет (FR-27, решение Заказчика; ОГР-10): в интерфейсе поле приоритета для fast-задачи заблокировано; на уровне API/хранения fast-задача с приоритетом, отличным от high, MUST отклоняться ошибкой валидации. Fast и приоритет более не являются независимыми признаками.

#### Scenario: Создание задачи с назначением на fast line

- **GIVEN** пользователь авторизован, активных fast-задач нет
- **WHEN** пользователь при создании задачи отмечает назначение на fast line
- **THEN** задача создается как fast-задача с приоритетом «высокий» (high) и отображается на fast line

#### Scenario: Создание обычной задачи без fast line

- **GIVEN** пользователь авторизован
- **WHEN** пользователь создает задачу, не отмечая назначение на fast line
- **THEN** задача создается как обычная с выбранным пользователем приоритетом и не отображается на fast line

#### Scenario: Поле приоритета заблокировано в форме fast-задачи

- **GIVEN** пользователь авторизован и отмечает в форме создания задачи назначение на fast line
- **WHEN** пользователь просматривает поле приоритета
- **THEN** поле приоритета показывает значение «высокий» (high) и заблокировано для изменения (FR-27, UI-часть)

#### Scenario: Негативный: fast-задача с приоритетом не-high через API

- **GIVEN** вызывающий авторизован, активных fast-задач нет
- **WHEN** вызывающий отправляет API-запрос создания задачи с назначением на fast line и приоритетом «low» (или «medium», или NULL)
- **THEN** API отклоняет запрос ошибкой валидации; fast-задача не создается (FR-27, ОГР-10 — обход через API невозможен)

#### Scenario: Негативный: снятие блокировки в UI не меняет приоритет fast-задачи

- **GIVEN** вызывающий авторизован
- **WHEN** вызывающий отправляет подделанный клиентский запрос (минуя блокировку поля) на создание fast-задачи с приоритетом, отличным от high
- **THEN** запрос отклоняется серверной валидацией — приоритет fast-задачи не может отличаться от high ни при каких клиентских действиях

#### Scenario: Обычная задача с любым приоритетом не ограничена

- **GIVEN** вызывающий авторизован
- **WHEN** вызывающий создает обычную (не fast) задачу с приоритетом «low»
- **THEN** задача создается успешно с приоритетом «low» (ограничение действует только на fast-задачи)

#### Scenario: Существующие fast-задачи с не-high приоритетом приводятся в соответствие

- **GIVEN** до внедрения изменения в системе существует fast-задача с приоритетом, отличным от high
- **WHEN** выполняется внедрение изменения
- **THEN** инвариант «fast ⇒ priority=high» выполняется для всех fast-задач (существующие значения приведены в соответствие); после этого любая fast-задача в системе имеет приоритет high
