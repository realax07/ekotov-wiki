## 1. Общее описание

Сервис изображений «Галерея»: загрузка изображений (multipart) и работа с ними
— категории, теги, лайк/дизлайк, скачивание, комментарии. Реализуется
отдельным контейнерным сервисом `images` по образцу `services/search`
(FastAPI за общим nginx); файлы изображений — в отдельном томе `images-data`
(в БД — только метаданные). В UI — **ЧЕТВЕРТЫЙ раздел сайдбара «Галерея»**
(после «Wiki»): страница `/gallery` — сетка превью с фильтрами по категории и
тегу, форма загрузки; клик по превью — просмотр «как в галлерее»: модальное
окно на весь экран с листанием (←/→), лайк/дизлайк, скачивание, комментарии.
Связь с трекером — **только общий фронт сайдбара** (без ссылок на задачи).
Доступ — **общий**: оба пользователя (owner и PE) равноправно, без разделения
прав (ОВ-4). БД ядра дополняется таблицами gallery миграцией ядра (one-shot
с репетицией на копии — правило deploy-спеки).

Нумерация продолжает сквозную: последние использованные — FR-78
(add-netdata-monitoring), NFR-19.

## 2. Аудитория

Пользователи галереи — оба пользователя системы: владелец (учетка `owner`,
роль «Product manager») и PE (учетка `wife`, роль «Product engineer») —
**равноправно**, без разделения прав (ОВ-4). Неавторизованные доступа не
имеют. Исполнители пакета: ui_designer (мокапы, зона `design/**`), dev
(сервис, миграция, фронтенд), devops (nginx/compose), QA (в т.ч.
design_validator), Заказчик (утверждение мокапов + прод-приемка).

## 3. Функциональные требования (FR)

- **FR-79** (Must): Сервис изображений — отдельный контейнерный сервис
  `images`: загрузка файла multipart-запросом, получение изображения и его
  метаданных, список изображений. Файлы MUST храниться в именованном томе
  `images-data` (НЕ в БД); в БД — только метаданные. При загрузке
  генерируется превью для сетки (оригинал сохраняется; скачивание —
  оригинала). Файлы отдаются nginx по `/images/` из тома (паритет
  `/avatars/`); API-операции требуют сессию (без сессии — 401).
- **FR-80** (Must): Категории и теги изображений: у изображения есть
  категория (опционально, значение из **справочника категорий галереи** —
  общего для обоих пользователей, НЕ справочник категорий задач) и теги
  (ноль или больше, из общего словаря тегов системы). Список изображений
  фильтруется по категории и/или по тегу; фильтры комбинируются; пустой
  фильтр показывает все изображения.
- **FR-81** (Must): Лайк/дизлайк: авторизованный пользователь ставит
  изображению голос «+1» или «−1»; у каждого пользователя ровно один голос
  на изображение; повторное действие меняет или снимает голос. Видны
  счетчики лайков/дизлайков и собственный голос пользователя.
- **FR-82** (Must): Комментарии к изображениям: просмотр всех комментариев
  (с автором и временем), добавление (непустой текст), удаление **своего**
  комментария; удаление чужого — запрещено.
- **FR-83** (Must): Просмотр «как в галлерее»: клик по превью в сетке
  открывает модальное окно на весь экран; листание — кнопками ←/→ и
  клавишами стрелок; в окне доступны лайк/дизлайк, скачивание оригинала,
  комментарии. Галерея не связана с трекером — без ссылок на задачи,
  фильтров по задачам и любых переходов в трекер (общий элемент — только
  сайдбар).
- **FR-84** (Must): Доступ общий (ОВ-4): оба пользователя имеют полный
  равноправный доступ — просмотр всей галереи, загрузка, реакции,
  комментарии; разделения прав по владельцу/роли НЕТ. Неавторизованный
  доступа не имеет (страница — редирект на `/login`, API — 401).
- **FR-85** (Must): Раздел «Галерея» в сайдбаре: **ЧЕТВЕРТЫЙ пункт**
  (после «Wiki»), виден **всем** авторизованным пользователям (owner и PE —
  паритет ОВ-4; в отличие от «Мониторинга» — без рендера по роли). Ведет на
  страницу `/gallery`: сетка превью, фильтры категория/тег, форма загрузки.
- **FR-86** (Must): Вид интерфейса галереи (сетка, карточки, full-screen
  просмотр, форма загрузки) — **по мокапам ui_designer, утвержденным
  Заказчиком ДО dev** (дизайн-фаза); после dev соответствие мокапам
  проверяет design_validator (преемственность: «Дизайн не забудь», «У нас
  есть дизайнер», паттерн Р4/Р5 пакета add-netdata-monitoring).

## 4. Нефункциональные требования (NFR)

- **NFR-20** (Must): Ресурсы сервиса изображений: `mem_limit` 128m;
  healthcheck; ротация логов json-file 10m×3 (паритет стеку). Суммарные
  лимиты стека с images — 1.54 GB, резерв хосту (VPS 3.9 GB) ≥ 2.3 GB
  (требование ≥ 2 GB deploy-спеки сохраняется). Фактическое потребление RAM
  замеряется на стенде до прод-выкатки (урок «вес меряем по факту»);
  стабильное превышение лимита блокирует выкатку до решения Заказчика.
- **NFR-21** (Must): Лимит загрузки: файл ≤ 10 МБ, типы JPEG/PNG/GIF/WebP;
  превышение размера или недопустимый тип — отказ 422, файл не сохраняется
  (nginx-лимит локации загрузки согласован с лимитом сервиса).

## 6. Ограничения

- VPS: 3.9 GB total / 2.7 GB available — +128m лимит укладывается (deploy:
  резерв ≥ 2 GB сохраняется).
- Только `docker compose`; без k8s (ограничение проекта).
- Внешние библиотеки в UI запрещены (ОГР-8): стили — токены V3 «Бумага»
  (app.css :root), иконки — inline-SVG.
- Файлы изображений — НЕ в БД (том `images-data`); БД — только метаданные.
- Миграция ядра (новые таблицы gallery) — по правилу deploy-спеки: one-shot
  до подъема, идемпотентно, **репетиция на копии прод-БД** обязательна.
- Дизайн-фаза: мокапы — ui_designer (зона `design/**`), утверждение —
  Заказчик, ревью вида — design_validator (паттерн Р4/Р5).
- Python-зависимость Pillow уже в backend/requirements.txt (пин 12.3.0) —
  новых зависимостей генерация превью не добавляет.

## 7. Открытые вопросы

Открытых вопросов Заказчику на момент сдачи СА нет. На этапе СА зафиксированы
открытые техпункты (закрываются решениями СА/design или предложениями
Заказчику; эскалация — в REPORT-0.1):

- Удаление изображений (кто/как) — **не в ТЗ**, вынесено предложением
  Заказчику (proposal, Out of scope); при желании — отдельным изменением.
- Переименование/удаление категорий галереи — вне ТЗ (создание категорий —
  есть); предложение Заказчику.
- Лимит размера файла (10 МБ) и набор типов — решение СА (ТЗ не задавало);
  меняется одной правкой NFR-21 до dev.
- Профиль записи в общую БД (images — первый сервис-писатель после ядра) —
  решение СА, design §2; WAL + busy_timeout, короткие транзакции.
