# Proposal: add-containerization

## Change ID

`add-containerization`

## Why

Пункт **P11 «Переход на сервисы в контейнерах + контракты между ними»** бэклога, ЭТАП 0+1 нормативного плана `docs/ba/architecture-services-plan.md` §1–6, §8 (решения Заказчика ОВ-1…ОВ-4 — все рекомендации ПМ приняты, 2026-10-03). ТЗ `requirements.md` r1 **УТВЕРЖДЕНО** Заказчиком (Telegram 2026-10-03 «Утверждаю»): FR-64…FR-74, NFR-9…NFR-11. Запись журнала решений: `decisions/2026-10-03-p11-containerization.md` (decision_id `2026-10-03-p11-containerization`, scope project=wiki).

Зачем: сайт живой (2 пользователя), деплой сегодня — rsync + systemd (uvicorn :8377 + хостовой nginx :10443), Docker на VPS отсутствует. Цель П11 «сайт работает из контейнеров» достигается **контейнеризацией монолита как есть** (ЭТАП 1): `app` (uvicorn) + `nginx` (статика + reverse proxy) + именованный том данных `wiki-data`, управление — `docker compose`. Внешнее поведение продукта не меняется (легкий БА-проход): все существующие маршруты `/api/*` и страницы Jinja2 отвечают идентично systemd-проду (FR-64). ЭТАП 2 (выделение сервисов, первый кандидат `search`) — вне скоупа, отдельный БА-цикл после паузы эксплуатации 1–2 недели (ОВ-1 = (а)).

Попутно закрывается долг «машинного контракта»: схема OpenAPI сейчас выключена (`main.py`: `openapi_url=None`, sdd §3 — проза без машинной схемы). Включение `/openapi.json` (только под сессией, 401 без нее) + фиксация схемы в `contracts/` — фундамент контрактного CI-gate ЭТАПА 2 (план §3, вариант А) и требование FR-68 этого пакета.

## What Changes

Дельта — **новая capability `deploy`** (в `openspec/specs/` домена деплоя/развертывания нет: NFR-6 покрыт задачей, не поведенческим Requirement — sdd §6; дельта создает capability пакетом; после архивации появится `openspec/specs/deploy/spec.md`). Все требования — **ADDED** (никаких MODIFIED: существующие домены auth/board/tasks/… поведение не меняют — FR-64 «идентично systemd-проду»).

## Scope

### In scope

- FR-64 (Must): контейнер `app` — текущий `backend/app` (uvicorn, 1 воркер) без изменения кода; маршруты и страницы отвечают идентично.
- FR-65 (Must): контейнер `nginx` — статика `/static/*`, `/avatars/*`, reverse proxy `app:8377`, security-заголовки, gzip; наружу только nginx `10443:10443`, `app` портов наружу не публикует.
- FR-66 (Must): `wiki.db` + `avatars/` — в именованном томе `wiki-data`, `app` — RW.
- FR-67 (Must): `deploy/compose.yaml` (прод) + `deploy/compose.test.yaml` (стенд: временный том, seeded-юзер, другой порт).
- FR-68 (Must): `openapi_url="/openapi.json"` включен, доступ только под сессией (401 без нее), docs/redoc выключены; зафиксированная схема — `contracts/openapi.json`.
- FR-69 (Must): e2e-сьют в `e2e/` против compose-стенда (playwright, база `tests/web`): заголовки кеша, gzip, security-заголовки проверяются тестом.
- FR-70 (Must): миграции — one-shot из того же образа до подъема нового `app`, идемпотентность, репетиция на копии прод-БД со старой схемой (урок инцидента Р4 2026-09-30).
- FR-71 (Must): бэкап (`sqlite3 .backup` + копия аватаров) до каждого деплоя, без остановки.
- FR-72 (Must): откат — предыдущим тегом `ekotov-wiki/app:<release>`; `latest` запрещен; при несовместимой схеме — возврат БД из пред-деплойного бэкапа.
- FR-73 (Must): `mem_limit` — nginx 64m, app 512m (VPS: 3.9 GB total / 2.7 GB available).
- FR-74 (Must): TLS self-signed `/etc/nginx/ssl/ekotov-wiki.{crt,key}` (до 2028-12-22) монтируется томом; валидация цепочки доверия не требуется ни на одном контуре (решение Заказчика, CA не строится).
- NFR-9 (Must): первый контейнерный деплой — параллельно с живым systemd (другой порт на время проверки), переключение — одна операция; откат на systemd за минуты (юнит остановлен, но не удален).
- NFR-10 (Must): dev/prod паритет — один образ, стенд воспроизводит прод-топологию (nginx → app → SQLite-том).
- NFR-11 (Should): ротация логов `json-file`, `max-size: 10m`, `max-file: 3`.
- ЭТАП 0: установка Docker/compose на VPS (сейчас НЕ установлен — факт §8 плана), структура `services/`, каталог `contracts/`, включение и экспорт `openapi.json`.

### Out of scope

- ЭТАП 2: выделение сервисов (`search` и далее) — Won't ТЗ, отдельный цикл после паузы эксплуатации (ОВ-1).
- Registry образов ghcr.io как обязательное условие ЭТАПА 1 — сборка на VPS допустима (ОВ-2 = (б) на последующие этапы).
- CA-инфраструктура TLS — штатный режим self-signed до 2028 (решение Заказчика).
- Изменение внешнего поведения продукта: контракты `/api/*`, страницы, инварианты fast line — не трогаются (FR-64).
- k8s и оркестраторы — только `docker compose` (ограничение ТЗ).

## Impact

- **Что меняется:** новый каталог `services/app/`, `services/frontend/` (Dockerfile'ы, nginx-конфиги в образе), `deploy/compose.yaml` + `deploy/compose.test.yaml`, `e2e/`, `contracts/openapi.json`; точечная правка `backend/app/main.py` (только `openapi_url`); эволюция `deploy/deploy.sh` и `deploy/RUNBOOK.md` тем же пакетом (правило плана: расхождение RUNBOOK и deploy недопустимо). systemd-юнит и хостовой nginx **не удаляются** — чекпоинт отката NFR-9.
- **Пользователи:** без изменений (два пользователя, HTTPS :10443, TLS self-signed с игнором ошибок).
- **Спеки:** новая capability `deploy` (13 Requirements ADDED); существующие домены не затронуты.
- **Риски:** расхождение «web-стенд эмулирует nginx через http.server» (architecture/map.md §6.1) закрывается e2e на compose (FR-69); правило «никогда два изменения инфры в одном шаге» (план §6) закреплено в tasks.md.
