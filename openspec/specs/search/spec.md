# search Specification

## Purpose
Поиск задач: вкладка с фильтрами по признакам и advanced-синтаксисом (AND, SQL-подобный), нормализация запроса, ошибки синтаксиса 400 с позицией; селект-поля фильтра заполняются из фактических данных.

## Requirements

### Requirement: Вкладка поиска старых задач
В системе MUST быть отдельная вкладка поиска по архивным (старым) задачам, доступная через сайдбар (FR-10).

#### Scenario: Переход на вкладку поиска через сайдбар
- **GIVEN** пользователь авторизован и видит сайдбар
- **WHEN** пользователь выбирает в сайдбаре раздел поиска
- **THEN** открывается вкладка поиска по старым задачам

### Requirement: Фильтр-конструктор по признакам задачи
Вкладка поиска MUST содержать фильтр-конструктор — выбор значений признаков задачи для фильтрации (FR-11): «аналог JQL, вариант с выбором». Пользователь MUST иметь возможность комбинировать условия по нескольким признакам.

#### Scenario: Фильтр по одному признаку
- **GIVEN** в системе есть задачи с разными значениями признака «приоритет»
- **WHEN** пользователь выбирает в конструкторе значение приоритета и выполняет поиск
- **THEN** в результатах отображаются только задачи с выбранным приоритетом

#### Scenario: Комбинация условий по нескольким признакам
- **GIVEN** в системе есть задачи с различными комбинациями признаков
- **WHEN** пользователь задает условия по двум признакам одновременно (например, категория + тег) и выполняет поиск
- **THEN** в результатах отображаются только задачи, удовлетворяющие обоим условиям

#### Scenario: Поиск без заданных условий
- **GIVEN** в системе есть архивные задачи
- **WHEN** пользователь выполняет поиск, не задавая ни одного условия
- **THEN** отображаются все задачи (пустой фильтр не ограничивает выборку)

### Requirement: Режим advanced с SQL-подобным синтаксисом
Фильтр-конструктор MUST иметь кнопку переключения в режим advanced: текстовое поле с фильтром в SQL-подобном синтаксисе, доступное для просмотра и правки (FR-12). Переключение MUST синхронизировать фильтр между режимами: условие, собранное в конструкторе, отображается в advanced как текст; отредактированный текст применяется при поиске.

#### Scenario: Переключение конструктора в advanced
- **GIVEN** пользователь задал в конструкторе условия поиска
- **WHEN** пользователь нажимает кнопку переключения на advanced
- **THEN** отображается текстовое поле с текущим фильтром в SQL-подобном синтаксисе, соответствующим заданным условиям

#### Scenario: Правка фильтра в advanced и применение
- **GIVEN** пользователь находится в режиме advanced с отображенным фильтром
- **WHEN** пользователь правит текст фильтра и выполняет поиск
- **THEN** результаты соответствуют отредактированному фильтру

#### Scenario: Негативный: некорректный фильтр в advanced
- **GIVEN** пользователь находится в режиме advanced
- **WHEN** пользователь вводит синтаксически некорректный текст фильтра и выполняет поиск
- **THEN** система показывает сообщение об ошибке синтаксиса фильтра; данные при этом не изменяются и не удаляются

### Requirement: Поиск через API
Поиск MUST быть доступен программно через API в дополнение к веб-интерфейсу (FR-8): API-запрос поиска принимает условия фильтра и возвращает совпадающие задачи.

#### Scenario: Поиск через API с фильтром
- **GIVEN** вызывающий авторизован и в системе есть задачи с разными признаками
- **WHEN** вызывающий отправляет API-запрос поиска с условием по признаку
- **THEN** API возвращает только задачи, удовлетворяющие условию

#### Scenario: Негативный: поиск через API без авторизации
- **GIVEN** вызывающий не авторизован
- **WHEN** вызывающий отправляет API-запрос поиска
- **THEN** API отвечает 401 Unauthorized, результаты не возвращаются

### Requirement: Подсказки тегов и категорий в поиске

Вкладка поиска MUST предоставлять подсказки значений для полей фильтра-конструктора «Теги» и «Категория»: при фокусировке на поле пользователю предлагается общий список подсказок, привязанный к обоим полям (FR-15). Множество подсказок MUST быть объединением значений тегов и категорий **существующих задач** — без дублей; значение, встречающееся и в тегах, и в категориях, входит в список один раз; список MUST быть отсортирован по возрастанию (FR-16). В подсказки MUST попадать только уже заведенные варианты: теги удаленных задач (осиротевшие) не включаются; пустые/незаполненные категории не включаются; новые значения через подсказки не создаются — только выбор из существующих (FR-17). Получение подсказок MUST требовать авторизации: без действующей сессии — отказ 401 (FR-18, следствие NFR-7 основного ТЗ).

#### Scenario: Подсказки при авторизации — 200 и множество значений

- **GIVEN** пользователь авторизован и открыл вкладку поиска
- **WHEN** пользователь фокусируется на поле «Теги» или «Категория» фильтра-конструктора
- **THEN** подсказки получены через API с кодом 200 в виде множества значений (JSON-объект со списком подсказок), и datalist показывает их в поле

#### Scenario: Негативный: без сессии — 401

- **GIVEN** вызывающий не имеет действующей сессии
- **WHEN** вызывающий запрашивает подсказки через API
- **THEN** API отвечает 401 с телом `{"error": "unauthorized"}`; подсказки не возвращаются

#### Scenario: Set-семантика — значение из тегов и категорий входит один раз

- **GIVEN** значение «home» заведено и как тег, и как категория на существующих задачах
- **WHEN** пользователь запрашивает подсказки
- **THEN** «home» присутствует в списке подсказок ровно один раз (без дублей)

#### Scenario: Сортировка списка подсказок

- **GIVEN** заведены значения тегов и категорий в разном порядке
- **WHEN** пользователь запрашивает подсказки
- **THEN** список отсортирован по возрастанию

#### Scenario: Объединение источников — и теги, и категории

- **GIVEN** на существующих задачах заведены и теги, и категории
- **WHEN** пользователь запрашивает подсказки
- **THEN** список содержит и теги, и категории существующих задач

#### Scenario: Только заведенные — осиротевшие теги и пустые категории исключены

- **GIVEN** существует тег, оставшийся только у удаленных задач, и задача с пустой (незаполненной) категорией
- **WHEN** пользователь запрашивает подсказки
- **THEN** осиротевший тег и пустая категория в списке подсказок отсутствуют; список содержит только значения существующих задач

#### Scenario: Подсказки не создают новых значений

- **GIVEN** пользователь авторизован и открыл вкладку поиска
- **WHEN** пользователь работает с полями «Теги» и «Категория» через список подсказок
- **THEN** новые значения из подсказок не создаются — доступен только выбор из уже заведенных вариантов

#### Scenario: Datalist привязан к обоим полям

- **GIVEN** пользователь авторизован и открыл вкладку поиска
- **WHEN** пользователь поочередно фокусируется на полях «Теги» и «Категория» фильтра-конструктора
- **THEN** оба поля показывают один и тот же общий список подсказок (один общий список привязан к обоим полям, FR-15)

### Requirement: Селект-поля и подсказки заполняются из фактических данных

Селект-поля — выбор категории в форме задачи и в фильтре-конструкторе поиска — и подсказки MUST заполняться из фактических данных хранилища: уникальные значения соответствующих столбцов (допустимо предвычислять и хранить множество значений) (FR-30, DEF-001). Статические или пустые списки значений в этих полях MUST НЕ использоваться. После внедрения справочника источник значений для категории — справочник (FR-19); для тегов и подсказок — множество уже заведенных значений существующих задач (FR-26, FR-15…FR-17).

#### Scenario: Выбор категории в форме заполняется из справочника

- **GIVEN** пользователь авторизован; в справочнике заведены категории «home», «work», «finance»
- **WHEN** пользователь открывает поле категории в форме задачи
- **THEN** список значений поля содержит ровно «home», «work», «finance» — фактическое содержимое справочника, а не статический захардкоженный список

#### Scenario: Выбор категории в фильтре-конструкторе заполняется из справочника

- **GIVEN** пользователь авторизован; в справочнике заведены категории «home», «work», «finance»
- **WHEN** пользователь раскрывает поле «Категория» в фильтре-конструкторе поиска
- **THEN** список значений содержит ровно «home», «work», «finance» — фактическое содержимое справочника

#### Scenario: Изменение данных отражается в селект-полях

- **GIVEN** пользователь авторизован; в справочнике есть категория «work»
- **WHEN** другой пользователь (или этот же) добавляет в справочник категорию «new-project» и первый пользователь обновляет форму/фильтр
- **THEN** «new-project» присутствует в списках выбора категории (селект-поля следуют за данными, не за статикой)

#### Scenario: Негативный: статические и пустые списки не допускаются

- **GIVEN** в справочнике есть хотя бы одна категория
- **WHEN** пользователь открывает селект-поля категории в форме и в фильтре-конструкторе
- **THEN** ни одно из полей не показывает пустой или заранее захардкоженный список, не соответствующий данным хранилища (DEF-001 закрыт: поля тянут уникальные значения из данных)
