# search Specification

## Purpose
Поиск задач: вкладка с фильтрами по признакам и advanced-синтаксисом (AND, SQL-подобный), нормализация запроса, ошибки синтаксиса 400 с позицией; селект-поля фильтра заполняются из фактических данных.

## Requirements

### Requirement: Вкладка поиска старых задач

Вкладка поиска старых задач MUST работать как прежде (действующий контракт
поиска — без изменений) на токенах «Пульт» (заявка 1 «весь фронт»;
tokens-console.html): страница и результаты — поверхности `--p-bg-100/200`,
результаты — карточки с hover-ступенью bg3, даты/счетчики — mono, подсветка
совпадений — янтарная инверсия (фон `--p-amber-900`, текст `--p-amber-400`);
пустой результат — оформленное состояние «ничего не найдено» на токенах
(преемственность подсветки wiki-дерева); окно просмотра задачи из поиска —
тот же модальный стиль «Пульта», что и с доски (computed styles совпадают —
преемственность BUG-014).

#### Scenario: Переход на вкладку поиска через сайдбар

- **GIVEN** пользователь авторизован и видит сайдбар
- **WHEN** пользователь выбирает в сайдбаре раздел поиска
- **THEN** открывается вкладка поиска по старым задачам

#### Scenario: Выдача поиска отображает assigned и creator

- **GIVEN** пользователь авторизован; в системе есть задачи с исполнителями и без
- **WHEN** пользователь выполняет поиск без условий (или с условием)
- **THEN** каждая строка выдачи отображает creator и assigned; задачи без исполнителя — с курсивной строкой «Unassigned» (FR-45, ОВ-24)
#### Scenario: Результаты поиска на темной теме

- **GIVEN** поиск возвращает совпадения
- **WHEN** отображается вкладка поиска
- **THEN** карточки результатов на `--p-bg-200`, совпадения подсвечены
  янтарной инверсией (AA), даты mono; просмотр задачи из поиска визуально
  идентичен окну с доски

#### Scenario: Пустой результат оформлен

- **GIVEN** поиск не вернул совпадений
- **WHEN** отображается вкладка поиска
- **THEN** состояние «ничего не найдено» читаемо (AA) на токенах «Пульта»,
  без «голого» экрана

### Requirement: Фильтр-конструктор по признакам задачи

Фильтр-конструктор MUST работать как прежде (действующий контракт фильтров,
advanced-режим, подсказки — без изменений) на токенах «Пульт»:
select/инпуты — поля `--p-bg-200` с границей `--p-border` и cyan-фокусом,
нативные контролы темные (`color-scheme: dark`); кнопка «Найти» и кнопки
фильтров — единый стиль кнопок действия «Пульта» (янтарные первичные,
контурные вторичные, геометрия стабильна — преемственность P12 п.8); подписи
и микро-лейблы — капс mono где мокап задает; чипы выбранных фильтров —
контурные бейджи на токенах.

#### Scenario: Фильтр по одному признаку

- **GIVEN** в системе есть задачи с разными значениями признака «приоритет»
- **WHEN** пользователь выбирает в конструкторе значение приоритета и выполняет поиск
- **THEN** в результатах отображаются только задачи с выбранным приоритетом

#### Scenario: Фильтр по исполнителю

- **GIVEN** в системе есть задачи с исполнителем «wife» и без исполнителя
- **WHEN** пользователь выбирает в конструкторе фильтр по assigned со значением «wife» и выполняет поиск
- **THEN** в результатах отображаются только задачи с исполнителем «wife» (FR-46)

#### Scenario: Фильтр по создателю

- **GIVEN** в системе есть задачи, созданные «owner»
- **WHEN** пользователь выбирает в конструкторе фильтр по creator со значением «owner» и выполняет поиск
- **THEN** в результатах отображаются только задачи, созданные «owner» (FR-46)

#### Scenario: Фильтр «без исполнителя»

- **GIVEN** в системе есть задачи с исполнителями и без
- **WHEN** пользователь выбирает в конструкторе фильтр по assigned со значением «без исполнителя» (Unassigned) и выполняет поиск
- **THEN** в результатах отображаются только задачи без исполнителя (FR-46, ОВ-24)

#### Scenario: Подсказки значений фильтров assigned/creator — из БД

- **GIVEN** в системе есть задачи с assigned/creator у пользователей «owner» и «wife»
- **WHEN** пользователь раскрывает поля фильтров assigned и creator
- **THEN** значения подсказываются из уникальных значений соответствующих столбцов БД (owner, wife) — тот же механизм, что FR-35/DEF-001; статические списки не используются (FR-46)

#### Scenario: Комбинация условий по нескольким признакам

- **GIVEN** в системе есть задачи с различными комбинациями признаков
- **WHEN** пользователь задает условия по двум признакам одновременно (например, assigned + категория) и выполняет поиск
- **THEN** в результатах отображаются только задачи, удовлетворяющие обоим условиям

#### Scenario: Поиск без заданных условий

- **GIVEN** в системе есть архивные задачи
- **WHEN** пользователь выполняет поиск, не задавая ни одного условия
- **THEN** отображаются все задачи (пустой фильтр не ограничивает выборку)
#### Scenario: Форма фильтров на темной теме

- **GIVEN** пользователь открыл фильтр-конструктор
- **WHEN** форма отображается
- **THEN** поля на `--p-bg-200`, фокус cyan, select'ы рендерятся темными
  нативно, кнопка «Найти» — янтарная первичная; подсказки тегов/категорий
  работают как прежде

#### Scenario: Тесты поиска без цветовых правок проходят

- **GIVEN** редизайн применен
- **WHEN** прогоняются test_navigation_search_ui, test_search_r4_ui,
  test_search_suggestions_ui, test_bug014_search_task_view (нестилевые
  ассерты)
- **THEN** проходят без правок селекторов; стилевой ассерт BUG-014
  (совпадение computed styles окон) сохраняется на новых токенах

### Requirement: Режим advanced с SQL-подобным синтаксисом

Фильтр-конструктор MUST иметь кнопку переключения в режим advanced: текстовое поле с фильтром в SQL-подобном синтаксисе, доступное для просмотра и правки (FR-12). Переключение MUST синхронизировать фильтр между режимами: условие, собранное в конструкторе, отображается в advanced как текст; отредактированный текст применяется при поиске. В advanced-синтаксисе поля assigned и creator MUST быть доступны как поля задачи: условие вида `assigned = "<login>"`, `creator = "<login>"` и сравнение с NULL для поиска задач без исполнителя (FR-46; конкретика синтаксиса решает СА, дельта задает наблюдаемое поведение).

#### Scenario: Переключение конструктора в advanced

- **GIVEN** пользователь задал в конструкторе условия поиска
- **WHEN** пользователь нажимает кнопку переключения на advanced
- **THEN** отображается текстовое поле с текущим фильтром в SQL-подобном синтаксисе, соответствующим заданным условиям

#### Scenario: Фильтр по assigned в advanced

- **GIVEN** пользователь находится в режиме advanced
- **WHEN** пользователь вводит условие по полю assigned (например, `assigned = "wife"`) и выполняет поиск
- **THEN** результаты содержат только задачи с исполнителем «wife» (FR-46)

#### Scenario: Фильтр по creator в advanced

- **GIVEN** пользователь находится в режиме advanced
- **WHEN** пользователь вводит условие по полю creator (например, `creator = "owner"`) и выполняет поиск
- **THEN** результаты содержат только задачи, созданные «owner» (FR-46)

#### Scenario: Поиск задач без исполнителя в advanced

- **GIVEN** пользователь находится в режиме advanced; в системе есть задачи без исполнителя
- **WHEN** пользователь вводит условие `assigned IS NULL` (или эквивалент по принятому синтаксису) и выполняет поиск
- **THEN** результаты содержат только задачи без исполнителя (FR-46, ОВ-24)

#### Scenario: Правка фильтра в advanced и применение

- **GIVEN** пользователь находится в режиме advanced с отображенным фильтром
- **WHEN** пользователь правит текст фильтра и выполняет поиск
- **THEN** результаты соответствуют отредактированному фильтру

#### Scenario: Негативный: некорректный фильтр в advanced

- **GIVEN** пользователь находится в режиме advanced
- **WHEN** пользователь вводит синтаксически некорректный текст фильтра и выполняет поиск
- **THEN** система показывает сообщение об ошибке синтаксиса фильтра; данные при этом не изменяются и не удаляются

### Requirement: Поиск через API

Поиск MUST быть доступен программно через API в дополнение к веб-интерфейсу (FR-8): API-запрос поиска принимает условия фильтра и возвращает совпадающие задачи. Ответы поиска (builder и advanced) MUST содержать в каждой задаче поля assigned и creator (имена пользователей), чтобы выдача могла их отображать (FR-45, FR-46).

#### Scenario: Поиск через API с фильтром

- **GIVEN** вызывающий авторизован и в системе есть задачи с разными признаками
- **WHEN** вызывающий отправляет API-запрос поиска с условием по признаку
- **THEN** API возвращает только задачи, удовлетворяющие условию

#### Scenario: Поиск через API по assigned

- **GIVEN** вызывающий авторизован; в системе есть задачи с исполнителем «wife» и без
- **WHEN** вызывающий отправляет API-запрос поиска с условием по assigned = «wife»
- **THEN** API возвращает только задачи с исполнителем «wife», каждая с полями assigned и creator (FR-46)

#### Scenario: Негативный: поиск через API без авторизации

- **GIVEN** вызывающий не авторизован
- **WHEN** вызывающий отправляет API-запрос поиска
- **THEN** API отвечает 401 Unauthorized, результаты не возвращаются

### Requirement: Подсказки тегов и категорий в поиске

Вкладка поиска MUST предоставлять подсказки значений для полей фильтра-конструктора «Теги» и «Категория»: при фокусировке на поле пользователю предлагается общий список подсказок, привязанный к обоим полям (FR-15). Множество подсказок MUST быть объединением значений тегов и категорий **существующих задач** — без дублей; значение, встречающееся и в тегах, и в категориях, входит в список один раз; список MUST быть отсортирован по возрастанию (FR-16). В подсказки MUST попадать только уже заведенные варианты: теги удаленных задач (осиротевшие) не включаются; пустые/незаполненные категории не включаются; новые значения через подсказки не создаются — только выбор из существующих (FR-17). Получение подсказок MUST требовать авторизации: без действующей сессии — отказ 401 (FR-18, следствие NFR-7 основного ТЗ).

#### Scenario: Подсказки при авторизации — 200 и множество значений

- **GIVEN** пользователь авторизован и открыл вкладку поиска
- **WHEN** пользователь фокусируется на поле «Теги» или «Категория» фильтра-конструктора
- **THEN** подсказки получены через API с кодом 200 в виде множества значений (JSON-объект со списком подсказок), и datalist показывает их в поле

#### Scenario: Негативный: без сессии — 401

- **GIVEN** вызывающий не имеет действующей сессии
- **WHEN** вызывающий запрашивает подсказки через API
- **THEN** API отвечает 401 с телом `{"error": "unauthorized"}`; подсказки не возвращаются

#### Scenario: Set-семантика — значение из тегов и категорий входит один раз

- **GIVEN** значение «home» заведено и как тег, и как категория на существующих задачах
- **WHEN** пользователь запрашивает подсказки
- **THEN** «home» присутствует в списке подсказок ровно один раз (без дублей)

#### Scenario: Сортировка списка подсказок

- **GIVEN** заведены значения тегов и категорий в разном порядке
- **WHEN** пользователь запрашивает подсказки
- **THEN** список отсортирован по возрастанию

#### Scenario: Объединение источников — и теги, и категории

- **GIVEN** на существующих задачах заведены и теги, и категории
- **WHEN** пользователь запрашивает подсказки
- **THEN** список содержит и теги, и категории существующих задач

#### Scenario: Только заведенные — осиротевшие теги и пустые категории исключены

- **GIVEN** существует тег, оставшийся только у удаленных задач, и задача с пустой (незаполненной) категорией
- **WHEN** пользователь запрашивает подсказки
- **THEN** осиротевший тег и пустая категория в списке подсказок отсутствуют; список содержит только значения существующих задач

#### Scenario: Подсказки не создают новых значений

- **GIVEN** пользователь авторизован и открыл вкладку поиска
- **WHEN** пользователь работает с полями «Теги» и «Категория» через список подсказок
- **THEN** новые значения из подсказок не создаются — доступен только выбор из уже заведенных вариантов

#### Scenario: Datalist привязан к обоим полям

- **GIVEN** пользователь авторизован и открыл вкладку поиска
- **WHEN** пользователь поочередно фокусируется на полях «Теги» и «Категория» фильтра-конструктора
- **THEN** оба поля показывают один и тот же общий список подсказок (один общий список привязан к обоим полям, FR-15)

### Requirement: Селект-поля и подсказки заполняются из фактических данных

Селект-поля — выбор категории в форме задачи и в фильтре-конструкторе поиска — и подсказки MUST заполняться из фактических данных хранилища: уникальные значения соответствующих столбцов БД (допустимо предвычислять и хранить множество значений) (FR-30, FR-35, DEF-001). Статические или пустые списки значений в этих полях MUST НЕ использоваться. Требование доводится до фактического исполнения в реальной сессии: в авторизованной сессии пользователя на развернутой системе подсказки и селект-поля MUST отображать фактические значения из БД (подтверждение закрытия DEF-001 — диагностика на проде с сессией Заказчика; эндпоинт отвечает, но значения в UI не появляются — причина подлежит диагностике до фикса). Механизм MUST быть общим для селект-полей (категория, теги и будущие справочники). После внедрения справочника источник значений для категории — справочник (FR-19); для тегов и подсказок — множество уже заведенных значений существующих задач (FR-26, FR-15…FR-17). Жесткая/мягкая валидация значений не затрагивается — багфикс исполнения, не новая валидация.

#### Scenario: Выбор категории в форме заполняется из справочника

- **GIVEN** пользователь авторизован; в справочнике заведены категории «home», «work», «finance»
- **WHEN** пользователь открывает поле категории в форме задачи
- **THEN** список значений поля содержит ровно «home», «work», «finance» — фактическое содержимое справочника, а не статический захардкоженный список

#### Scenario: Выбор категории в фильтре-конструкторе заполняется из справочника

- **GIVEN** пользователь авторизован; в справочнике заведены категории «home», «work», «finance»
- **WHEN** пользователь раскрывает поле «Категория» в фильтре-конструкторе поиска
- **THEN** список значений содержит ровно «home», «work», «finance» — фактическое содержимое справочника

#### Scenario: Изменение данных отражается в селект-полях

- **GIVEN** пользователь авторизован; в справочнике есть категория «work»
- **WHEN** другой пользователь (или этот же) добавляет в справочник категорию «new-project» и первый пользователь обновляет форму/фильтр
- **THEN** «new-project» присутствует в списках выбора категории (селект-поля следуют за данными, не за статикой)

#### Scenario: Подсказки поиска показывают значения из БД в реальной сессии

- **GIVEN** пользователь авторизован в реальной сессии на развернутой системе; на существующих задачах заведены теги/категории со значениями, например «home» и «work»
- **WHEN** пользователь фокусируется на полях подсказок фильтра-конструктора поиска
- **THEN** подсказки в UI отображают фактические уникальные значения из БД («home», «work») — значения видны пользователю, а не только в ответе API (закрытие DEF-001 подтверждено в реальной сессии)

#### Scenario: Единый механизм для селект-полей и подсказок

- **GIVEN** в системе есть селект-поля (категория в форме и в фильтре) и подсказки (теги/категории поиска)
- **WHEN** выполняется осмотр источников их значений
- **THEN** все они используют один общий механизм получения уникальных значений соответствующих столбцов БД (допустимо предвычисленное множество); отдельные статические списки отсутствуют

#### Scenario: Негативный: статические и пустые списки не допускаются

- **GIVEN** в справочнике есть хотя бы одна категория
- **WHEN** пользователь открывает селект-поля категории в форме и в фильтре-конструкторе
- **THEN** ни одно из полей не показывает пустой или заранее захардкоженный список, не соответствующий данным хранилища (DEF-001 закрыт: поля тянут уникальные значения из данных)

### Requirement: Поиск на мобильном — одна колонка

На ширинах ≤480px страница поиска MUST перестраиваться в одну колонку:
инпут поиска, фильтр-конструктор (поля условий), advanced-режим и выдача —
вертикально, полной шириной (FR-103). Страница MUST NOT иметь горизонтальной
прокрутки; строка выдачи MUST читаться без обрезки и без зума (минимальный
вьюпорт 375px, NFR-26). Инпуты и селекты на ≤480px MUST иметь font-size
≥16px (NFR-24); интерактивные элементы (кнопки «Найти», добавление условия,
селекты) — тач-таргет ≥44×44px (NFR-23). Вид — по утвержденным мокапам
дизайн-фазы (FR-106). На ширинах >480px вид поиска НЕ меняется (NFR-29).

#### Scenario: Перестройка в одну колонку

- **GIVEN** пользователь авторизован; вьюпорт ≤480px (проверка 375×812,
  device-эмуляция)
- **WHEN** пользователь открывает вкладку поиска
- **THEN** инпут, фильтры и выдача расположены вертикально полной шириной;
  горизонтальной прокрутки страницы нет (NFR-26)

#### Scenario: Выдача читается без обрезки

- **GIVEN** поиск выполнен; в выдаче есть строки с задачами (assigned,
  creator, признаки)
- **WHEN** пользователь просматривает выдачу на вьюпорте 375px
- **THEN** каждая строка читается без обрезки и без зума (FR-103)

#### Scenario: Инпут без авто-зума и тач-таргеты

- **GIVEN** вкладка поиска открыта на вьюпорте ≤480px
- **WHEN** пользователь фокусирует инпут поиска и нажимает кнопки/селекты
- **THEN** инпут имеет font-size ≥16px — авто-зум iOS не включается
  (NFR-24); тач-таргеты интерактивных элементов ≥44×44px (NFR-23)

#### Scenario: Функции поиска не деградировали

- **GIVEN** вьюпорт ≤480px
- **WHEN** пользователь выполняет поиск фильтром, advanced-запросом и по
  подсказкам
- **THEN** все функции поиска работают как на desktop (поведение не
  меняется — меняется только представление, FR-103)

#### Scenario: Desktop-вид поиска не меняется

- **GIVEN** ширина вьюпорта >480px (проверка ≥1024px)
- **WHEN** пользователь открывает поиск
- **THEN** вид и поведение совпадают с существующими (NFR-29)
