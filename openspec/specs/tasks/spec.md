# tasks Specification

## Purpose
Задачи: CRUD через API, поля title/description/priority/tags, только создание и чтение без user-разграничения (общая доска), комментарии.

## Requirements

### Requirement: Создание задачи
Пользователь MUST иметь возможность создать задачу, указав как минимум ее название (FR-5). Создание задачи с прочими признаками или без них MUST быть возможно.

#### Scenario: Создание задачи только с названием
- **GIVEN** пользователь авторизован и открыл форму создания задачи
- **WHEN** пользователь вводит название и подтверждает создание
- **THEN** задача создается и появляется на доске в столбце «Ожидает»

#### Scenario: Создание задачи с заполненными признаками
- **GIVEN** пользователь авторизован и открыл форму создания задачи
- **WHEN** пользователь вводит название и заполняет другие признаки задачи (описание, приоритет, категория, срок, теги) и подтверждает создание
- **THEN** задача создается со всеми введенными признаками

#### Scenario: Негативный: создание без названия
- **GIVEN** пользователь авторизован и открыл форму создания задачи
- **WHEN** пользователь оставляет название пустым и подтверждает создание
- **THEN** задача не создается, пользователю показывается сообщение о необходимости названия

### Requirement: Признаки задачи
Задача MUST иметь признаки: название, описание, приоритет, категория, срок, комментарии, теги (FR-9). Признаки MUST отображаться и редактироваться в карточке задачи.

#### Scenario: Просмотр признаков в карточке
- **GIVEN** существует задача с заполненными признаками
- **WHEN** пользователь открывает карточку задачи
- **THEN** все заполненные признаки отображаются в карточке

#### Scenario: Редактирование признаков
- **GIVEN** пользователь открыл карточку существующей задачи
- **WHEN** пользователь изменяет значения признаков и сохраняет
- **THEN** измененные значения сохраняются и отображаются при последующем открытии карточки

#### Scenario: Комментарии к задаче
- **GIVEN** пользователь открыл карточку существующей задачи
- **WHEN** пользователь добавляет комментарий
- **THEN** комментарий сохраняется и отображается в карточке

### Requirement: Редактирование задачи
Пользователь MUST иметь возможность редактировать свою задачу (FR-7).

#### Scenario: Изменение названия существующей задачи
- **GIVEN** существует задача с известным названием
- **WHEN** пользователь изменяет название в карточке и сохраняет
- **THEN** новое название сохраняется и отображается на доске и в карточке

### Requirement: Удаление задачи
Пользователь MUST иметь возможность удалить свою задачу (FR-7).

#### Scenario: Удаление существующей задачи
- **GIVEN** существует задача на доске
- **WHEN** пользователь удаляет задачу и подтверждает удаление
- **THEN** задача исчезает с доски и больше не появляется ни в интерфейсе, ни в результатах поиска

### Requirement: Перемещение задачи через API
Функции доски и задач MUST быть доступны программно через API в дополнение к веб-интерфейсу (FR-8). API-вызовы MUST требовать авторизацию (см. домен auth).

#### Scenario: Создание задачи через API
- **GIVEN** вызывающий авторизован (имеет действующую сессию)
- **WHEN** вызывающий отправляет API-запрос создания задачи с корректным названием
- **THEN** API отвечает успехом, задача создается и видна на доске

#### Scenario: Негативный: создание задачи через API без обязательного поля
- **GIVEN** вызывающий авторизован
- **WHEN** вызывающий отправляет API-запрос создания задачи без названия
- **THEN** API отвечает ошибкой валидации (4xx), задача не создается

### Requirement: Данные не теряются при перезапуске сервера
Система MUST сохранять все данные задач при перезапуске сервера (NFR-3): после штатного перезапуска задачи, их признаки, статусы и комментарии MUST быть доступны в том же виде, что до перезапуска.

#### Scenario: Сохранность данных после перезапуска
- **GIVEN** в системе есть задачи в разных столбцах, fast-задача, комментарии
- **WHEN** сервер перезапускается штатно и пользователь открывает доску и заново входит (сессии не переживают рестарт — это допустимо)
- **THEN** все задачи, их статусы, признаки и комментарии отображаются без изменений и потерь

#### Scenario: Сохранность архива после перезапуска
- **GIVEN** в архиве есть завершенные задачи
- **WHEN** сервер перезапускается штатно
- **THEN** архивные задачи доступны на вкладке поиска в полном объеме

### Requirement: Автодополнение тегов в форме задачи

Форма задачи MUST иметь автодополнение в поле «Теги» (FR-26, FR-57): подсказки показывают ТОЛЬКО существующие теги проекта — начинаешь вводить, показываются совпадающие заведенные теги (ОВ-1). Категории в подсказках поля «Теги» MUST НЕ участвовать — у категории свой select (FR-57, ОВ-1). Источник подсказок — `GET /api/suggestions?kind=tags` (Д-14); контракт `GET /api/suggestions` без параметра не меняется (ОГР-26 — см. дельту suggestions). Автодополнение MUST работать в обоих режимах — при создании и при редактировании задачи. В отличие от подсказок поиска (там создание новых значений запрещено — FR-17), в форме задачи пользователь MUST иметь право выбрать существующее значение ИЛИ создать новое — явными действиями: выбор пункта дропдауна добавляет тег; при вводе значения, которого нет, дропдаун показывает явный пункт «+ Добавить тег „‹ввод›“» (FR-59, ОВ-2). Совпадение с подсказкой визуально подсвечивается, введенные теги из подсказок исключаются, выбранные теги видны чипами (FR-58; существующий UI чипов сохранен, источник истины — input не меняется, ОГР-27).

#### Scenario: Подсказки показывают только существующие теги проекта

- **GIVEN** пользователь авторизован, открыл форму задачи; на существующих задачах заведены теги «home» и «urgent» и категория «work»
- **WHEN** пользователь вводит текст в поле «Теги»
- **THEN** подсказки содержат только теги «home» и «urgent»; категория «work» в подсказках отсутствует (ОВ-1, FR-57, СЦ-1)

#### Scenario: Подсказки показывают заведенные значения

- **GIVEN** пользователь авторизован, открыл форму задачи; на существующих задачах заведены теги «home» и «urgent» и категория «work»
- **WHEN** пользователь открывает подсказки поля «Теги»
- **THEN** подсказки содержат заведенные значения из источника `?kind=tags` («home», «urgent»); категории в подсказках нет (ОВ-1, преемственность FR-26)

#### Scenario: Фильтрация по вводу

- **GIVEN** заведены теги «home», «urgent», «hardware»
- **WHEN** пользователь вводит «ur» в поле «Теги»
- **THEN** дропдаун показывает только совпадающие теги («urgent», «hardware»), несовпадающие («home») скрыты; совпавшая часть подсвечена (FR-58, СЦ-1)

#### Scenario: Исключение уже введенных тегов

- **GIVEN** тег «urgent» уже введен и виден чипом в форме
- **WHEN** пользователь продолжает вводить «ur» в поле «Теги»
- **THEN** «urgent» в дропдауне не предлагается (уже введен); другие совпадения показаны (FR-58, СЦ-2)

#### Scenario: Подсветка совпадения с подсказкой

- **GIVEN** заведены теги «urgent» и «hardware»
- **WHEN** пользователь вводит «ur»
- **THEN** в пунктах дропдауна совпадающая часть («ur») визуально подсвечена — как в Jira (FR-58)

#### Scenario: Выбор подсказки явным действием

- **GIVEN** подсказки содержат значение «work»
- **WHEN** пользователь выбирает «work» — кликом по пункту дропдауна или стрелками + Enter
- **THEN** значение «work» добавляется как тег задачи (в input/чипы); поле готово к вводу следующего тега (FR-59, СЦ-3)

#### Scenario: Создание нового значения — явный пункт «+ Добавить тег»

- **GIVEN** значения «newtag» нет среди подсказок (ни на одной существующей задаче)
- **WHEN** пользователь вводит «newtag» в поле «Теги»
- **THEN** дропдаун показывает явный пункт «+ Добавить тег „newtag“»; выбор пункта добавляет тег в input/чипы; после сохранения задачи тег заведен (get-or-create) и попадает в подсказки (FR-59, ОГР-27, СЦ-4)

#### Scenario: Подсказки работают в обоих режимах формы

- **GIVEN** пользователь авторизован; на существующих задачах заведены теги
- **WHEN** пользователь открывает форму создания и форму редактирования задачи и фокусируется на поле «Теги»
- **THEN** подсказки загружены и работают в обоих режимах (преемственность `loadTagHints()`)

#### Scenario: Set-семантика — без дублей

- **GIVEN** значение «home» заведено и как тег, и как категория на существующих задачах
- **WHEN** пользователь открывает подсказки поля «Теги»
- **THEN** «home» присутствует в списке подсказок ровно один раз (множество подсказок не содержит дублей)

#### Scenario: Выбор существующего значения

- **GIVEN** подсказки содержат значение «work»
- **WHEN** пользователь выбирает «work» из подсказок
- **THEN** значение «work» добавляется как тег задачи

#### Scenario: Создание нового значения, отсутствующего в подсказках

- **GIVEN** значения «newtag» нет среди подсказок (ни на одной существующей задаче)
- **WHEN** пользователь вводит «newtag» в поле «Теги» и сохраняет задачу
- **THEN** задача сохраняется с тегом «newtag» — в форме (в отличие от поиска) новое значение допустимо

#### Scenario: Сбой загрузки подсказок не блокирует ввод тегов

- **GIVEN** открыт дропдаун
- **WHEN** запрос подсказок завершается ошибкой
- **THEN** дропдаун не показан; ввод и сохранение тегов работают как прежде — ввод тегов не заблокирован (NFR-17, преемственность FR-26, СЦ-5)

#### Scenario: Негативный: подсказки формы требуют авторизации

- **GIVEN** вызывающий не имеет действующей сессии
- **WHEN** вызывающий запрашивает подсказки через API
- **THEN** API отвечает отказом авторизации (401); значения не возвращаются (следствие NFR-7 основного ТЗ)

#### Scenario: Логика сохранения тегов не изменилась

- **GIVEN** пользователь добавил теги через комбобокс (выбор подсказок и «+ Добавить тег»)
- **WHEN** задача сохраняется
- **THEN** payload не изменился: источник истины — input «Теги», отправка строкой через запятую в POST/PATCH, get-or-create на сервере (ОГР-27, СЦ-10)

### Requirement: Крестик закрытия формы в правом верхнем углу

Модальное окно формы задачи MUST иметь крестик закрытия, расположенный в правом верхнем углу окна (FR-28).

#### Scenario: Крестик закрывает форму

- **GIVEN** пользователь авторизован и открыл модальное окно формы задачи
- **WHEN** пользователь просматривает окно
- **THEN** крестик закрытия отображается в правом верхнем углу окна

#### Scenario: Нажатие крестика закрывает окно без сохранения

- **GIVEN** открыто модальное окно формы задачи с заполненными полями
- **WHEN** пользователь нажимает крестик в правом верхнем углу
- **THEN** окно закрывается без сохранения введенных значений

### Requirement: Визуал формы: приоритеты цветом и иконкой, состояния ошибок

Приоритеты (low/medium/high) MUST визуально различаться цветом и иконкой как в форме задачи, так и на карточке задачи (FR-29); иконки MUST быть выполнены inline SVG без внешних библиотек (ОГР-8, Д-4). Форма MUST отображать состояния ошибок: невалидные поля подсвечиваются, включая категорию при отклонении по жесткой валидации (FR-21). Форма MUST иметь единый визуальный стиль (сетка полей, типографика, анимация открытия/закрытия). Конкретный стиль выбирается Заказчиком из 2–3 вариантов до начала задачи 2.5 (Д-5); без выбора — текущий стиль плюс обязательный минимум (FR-28, цвета/иконки приоритетов, состояния ошибок).

#### Scenario: Приоритеты различимы цветом и иконкой

- **GIVEN** в системе есть задачи с приоритетами low, medium, high
- **WHEN** пользователь открывает форму задачи (список выбора приоритета) и карточки этих задач
- **THEN** каждый приоритет визуально различается и цветом, и иконкой — в форме и на карточке

#### Scenario: Иконки приоритетов не требуют внешних библиотек

- **GIVEN** страница формы задачи открыта
- **WHEN** пользователь просматривает загруженные ресурсы страницы
- **THEN** иконки приоритетов отрисованы inline SVG, внешние библиотеки иконок/шрифтов не подключаются (ОГР-8)

#### Scenario: Подсветка невалидной категории

- **GIVEN** пользователь заполняет форму задачи с категорией, которая была удалена из справочника (или значение отклонено серверной валидацией по FR-21)
- **WHEN** пользователь пытается сохранить задачу и сохранение отклоняется
- **THEN** поле категории визуально подсвечено как невалидное с сообщением об ошибке; задача не сохранена

#### Scenario: Анимация открытия и закрытия формы

- **GIVEN** пользователь авторизован и находится на доске
- **WHEN** пользователь открывает и закрывает форму задачи
- **THEN** окно открывается и закрывается с анимацией в рамках единого визуального стиля формы

### Requirement: Формы создания и редактирования по дизайну V3

Формы создания и редактирования задачи MUST быть приведены к дизайну V3 по всем зонам расхождения (FR-34, DEF-005): (1) вид выбранных тегов в форме; (2) оформление полей ввода (input/textarea) по токенам полей V3 — радиус, рамки, фокус-кольцо; (3) отображение выбранного приоритета (селект/иконки/цвет); (4) форма редактирования целиком — сверка с мокапом V3. Критерий приемки: формы создания/редактирования соответствуют мокапу V3 по токенам — цвета, радиусы, типографика, состояния; все интерактивные элементы форм MUST быть покрыты стилями (урок DEF-004). Соответствие не вводит новых функций и не меняет валидацию — только визуал и состояния.

**Изменение (r6, FR-60, Д-15):** визуальный проход по форме доводит консистентность по токенам V3 («Бумага») — состояния полей (hover/focus/ошибка), кнопки, отступы, типографика — по чек-листу Д-15 и живому макету в `design/`; логика, состав полей и валидация не меняются (рамка DEF-005).

**Изменение (r6, FR-61, ОВ-3):** форма задачи закрывается клавишей Escape — без сохранения, без потери данных на сервере (аналог «Отмена»); при несохраненных изменениях — подтверждение по паттерну существующих модалок (`window.confirm`).

**Изменение (r6, FR-62, ОВ-3):** форма адаптивна на узких экранах ≤480px — одна колонка, все поля full-width, без горизонтальной прокрутки.

**Изменение (r6, FR-63, ОВ-4):** в режиме редактирования всё управление задачей собрано в единую зону действий внизу формы (см. ADDED Requirement «Единая зона действий задачи»).

#### Scenario: Поля ввода оформлены по токенам полей V3

- **GIVEN** пользователь авторизован и открыл форму создания задачи
- **WHEN** пользователь осматривает поля ввода (input/textarea) и фокусируется на поле
- **THEN** поля оформлены по токенам полей V3 — радиус, рамки, фокус-кольцо; фокус отображается фокус-кольцом

#### Scenario: Выбранные теги отображаются по дизайну V3

- **GIVEN** пользователь открыл форму задачи и выбрал в поле «Теги» значения
- **WHEN** пользователь осматривает выбранные теги
- **THEN** выбранные теги отображаются по дизайну V3 (оформление выбранных значений — одна из зон расхождения DEF-005 устранена)

#### Scenario: Выбранный приоритет отображается по дизайну V3

- **GIVEN** пользователь открыл форму задачи
- **WHEN** пользователь выбирает приоритет (low/medium/high)
- **THEN** выбранный приоритет отображается по дизайну V3 (селект/иконки/цвет)

#### Scenario: Форма редактирования соответствует мокапу V3

- **GIVEN** пользователь открыл форму редактирования существующей задачи
- **WHEN** форма сверяется с мокапом V3 по токенам
- **THEN** цвета, радиусы, типографика и состояния формы соответствуют мокапу V3

#### Scenario: Негативный: все интерактивные элементы покрыты стилями

- **GIVEN** открыта форма создания или редактирования задачи
- **WHEN** пользователь осматривает все интерактивные элементы формы (поля, кнопки, крестики, селекты)
- **THEN** ни один интерактивный элемент не остался с дефолтным браузерным оформлением без стилей (урок DEF-004)

#### Scenario: Полиш не меняет логику и валидацию

- **GIVEN** визуальный проход по форме выполнен (FR-60, Д-15)
- **WHEN** пользователь выполняет обычные операции формы — создание, редактирование, валидацию ошибок (422), fast line, комментарии
- **THEN** логика, состав полей и валидация работают как прежде — изменился только визуал и состояния; регресс формы зеленый (FR-60, DEF-005, СЦ-7)

#### Scenario: Escape закрывает чистую форму сразу

- **GIVEN** открыта форма задачи (создание или редактирование), поля не тронуты
- **WHEN** пользователь нажимает Escape
- **THEN** форма закрывается сразу, без вопроса; данные на сервере не изменились (FR-61, ОВ-3, СЦ-8)

#### Scenario: Escape на грязной форме требует подтверждения

- **GIVEN** открыта форма задачи с несохраненными изменениями (поля отличаются от состояния на момент открытия)
- **WHEN** пользователь нажимает Escape
- **THEN** показывается подтверждение «Закрыть без сохранения?» (паттерн `window.confirm` существующих модалок); отмена → форма осталась с введенными значениями; подтверждение → форма закрыта без сохранения; данные на сервере не изменились (FR-61, СЦ-8)

#### Scenario: Адаптив одной колонкой на узких экранах

- **GIVEN** пользователь открыл форму задачи
- **WHEN** форма просматривается на экране шириной ≤480px (проверка ~375px)
- **THEN** форма перестроена в одну колонку, все поля full-width, модалка без горизонтальной прокрутки, все поля доступны; дропдаун подсказок позиционируется корректно (FR-62, ОВ-3, СЦ-9)

### Requirement: Кастомный комбобокс подсказок тегов

Автодополнение поля «Теги» MUST быть кастомным комбобоксом — полноценной заменой нативного datalist (ОВ-2, NFR-17): отклик на ввод ≤100 мс — фильтрация локальная, без запроса на каждый символ; навигация стрелками вверх/вниз + выбор Enter; Escape закрывает дропдаун; клик вне — закрытие. При сбое загрузки подсказок ввод тегов MUST НЕ блокироваться (преемственность FR-26). На тач-устройствах тап по пункту MUST выбирать значение; дропдаун MUST НЕ ломать скролл страницы (NFR-17). Доступность (NFR-18): поле «Теги» несет роль combobox, дропдаун — listbox с пунктами option; состояние раскрытия отражается aria-expanded; активный пункт навигации клавиатурой — aria-activedescendant; количество подсказок озвучивается скринридером. Значения в DOM MUST попадать только через textContent — не через innerHTML (XSS, преемственность dom.js и правил FR-29/FR-34).

#### Scenario: Отклик фильтрации локальный и быстрый

- **GIVEN** дропдаун комбобокса открыт, подсказки загружены
- **WHEN** пользователь вводит символы в поле «Теги»
- **THEN** фильтрация дропдауна выполняется локально на клиенте (без запроса на каждый символ) с откликом ≤100 мс (NFR-17)

#### Scenario: Клавиатурная навигация и выбор

- **GIVEN** дропдаун показывает подсказки
- **WHEN** пользователь перемещается стрелками вверх/вниз и нажимает Enter
- **THEN** активный пункт подсвечивается и перемещается, Enter выбирает активную подсказку (NFR-17, СЦ-6)

#### Scenario: Escape и клик вне закрывают дропдаун

- **GIVEN** дропдаун комбобокса открыт, форма задачи открыта
- **WHEN** пользователь нажимает Escape первый раз
- **THEN** закрывается только дропдаун — форма остается открытой; второе нажатие Escape закрывает форму (FR-61, СЦ-8); клик вне дропдауна также закрывает его (NFR-17)

#### Scenario: Тач — тап по пункту, скролл не сломан

- **GIVEN** форма задачи открыта на тач-устройстве (или в эмуляции)
- **WHEN** пользователь тапает по пункту дропдауна и скроллит страницу
- **THEN** тап выбирает значение; скролл страницы вне дропдауна не нарушен (NFR-17, СЦ-6)

#### Scenario: Aria-атрибуты комбобокса

- **GIVEN** пользователь открыл форму и фокусируется на поле «Теги»
- **WHEN** дропдаун раскрывается и пользователь navigирует стрелками
- **THEN** поле имеет роль combobox с aria-expanded, дропдаун — listbox с пунктами option, активный пункт — aria-activedescendant; количество подсказок озвучивается скринридером (NFR-18, ОВ-2, СЦ-6)

#### Scenario: Значения в DOM только через textContent

- **GIVEN** заведен тег, содержащий HTML-специальные символы (например, `<b>x</b>`)
- **WHEN** значение попадает в пункты дропдауна и чипы
- **THEN** значения отрисованы как текст через textContent — разметка не исполняется (XSS-safe, NFR-18)

### Requirement: Единая зона действий задачи

В режиме редактирования задачи всё управление задачей MUST быть собрано в одну визуальную зону/ряд внизу формы, а не разнесено по форме (FR-63, ОВ-4): `[Столбец ▾] [Сохранить] [Отмена] │ [Удалить]` — смена столбца, «Сохранить», «Отмена» и «Удалить» в одном визуальном блоке. Деструктивное действие «Удалить» MUST быть визуально отделено отступом от «безопасных» действий; подтверждение удаления сохраняется (`window.confirm`, FR-7). В режиме создания зоны `#task-actions` нет — блок скрыт (как сейчас), ряд действий — `[Создать] [Отмена]`. Идентификаторы элементов (`#task-form-submit`, `#task-form-cancel`, `#task-delete-button`, `#task-move-select`, `#task-actions`) MUST НЕ переименовываться — меняется разметка/раскладка, не контракт DOM (ОГР-28; e2e и unit-тесты цепляются по id).

#### Scenario: Состав и порядок зоны действий в редактировании

- **GIVEN** пользователь открыл форму редактирования задачи
- **WHEN** пользователь осматривает нижнюю часть формы
- **THEN** селект «Столбец», «Сохранить», «Отмена» и «Удалить» находятся в одном визуальном блоке-ряду в составе `[Столбец ▾] [Сохранить] [Отмена] │ [Удалить]`; кнопки управления задачей не разнесены по форме (FR-63, ОВ-4, СЦ-11)

#### Scenario: «Удалить» отделен отступом от безопасных действий

- **GIVEN** открыта форма редактирования с зоной действий
- **WHEN** пользователь осматривает кнопку «Удалить»
- **THEN** «Удалить» визуально отделена отступом от «Сохранить»/«Отмена»/селекта столбца (destructive отдельно) (FR-63, СЦ-11)

#### Scenario: Подтверждение удаления сохранено

- **GIVEN** открыта форма редактирования задачи
- **WHEN** пользователь нажимает «Удалить» и подтверждает удаление
- **THEN** задача удаляется после подтверждения `window.confirm` — механика удаления не изменилась (FR-7, FR-63, СЦ-11)

#### Scenario: Действия зоны работают

- **GIVEN** открыта форма редактирования задачи
- **WHEN** пользователь переключает столбец селектом, сохраняет задачу и отменяет правки
- **THEN** перенос столбца, сохранение и отмена работают как прежде — обработчики не переписывались, перенесена разметка (FR-63, ОГР-28, СЦ-11)

#### Scenario: В режиме создания зоны нет

- **GIVEN** пользователь открыл форму создания задачи
- **WHEN** пользователь осматривает форму
- **THEN** блок `#task-actions` скрыт; ряд действий — `[Создать] [Отмена]` (FR-63)

#### Scenario: Идентификаторы элементов не изменились

- **GIVEN** форма задачи открыта в любом режиме
- **WHEN** e2e и unit-тесты обращаются к элементам по id `#task-form-submit`, `#task-form-cancel`, `#task-delete-button`, `#task-move-select`, `#task-actions`
- **THEN** все элементы найдены по прежним id — контракт DOM не изменен (ОГР-28, преемственность FR-47, СЦ-11)

### Requirement: Escape-закрытие формы задачи

Форма задачи MUST закрываться клавишей Escape — закрытие без сохранения, без потери данных на сервере (аналог «Отмена») (FR-61, ОВ-3). При несохраненных изменениях в форме MUST запрашиваться подтверждение по паттерну существующих модалок (`window.confirm`, как «Удалить задачу?» в `task-form.js` / категория в `settings.js`): грязная форма → «Закрыть без сохранения?»; чистая форма (открыта и не тронута) — закрыть сразу, без вопроса. Признак «грязности» — diff полей относительно состояния на момент открытия. При открытом дропдауне комбобокса первое нажатие Escape MUST закрывать только дропдаун, второе — форму (см. «Кастомный комбобокс подсказок тегов»).

#### Scenario: Чистая форма закрывается сразу

- **GIVEN** открыта форма создания или редактирования, поля не тронуты
- **WHEN** пользователь нажимает Escape
- **THEN** форма закрывается сразу, без вопроса подтверждения (FR-61, СЦ-8)

#### Scenario: Грязная форма — подтверждение и обе ветки

- **GIVEN** открыта форма редактирования, пользователь изменил поля
- **WHEN** пользователь нажимает Escape
- **THEN** вопрос «Закрыть без сохранения?»; отмена → форма осталась открытой со значениями; подтверждение → форма закрыта без сохранения (FR-61, СЦ-8)

#### Scenario: Данные на сервере не изменились

- **GIVEN** пользователь редактировал задачу и закрыл форму по Escape (с подтверждением или без)
- **WHEN** пользователь открывает доску и карточку задачи
- **THEN** задача на сервере в прежнем виде — закрытие по Escape не сохранило изменений (FR-61, СЦ-8)

#### Scenario: Первый Escape при открытом дропдауне закрывает только дропдаун

- **GIVEN** открыта форма задачи и дропдаун комбобокса
- **WHEN** пользователь нажимает Escape дважды
- **THEN** первое нажатие закрывает дропдаун (форма открыта), второе — закрывает форму (по правилам чистой/грязной формы) (FR-61, СЦ-8)

#### Scenario: Escape не срабатывает при открытой view-модалке

- **GIVEN** открыта view-модалка карточки (read-only), форма задачи закрыта
- **WHEN** пользователь нажимает Escape
- **THEN** закрывается view-модалка по своей существующей логике (`task-detail.js`); форма задачи не открывается и не закрывается — guard «форма открыта, view не открыта» (FR-61)
