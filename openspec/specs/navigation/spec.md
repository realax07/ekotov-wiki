# navigation Specification

## Purpose
Навигация приложения сайдбаром: доска, поиск, wiki (заглушка todo), настройки; редирект неавторизованных на /login.

## Requirements

### Requirement: Навигация через сайдбар

Навигация по разделам MUST выполняться через левый сайдбар (действующий
контракт путей, прав доступа и активного раздела — без изменений) в визуале
утвержденного мокапа `design/redesign-pro/board-console.html` §sidebar:
сайдбар — панель `--p-bg-100` с правой границей `--p-border` в grid-раскладке
232px + 1fr; вверху — бренд `ekotov.wiki` с LED-точкой (teal, свечение) и
микро-подзаголовком капсом (mono, SYS-стиль); основная группа пунктов —
Доска, Wiki, Галерея, Видео, Погода, Поиск, Игры (7 пунктов, порядок и пути
без изменений), в футере сайдбара — Настройки и Профиль; каждый пункт —
inline-SVG-иконка 16px `stroke="currentColor"` + подпись 14px (`--p-text-600`),
hover — фон `--p-bg-200` + текст `--p-text-900`; активный раздел
(`aria-current="page"`) — фон `--p-bg-200`, текст `--p-text-900`, рамка
rgba-cyan 45%, иконка cyan и LED-точка cyan справа со свечением. Внизу
сайдбара МОЖЕТ быть блок kbd-подсказок (mono, отделенный границей; на
мобильной раскладке скрывается): блок декоративный (`aria-hidden`) и
перечисляет ТОЛЬКО хоткеи, реально обрабатываемые глобальным JS (глобальных
обработчиков `n`/`/`/`f` нет — подсказки к ним запрещены как ложный
аффорданс; появление хоткеев — отдельный change-пакет, design §D2).
DOM-хуки (классы `.sidebar`, `.nav-item`, `.nav-item-<page>`, id `#sidebar`,
aria-атрибуты) MUST сохраниться (ОГР-28). Ссылка «Мониторинг» (owner) и состав
пунктов по ролям — без изменений.

#### Scenario: Переход на доску через сайдбар
- **GIVEN** пользователь авторизован и находится на любой странице функционала
- **WHEN** пользователь выбирает в сайдбаре раздел «Доска»
- **THEN** открывается страница канбан-доски

#### Scenario: Переход на вкладку поиска через сайдбар
- **GIVEN** пользователь авторизован и находится на странице доски
- **WHEN** пользователь выбирает в сайдбаре раздел поиска
- **THEN** открывается вкладка поиска по старым задачам

#### Scenario: Сайдбар доступен со всех страниц функционала
- **GIVEN** пользователь авторизован
- **WHEN** пользователь открывает любую страницу функционала (доска, поиск)
- **THEN** сайдбар отображается и позволяет перейти в любой другой раздел

#### Scenario: Иконки у всех разделов сайдбара в едином стиле

- **GIVEN** пользователь авторизован и видит сайдбар
- **WHEN** пользователь осматривает разделы сайдбара (доска, поиск, wiki,
  настройки)
- **THEN** каждый раздел имеет иконку inline-SVG, стилистически единую с
  иконками «Мониторинг» и «Галерея»; порядок разделов, подписи и переходы
  работают как прежде (P12 п.9, FR-94) — в редизайне иконки соответствуют
  мокапу «Пульта» (16px, stroke currentColor)

#### Scenario: Иконки без внешних файлов

- **GIVEN** любая страница функционала отрисована
- **WHEN** проверяются сетевые запросы страницы
- **THEN** иконки разделов отрисованы inline-SVG — внешних файлов иконок
  нет (ОГР-8, FR-94)

#### Scenario: Сайдбар в визуале «Пульта»

- **GIVEN** пользователь авторизован и открыл доску
- **WHEN** проверяется сайдбар
- **THEN** панель на `--p-bg-100`, бренд с teal-LED, 7 пунктов основной группы
  + Настройки и Профиль в футере, иконки 16px inline-SVG; kbd-блок внизу —
  если присутствует, то aria-hidden и только с реально действующими хоткеями;
  цвета и отступы соответствуют мокапу board-console.html

#### Scenario: Активный раздел читается по cyan

- **GIVEN** открыт раздел «Доска»
- **WHEN** проверяется пункт «Доска»
- **THEN** у него `aria-current="page"`, фон `--p-bg-200`, cyan-рамка, cyan
  иконка и cyan-LED справа; остальные пункты — `--p-text-600` без подсветки

#### Scenario: Хуки навигации сохранены

- **GIVEN** редизайн применен
- **WHEN** прогоняются существующие web-тесты на навигацию (games_nav,
  navigation_search_ui, p12n004_sidebar_footer)
- **THEN** селекторы `.nav-item-*`, `#sidebar`, aria-атрибуты работают без
  правок тестов (ОГР-28)

### Requirement: Пустой раздел Wiki с пометкой todo
Сайдбар MUST содержать раздел «Wiki» (FR-13), ведущий на рабочую страницу `/wiki` — полноценный раздел wiki-функционала (FR-107…FR-116; функции определены в capability `wiki`). Won't прежнего релиза («пустой раздел с пометкой todo, wiki-функционал отсутствует») СНЯТ пакетом add-wiki (P15): раздел больше НЕ является заглушкой. Для авторизованного пользователя пункт «Wiki» MUST открывать `/wiki` — список корневых страниц с поддеревьями (дерево страниц, capability wiki). Для неавторизованного пользователя страница `/wiki` MUST выполнять редирект на `/login` (как остальные страницы функционала). Порядок разделов сайдбара НЕ меняется: «Wiki» остается третьим пунктом, перед «Галереей» (преемственность FR-85).

#### Scenario: Раздел Wiki отображается как полноценный
- **GIVEN** пользователь авторизован и видит сайдбар
- **WHEN** пользователь просматривает сайдбар и раздел Wiki
- **THEN** раздел «Wiki» присутствует в сайдбаре (пометки «todo» нет) и ведет на рабочую страницу `/wiki` со списком корневых страниц (FR-107); прежняя заглушка отсутствует

#### Scenario: Переход в Wiki через сайдбар
- **GIVEN** пользователь авторизован и находится на любой странице функционала
- **WHEN** пользователь выбирает в сайдбаре раздел «Wiki»
- **THEN** открывается страница `/wiki` — список корневых страниц с поддеревьями (FR-107); заглушки «todo» нет

### Requirement: Раздел «Настройки» в сайдбаре

Пункт «Настройки» (ведет на /settings) MUST оставаться в футере сайдбара рядом
с профилем/выходом (действующее поведение — без изменений) и MUST следовать
визуалу мокапа: иконка 16px `stroke="currentColor"`, подпись `--p-text-600`,
hover `--p-bg-200`, активное состояние — cyan по общему паттерну навигации;
геометрия active/focus фиксирована (текст не смещается — преемственность P12
п.1).

#### Scenario: Раздел настроек отображается внизу слева

- **GIVEN** пользователь авторизован и находится на любой странице функционала
- **WHEN** пользователь просматривает сайдбар
- **THEN** в сайдбаре присутствует раздел «Настройки», расположенный внизу слева, рядом с кнопкой выхода

#### Scenario: Переход в настройки через сайдбар

- **GIVEN** пользователь авторизован и видит сайдбар
- **WHEN** пользователь выбирает раздел «Настройки»
- **THEN** открывается страница настроек

#### Scenario: Раздел настроек доступен со всех страниц функционала

- **GIVEN** пользователь авторизован
- **WHEN** пользователь открывает любую страницу функционала (доска, поиск, настройки)
- **THEN** раздел «Настройки» отображается в сайдбаре и позволяет перейти на страницу настроек
#### Scenario: Пункт настроек в стиле «Пульта»

- **GIVEN** пользователь открыл /settings
- **WHEN** проверяется футер сайдбара
- **THEN** пункт «Настройки» активен по паттерну cyan, геометрия стабильна,
  ведёт на /settings (маршрут не менялся)

### Requirement: Профиль текущего пользователя внизу сайдбара

Блок профиля текущего пользователя (аватар, имя, ссылка на профиль) MUST
оставаться внизу сайдбара (действующее поведение — без изменений) в визуале
«Пульта»: панель на фоне сайдбара с верхней границей `--p-border`, имя —
`--p-text-900`, служебные подписи — `--p-text-500`, аватар — существующая
функциональность без изменений.

#### Scenario: Профиль отображается внизу сайдбара

- **GIVEN** пользователь авторизован (логин «owner», display_name не задан) и находится на любой странице функционала
- **WHEN** пользователь просматривает сайдбар
- **THEN** внизу сайдбара отображается профиль: кружок с буквой «o» (первая буква логина) и подпись с логином «owner» целиком (Д-10)

#### Scenario: Подпись профиля — display_name, если задан

- **GIVEN** пользователь авторизован и задал display_name в профиле (FR-40)
- **WHEN** пользователь просматривает сайдбар (после обновления страницы)
- **THEN** подписью блока профиля является display_name; логин остается идентификатором в tooltip'е (FR-43, Д-10)

#### Scenario: Аватар отображается в блоке профиля

- **GIVEN** пользователь авторизован и загрузил аватар (FR-42)
- **WHEN** пользователь просматривает блок профиля (после обновления страницы)
- **THEN** вместо кружка с первой буквой отображается загруженный аватар

#### Scenario: Клик по профилю открывает настройки пользователя

- **GIVEN** пользователь авторизован и видит блок профиля
- **WHEN** пользователь кликает по блоку профиля
- **THEN** открывается страница настроек пользователя (свой профиль, FR-39) — а не общий раздел «Настройки» со справочником категорий (ОГР-20)

#### Scenario: Профиль показывает сессионного пользователя

- **GIVEN** второй пользователь (жена владельца) авторизована в своей сессии
- **WHEN** второй пользователь открывает любую страницу функционала
- **THEN** внизу сайдбара отображается профиль второго пользователя — его подпись и его аватар (или кружок с первой буквой), не данные другого пользователя

#### Scenario: В профиле нет аватарок-файлов и смены пароля

- **GIVEN** пользователь авторизован и просматривает блок профиля (Релиз 4: ОГР-13 отменено решением Заказчика — ОГР-15)
- **WHEN** пользователь осматривает доступные действия блока профиля
- **THEN** загрузка аватарки, редактирование профиля и смена пароля доступны на открываемой кликом странице настроек пользователя (FR-39…FR-42) — прежнее исключение «в профиле НЕТ аватарок и смены пароля» (ОГР-13) больше не действует; сам блок профиля остается только отображением + переходом в настройки

#### Scenario: Профиль не нарушает верстку сайдбара

- **GIVEN** пользователь авторизован и находится на любой странице функционала
- **WHEN** пользователь просматривает сайдбар
- **THEN** блок профиля размещен внизу сайдбара и не вытесняет существующие разделы (доска, поиск, Wiki, настройки, выход)
#### Scenario: Блок профиля в визуале «Пульта»

- **GIVEN** пользователь авторизован
- **WHEN** проверяется низ сайдбара
- **THEN** блок профиля присутствует: аватар, имя t900, навигация в профиль
  работает; стили на токенах «Пульта»

### Requirement: Раздел «Галерея» в сайдбаре для всех

Сайдбар MUST содержать раздел «Галерея» — **ЧЕТВЕРТЫМ пунктом**, после
раздела «Wiki» (ОВ-3, FR-85). Раздел MUST вести на страницу галереи
(`/gallery`) и MUST отображаться **всем** авторизованным пользователям —
owner и PE паритетно, без рендера по роли (ОВ-4; преемственность
navigation: разделы сайдбара доступны на страницах функционала). Вид
пункта (иконка, состояния) — по мокапам ui_designer, утвержденным
Заказчиком ДО dev; после dev соответствие мокапам проверяет
design_validator (FR-86).

#### Scenario: Пункт «Галерея» — четвертый в сайдбаре

- **GIVEN** пользователь авторизован и находится на любой странице
  функционала
- **WHEN** пользователь просматривает сайдбар
- **THEN** присутствует раздел «Галерея» четвертым пунктом, после «Wiki»
  (порядок: Доска, Поиск, Wiki, Галерея); существующие разделы и блок
  профиля работают как прежде

#### Scenario: Оба пользователя видят раздел паритетно

- **GIVEN** владелец (owner) и второй пользователь (PE) авторизованы в
  своих сессиях
- **WHEN** каждый просматривает сайдбар
- **THEN** раздел «Галерея» присутствует у обоих — без разделения по
  роли (ОВ-4)

#### Scenario: Переход в галерею через сайдбар

- **GIVEN** пользователь авторизован
- **WHEN** пользователь выбирает раздел «Галерея» в сайдбаре
- **THEN** открывается страница галереи (`/gallery`): сетка превью,
  фильтры категория/тег, форма загрузки

#### Scenario: Вид пункта по утвержденным мокапам

- **GIVEN** мокапы интерфейса галереи утверждены Заказчиком (дизайн-фаза
  пакета)
- **WHEN** dev внедряет интерфейс
- **THEN** фактический вид сетки, карточек, full-screen просмотра, формы
  загрузки и пункта сайдбара соответствует утвержденным мокапам;
  соответствие проверяет design_validator (ревью против мокапов, FR-86)

### Requirement: Ссылка «Мониторинг» в сайдбаре для owner

Сайдбар MUST содержать ссылку «Мониторинг» в нижнем левом блоке
(`sidebar-footer`), рядом с разделом «Настройки» и кнопкой выхода (вводные
Заказчика: «В UI в нижнем левом углу сделай просто ссылку на нее»). Ссылка
MUST вести на `/netdata/` и открывать дашборд в новой вкладке
(`target="_blank"`). Ссылка MUST отображаться только пользователю с ролью
owner — рендер выполняется по роли из `GET /api/auth/me` (серверная
проверка доступа остается за nginx, см. capability monitoring); до получения
ответа и при 401 ссылка MUST NOT отображаться (паттерн блока профиля).
Пользователи с ролью PE и неавторизованные ссылку MUST NOT видеть.

#### Scenario: Owner видит ссылку и открывает дашборд

- **GIVEN** владелец (роль owner, логин `owner`) авторизован в wiki и
  находится на любой странице функционала
- **WHEN** он смотрит нижний левый блок сайдбара
- **THEN** присутствует ссылка «Мониторинг» рядом с «Настройки»/«Выйти»;
  клик открывает дашборд мониторинга в новой вкладке (FR-78)

#### Scenario: PE и неавторизованный ссылку не видят

- **GIVEN** пользователь с ролью PE авторизован (или сессии нет)
- **WHEN** любая страница функционала отрисована
- **THEN** ссылки «Мониторинг» в сайдбаре нет — существующие разделы и блок
  профиля работают как прежде (ОВ-2, FR-78)

#### Scenario: Скрытие ссылки не является границей доступа

- **GIVEN** пользователь PE знает адрес `/netdata/`
- **WHEN** он открывает его напрямую
- **THEN** доступ закрывает nginx basic auth (401 без кредов owner) —
  скрытие ссылки только удобство интерфейса (OV-2, преемственность
  monitoring: «Доступ к дашборду — только учетка owner через nginx»)

#### Scenario: Вид ссылки по утвержденному мокапу

- **GIVEN** мокап пункта сайдбара утвержден Заказчиком (дизайн-фаза пакета)
- **WHEN** dev внедряет ссылку
- **THEN** фактический вид (место, иконка, состояния hover/focus/active)
  соответствует утвержденному мокапу; соответствие проверяет design_validator
  (ревью против мокапа)

### Requirement: Мобильная навигация — бургер и drawer

На ширинах вьюпорта ≤768px сайдбар MUST скрываться и открываться по
кнопке-бургеру в шапке как выезжающая панель (drawer) с затемненной
подложкой (ОВ-2, FR-99). Навигация MUST переиспользовать существующий DOM
сайдбара — дублирование списка разделов НЕ допускается. Drawer MUST
закрываться: при выборе пункта, клике по подложке, повторном нажатии бургера
и по Escape. На ≤768px сцена контента MUST занимать всю ширину вьюпорта.
На ширинах >768px вид НЕ меняется (desktop-сайдбар сохраняется, NFR-29).

#### Scenario: Открытие drawer по бургеру

- **GIVEN** пользователь авторизован; ширина вьюпорта ≤768px (проверка
  375×812, device-эмуляция)
- **WHEN** пользователь нажимает кнопку-бургер в шапке
- **THEN** сайдбар выезжает как панель поверх затемненной подложки; все
  разделы (включая footer-зону профиля и Мониторинг для owner) доступны

#### Scenario: Закрытие drawer

- **GIVEN** drawer открыт
- **WHEN** пользователь выбирает пункт ИЛИ кликает по подложке ИЛИ нажимает
  бургер повторно ИЛИ нажимает Escape
- **THEN** drawer закрывается; при выборе пункта выполняется переход в
  соответствующий раздел

#### Scenario: Навигация не дублируется

- **GIVEN** страница открыта на ширине ≤768px
- **WHEN** проверяется DOM мобильного drawer
- **THEN** используется тот же список разделов, что и в desktop-сайдбаре —
  второго независимого списка навигации нет (единый источник, ОВ-2)

#### Scenario: Сцена занимает всю ширину

- **GIVEN** ширина вьюпорта ≤768px
- **WHEN** пользователь открывает любой раздел при закрытом drawer
- **THEN** контент занимает всю ширину вьюпорта — пустой колонки под
  скрытый сайдбар нет

#### Scenario: Desktop-вид не меняется

- **GIVEN** ширина вьюпорта >768px (проверка ≥1024px)
- **WHEN** пользователь работает с любым разделом
- **THEN** сайдбар постоянный, кнопки-бургера нет — вид совпадает с
  существующим desktop-поведением (NFR-29)

### Requirement: Индикация активного раздела на мобильном

При закрытой мобильной навигации пользователь MUST видеть, в каком разделе
находится: заголовок раздела в шапке (или эквивалентная читаемая метка) —
проверяемо на 375px (FR-100). Активный пункт в drawer MUST подсвечиваться
существующим стилем активного раздела.

#### Scenario: Активный раздел читаем при закрытом drawer

- **GIVEN** пользователь авторизован; вьюпорт 375×812; drawer закрыт
- **WHEN** пользователь находится в любом из разделов (доска, поиск, wiki,
  галерея, настройки)
- **THEN** в шапке отображается заголовок текущего раздела, читаемый на
  375px без зума

#### Scenario: Активный пункт в drawer подсвечен

- **GIVEN** пользователь находится в разделе «Поиск» на ширине ≤768px
- **WHEN** пользователь открывает drawer
- **THEN** пункт «Поиск» визуально выделен как активный (существующий стиль
  активного раздела сайдбара)

### Requirement: Мобильный вид разделов по утвержденным мокапам

Мобильный вид всех разделов (каркас, доска, модалка тикета, поиск,
настройки, лайтбокс) MUST соответствовать мокапам ui_designer, утвержденным
Заказчиком ДО dev (дизайн-фаза волна 0, преемственность FR-86/FR-90,
паттерн Р4/Р5); после dev соответствие мокапам проверяет design_validator
(FR-106).

#### Scenario: Мокапы утверждены до dev

- **GIVEN** пакет add-responsive-mobile в dev-фазе
- **WHEN** проверяется история утверждения мокапов
- **THEN** мокапы волны 0 утверждены Заказчиком до старта dev-задач
  (прецедент Д-5); фактический вид сверен design_validator'ом после dev

#### Scenario: Вид совпадает с мокапами

- **GIVEN** мокапы волны 0 утверждены; dev-задачи выполнены
- **WHEN** design_validator сверяет фактический мобильный вид на 375px с
  мокапами
- **THEN** токены, состояния и компоновка соответствуют эталону (вердикт
  approve) либо возвращены на доработку (return) с баг-репортами

### Requirement: Favicon страницы

Каждая страница системы MUST содержать favicon (P12 п.10, FR-95): иконка
в стиле V3 «Бумага» с терракотовым акцентом, объявленная inline-SVG data-URI
в базовом шаблоне — БЕЗ внешних файлов (ОГР-8). При изменении иконки URL
favicon MUST меняться (браузеры агрессивно кешируют favicon; политика
cache-busting — смена URL, паритет кеш-бастингу статики).

#### Scenario: Favicon присутствует на страницах

- **GIVEN** пользователь авторизован и открывает любую страницу функционала
- **WHEN** проверяется разметка страницы
- **THEN** присутствует `<link rel="icon">` с inline-SVG data-URI — иконка
  отображается во вкладке браузера (FR-95)

#### Scenario: Favicon без внешних файлов

- **GIVEN** любая страница системы отрисована
- **WHEN** проверяются сетевые запросы страницы
- **THEN** запросов внешних файлов favicon нет — иконка объявлена data-URI
  (ОГР-8, FR-95)

#### Scenario: Изменение иконки доходит до браузеров

- **GIVEN** иконка favicon изменена в новой версии
- **WHEN** пользователь открывает страницу после релиза
- **THEN** браузер получает favicon по новому URL (cache-bust) — отображается
  новая иконка без ручной очистки кеша (FR-95)

### Requirement: Мобильная раскладка каркаса (≤ 860px) (FR-131)

При ширине вьюпорта ≤ 860px каркас MUST перестраиваться по утвержденному
мокапу (board-console.html, `@media (max-width:860px)`): сайдбар переезжает
наверх одной колонкой, основная группа навигации — горизонтальная строка с
переносом, kbd-блок и LED активного пункта скрываются, содержимое получает
отступы 16px, hit-targets пунктов навигации ≥ 44px по высоте. Существующее
поведение бургера (`#burger-button`, `aria-expanded`, класс `sidebar-open`)
MUST сохраниться.

#### Scenario: Каркас на узком экране

- **GIVEN** вьюпорт 860px и меньше (мобильный профиль Playwright)
- **WHEN** открывается доска
- **THEN** сайдбар сверху с горизонтальной навигацией, kbd-блок скрыт,
  содержимое в одну колонку с отступами 16px, высота пунктов навигации ≥ 44px

#### Scenario: Пункты навигации кликабельны на тач

- **GIVEN** мобильный вьюпорт
- **WHEN** выполняется тап по пункту «Wiki»
- **THEN** переход происходит с первого тапа; hit-target ≥ 44px (проверка
  web-mobile набором)
