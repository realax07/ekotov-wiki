# fastline Specification

## Purpose
Быстрая линия: не более одной задачи в активной фазе, инвариант на создании и при возврате из архива/done, 409 при попытке второй; fast-задача при создании получает приоритет high, заблокированный для изменения (priority-lock, FR-27).

## Requirements

### Requirement: Выделенная линия fast line

Fast line MUST оставаться выделенной линией с действующим поведением (одна
fast-задача в активных статусах, назначение при создании/редактировании,
перенос вручную, комментарий, приоритетный порядок — без изменений) и MUST
читаться как сигнальный канал в визуале утвержденного мокапа
`design/redesign-pro/board-console.html` §fastline: панель над канбаном с
янтарной границей `--p-amber-400`, подложкой `--p-amber-900`, glow
`--glow-amber` и янтарными HUD-уголками; слева — микро-лейбл капсом
«Фастлайн · FST-код» (mono, `--tracking-micro`) с янтарной LED-точкой
(blink 2s step-end); задача — 14px 600 `--p-text-900`, под ней человекочитаемый
комментарий/служебная строка 400 `--p-text-600`; справа — mono-отсчет до срока
(«T-ЧЧ:ММ до срока»); внизу панели — трек отсчета: полоса 2px, фон
rgba-amber 16%, заполненная часть — градиент amber→cyan (доля = прошедшая
часть окна до дедлайна; градиент — на данных). Блок fastline в формах
создания/редактирования MUST следовать тем же токенам (янтарная сигнализация
на dark-полях). На ≤ 860px отсчет переносится под задачу (мокап).

#### Scenario: Fast line отображается на доске
- **GIVEN** пользователь авторизован и открыл доску
- **WHEN** пользователь просматривает доску
- **THEN** на доске присутствует визуально выделенная линия (янтарная
  сигнализация: граница, подложка, glow), отличимая от обычных столбцов
#### Scenario: Фастлайн — сигнальный янтарный канал

- **GIVEN** назначена fast-задача со сроком и комментарием
- **WHEN** пользователь открывает доску
- **THEN** панель фастлайна янтарная (граница, подложка, glow, HUD-уголки),
  FST-лейбл с мигающей LED, задача и комментарий читаемы (AA), T-отсчет
  набран mono, трек показывает прогресс градиентом amber→cyan

#### Scenario: Поведение fast line не изменилось

- **GIVEN** редизайн применен
- **WHEN** прогоняются тесты fastline (test_fastline_ui, test_board_fastline
  нецветовые ассерты, test_p23_fastline_mobile_ui)
- **THEN** единственность fast-задачи, блокировка приоритета, перенос и
  комментарий работают как прежде; DOM-хуки зоны сохранены

#### Scenario: Пустая fast line

- **GIVEN** fast-задача не назначена
- **WHEN** пользователь открывает доску
- **THEN** линия fast line не отображает задачу (действующее поведение); если
  панель показывается в пустом состоянии — без янтарного сигнала и LED-blink
  (сигнал только при наличии задачи)

#### Scenario: Фастлайн на мобильной раскладке

- **GIVEN** вьюпорт ≤ 860px и назначена fast-задача
- **WHEN** открывается доска
- **THEN** панель фастлайна складывается в столбец (лейбл, задача, отсчет),
  янтарная сигнализация сохранена, hit-targets не меньше 44px

#### Scenario: Fast-задачи исключены из канбана

- **GIVEN** в зоне есть fast-задача, в канбане — обычные задачи
- **WHEN** пользователь просматривает столбцы основного канбана
- **THEN** fast-задач среди них нет — все fast-задачи только в зоне FASTLINE

#### Scenario: Fast-задача выделяется визуально

- **GIVEN** fast-задача присутствует в зоне FASTLINE
- **WHEN** пользователь просматривает зону
- **THEN** задача читаема и отличается от обычных задач канбана (янтарная
  сигнализация редизайна)

### Requirement: Назначение задачи на fast line вручную при создании

Задача MUST назначаться на fast line вручную пользователем в момент создания задачи (FR-3, ОГР-5). Система MUST НЕ назначать задачи на fast line автоматически. Fast-задача при создании MUST получать приоритет «высокий» (high) автоматически, и пользователь MUST НЕ иметь возможности назначить fast-задаче другой приоритет (FR-27, решение Заказчика; ОГР-10): в интерфейсе поле приоритета для fast-задачи заблокировано; на уровне API/хранения fast-задача с приоритетом, отличным от high, MUST отклоняться ошибкой валидации. Fast и приоритет более не являются независимыми признаками.

#### Scenario: Создание задачи с назначением на fast line

- **GIVEN** пользователь авторизован, активных fast-задач нет
- **WHEN** пользователь при создании задачи отмечает назначение на fast line
- **THEN** задача создается как fast-задача с приоритетом «высокий» (high) и отображается на fast line

#### Scenario: Создание обычной задачи без fast line

- **GIVEN** пользователь авторизован
- **WHEN** пользователь создает задачу, не отмечая назначение на fast line
- **THEN** задача создается как обычная с выбранным пользователем приоритетом и не отображается на fast line

#### Scenario: Поле приоритета заблокировано в форме fast-задачи

- **GIVEN** пользователь авторизован и отмечает в форме создания задачи назначение на fast line
- **WHEN** пользователь просматривает поле приоритета
- **THEN** поле приоритета показывает значение «высокий» (high) и заблокировано для изменения (FR-27, UI-часть)

#### Scenario: Негативный: fast-задача с приоритетом не-high через API

- **GIVEN** вызывающий авторизован, активных fast-задач нет
- **WHEN** вызывающий отправляет API-запрос создания задачи с назначением на fast line и приоритетом «low» (или «medium», или NULL)
- **THEN** API отклоняет запрос ошибкой валидации; fast-задача не создается (FR-27, ОГР-10 — обход через API невозможен)

#### Scenario: Негативный: снятие блокировки в UI не меняет приоритет fast-задачи

- **GIVEN** вызывающий авторизован
- **WHEN** вызывающий отправляет подделанный клиентский запрос (минуя блокировку поля) на создание fast-задачи с приоритетом, отличным от high
- **THEN** запрос отклоняется серверной валидацией — приоритет fast-задачи не может отличаться от high ни при каких клиентских действиях

#### Scenario: Обычная задача с любым приоритетом не ограничена

- **GIVEN** вызывающий авторизован
- **WHEN** вызывающий создает обычную (не fast) задачу с приоритетом «low»
- **THEN** задача создается успешно с приоритетом «low» (ограничение действует только на fast-задачи)

#### Scenario: Существующие fast-задачи с не-high приоритетом приводятся в соответствие

- **GIVEN** до внедрения изменения в системе существует fast-задача с приоритетом, отличным от high
- **WHEN** выполняется внедрение изменения
- **THEN** инвариант «fast ⇒ priority=high» выполняется для всех fast-задач (существующие значения приведены в соответствие); после этого любая fast-задача в системе имеет приоритет high

### Requirement: Не более одной fast-задачи в активных статусах
В активных статусах («Ожидает» или «В работе») MUST находиться не более одной fast-задачи одновременно (FR-3, ОГР-5). Система MUST отклонять назначение второй fast-задачи, пока текущая находится в активном статусе.

#### Scenario: Негативный: вторая fast-задача при активной существующей — через интерфейс
- **GIVEN** на fast line находится fast-задача в статусе «Ожидает» (или «В работе»)
- **WHEN** пользователь пытается создать новую задачу с назначением на fast line
- **THEN** создание отклоняется, пользователю показывается сообщение, что fast line занята активной задачей; вторая fast-задача не создается

#### Scenario: Негативный: вторая fast-задача при активной существующей — через API
- **GIVEN** на fast line находится fast-задача в активном статусе
- **WHEN** авторизованный вызывающий отправляет API-запрос создания задачи с назначением на fast line
- **THEN** API отвечает ошибкой конфликта (409), задача не создается

#### Scenario: Повторная попытка после отказа
- **GIVEN** попытка создания второй fast-задачи была отклонена
- **WHEN** пользователь создает новую задачу без fast line
- **THEN** задача создается успешно как обычная

### Requirement: Освобождение fast line после завершения задачи
Когда fast-задача ушла в «Выполнено» (архив), MUST стать возможным назначить новую fast-задачу (FR-3, ОГР-5).

#### Scenario: Назначение новой fast-задачи после завершения предыдущей
- **GIVEN** fast-задача была в активном статусе и переведена в «Выполнено» (ушла в архив)
- **WHEN** пользователь создает новую задачу с назначением на fast line
- **THEN** создание выполняется успешно, новая fast-задача отображается на fast line

#### Scenario: Обычная задача не блокирует fast line
- **GIVEN** на fast line активной fast-задачи нет, но в «Ожидает»/«В работе» есть обычные задачи
- **WHEN** пользователь создает задачу с назначением на fast line
- **THEN** создание выполняется успешно — обычные задачи не влияют на правило ≤1

### Requirement: Приоритетный порядок прохождения fast line
По fast line задачи MUST идти в приоритете (FR-3): fast-задача выделяется среди прочих как первоочередная.

#### Scenario: Fast-задача выделяется визуально
- **GIVEN** на fast line есть активная fast-задача, на доске есть обычные задачи
- **WHEN** пользователь просматривает доску
- **THEN** fast-задача визуально выделена на fast line как первоочередная относительно обычных задач
