# gallery Specification

## Purpose

Галерея — раздел личной wiki для хранения и просмотра изображений (скриншоты,
диаграммы, фото): загрузка с валидацией (JPEG/PNG/GIF/WebP ≤10 МБ по magic-байтам),
сетка превью с фильтрами по категории/тегам, full-screen просмотр с листанием,
лайки и комментарии. Изображения обслуживаются отдельным сервисом images
(FastAPI, порт 8379): файлы — в томе images-data (вне БД, FR-79), метаданные —
в собственных таблицах gallery (владелец схемы — images; ядро их не читает,
обратная совместимость отката). Маршрутизация — nginx (images-семейство с
X-Service: images, деградация 503), отдача файлов — nginx из тома напрямую.

## Requirements

### Requirement: Изображения обслуживаются отдельным сервисом images

Загрузка, список и получение изображений MUST обслуживаться отдельным
контейнерным сервисом `images` (FR-79); маршруты `/api/images*` MUST NOT
содержаться в ядре (`app`). Для клиента URL не меняются — маршрутизацию
выполняет nginx. Сервис images MUST иметь healthcheck и MUST NOT публиковать
порты наружу (доступ — только через nginx-контейнер по существующему порту).
При недоступности сервиса images nginx MUST отвечать быстрым управляемым
503 (не таймаут), остальные маршруты MUST работать.

#### Scenario: Маршрутизация nginx на сервис images

- **GIVEN** прод-стек поднят (app, frontend, images, search, backup, netdata)
- **WHEN** авторизованный пользователь вызывает `/api/images` через nginx
- **THEN** запрос проксируется сервису `images`; запросы существующих
  маршрутов (`/api/tasks`, `/api/search`) обслуживаются как прежде

#### Scenario: Ядро без маршрутов изображений

- **GIVEN** стек поднят
- **WHEN** запрос `/api/images` приходит напрямую контейнеру `app` внутри сети
- **THEN** ответ 404/405 — маршрутов изображений в ядре нет

#### Scenario: Деградация при отказе images

- **GIVEN** стек поднят
- **WHEN** контейнер `images` остановлен
- **THEN** nginx отвечает 503 быстро на `/api/images*` (не таймаут);
  доска, поиск и страницы работают как прежде

### Requirement: Файлы изображений вне БД, в отдельном томе

Файлы загруженных изображений (оригиналы и превью) MUST храниться в
именованном томе `images-data` вне БД (FR-79); в БД MUST храниться только
метаданные. Образы контейнеров MUST NOT содержать пользовательские файлы
изображений. Файлы MUST отдаваться nginx по `/images/` из тома (паритет
отдаче аватаров) — сервис images не обязан участвовать в отдаче файлов.

#### Scenario: Загрузка сохраняет файл в том и метаданные в БД

- **GIVEN** авторизованный пользователь загружает валидный JPEG ≤ 10 МБ
- **WHEN** загрузка завершается успешно
- **THEN** оригинал и превью появились в томе `images-data` (файлы,
  не BLOB), в БД появилась запись метаданных (имя файла, mime, размер,
  загрузивший, время) — файл в БД отсутствует (FR-79)

#### Scenario: Файлы переживают пересоздание контейнеров

- **GIVEN** в томе `images-data` есть загруженные изображения
- **WHEN** контейнеры пересоздаются (`docker compose up -d` с новым образом)
- **THEN** все изображения доступны по `/images/...` без повторной
  загрузки — том переиспользуется

#### Scenario: Отдача файла nginx из тома

- **GIVEN** изображение загружено, имя файла известно
- **WHEN** клиент запрашивает `/images/<файл>`
- **THEN** nginx отдает файл из тома `images-data` с кеш-заголовками
  (паритет `/avatars/`) — обращения к сервису images не требуется

### Requirement: Категории и теги изображений

У изображения MUST быть опциональная категория — значение из справочника
категорий галереи (отдельного от справочника категорий задач, FR-80) и
ноль или более тегов из общего словаря тегов системы. При загрузке
пользователь MAY указать категорию и теги; новое имя категории/тега MAY
создаваться при загрузке. Список изображений MUST фильтроваться по
категории и/или тегу; фильтры MUST комбинироваться (изображение
удовлетворяет обоим условиям); пустой фильтр MUST показывать все
изображения.

#### Scenario: Загрузка с категорией и тегами

- **GIVEN** авторизованный пользователь загружает изображение с
  категорией «семья» и тегами «лето», «дача»
- **WHEN** загрузка завершается успешно
- **THEN** у изображения категория «семья» и два тега; новые значения
  («семья», «лето», «дача») при отсутствии созданы в справочнике/словаре

#### Scenario: Загрузка без категории и тегов допустима

- **GIVEN** авторизованный пользователь загружает изображение без
  категории и тегов
- **WHEN** загрузка завершается успешно
- **THEN** изображение сохранено с пустой категорией и без тегов и видно
  в общем списке

#### Scenario: Фильтр по категории

- **GIVEN** в галерее есть изображения категорий «семья» и «дом»
- **WHEN** пользователь фильтрует список по категории «семья»
- **THEN** показываются только изображения категории «семья»

#### Scenario: Фильтр по тегу

- **GIVEN** в галерее есть изображения с тегами «лето» и «зима»
- **WHEN** пользователь фильтрует список по тегу «лето»
- **THEN** показываются только изображения с тегом «лето»

#### Scenario: Комбинация фильтров категория+тег

- **GIVEN** в галерее есть изображения разных категорий и тегов
- **WHEN** пользователь задает одновременно категорию «семья» и тег «лето»
- **THEN** показываются только изображения, у которых категория «семья»
  И тег «лето»

#### Scenario: Пустой фильтр показывает все

- **GIVEN** в галерее есть изображения
- **WHEN** пользователь открывает галерею без фильтров
- **THEN** показываются все изображения

#### Scenario: Справочник галереи отделен от справочника задач

- **GIVEN** в справочнике задач есть категория «work», в галерее создана
  категория «семья»
- **WHEN** пользователь открывает список категорий в форме загрузки
  галереи
- **THEN** предложены категории галереи («семья»); категории задач
  («work») в списке галереи отсутствуют и наоборот — справочники
  независимы

### Requirement: Лайк/дизлайк — один голос пользователя

Авторизованный пользователь MAY ставить изображению голос «+1» (лайк) или
«−1» (дизлайк) (FR-81). У каждого пользователя MUST быть ровно один голос
на изображение; повторное действие MUST изменять голос, а не добавлять
новый; голос MUST сниматься повторным действием того же знака либо
явным снятием. Видны счетчики лайков/дизлайков и собственный голос
пользователя (для подсветки в UI).

#### Scenario: Постановка лайка

- **GIVEN** пользователь авторизован; изображение имеет 2 лайка / 1 дизлайк
- **WHEN** пользователь ставит лайк
- **THEN** счетчик лайков = 3, собственный голос пользователя = «+1»

#### Scenario: Смена голоса

- **GIVEN** пользователь поставил изображению лайк
- **WHEN** пользователь ставит дизлайк
- **THEN** лайк снят, дизлайк учтен — счетчики изменились ровно на один
  голос, собственный голос = «−1» (дублей голосов нет)

#### Scenario: Снятие голоса повторным действием

- **GIVEN** пользователь поставил изображению лайк
- **WHEN** пользователь повторно нажимает лайк
- **THEN** голос снят — счетчик лайков уменьшился, собственный голос
  отсутствует

#### Scenario: Негативный: без сессии реакция недоступна

- **GIVEN** вызывающий не имеет действующей сессии
- **WHEN** вызывающий ставит лайк через API
- **THEN** API отвечает 401, голос не учтен

### Requirement: Комментарии к изображениям

Авторизованные пользователи MUST видеть все комментарии изображения
(автор, время, текст) и MAY добавлять комментарий с непустым текстом
(FR-82). Пользователь MAY удалять ТОЛЬКО свой комментарий; попытка
удалить чужой MUST отклоняться.

#### Scenario: Добавление и просмотр комментария

- **GIVEN** пользователь авторизован, у изображения есть комментарии
- **WHEN** пользователь добавляет комментарий «Отличный кадр»
- **THEN** комментарий появился в списке с текстом, автором и временем;
  оба пользователя видят его

#### Scenario: Негативный: пустой комментарий отклоняется

- **GIVEN** пользователь авторизован
- **WHEN** пользователь пытается добавить комментарий из одних пробелов
- **THEN** добавление отклоняется (валидация), комментарий не создан

#### Scenario: Удаление своего комментария

- **GIVEN** пользователь добавил комментарий
- **WHEN** пользователь удаляет свой комментарий
- **THEN** комментарий исчез из списка

#### Scenario: Негативный: чужой комментарий удалить нельзя

- **GIVEN** второй пользователь добавил комментарий
- **WHEN** первый пользователь пытается удалить чужой комментарий
- **THEN** удаление отклоняется (запрещено) — комментарий остался

### Requirement: Full-screen просмотр с листанием

Клик по превью в сетке MUST открывать модальное окно на весь экран с
изображением (ОВ-3, FR-83). Листание MUST выполняться кнопками ←/→ и
клавишами стрелок; в окне MUST быть доступны лайк/дизлайк, скачивание
оригинала, комментарии И переименование файла (P12 п.11, FR-97): авторизованный
пользователь MAY изменить отображаемое имя (original_name) операцией
`PUT /api/images/{id}/name` — непустое имя ≤255 символов (422 при пустом или
отсутствующем, 401 без сессии, 404 для несуществующего изображения); новое имя
MUST отображаться в лайтбоксе и карточке сетки без перезагрузки страницы.
Физические файлы и путь `/images/…` MUST NOT меняться при переименовании.
Галерея MUST NOT содержать связей с трекером (ссылок на задачи, фильтров по
задачам) — общий элемент интерфейса только сайдбар (ОВ-3).

#### Scenario: Открытие full-screen просмотра

- **GIVEN** пользователь авторизован и видит сетку превью
- **WHEN** пользователь кликает по превью
- **THEN** открывается модальное окно на весь экран с этим изображением
  и панелью действий (лайк/дизлайк, скачать, переименовать, комментарии)

#### Scenario: Листание стрелками

- **GIVEN** full-screen просмотр открыт; в выдаче сетки несколько
  изображений
- **WHEN** пользователь нажимает → (или клавишу стрелки вправо)
- **THEN** показывается следующее изображение выдачи; ← — предыдущее;
  листание идет по текущей отфильтрованной выдаче

#### Scenario: Реакции и комментарий из окна просмотра

- **GIVEN** full-screen просмотр открыт
- **WHEN** пользователь ставит лайк и добавляет комментарий
- **THEN** счетчик лайков обновился, комментарий появился — действия
  окна просмотра работают без выхода из него

#### Scenario: Скачивание оригинала

- **GIVEN** full-screen просмотр открыт
- **WHEN** пользователь нажимает «скачать»
- **THEN** скачивается оригинальный файл (не превью) под исходным именем
  загрузки

#### Scenario: Переименование файла из окна просмотра

- **GIVEN** full-screen просмотр открыт у изображения «IMG_1234.jpg»
- **WHEN** пользователь вводит новое имя «Дача лето» и подтверждает
- **THEN** имя в лайтбоксе и на карточке сетки обновилось без перезагрузки;
  повторное открытие показывает новое имя (FR-97)

#### Scenario: Негативный: пустое имя переименования отклоняется

- **GIVEN** full-screen просмотр открыт
- **WHEN** пользователь отправляет переименование с пустым именем
  (или имя отсутствует в теле запроса)
- **THEN** `PUT /api/images/{id}/name` отвечает 422, имя не изменено (FR-97)

#### Scenario: Негативный: переименование без сессии

- **GIVEN** сессии нет
- **WHEN** вызывающий вызывает `PUT /api/images/{id}/name`
- **THEN** API отвечает 401, имя не изменено (FR-97)

#### Scenario: Негативный: переименование несуществующего изображения

- **GIVEN** изображение с указанным id не существует
- **WHEN** вызывающий вызывает `PUT /api/images/{id}/name`
- **THEN** API отвечает 404 (FR-97)

#### Scenario: Файлы не меняются при переименовании

- **GIVEN** изображение переименовано успешно
- **WHEN** пользователь скачивает файл и открывает `/images/<файл>`
- **THEN** скачивается тот же оригинал по прежнему пути — физические имена
  файлов и URL не изменились (FR-97)

#### Scenario: Закрытие окна просмотра

- **GIVEN** full-screen просмотр открыт
- **WHEN** пользователь нажимает Esc (или крестик)
- **THEN** окно закрылось, сетка галереи осталась в прежнем состоянии

#### Scenario: Галерея не связана с трекером

- **GIVEN** пользователь находится в галерее (сетка или full-screen)
- **WHEN** пользователь осматривает элементы интерфейса
- **THEN** ссылок на задачи, фильтров по задачам и переходов в трекер
  нет — из галереи в трекер ведет только общий сайдбар (ОВ-3)

#### Scenario: Листание свайпом по изображению

- **GIVEN** full-screen просмотр открыт на тач-устройстве (проверка
  device-эмуляция 375×812, синтетический touch-свайп)
- **WHEN** пользователь свайпает по изображению влево или вправо (сдвиг
  ≥50px, |dx| > |dy|)
- **THEN** показывается следующее/предыдущее изображение выдачи циклично —
  паритет листания стрелками (FR-105, ОВ-1/С3)
#### Scenario: Короткое или диагональное движение — это тап

- **GIVEN** full-screen просмотр открыт на тач-устройстве
- **WHEN** пользователь проводит по изображению короче порога (~50px) или
  с преобладанием вертикальной составляющей
- **THEN** листания нет — движение обрабатывается как тап (существующее
  поведение тапа не меняется)
#### Scenario: Скролл комментариев не перехватывается жестом листания

- **GIVEN** full-screen просмотр открыт; у изображения есть комментарии
  (панель скроллится)
- **WHEN** пользователь прокручивает панель комментариев вертикально
- **THEN** панель скроллится, листания изображений не происходит (жест
  привязан только к области изображения, FR-105)
#### Scenario: Desktop-способы листания не деградировали

- **GIVEN** full-screen просмотр открыт на desktop (≥1024px)
- **WHEN** пользователь листает стрелками-зонами и клавиатурой
- **THEN** листание работает как прежде — свайп-логика не влияет на
  desktop-поведение (NFR-29)

### Requirement: Доступ к галерее общий для всех пользователей

Оба пользователя системы (owner и PE) MUST иметь полный равноправный
доступ к галерее: просмотр всей галереи, загрузка, реакции, комментарии
(ОВ-4, FR-84). Разделение прав по пользователю/роли MUST NOT вводиться.
Неавторизованный доступ MUST отсутствовать: страница галереи без сессии —
редирект на `/login`, API — 401 (паттерн существующих страниц и API).

#### Scenario: PE видит и загружает как owner

- **GIVEN** пользователь PE авторизован
- **WHEN** он открывает галерею
- **THEN** доступна вся галерея и все действия (загрузка, лайк/дизлайк,
  комментарии) — паритет с owner, без ограничений по роли (ОВ-4)

#### Scenario: Негативный: без сессии страница недоступна

- **GIVEN** сессии нет
- **WHEN** клиент запрашивает страницу `/gallery`
- **THEN** выполняется редирект на `/login`; после входа галерея доступна

#### Scenario: Негативный: без сессии API недоступен

- **GIVEN** сессии нет
- **WHEN** клиент вызывает `/api/images` (список или загрузку)
- **THEN** API отвечает 401, данные не возвращаются

### Requirement: Лимиты загрузки

Загрузка MUST принимать файлы ≤ 10 МБ типов JPEG/PNG/GIF/WebP (NFR-21).
Превышение размера или недопустимый тип MUST отклоняться ошибкой 422 без
сохранения файла. Лимит nginx на локации загрузки MUST быть согласован с
лимитом сервиса (multipart-обвязка).

#### Scenario: Валидная загрузка принимается

- **GIVEN** пользователь загружает PNG 3 МБ
- **WHEN** загрузка выполняется
- **THEN** изображение сохранено и видно в галерее

#### Scenario: Негативный: превышение размера

- **GIVEN** пользователь загружает файл 12 МБ
- **WHEN** загрузка выполняется
- **THEN** отказ 422, файл не сохранен ни в том, ни в БД

#### Scenario: Негативный: недопустимый тип

- **GIVEN** пользователь загружает PDF с переименованием в .jpg
- **WHEN** загрузка выполняется
- **THEN** отказ 422 (тип проверяется по содержимому), файл не сохранен

### Requirement: Ресурсы сервиса изображений ограничены

Контейнер `images` MUST иметь лимит памяти 128m, healthcheck и стандартную
ротацию логов (json-file, 10m×3) — паритет остальному стеку (NFR-20).
Суммарные лимиты стека с images MUST сохранять резерв памяти хосту ≥ 2 GB
(преемственность deploy: «Лимиты памяти контейнеров»). Фактическое
потребление RAM MUST измеряться на стенде до прод-выкатки; стабильное
превышение лимита блокирует выкатку до решения Заказчика.

#### Scenario: Лимит images применен

- **GIVEN** полный стек с images поднят
- **WHEN** `docker stats --no-stream` выполняется
- **THEN** images работает в пределах 128m, суммарные лимиты стека —
  1.54 GB, резерв хосту ≥ 2 GB (NFR-20)

#### Scenario: Фактическое потребление измерено до прод-выкатки

- **GIVEN** стенд с images поднят
- **WHEN** фактическое потребление RAM images измеряется после загрузки
  изображений и генерации превью
- **THEN** значение зафиксировано в отчете задачи; стабильное превышение
  лимита блокирует прод-выкатку до решения Заказчика (NFR-20)

### Requirement: Сетка галереи держит ритм при разнопропорциональных изображениях

Сетка галереи MUST сохранять визуальный ритм при загрузке изображений
разных пропорций (P12 п.12, FR-98): ячейки MUST быть выровнены по единому
макету превью утвержденного варианта В (masonry, решение
2026-10-06-p12-design-approve); адаптив 2/3/4 колонки сохраняется; после
dev соответствие утвержденному мокапу MUST проверять design_validator
(преемственность FR-86).

#### Scenario: Разнопропорциональные загрузки не ломают сетку

- **GIVEN** в галерее загружены изображения разного соотношения сторон
  (квадрат, вертикальный портрет, панорама)
- **WHEN** пользователь открывает сетку галереи
- **THEN** все ячейки выровнены по единому макету (утвержденный вариант В —
  masonry) — ни одна плитка не растягивает ряд и не выбивается из ритма
  (FR-98)

#### Scenario: Вид превью соответствует утвержденному мокапу

- **GIVEN** вариант превью В (masonry) утвержден Заказчиком (решение
  2026-10-06-p12-design-approve, дизайн-фаза пакета)
- **WHEN** dev реализует сетку
- **THEN** фактический вид превью соответствует утвержденному варианту В
  (masonry) —
  соответствие проверяет design_validator (FR-98, преемственность FR-86)

#### Scenario: Адаптив колонок сохранен

- **GIVEN** сетка галереи открыта на разных ширинах окна
- **WHEN** ширина меняется (узкое/среднее/широкое)
- **THEN** сетка перестраивается 2/3/4 колонки как прежде, ячейки остаются
  выровненными по утвержденному макету превью (FR-98)
