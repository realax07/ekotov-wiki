## Requirements

### Requirement: Раздел «Погода» в сайдбаре и страница сервиса

Пункт «Погода» MUST отображаться в сайдбаре после «Видео» для всех
авторизованных пользователей (прецедент FR-85, ОВ-2) и вести на
страницу `/weather`. Страница `/weather` MUST рендериться ядром (Jinja
из `base.html`, `active_page='weather'`; паритет `/video`) —
статическая копия и синхронизация сайдбара MUST NOT использоваться.
Без сессии — редирект на `/login` (middleware ядра). Виджеты в других
разделах MUST NOT реализовываться (ОВ-3). Вид — по мокапу A
(`design/p18-weather/variant-a.html`).

#### Scenario: Пункт сайдбара виден авторизованным

- **GIVEN** авторизованный пользователь (owner или PE) открыл любую страницу
- **WHEN** сайдбар отрисован
- **THEN** в нем есть пункт «Погода» после «Видео» с иконкой в едином
  стиле (эталон «Видео»/«Галерея»), ведущий на страницу `/weather`

#### Scenario: Неавторизованный — редирект на login

- **GIVEN** сессия отсутствует
- **WHEN** пользователь открывает `/weather`
- **THEN** происходит редирект на `/login`; после входа раздел доступен

### Requirement: API погоды — только по сессии

Все маршруты API сервиса (`/api/weather*`) MUST требовать валидную
сессию (сессионный middleware, паттерн API-локаций images/video);
без сессии — 401 `{"error": "unauthorized"}` (NFR-7-паттерн, ОВ-1).
Анонимное получение данных погоды MUST NOT быть возможным.

#### Scenario: Негативный: /api/weather без сессии

- **GIVEN** запрос к `/api/weather` без валидной сессии
- **WHEN** middleware обрабатывает запрос
- **THEN** ответ 401 `{"error": "unauthorized"}`; обращений к провайдеру и
  к кэшу нет

### Requirement: Карточка «Сегодня» с 8 метриками

Карточка «Сегодня» MUST отображать 8 метрик текущей погоды по Москве
(ОВ-3, мокап A): температура, описание, «ощущается как», максимум и
минимум за день, осадки (%), ветер (румб + м/с), влажность (%),
давление (мм рт. ст.). Отсутствие отдельной метрики в ответе
провайдера MUST деградировать в прочерк («—»), не ломая карточку
целиком. Преобразования единиц — в сценариях и design §3.

#### Scenario: Полная карточка по мокапу A

- **GIVEN** провайдер вернул все текущие поля и daily-экстремумы
- **WHEN** авторизованный пользователь открывает `/weather`
- **THEN** карточка «Сегодня» показывает все 8 метрик в компоновке
  мокапа A; давление конвертировано из гПа в мм рт. ст., ветер —
  «ЮЗ, 5 м/с»-формата (румб по русским румбам, м/с), описание —
  по коду погоды провайдера, на русском

#### Scenario: Деградация при отсутствии метрики

- **GIVEN** поле давления в ответе провайдера отсутствует или null
- **WHEN** карточка «Сегодня» отрисована
- **THEN** в поле давления — прочерк («—»), остальные 7 метрик
  отображаются как обычно

### Requirement: Прогноз на 7 дней

Секция «Прогноз на неделю» MUST отображать 7 карточек-дней (включая
сегодня) с датой, описанием (иконка/текст), дневной и ночной температурой
(°C), вероятностью осадок (%) и ветром (направление + м/с) — по мокапу A
(сетка карточек 4-в-ряд). Дни MUST быть упорядочены по возрастанию даты,
названия дней и даты — в часовом поясе `Europe/Moscow`.

#### Scenario: Семь карточек с полным набором полей

- **GIVEN** провайдер вернул daily-прогноз на 7 дней
- **WHEN** секция «Прогноз на неделю» отрисована
- **THEN** показаны ровно 7 карточек, у каждой — дата, описание,
  дневная/ночная температура, осадки (%), ветер; порядок — по датам

#### Scenario: Сегодня входит в прогноз недели

- **GIVEN** данные получены в день X
- **WHEN** секция «Прогноз на неделю» отрисована
- **THEN** первая карточка соответствует дню X и согласована с карточкой
  «Сегодня» (максимум/минимум того же дня)

### Requirement: Провайдер Open-Meteo — параметры запроса

Единственным внешним провайдером MUST быть Open-Meteo Forecast API
(без ключа). Запрос MUST использовать фиксированные координаты Москвы
(55.7539, 37.6208), `timezone=Europe/Moscow`, `forecast_days=7`,
`wind_speed_unit=ms` (ветер сразу в м/с) и полный набор current/daily-
полей (перечень — в сценарии; `current.precipitation` (мм) НЕ
запрашивается — осадки карточки из daily[0], ревью №1 F2). Изменение
города или координат MUST NOT быть возможным через конфиг или API
(граница PLAN — один город).

#### Scenario: Запрос к провайдеру с зафиксированными параметрами

- **GIVEN** кэш истек и сервис запрашивает данные
- **WHEN** HTTP-запрос уходит к Open-Meteo
- **THEN** URL содержит latitude=55.7539, longitude=37.6208,
  timezone=Europe/Moscow, forecast_days=7, wind_speed_unit=ms и полный
  набор полей: current — температура, ощущается как, код погоды,
  влажность, давление, скорость и направление ветра; daily — код
  погоды, max/min температуры, вероятность осадок, максимальный
  ветер и доминирующее направление дневного ветра
  (wind_direction_10m_dominant); никаких других внешних вызовов сервис не делает

#### Scenario: Локальное время Москвы в данных

- **GIVEN** провайдер вернул прогноз с timezone=Europe/Moscow
- **WHEN** данные отображаются в UI
- **THEN** даты дней и время обновления показаны в московском времени
  независимо от таймзоны браузера

### Requirement: Кэш 60 минут

Успешный ответ провайдера MUST сохраняться в кэш-файле (том
`weather-cache`, атомарная запись) и переиспользоваться 60 минут
(ОВ-4): в течение TTL ответы `/api/weather` MUST отдаваться из кэша без
обращения к провайдеру. Кэш MUST содержать время получения
(`fetched_at`) и использоваться всеми пользователями сервиса (кэш общий,
не персональный).

#### Scenario: Повторные запросы в течение часа идут из кэша

- **GIVEN** кэш свежий (получен 5 минут назад)
- **WHEN** разные пользователи запрашивают `/api/weather` несколько раз
- **THEN** все ответы отдаются из кэша мгновенно; обращений к Open-Meteo
  нет; `fetched_at` одинаков во всех ответах

#### Scenario: Истечение TTL — обновление с провайдера

- **GIVEN** кэшу больше 60 минут, провайдер доступен
- **WHEN** поступает запрос `/api/weather`
- **THEN** сервис запрашивает Open-Meteo, обновляет кэш-файл и возвращает
  свежие данные с новым `fetched_at`; ответ переживает перезапуск
  контейнера (кэш-файл в томе)

### Requirement: Недоступность провайдера — кэш с флагом устаревания

При недоступности провайдера (сетевая ошибка, таймаут, 5xx) при
истекшем TTL сервис MUST отдать последний кэшированный ответ с явным
флагом устаревания (`stale: true`) — управляемая деградация, а не ошибка.
UI MUST показывать при этом баннер «данные устарели» с временем
последнего обновления. Провайдер, ответивший невалидным JSON или
неполными данными, приравнивается к недоступному (кэш НЕ затирается
битым ответом).

#### Scenario: Отдача устаревшего кэша при отказе провайдера

- **GIVEN** кэш старше 60 минут, Open-Meteo недоступен (таймаут/5xx)
- **WHEN** авторизованный пользователь запрашивает `/api/weather`
- **THEN** ответ 200 из кэша с `stale: true` и прежним `fetched_at`;
  UI показывает баннер «данные устарели» с временем обновления; кэш-файл
  не изменен

#### Scenario: Битый ответ провайдера не затирает кэш

- **GIVEN** кэш старше 60 минут, провайдер ответил 200 с невалидным JSON
- **WHEN** сервис обрабатывает ответ
- **THEN** невалидный ответ отброшен, кэш-файл сохранен, пользователь
  получает устаревшие данные с флагом `stale: true` (паритет отказу
  провайдера)

### Requirement: Пустой кэш и недоступный провайдер — честная ошибка UI

Если кэша нет (первый запуск, том пуст) И провайдер недоступен, сервис
MUST вернуть управляемую ошибку (503 с JSON-телом), а UI MUST показать
честное сообщение о недоступности данных погоды с возможностью повторить
загрузку. Выдуманные/нулевые заглушки вместо данных MUST NOT
отображаться. Кэш-файл при этом MUST NOT создаваться.

#### Scenario: Честное сообщение вместо данных

- **GIVEN** том `weather-cache` пуст (первый запуск), Open-Meteo
  недоступен
- **WHEN** авторизованный пользователь открывает `/weather`
- **THEN** API отвечает 503 с JSON-ошибкой; страница показывает сообщение
  «не удалось получить данные погоды» с кнопкой повторить; карточки с
  нулевыми/выдуманными данными не показываются

### Requirement: Таймауты провайдера и повтор при ошибке

Запрос к Open-Meteo MUST иметь таймаут 5 секунд (на соединение и чтение);
истечение таймаута приравнивается к ошибке провайдера. При ошибке MUST
выполняться ровно один автоматический повтор; после второй неудачи
срабатывает деградация (кэш с флагом / управляемая 503). Повторные
запросы MUST NOT выполняться дольше суммарных ~10–11 с, UI при ожидании
показывает индикатор загрузки. User-Agent запросов MUST задаваться в
конфиге сервиса (не дефолт HTTP-библиотеки).

#### Scenario: Таймаут считается ошибкой провайдера

- **GIVEN** Open-Meteo не отвечает (соединение установлено, ответа нет)
- **WHEN** истекают 5 секунд ожидания
- **THEN** запрос прерывается по таймауту, фиксируется ошибка провайдера
  (выполняется повтор, затем деградация); воркер сервиса не блокируется

#### Scenario: Ровно один автоматический повтор

- **GIVEN** первый запрос к провайдеру завершился ошибкой
- **WHEN** сервис обрабатывает неудачу
- **THEN** выполняется ровно один автоматический повтор; при успехе —
  данные сохраняются в кэш и отдаются пользователю (без флага stale);
  при второй неудаче — деградация (кэш/503)

### Requirement: Отдельный контейнерный сервис weather, кэш-файл в томе, без БД

Данные погоды MUST обслуживаться отдельным контейнерным сервисом
`weather` (FastAPI, `services/weather/`, порт 8381, по образцу
`services/video`): compose-контейнер за nginx, healthcheck, порты не
публикуются; при отказе сервиса nginx отвечает на `/api/weather*`
быстрым управляемым 503 (JSON + Retry-After), остальное MUST работать.
Сервис MUST работать БЕЗ БД: единственное состояние — кэш-файл в named
volume `weather-cache`; миграции для пакета MUST NOT создаваться.

#### Scenario: Маршрутизация и деградация

- **GIVEN** прод-стек поднят
- **WHEN** авторизованный пользователь вызывает `/api/weather`, затем
  контейнер `weather` останавливают
- **THEN** до остановки запрос проксируется сервису `weather`; после
  остановки nginx отвечает на `/api/weather*` быстрым 503 (JSON +
  Retry-After, не таймаут), доска/поиск/wiki/галерея/видео работают
  как прежде

#### Scenario: Кэш в томе переживает пересоздание контейнера

- **GIVEN** сервис успешно получил и закэшировал данные
- **WHEN** контейнер `weather` пересоздается (down/up)
- **THEN** кэш-файл присутствует в томе `weather-cache` и используется
  после старта (первый запрос не обязан идти к провайдеру до истечения
  TTL); в репозитории и БД данных погоды нет

#### Scenario: Миграций у пакета нет

- **GIVEN** деплой пакета выполняется на существующий стек
- **WHEN** проверяются миграции ядра
- **THEN** новых миграций пакет не добавляет (БД не трогается) —
  `MIGRATE_MODULE` ядра не изменяется пакетом

### Requirement: nginx-маршрутизация API погоды (только /api/weather*)

nginx MUST маршрутизировать к `weather:8381` только API-семейство
`/api/weather*`; страница `/weather` nginx'ом НЕ обслуживается (рендер
ядра). Локации API MUST NOT использовать `auth_request` — сессию
проверяет middleware сервиса (401 JSON; паттерн API-локаций video).
Резолв upstream — переменная + Docker DNS resolver (анти-stale-DNS,
старт без `weather` безопасен). `proxy_intercept_errors` MUST быть
off — 503 сервиса без подмены; отказ соединения — управляемый 503
nginx (JSON + Retry-After).

#### Scenario: API-семейство за middleware, деградация nginx

- **GIVEN** запросы к `/api/weather` выполняются без валидной сессии,
  затем — с валидной сессией при остановленном контейнере `weather`
- **WHEN** nginx обрабатывает запросы к `/api/weather*`
- **THEN** без сессии — 401 JSON от middleware сервиса (auth_request
  на API-локациях не используется); при остановленном контейнере —
  быстрый управляемый 503 nginx (JSON + Retry-After); честный 503
  `weather_unavailable` живого сервиса проходит до клиента без подмены

### Requirement: Вид интерфейса по утвержденному мокапу A

Вид страницы `/weather` (сайдбар-пункт, карточка «Сегодня», сетка
7 дней, состояния загрузки/ошибки/устаревания) MUST соответствовать
мокапу ui_designer **вариант A**, утвержденному Заказчиком 2026-10-19
ДО dev (Д-паттерн Р4/Р5, прецедент FR-86; варианты B/C —
не утверждены, не реализуются); соответствие после dev MUST
проверяться design_validator. Страница MUST работать без внешних
библиотек/CDN (ОГР-8, токены V3 «Бумага»).

#### Scenario: Дизайн по мокапу A и валидация после dev

- **GIVEN** мокап A утвержден Заказчиком 2026-10-19
- **WHEN** dev реализует страницу и design_validator сверяет вид
- **THEN** страница соответствует мокапу A (сетка карточек: «сегодня»
  сверху, 7 дней 4-в-ряд); мокапы B/C не реализованы; внешних
  библиотек/CDN на странице нет

### Requirement: Ресурсы и здоровье сервиса weather (NFR)

Контейнер `weather` MUST иметь healthcheck (`/api/health`), `mem_limit`
и ротацию логов (json-file 10m×3 — паритет стеку); суммарные лимиты
стека MUST сохранять резерв хосту ≥ 2 GB (прецедент NFR-20). Стабильное
превышение лимита на стенде блокирует выкатку до решения Заказчика.

#### Scenario: Здоровье и лимиты на стенде

- **GIVEN** контейнер `weather` запущен с mem_limit и healthcheck
- **WHEN** выполняется обычный профиль нагрузки (периодические запросы
  страницы и API) и проверяется стек
- **THEN** healthcheck отвечает, потребление RAM в пределах лимита;
  замеры зафиксированы в REPORT до выкатки

### Requirement: Отзывчивость при недоступности провайдера (NFR)

Пока провайдер недоступен (таймауты, повторы), синхронные операции
MUST сохранять отзывчивость: запрос `/api/weather` при отказе провайдера
MUST завершаться не дольше ~10–11 с (два таймаута 5 с) при наличии кэша —
быстрее (кэш без вызова провайдера); UI MUST NOT блокироваться;
остальные маршруты nginx работать как прежде.

#### Scenario: Замер отзывчивости при отказе провайдера

- **GIVEN** Open-Meteo недоступен, кэш отсутствует
- **WHEN** выполняется запрос `/api/weather` и параллельно открываются
  другие страницы wiki
- **THEN** запрос `/api/weather` завершается управляемой ошибкой не
  дольше ~11 с; другие разделы отвечают без деградации
