# deploy Specification

## Purpose

Контейнерный деплой ekotov-wiki: воспроизводимый релизный цикл (бэкап → build → миграция one-shot → healthy-подъем → смоук), лимиты памяти под VPS 3.9 GB, идемпотентные миграции из релизного образа и откат предыдущим тегом одним compose-up.

## Requirements

### Requirement: Монолит работает как контейнер без изменения кода

Система MUST работать в контейнерной топологии ЭТАПА 1: контейнер `app` (uvicorn, 1 воркер) исполняет текущий монолит без изменения логики кода (FR-64), контейнер `nginx` отдает статику `/static/*` и `/avatars/*` и является reverse proxy на `app:8377` с security-заголовками и gzip (FR-65). Все существующие маршруты `/api/*` и страницы Jinja2 MUST отвечать идентично systemd-проду. Наружу MUST публиковаться только контейнер `nginx` (published `10443:10443`); контейнер `app` MUST NOT публиковать портов наружу (паритет с текущим localhost-only :8377, FR-65).

#### Scenario: Маршруты API отвечают идентично systemd-проду

- **GIVEN** контейнерный стек поднят (nginx → app → том данных), пользователь авторизован
- **WHEN** пользователь выполняет любой существующий запрос к `/api/*` (чтение доски, создание/перемещение задачи, поиск)
- **THEN** ответы идентичны ответам systemd-прода по коду, контракту тела и инвариантам (fast line, валидация категории) — внешнее поведение не изменилось (FR-64)

#### Scenario: Наружу открыт только nginx

- **GIVEN** контейнерный стек поднят на VPS
- **WHEN** клиент обращается снаружи по `https://<host>:10443`
- **THEN** запрос обслуживает контейнерный nginx (статика с кеш-заголовками, страницы и API — через proxy на app) (FR-65)

#### Scenario: app недоступен снаружи напрямую

- **GIVEN** контейнерный стек поднят
- **WHEN** клиент снаружи пытается обратиться напрямую к порту контейнера `app` (8377)
- **THEN** соединение отклоняется — порт `app` не опубликован на хост (паритет localhost-only, FR-65)

### Requirement: Данные SQLite и аватары в именованном томе

Данные SQLite (`wiki.db`) и каталог `avatars/` MUST жить в именованном томе `wiki-data` вне образов (FR-66; урок rsync-инцидента C-1 — данные не в образе). Контейнер `app` MUST иметь к тому доступ RW. Образы контейнеров MUST NOT содержать пользовательские данные.

#### Scenario: Данные переживают замену контейнеров

- **GIVEN** в томе `wiki-data` есть задачи, сессии и аватары пользователей
- **WHEN** контейнеры `app` и `nginx` пересоздаются (`docker compose up -d` с новым образом)
- **THEN** после подъема все данные, включая аватары по `/avatars/*`, доступны без восстановления — том переиспользуется (FR-66)

#### Scenario: Образ не содержит пользовательских данных

- **GIVEN** образ `app` собран
- **WHEN** образ инспектируется
- **THEN** в нем нет `wiki.db`, каталога `avatars/` и каких-либо пользовательских данных — только код и зависимости (FR-66, урок C-1)

### Requirement: Прод и стенд на одном образе

Деплой-конфигурация MUST состоять из `deploy/compose.yaml` (прод-топология) и `deploy/compose.test.yaml` (стенд) (FR-67). Стенд MUST использовать временный том БД, seeded-пользователя и другой порт; прод и стенд MUST использовать один и тот же образ, различаясь только env и томами (dev/prod паритет, NFR-10). Топология стенда MUST воспроизводить прод-топологию: nginx → app → SQLite-том.

#### Scenario: Стенд воспроизводит прод-топологию

- **GIVEN** стенд поднят из `deploy/compose.test.yaml`
- **WHEN** запрос проходит через стенд
- **THEN** цепочка обслуживания — nginx-контейнер → app-контейнер → SQLite на временном томе, та же топология, что прод, но другой порт и временный том (FR-67, NFR-10)

#### Scenario: Один образ на обоих контурах

- **GIVEN** собран образ релиза
- **WHEN** поднимаются прод и стенд
- **THEN** оба контура используют один и тот же тег образа; различия — только переменные окружения и тома (NFR-10)

#### Scenario: Временный том стенда не трогает прод-данные

- **GIVEN** прод работает на томе `wiki-data`
- **WHEN** стенд поднимается и прогоняет тесты
- **THEN** прод-данные не изменяются — стенд пишет только в свой временный том (FR-67)

### Requirement: Машинный контракт OpenAPI включен и зафиксирован

Монолит MUST предоставлять машинную схему API: `openapi_url="/openapi.json"` включен; схема MUST NOT раскрываться публично — без действующей сессии доступ к схеме MUST завершаться редиректом на login (302) или 401 (поведение существующего middleware, которое не меняется — FR-68); `docs`/`redoc` MUST оставаться выключенными. Зафиксированная схема MUST храниться в `contracts/openapi.json` и обновляться той же выкаткой, что изменение схемы (монорепо, план §3).

#### Scenario: Схема доступна под сессией

- **GIVEN** вызывающий авторизован
- **WHEN** вызывающий запрашивает `/openapi.json`
- **THEN** ответ 200 с валидным OpenAPI-документом, описывающим все маршруты `/api/*` (FR-68)

#### Scenario: Негативный: без сессии схема не раскрывается публично

- **GIVEN** вызывающий не имеет действующей сессии
- **WHEN** вызывающий запрашивает `/openapi.json`
- **THEN** схема не раскрывается публично: редирект на login (302) или 401 — без изменения middleware (FR-68, преемственность NFR-7)

#### Scenario: docs/redoc остаются выключенными

- **GIVEN** монолит работает (контейнерно или на systemd)
- **WHEN** вызывающий запрашивает `/docs` и `/redoc`
- **THEN** ответы не отдают интерактивную документацию — эндпоинты выключены, как и до пакета (FR-68)

#### Scenario: Зафиксированная схема соответствует коду

- **GIVEN** в `contracts/openapi.json` зафиксирована схема релиза
- **WHEN** схема экспортируется из работающего приложения того же релиза
- **THEN** экспорт совпадает с зафиксированным файлом — расхождение означает незакрытую правку контракта (план §3, фундамент CI-gate ЭТАПА 2)

### Requirement: Сквозные тесты против compose-стенда

Система MUST иметь e2e-сьют в `e2e/` монорепо против compose-стенда (та же база playwright, что `tests/web`) (FR-69). Сьют MUST проверять поведение реального nginx-контейнера: заголовки кеша статики, gzip, security-заголовки — проверяются тестом, а не только прод-смоуком. Сьют MUST быть запускаемым одинаково локально и в CI.

#### Scenario: Заголовки кеша статики проверяются тестом

- **GIVEN** compose-стенд поднят
- **WHEN** e2e-сьют запрашивает файл статики через nginx-контейнер
- **THEN** ответ содержит кеш-заголовки nginx (`expires 7d`) — заголовки проверены тестом против реального nginx, а не эмуляции `http.server` (FR-69, закрытие риска architecture/map.md §6.1)

#### Scenario: Gzip и security-заголовки проверяются тестом

- **GIVEN** compose-стенд поднят
- **WHEN** e2e-сьют запрашивает страницу и статик-ресурсы
- **THEN** ответы содержат gzip-кодирование и security-заголовки конфига nginx — впервые покрыто автотестом, а не только прод-смоуком (FR-69)

#### Scenario: Сьют воспроизводим локально и в CI

- **GIVEN** чистая машина разработчика / CI-раннер с Docker
- **WHEN** запускается `docker compose -f deploy/compose.test.yaml up --build` и затем e2e-сьют
- **THEN** сьют проходит против стенда одинаково в обоих окружениях — без доступа к прод (FR-69, план §4)

### Requirement: Миграции БД — one-shot до подъема нового app

Миграции MUST выполняться one-shot из образа ядра строго до подъема app; сервисы-читатели
(search, backup) не выполняют миграций и поднимаются после healthy ядра.
Порядок матрицы: бэкап → build всех сервисов → миграция ядра → up app → healthy →
up search/backup → healthy → смоук-матрица (health×2, поиск через nginx, статика,
аватары, 502=0, релизные теги).

#### Scenario: Миграция выполняется из того же образа до подъема

- **Когда** деплой стартует
- **то** миграция выполняется one-shot контейнером из того же образа, что и app,
  строго до `up` app.

#### Scenario: Идемпотентность — повтор не ломает

- **Когда** миграция выполняется повторно на уже мигрированной БД
- **то** повтор завершается успехом без изменения данных (sha256-контроль сценариев).

#### Scenario: Репетиция на копии прод-БД обязательна

- **Когда** готовится новый migration-шаг
- **то** репетиция выполняется на свежей копии прод-БД до релиза.

#### Scenario: Падение миграции прерывает деплой

- **Когда** миграция ядра падает
- **то** деплой прерван ДО up любого сервиса, читатели не поднимаются, работает предыдущий стек.

#### Scenario: Порядок деплоя матрицы

- **Когда** деплой выполняется с матрицей сервисов
- **то** search/backup стартуют только после `healthy` ядра.

### Requirement: Бэкап тома до каждого деплоя

Перед каждым деплоем MUST выполняться бэкап тома данных: консистентная копия БД (метод `sqlite3`-бэкапа — python-модуль `sqlite3` через `docker exec` в контейнер `app` либо one-shot-контейнер из того же образа: sqlite3 CLI в python:3.12-slim отсутствует) плюс копия каталога `avatars/`, без остановки сервиса (FR-71; урок Р4 — аватары в том же контуре, что БД). Конкретный метод и путь бэкапа MUST быть зафиксированы в `deploy/RUNBOOK.md` и проверены dry-run'ом до первой боевой выкатки. Откат данных MUST выполняться из этого пред-деплойного бэкапа.

#### Scenario: Бэкап перед деплоем без остановки

- **GIVEN** прод работает из контейнеров, готовится деплой нового тега
- **WHEN** деплой начинается
- **THEN** первым шагом создается консистентный бэкап: БД — python-модуль `sqlite3` (`.backup`) через `docker exec` в контейнер `app` (sqlite3 CLI в slim-образе отсутствует), аватары — tar каталога тома; сервис при этом продолжает отвечать (FR-71)

#### Scenario: Возврат пары код+БД при откате

- **GIVEN** деплой выполнен, обнаружен дефект, требующий отката несовместимой схемы
- **WHEN** выполняется откат
- **THEN** восстанавливается БД из пред-деплойного бэкапа вместе с возвратом к предыдущему тегу образа — откат парой «код+БД» (FR-71, FR-72)

### Requirement: Откат предыдущим тегом образа

Образы MUST тегироваться по релизу (`ekotov-wiki/app:<release>`); тег `latest` MUST NOT использоваться (FR-72). Откат MUST выполняться повторным подъемом предыдущего тега; при несовместимой схеме — вместе с возвратом БД из пред-деплойного бэкапа (пара «код+БД»).

#### Scenario: Откат одним действием

- **GIVEN** в бою тег `<release-2>`, предыдущий боевой тег — `<release-1>`
- **WHEN** требуется откат кода
- **THEN** стек поднимается с тегом `<release-1>` — без пересборки (FR-72)

#### Scenario: Негативный: latest запрещен

- **GIVEN** описывается или выполняется деплой
- **WHEN** конфигурация ссылается на образ по тегу `latest`
- **THEN** конфигурация недопустима — только явные теги релизов (FR-72; вопрос «тот ли образ в бою» решается проверкой тега)

#### Scenario: Откат при несовместимой схеме

- **GIVEN** релиз включал несовместимую миграцию схемы
- **WHEN** выполняется откат на предыдущий тег
- **THEN** БД восстанавливается из пред-деплойного бэкапа вместе с предыдущим тегом — откат парой «код+БД», прежний откат rsync-снапшотом не используется (FR-72, план §5)

### Requirement: Лимиты памяти контейнеров

Лимиты памяти MUST быть: app 512m, frontend 64m, search 512m, backup 64m,
netdata 256m, images 128m — суммарно 1.54 GB, резерв хосту (VPS 3.9 GB)
≥ 2.3 GB (проверка резерва ≥ 2 GB сохраняется; NFR-20).

#### Scenario: Лимиты применены

- **Когда** контейнеры подняты
- **то** каждый работает в пределах своего mem_limit.

#### Scenario: Хост сохраняет резерв памяти

- **Когда** полный стек работает
- **то** свободная память хоста сохраняет резерв для пиков.

#### Scenario: Лимиты применены (матрица)

- **Когда** полный стек работает
- **то** `docker stats --no-stream` каждого контейнера (включая netdata и
  images) в пределах лимита, свободная память хоста ≥ 2 GB.

### Requirement: TLS self-signed монтируется томом

Контейнерный nginx MUST использовать TLS-сертификат и ключ, смонтированные томом с хоста (`/etc/nginx/ssl/ekotov-wiki.{crt,key}`, self-signed, срок до 2028-12-22) (FR-74). Перевыпуск сертификата пакетом не выполняется. Валидация цепочки доверия MUST NOT требоваться ни на одном контуре — клиенты ходят с игнором ошибок TLS (штатный режим, решение Заказчика; CA-инфраструктура не строится).

#### Scenario: Сертификат смонтирован с хоста

- **GIVEN** прод-стек поднят
- **WHEN** клиент устанавливает HTTPS-соединение по :10443
- **THEN** соединение обслуживается сертификатом `/etc/nginx/ssl/ekotov-wiki.crt` с хоста — файлы не копируются в образ (FR-74)

#### Scenario: Клиенты работают без валидации цепочки

- **GIVEN** сертификат self-signed (CN=IP, без CA)
- **WHEN** пользователи и смоук-проверки обращаются по HTTPS
- **THEN** доступ работает с игнором ошибок TLS на всех контурах — валидация цепочки не требуется (FR-74, решение Заказчика)

### Requirement: Первый контейнерный деплой — параллельно с systemd

Первый контейнерный деплой MUST запускаться параллельно с живым systemd-стеком: на переходный период контейнерный nginx публикует другой порт (10444, `${NGINX_PORT:-10443}` в compose), хостовой nginx продолжает держать 10443 — коллизии порта нет (NFR-9; механика — design §6, фаза 1). Переключение прод-трафика MUST выполняться одним шагом, состоящим из двух действий: освобождение 10443 (отключение сайта/остановка хостового nginx) и публикация 10443 контейнерным nginx (`NGINX_PORT=10443 docker compose up -d`); разрыв между действиями — секунды. systemd-юнит и файлы systemd-прода MUST сохраняться (остановлен, но не удален) — откат на systemd возможен за минуты.

#### Scenario: Параллельная проверка без простоя

- **GIVEN** systemd-прод обслуживает пользователей
- **WHEN** первый контейнерный стек поднимается для проверки
- **THEN** systemd-прод продолжает работать — пользователи не замечают проверку (NFR-9, план §6 ЭТАП 1)

#### Scenario: Переключение — один шаг без длительного простоя

- **GIVEN** контейнерный стек проверен параллельно (контейнерный nginx на 10444, хостовой nginx держит 10443)
- **WHEN** выполняется переключение
- **THEN** 10443 освобождается хостовым nginx и публикуется контейнерным (`NGINX_PORT=10443 up -d`) двумя действиями одного шага — разрыв секунды, простой минимален (NFR-9; design §6 фаза 2)

#### Scenario: Обратный откат на systemd за минуты

- **GIVEN** прод переключен на контейнеры, обнаружен дефект
- **WHEN** выполняется откат на systemd
- **THEN** `systemctl start ekotov-wiki` и возврат предыдущего хостового nginx-конфига восстанавливают прод за минуты — файлы systemd-прода не удалялись (NFR-9, план §6 ЭТАП 2)

### Requirement: Ротация логов контейнеров

Логи контейнеров SHOULD ротироваться: драйвер `json-file` с `max-size: 10m` и `max-file: 3` на контейнер (NFR-11). Просмотр логов MUST выполняться командой `docker compose logs` (перенос привычек journald RUNBOOK, план §5).

#### Scenario: Ротация применена на каждом контейнере

- **GIVEN** прод-стек поднят из compose-файла
- **WHEN** конфигурация логов контейнеров инспектируется
- **THEN** у каждого контейнера `json-file` с `max-size: 10m`, `max-file: 3` — диск не переполняется логами (NFR-11)

#### Scenario: Логи доступны для диагностики

- **GIVEN** прод-стек работает
- **WHEN** оператор выполняет `docker compose logs app` (или nginx)
- **THEN** логи контейнера доступны — диагностика без захода в контейнер (NFR-11, план §5)
