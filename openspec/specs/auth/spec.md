# auth Specification

## Purpose
Аутентификация двух фиксированных пользователей (owner, wife): логин по bcrypt-хешам, серверные сессии в HttpOnly/SameSite=lax/Secure куке, единый текст ошибок, middleware-защита всех страниц и API.


## Requirements

### Requirement: Авторизация обязательна для API
Система MUST требовать действующую сессию для любого обращения к API, кроме явно перечисленного exempt-списка (NFR-7, следствие для FR-8). Exempt-список — только два пути: `POST /api/auth/login` (сам вход: без него сессию получить нельзя) и `GET /api/health` (health-check для мониторинга и deploy, работает без сессии). Любой API-запрос вне exempt-списка без действующей сессии MUST отклоняться с кодом 401 Unauthorized.

#### Scenario: API-запрос без сессии
- **GIVEN** вызывающий не имеет действующей сессии
- **WHEN** вызывающий отправляет любой API-запрос вне exempt-списка (чтение, создание, изменение, удаление, поиск)
- **THEN** API отвечает кодом 401 Unauthorized, данные и операции недоступны

#### Scenario: API-запрос с просроченной сессией
- **GIVEN** у вызывающего была сессия, но она истекла
- **WHEN** вызывающий отправляет API-запрос вне exempt-списка
- **THEN** API отвечает кодом 401 Unauthorized

#### Scenario: Health отвечает 200 без сессии
- **GIVEN** вызывающий не имеет действующей сессии (например, монитор или deploy-скрипт до запуска пользователей)
- **WHEN** вызывающий отправляет `GET /api/health`
- **THEN** API отвечает кодом 200 с телом `{"status": "ok"}`, авторизация не требуется

#### Scenario: Exempt не распространяется на прочие API-запросы
- **GIVEN** вызывающий не имеет действующей сессии
- **WHEN** вызывающий отправляет любой API-запрос, кроме `POST /api/auth/login` и `GET /api/health` (например, `GET /api/board`)
- **THEN** API отвечает кодом 401 Unauthorized — exempt-список исчерпывающий и расширительному толкованию не подлежит

### Requirement: Вход по логину и паролю
Система MUST предоставлять веб-форму входа, принимающую логин и пароль пользователя (FR-14). Аутентификация MUST выполняться только для существующих пользователей системы (NFR-4: пользователей двое — владелец и жена владельца).

#### Scenario: Успешный вход существующего пользователя
- **GIVEN** пользователь с корректной парой логин/пароль существует в системе
- **WHEN** пользователь вводит корректные логин и пароль в форму входа и отправляет ее
- **THEN** вход выполняется успешно, пользователь получает доступ к функционалу системы

#### Scenario: Неверный пароль
- **GIVEN** пользователь существует в системе
- **WHEN** пользователь вводит корректный логин и неверный пароль
- **THEN** вход отклоняется, пользователю показывается сообщение об ошибке входа, доступ к функционалу не предоставляется

#### Scenario: Несуществующий пользователь
- **GIVEN** логин не принадлежит ни одному пользователю системы
- **WHEN** пользователь вводит несуществующий логин и любой пароль
- **THEN** вход отклоняется с сообщением об ошибке входа, не раскрывающим причину (существование логина не раскрывается)

### Requirement: Сохранение входа через сессии и куки
Система MUST сохранять факт входа между обращениями пользователя с помощью сессий и куки (FR-14): после успешного входа повторный ввод логина и пароля при последующих открытиях приложения не требуется, пока сессия действительна.

#### Scenario: Повторное открытие приложения в рамках действующей сессии
- **GIVEN** пользователь успешно вошел в систему и сессия еще действительна
- **WHEN** пользователь повторно открывает приложение в браузере
- **THEN** форма входа не показывается, пользователь сразу попадает в функционал системы

#### Scenario: Истечение сессии
- **GIVEN** пользователь ранее вошел в систему, но сессия истекла
- **WHEN** пользователь обращается к защищенной странице
- **THEN** ему требуется пройти вход повторно (показывается форма входа)

### Requirement: Авторизация обязательна для всех страниц
Система MUST требовать действующую сессию для доступа к любой странице функционала (NFR-7). Без входа функционал системы недоступен.

#### Scenario: Неавторизованный доступ к странице доски
- **GIVEN** пользователь не вошел в систему (действующей сессии нет)
- **WHEN** пользователь открывает страницу канбан-доски
- **THEN** доска не отображается, пользователь перенаправляется на форму входа

#### Scenario: Неавторизованный доступ к любой другой странице функционала
- **GIVEN** пользователь не вошел в систему
- **WHEN** пользователь открывает любую страницу функционала (вкладка поиска, разделы сайдбара)
- **THEN** содержимое страницы не отображается, пользователь перенаправляется на форму входа

### Requirement: Доступ только для своих пользователей
Система MUST различать своих пользователей (двое: владелец и жена владельца, NFR-4) от посторонних. Вход возможен только с учетными данными, заведенными в системе.

#### Scenario: Пользователь №2 входит со своими данными
- **GIVEN** в системе заведены учетные данные двух пользователей
- **WHEN** второй пользователь (жена владельца) вводит свои корректные логин и пароль
- **THEN** вход выполняется успешно, доступны те же функции системы, что и первому пользователю

#### Scenario: Посторонний не может войти
- **GIVEN** учетные данные посетителя не заведены в системе
- **WHEN** посетитель пытается войти с произвольной парой логин/пароль
- **THEN** вход отклоняется, доступ к функционалу не предоставляется

### Requirement: Пароли не хранятся в открытом виде
Система MUST хранить пароли пользователей только в виде, не позволяющем восстановить исходный пароль (NFR-7). Исходный пароль MUST отсутствовать в любых хранимых данных системы.

#### Scenario: Проверка хранимых учетных данных
- **GIVEN** в системе заведены учетные данные пользователей
- **WHEN** выполняется осмотр хранимых данных системы (БД, конфигурация)
- **THEN** исходные пароли в них отсутствуют; хранятся только необратимые представления паролей
