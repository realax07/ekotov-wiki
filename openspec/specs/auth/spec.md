# auth Specification

## Purpose
Аутентификация двух фиксированных пользователей (owner, wife): логин по bcrypt-хешам, серверные сессии в HttpOnly/SameSite=lax/Secure куке, единый текст ошибок, middleware-защита всех страниц и API.

## Requirements

### Requirement: Авторизация обязательна для API
Система MUST требовать действующую сессию для любого обращения к API, кроме явно перечисленного exempt-списка (NFR-7, следствие для FR-8). Exempt-список — только два пути: `POST /api/auth/login` (сам вход: без него сессию получить нельзя) и `GET /api/health` (health-check для мониторинга и deploy, работает без сессии). Любой API-запрос вне exempt-списка без действующей сессии MUST отклоняться с кодом 401 Unauthorized.

#### Scenario: API-запрос без сессии
- **GIVEN** вызывающий не имеет действующей сессии
- **WHEN** вызывающий отправляет любой API-запрос вне exempt-списка (чтение, создание, изменение, удаление, поиск)
- **THEN** API отвечает кодом 401 Unauthorized, данные и операции недоступны

#### Scenario: API-запрос с просроченной сессией
- **GIVEN** у вызывающего была сессия, но она истекла
- **WHEN** вызывающий отправляет API-запрос вне exempt-списка
- **THEN** API отвечает кодом 401 Unauthorized

#### Scenario: Health отвечает 200 без сессии
- **GIVEN** вызывающий не имеет действующей сессии (например, монитор или deploy-скрипт до запуска пользователей)
- **WHEN** вызывающий отправляет `GET /api/health`
- **THEN** API отвечает кодом 200 с телом `{"status": "ok"}`, авторизация не требуется

#### Scenario: Exempt не распространяется на прочие API-запросы
- **GIVEN** вызывающий не имеет действующей сессии
- **WHEN** вызывающий отправляет любой API-запрос, кроме `POST /api/auth/login` и `GET /api/health` (например, `GET /api/board`)
- **THEN** API отвечает кодом 401 Unauthorized — exempt-список исчерпывающий и расширительному толкованию не подлежит

### Requirement: Вход по логину и паролю
Система MUST предоставлять веб-форму входа, принимающую логин и пароль пользователя (FR-14). Аутентификация MUST выполняться только для существующих пользователей системы (NFR-4: пользователей двое — владелец и жена владельца).

#### Scenario: Успешный вход существующего пользователя
- **GIVEN** пользователь с корректной парой логин/пароль существует в системе
- **WHEN** пользователь вводит корректные логин и пароль в форму входа и отправляет ее
- **THEN** вход выполняется успешно, пользователь получает доступ к функционалу системы

#### Scenario: Неверный пароль
- **GIVEN** пользователь существует в системе
- **WHEN** пользователь вводит корректный логин и неверный пароль
- **THEN** вход отклоняется, пользователю показывается сообщение об ошибке входа, доступ к функционалу не предоставляется

#### Scenario: Несуществующий пользователь
- **GIVEN** логин не принадлежит ни одному пользователю системы
- **WHEN** пользователь вводит несуществующий логин и любой пароль
- **THEN** вход отклоняется с сообщением об ошибке входа, не раскрывающим причину (существование логина не раскрывается)

### Requirement: Сохранение входа через сессии и куки
Система MUST сохранять факт входа между обращениями пользователя с помощью сессий и куки (FR-14): после успешного входа повторный ввод логина и пароля при последующих открытиях приложения не требуется, пока сессия действительна.

#### Scenario: Повторное открытие приложения в рамках действующей сессии
- **GIVEN** пользователь успешно вошел в систему и сессия еще действительна
- **WHEN** пользователь повторно открывает приложение в браузере
- **THEN** форма входа не показывается, пользователь сразу попадает в функционал системы

#### Scenario: Истечение сессии
- **GIVEN** пользователь ранее вошел в систему, но сессия истекла
- **WHEN** пользователь обращается к защищенной странице
- **THEN** ему требуется пройти вход повторно (показывается форма входа)

### Requirement: Авторизация обязательна для всех страниц
Система MUST требовать действующую сессию для доступа к любой странице функционала (NFR-7). Без входа функционал системы недоступен.

#### Scenario: Неавторизованный доступ к странице доски
- **GIVEN** пользователь не вошел в систему (действующей сессии нет)
- **WHEN** пользователь открывает страницу канбан-доски
- **THEN** доска не отображается, пользователь перенаправляется на форму входа

#### Scenario: Неавторизованный доступ к любой другой странице функционала
- **GIVEN** пользователь не вошел в систему
- **WHEN** пользователь открывает любую страницу функционала (вкладка поиска, разделы сайдбара)
- **THEN** содержимое страницы не отображается, пользователь перенаправляется на форму входа

### Requirement: Доступ только для своих пользователей
Система MUST различать своих пользователей (двое: владелец и жена владельца, NFR-4) от посторонних. Вход возможен только с учетными данными, заведенными в системе.

#### Scenario: Пользователь №2 входит со своими данными
- **GIVEN** в системе заведены учетные данные двух пользователей
- **WHEN** второй пользователь (жена владельца) вводит свои корректные логин и пароль
- **THEN** вход выполняется успешно, доступны те же функции системы, что и первому пользователю

#### Scenario: Посторонний не может войти
- **GIVEN** учетные данные посетителя не заведены в системе
- **WHEN** посетитель пытается войти с произвольной парой логин/пароль
- **THEN** вход отклоняется, доступ к функционалу не предоставляется

### Requirement: Пароли не хранятся в открытом виде
Система MUST хранить пароли пользователей только в виде, не позволяющем восстановить исходный пароль (NFR-7). Исходный пароль MUST отсутствовать в любых хранимых данных системы.

#### Scenario: Проверка хранимых учетных данных
- **GIVEN** в системе заведены учетные данные пользователей
- **WHEN** выполняется осмотр хранимых данных системы (БД, конфигурация)
- **THEN** исходные пароли в них отсутствуют; хранятся только необратимые представления паролей

### Requirement: API текущего пользователя

Система MUST предоставлять API-эндпоинт `GET /api/auth/me`, возвращающий данные текущего авторизованного пользователя: логин, display_name, роль, «о себе» (bio) и URL аватара (FR-33, FR-36; расширение состава ответа в Релизе 4 — источник блока профиля и tooltip'а, FR-43). Эндпоинт MUST требовать действующую сессию: без сессии — отказ 401, как для всех API вне exempt-списка (NFR-7; exempt-список авторизации не расширяется). Эндпоинт MUST быть read-only: состояние не изменяет (редактирование профиля — отдельные эндпоинты профиля, FR-40). При незаполненном профиле поля display_name, роль, bio, URL аватара возвращаются пустыми (null) — логин заполнен всегда (Д-10: отображаемое имя заменяется логином, пока не задано).

#### Scenario: Текущий пользователь определен по сессии — полный состав

- **GIVEN** пользователь авторизован (действующая сессия; логин, например, «owner») и его профиль заполнен (display_name, роль, bio, аватар)
- **WHEN** вызывающий отправляет `GET /api/auth/me`
- **THEN** API отвечает 200 с логином, display_name, ролью, bio и URL аватара текущего пользователя, соответствующим сессии

#### Scenario: Текущий пользователь определен по сессии

- **GIVEN** пользователь авторизован (действующая сессия; логин, например, «owner»)
- **WHEN** вызывающий отправляет `GET /api/auth/me`
- **THEN** API отвечает 200 с логином текущего пользователя, соответствующим сессии (ключ `user` присутствует в ответе всегда — обратная совместимость)

#### Scenario: Дефолты при незаполненном профиле

- **GIVEN** пользователь авторизован, но никогда не заполнял профиль (нет display_name, роли, bio, аватара)
- **WHEN** вызывающий отправляет `GET /api/auth/me`
- **THEN** API отвечает 200: логин заполнен, display_name, роль, bio и URL аватара — пустые (null)

#### Scenario: Негативный: без сессии — 401

- **GIVEN** вызывающий не имеет действующей сессии
- **WHEN** вызывающий отправляет `GET /api/auth/me`
- **THEN** API отвечает 401 `{"error": "unauthorized"}` — эндпоинт не входит в exempt-список авторизации (NFR-7)

#### Scenario: Второй пользователь получает свои данные

- **GIVEN** второй пользователь (жена владельца) авторизована в своей сессии
- **WHEN** вызывающий в этой сессии отправляет `GET /api/auth/me`
- **THEN** API отвечает 200 с данными (логин, display_name, роль, bio, аватар) второго пользователя — каждый пользователь получает данные своей сессии

#### Scenario: Второй пользователь получает свой логин

- **GIVEN** второй пользователь (жена владельца) авторизована в своей сессии
- **WHEN** вызывающий в этой сессии отправляет `GET /api/auth/me`
- **THEN** API отвечает 200 с логином второго пользователя — каждый пользователь получает логин своей сессии

### Requirement: Профиль пользователя — просмотр и редактирование

Система MUST предоставлять API профиля текущего пользователя (FR-36, FR-40): `GET /api/profile` возвращает логин, display_name, роль, bio и URL аватара; `PUT /api/profile` сохраняет display_name, роль и bio. Роль MUST приниматься только из фиксированного справочника значений «Product manager» и «Product engineer» (ОВ-21); роль — чисто отображаемое поле: не влияет на права, авторизацию и поведение системы (ОВ-21, NFR-4). Редактирование доступно только своего профиля: эндпоинты operate исключительно над пользователем сессии (FR-39). Оба эндпоинта MUST требовать действующую сессию (401, NFR-7). Сохранение пустого display_name допустимо — при этом везде, где показывается имя, отображается логин (Д-10).

#### Scenario: Просмотр своего профиля

- **GIVEN** пользователь авторизован
- **WHEN** вызывающий отправляет `GET /api/profile`
- **THEN** API отвечает 200 с логином, display_name, ролью, bio и URL аватара пользователя сессии

#### Scenario: Сохранение профиля

- **GIVEN** пользователь авторизован
- **WHEN** вызывающий отправляет `PUT /api/profile` с display_name, ролью «Product engineer» и текстом bio
- **THEN** API отвечает 200; повторный `GET /api/profile` возвращает сохраненные значения; блок профиля и tooltip после обновления страницы отображают новые значения (FR-40, FR-43)

#### Scenario: Негативный: роль вне справочника отклоняется

- **GIVEN** пользователь авторизован
- **WHEN** вызывающий отправляет `PUT /api/profile` с ролью, отличной от «Product manager» и «Product engineer» (например, «Admin»)
- **THEN** API отвечает ошибкой валидации (422); профиль не изменяется — прежние значения сохраняются (ОВ-21)

#### Scenario: Негативный: без сессии — 401

- **GIVEN** вызывающий не имеет действующей сессии
- **WHEN** вызывающий отправляет `GET /api/profile` или `PUT /api/profile`
- **THEN** API отвечает 401 `{"error": "unauthorized"}` — эндпоинты не входят в exempt-список (NFR-7)

### Requirement: Смена пароля

Система MUST предоставлять текущему пользователю смену своего пароля: вводится текущий пароль и новый пароль (FR-41; ОГР-13 отменено решением Заказчика, ОГР-15). Смена MUST требовать корректный текущий пароль (Д-11); после успешной смены текущая сессия пользователя MUST сохраняться — принудительный повторный вход не требуется (Д-11). Новый пароль MUST храниться только в необратимом виде (NFR-7). Эндпоинт MUST требовать действующую сессию.

#### Scenario: Успешная смена пароля

- **GIVEN** пользователь авторизован и знает свой текущий пароль
- **WHEN** пользователь вводит корректный текущий пароль и новый пароль и подтверждает смену
- **THEN** пароль изменен; текущая сессия сохраняется без повторного входа (Д-11); вход со старым паролем после выхода отклоняется, вход с новым паролем выполняется успешно

#### Scenario: Негативный: неверный текущий пароль

- **GIVEN** пользователь авторизован
- **WHEN** пользователь вводит неверный текущий пароль и любой новый пароль
- **THEN** смена отклоняется с понятным сообщением об ошибке; пароль не изменен — вход со старым паролем продолжает работать (Д-11)

#### Scenario: Негативный: без сессии — 401

- **GIVEN** вызывающий не имеет действующей сессии
- **WHEN** вызывающий отправляет запрос смены пароля
- **THEN** API отвечает 401 `{"error": "unauthorized"}` (NFR-7)

### Requirement: Загрузка аватара

Пользователь MUST иметь возможность загрузить файл аватара в своем профиле (FR-42). Принимаются ТОЛЬКО файлы png/jpg: файл иного типа MUST отклоняться с понятной ошибкой, аватар не изменяется (FR-42, NFR-12). Исходный файл размером более 2 МБ MUST отклоняться с понятной ошибкой «файл слишком большой» — не молча и не падением (NFR-10, NFR-12, ОВ-22). Контракт загрузки MUST сохраняться: `POST /api/profile/avatar` (multipart/form-data, поле `file`) — путь, поле, коды ошибок и тела ответов без изменений (ОВ-СА-3); параметров кропа в контракте нет (ОВ-СА-1: принят вариант А — фронт-кроп, FR-54).

**Изменение (r5, вариант А):** при доступности кроп-виджета на сервер передается только итоговый обрезанный квадрат 256×256, сформированный клиентом (canvas), — исходник остается в браузере: трафик загрузки НЕ зависит от размера исходника (NFR-11, FR-54). Сервер MUST НЕ доверять клиенту: содержимое запроса в любом случае проходит полную серверную проверку (тип png/jpg по декларации И по декодированию, размер ≤2 МБ до декодирования) и MUST безусловно приводиться сервером к квадрату 256×256 PNG (Д-8, Д-13) — даже если присланный файл не квадратный. Итоговое хранимое изображение всегда 256×256 PNG независимо от честности клиента.

**Fallback (NFR-14):** при недоступности canvas/JS (старый браузер, отключен JS) загрузка аватара остается работоспособной как в Релизе 4 — простая отправка исходного файла, сервер выполняет автосжатие center-crop до квадрата 256×256; ошибки клиентского виджета MUST NOT нарушать работоспособность страницы профиля.

Хранение и отдача аватара — статика с кеш-бастингом `?v=<avatar_updated_at>` (ОГР-16, ОГР-23); существующие аватары, сохраненные до этого изменения, MUST NOT перекраиваться и мигрировать — серверная нормализация применяется только к новым загрузкам (ОГР-21). Эндпоинт загрузки MUST требовать действующую сессию; аватар загружается только свой. При отсутствии аватара отображается кружок с первой буквой логина (fallback, FR-33/FR-42).

#### Scenario: Вариант А — на сервер уходит только итоговый квадрат

- **GIVEN** пользователь авторизован, у браузера есть canvas/JS (кроп-виджет доступен)
- **WHEN** пользователь загружает png/jpg ≤2 МБ, выбирает область в кроп-виджете и подтверждает («Применить»)
- **THEN** на сервер отправляется один запрос `POST /api/profile/avatar` с итоговым квадратом 256×256 (исходный файл на сервер не передается: размер тела запроса не зависит от размера исходника — NFR-11); аватар заменен выбранной областью (FR-52)

#### Scenario: Серверная нормализация не доверяет клиенту

- **GIVEN** пользователь авторизован
- **WHEN** на `POST /api/profile/avatar` приходит валидный png, геометрия которого НЕ квадрат 256×256 (например, 512×300 — подмененный или устаревший клиент)
- **THEN** сервер сохраняет изображение, приведенное к ровно 256×256 PNG (безусловная серверная нормализация, Д-8/Д-13); ответ 200, аватар отображается корректно (ОВ-СА-2)

#### Scenario: Серверная валидация пришедшего содержимого сохранена

- **GIVEN** пользователь авторизован
- **WHEN** на `POST /api/profile/avatar` приходит файл неподдерживаемого содержимого (не png/jpg по декодированию) или размером более 2 МБ
- **THEN** загрузка отклоняется (422 «invalid file type» / 422 «file too large» соответственно) с теми же телами ответов, что в Релизе 4; аватар не изменяется (NFR-12, ОВ-СА-3)

#### Scenario: Контракт загрузки не расширялся

- **GIVEN** пользователь авторизован
- **WHEN** аватар загружается корректным multipart-запросом с полем `file` (png/jpg ≤2 МБ)
- **THEN** запрос обрабатывается успешно без дополнительных полей/параметров кропа; ответ 200 содержит `avatar_url`, версия `?v=` в URL изменилась (ОВ-СА-3, ОГР-23)

#### Scenario: Fallback без canvas — загрузка как в Релизе 4

- **GIVEN** пользователь авторизован, окружение без canvas/JS (кроп-виджет недоступен, NFR-14)
- **WHEN** пользователь загружает png/jpg ≤2 МБ простым выбором файла
- **THEN** загрузка выполняется успешно: сервер сам приводит изображение к квадрату 256×256 (center-crop, как в Релизе 4); страница профиля функциональна, ошибок JS нет (СЦ-11)

#### Scenario: Успешная загрузка png
- **GIVEN** пользователь авторизован и находится в форме профиля
- **WHEN** пользователь загружает файл формата png размером не более 2 МБ
- **THEN** загрузка выполняется успешно; аватар отображается в блоке профиля внизу сайдбара и в tooltip'е профиля вместо кружка с буквой (FR-42, FR-43)

#### Scenario: Успешная загрузка jpg

- **GIVEN** пользователь авторизован
- **WHEN** пользователь загружает файл формата jpg размером не более 2 МБ
- **THEN** загрузка выполняется успешно, аватар отображается в блоке профиля и в tooltip'е (FR-42)

#### Scenario: Серверное автосжатие в квадрат ≤256px

- **GIVEN** пользователь авторизован
- **WHEN** пользователь загружает корректный png/jpg с размерами, превышающими 256px по любой стороне (например, 1000×800)
- **THEN** сервер сохраняет и отдает изображение, приведенное к квадрату не более 256px (Д-8, ОГР-16); от пользователя никаких действий по обработке файла не требуется
#### Scenario: Негативный: исходник больше 2 МБ
- **GIVEN** пользователь авторизован
- **WHEN** пользователь выбирает корректный png/jpg размером более 2 МБ
- **THEN** файл отклоняется с понятной ошибкой «файл слишком большой» ДО отправки на сервер (клиентская проверка теми же правилами) и/или на сервере (NFR-10, NFR-12); аватар не изменяется

#### Scenario: Негативный: тип файла не png/jpg
- **GIVEN** пользователь авторизован, у него установлен действующий аватар
- **WHEN** пользователь загружает файл иного типа (например, gif или bmp)
- **THEN** загрузка отклоняется с понятной ошибкой о недопустимом типе файла; ранее установленный аватар не изменяется (FR-42, NFR-12)

#### Scenario: Backward-compat существующих аватаров
- **GIVEN** у пользователя есть аватар, сохраненный до этого изменения (center-crop Релиза 4)
- **WHEN** пользователь открывает профиль, не загружая новый файл
- **THEN** аватар отображается как был (не перекроен); серверный файл не изменяется (ОГР-21, СЦ-13)

#### Scenario: Негативный: без сессии — 401
- **GIVEN** вызывающий не имеет действующей сессии
- **WHEN** вызывающий отправляет файл аватара на эндпоинт загрузки
- **THEN** API отвечает 401 `{"error": "unauthorized"}`; файл не сохраняется (NFR-7)

### Requirement: Миграция пользователей и задач без потери данных

Миграция схемы (users: display_name, role, bio, avatar — FR-36; tasks: creator_id, assigned_to_id — FR-37) MUST выполняться без потери данных (NFR-9): после миграции каждый пользователь сохраняет логин и пароль (вход работает), каждая задача сохраняет все прежние значения полей; creator_id заполнен у 100% задач (бэкфилл = owner, FR-38); assigned_to_id заполнен = owner у всех существующих задач (ОВ-23). Роли существующих пользователей проставляются по умолчанию: owner → «Product manager», wife → «Product engineer» (ОВ-21, значение по умолчанию для существующих записей). Миграция прода выполняется только после бэкапа (ОГР-19). Повторный запуск миграции MUST не дублировать данные и не менять значений (по образцу NFR-8).

#### Scenario: Вход работает после миграции

- **GIVEN** до миграции в системе заведены пользователи «owner» и «wife» с действующими паролями
- **WHEN** миграция выполнена и пользователь входит со своими прежними логином и паролем
- **THEN** вход выполняется успешно — учетные данные не потеряны (NFR-9)

#### Scenario: Значения задач сохранены

- **GIVEN** до миграции существует задача с известными значениями всех полей (название, описание, приоритет, категория, статус, теги, комментарии)
- **WHEN** миграция выполнена и пользователь открывает эту задачу
- **THEN** все прежние значения отображаются без изменений и потерь (NFR-9)

#### Scenario: Бэкфилл creator = owner у всех задач

- **GIVEN** до миграции в системе есть задачи (созданные владельцем)
- **WHEN** миграция выполнена
- **THEN** у каждой задачи (100%) creator = «owner» — включая архивные и fast-задачи (FR-38)

#### Scenario: Бэкфилл assigned = owner у всех существующих задач

- **GIVEN** до миграции в системе есть задачи без поля исполнителя
- **WHEN** миграция выполнена
- **THEN** у каждой существующей задачи assigned = «owner» (ОВ-23; ни одна существующая задача не остается без исполнителя после миграции)

#### Scenario: Роли по умолчанию после миграции

- **GIVEN** до миграции пользователи «owner» и «wife» не имели ролей
- **WHEN** миграция выполнена
- **THEN** роль «owner» = «Product manager», роль «wife» = «Product engineer» (ОВ-21, значение по умолчанию для существующих записей)

#### Scenario: Идемпотентность миграции

- **GIVEN** миграция уже выполнена один раз
- **WHEN** миграционный скрипт запускается повторно
- **THEN** повторный запуск не дублирует данные и не меняет значений — creator/assigned остаются = owner, значения задач не искажаются (по образцу миграции категорий Релиза 2, NFR-8)
