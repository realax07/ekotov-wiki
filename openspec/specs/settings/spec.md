# settings Specification

## Purpose
Настройки: страница настроек для авторизованных пользователей, общие для всех; состав первого релиза — управление справочником категорий.

## Requirements

### Requirement: Страница настроек

В системе MUST существовать страница настроек, доступная только авторизованным пользователям (FR-23). Без действующей сессии доступ к странице настроек MUST отклоняться редиректом на страницу входа (следствие NFR-7 основного ТЗ).

#### Scenario: Авторизованный пользователь открывает настройки

- **GIVEN** пользователь авторизован
- **WHEN** пользователь переходит в раздел «Настройки»
- **THEN** открывается страница настроек

#### Scenario: Негативный: неавторизованный доступ к настройкам

- **GIVEN** вызывающий не имеет действующей сессии
- **WHEN** вызывающий открывает страницу настроек
- **THEN** доступ отклоняется редиректом на страницу входа; содержимое настроек не отображается

### Requirement: Настройки общие для всех пользователей

Настройки MUST быть общими для всех пользователей системы (FR-24, решение Заказчика «Общие»): оба пользователя видят одни и те же настройки, и изменение, сделанное одним пользователем, MUST быть видно другому. Справочник категорий един для системы; пер-пользовательские списки настроек MUST отсутствовать (ОГР-7). Ограничений вида «только owner» на изменение настроек MUST быть.

#### Scenario: Изменение настроек одного пользователя видно другому

- **GIVEN** оба пользователя системы авторизованы в разных сессиях; в справочнике заведена категория «home»
- **WHEN** первый пользователь создает в настройках категорию «work», а второй пользователь обновляет страницу настроек
- **THEN** второй пользователь видит категорию «work» в справочнике (изменения общие)

#### Scenario: Второй пользователь может менять настройки

- **GIVEN** второй пользователь (не владелец) авторизован
- **WHEN** второй пользователь переименовывает или удаляет категорию в настройках
- **THEN** изменение выполняется успешно и применяется ко всей системе (нет ограничений «только owner», FR-24)

#### Scenario: Справочник един — пер-пользовательских списков нет

- **GIVEN** первый пользователь видит в настройках справочник с категорией «home»
- **WHEN** второй пользователь открывает настройки и поле выбора категории
- **THEN** второй пользователь видит тот же единственный справочник (та же категория «home»), отдельного личного списка категорий у него нет

### Requirement: Состав настроек первого релиза — справочник категорий

Состав настроек первого релиза MUST ограничиваться управлением справочником категорий (FR-25, FR-20). Другие настройки (справочник тегов, профиль, смена пароля) MUST отсутствовать (Won't этого релиза).

#### Scenario: В настройках доступно только управление категориями

- **GIVEN** пользователь авторизован и находится на странице настроек
- **WHEN** пользователь просматривает доступные действия на странице настроек
- **THEN** доступно только создание, переименование и удаление категорий справочника; функций профиля, смены пароля или управления тегами как справочником нет

### Requirement: Страница настроек пользователя

Система MUST содержать страницу настроек пользователя, отдельную от общего раздела «Настройки» со справочником категорий (FR-39, ОГР-20): страница показывает настройки профиля СВОЕГО аккаунта — форму профиля (display_name, роль, bio; FR-40), смену пароля (FR-41) и загрузку аватара с выбором области отображения (FR-42, FR-49…FR-54). Доступ — только авторизованному пользователю; без сессии — редирект на страницу входа (NFR-7). Страница настроек пользователя MUST NOT изменять общие настройки (справочник категорий) и MUST NOT давать доступ к профилю другого пользователя.

**Изменение (r5, FR-55):** все элементы страницы — аватар с кроп-виджетом, display_name, роль, «о себе» (bio) и смена пароля — MUST быть оформлены как ЕДИНАЯ карточка V3: один визуальный блок без разнобоя секций — единые отступы, рамки, типографика и состояния по токенам V3 и мокапу `design/form-style-v3.html` (ОГР-25). Состав полей не меняется: все поля Релиза 4 (bio, роль, пароль, аватар) сохранены без потери функций. Карточка MUST быть адаптивной: на узких экранах блок перестраивается в одну колонку без горизонтальной прокрутки, кроп-виджет остается полнофункциональным (FR-56, NFR-13).

#### Scenario: Единая карточка V3
- **GIVEN** пользователь авторизован и открывает страницу настроек пользователя
- **WHEN** пользователь просматривает страницу
- **THEN** аватар, display_name, роль, bio и смена пароля находятся в одной визуальной карточке V3 (единые токены/отступы/типографика, сверка с мокапом V3); разнобоя секций нет (FR-55, СЦ-7)

#### Scenario: Все функции Релиза 4 сохранены
- **GIVEN** пользователь находится на странице настроек пользователя
- **WHEN** пользователь редактирует display_name/роль/bio, меняет пароль и загружает аватар с выбором области
- **THEN** все операции выполняются успешно — состав и поведение полей Релиза 4 не потеряны (FR-40, FR-41, FR-42; СЦ-7)

#### Scenario: Открытие страницы настроек пользователя
- **GIVEN** пользователь авторизован
- **WHEN** пользователь переходит на страницу настроек пользователя (клик по профилю внизу сайдбара, FR-39)
- **THEN** открывается страница с единой карточкой профиля — данными своего аккаунта

#### Scenario: Негативный: неавторизованный доступ
- **GIVEN** вызывающий не имеет действующей сессии
- **WHEN** вызывающий открывает страницу настроек пользователя
- **THEN** доступ отклоняется редиректом на страницу входа; содержимое не отображается (NFR-7)

#### Scenario: Настройки пользователя — только свои данные

- **GIVEN** пользователь авторизован (логин «owner»)
- **WHEN** пользователь открывает страницу настроек пользователя
- **THEN** на странице отображаются и редактируются данные профиля «owner»; профиль второго пользователя недоступен с этой страницы
#### Scenario: Адаптив одной колонкой
- **GIVEN** пользователь авторизован
- **WHEN** страница открывается на узком экране (ширина ~375px)
- **THEN** карточка перестроена в одну колонку, горизонтальной прокрутки нет; кроп-виджет (маска, перемещение, зум) полнофункционален (FR-56, СЦ-8)

#### Scenario: Независимость от общих настроек
- **GIVEN** пользователь находится на странице настроек пользователя
- **WHEN** пользователь просматривает состав страницы
- **THEN** управление справочником категорий на странице отсутствует — оно остается в общем разделе «Настройки» сайдбара (FR-23, ОГР-20)

### Requirement: Форма профиля на странице настроек пользователя

Страница настроек пользователя MUST содержать форму редактирования display_name, роли и bio с сохранением (FR-40). Роль выбирается из фиксированного списка значений «Product manager» и «Product engineer» (ОВ-21); свободный ввод роли недоступен. После успешного сохранения новые значения отображаются в блоке профиля и в его tooltip'е (FR-43, Д-10).

#### Scenario: Редактирование и сохранение профиля

- **GIVEN** пользователь находится на странице настроек пользователя
- **WHEN** пользователь заполняет display_name, выбирает роль «Product manager», вводит текст «о себе» и сохраняет
- **THEN** значения сохраняются; после обновления страницы блок профиля показывает display_name, tooltip — display_name, роль и bio (FR-40, FR-43)

#### Scenario: Роль — только выбор из справочника

- **GIVEN** пользователь открыл форму профиля
- **WHEN** пользователь раскрывает поле роли
- **THEN** доступны ровно два значения: «Product manager» и «Product engineer»; ввод произвольного текста роли невозможен (ОВ-21)

#### Scenario: Очистка display_name — показывается логин

- **GIVEN** пользователь ранее задал display_name
- **WHEN** пользователь очищает display_name и сохраняет профиль
- **THEN** сохранение выполняется успешно; в местах отображения имени показывается логин (Д-10)

### Requirement: Кроп-виджет аватара — выбор области отображения

При выборе нового файла аватара в карточке профиля система MUST показать кроп-виджет (Д-12): загруженное изображение под круглой маской, где маска = итоговый кружок аватара. Пользователь MUST иметь возможность перемещать фото под маской перетаскиванием (drag) (FR-49) и зумировать его слайдером и колесом мыши (FR-50). При любом масштабе и положении фото MUST полностью закрывать маску — «дыр» быть не может (FR-50). Пределы зума (ОВ-СА-4): минимальный масштаб — фото покрывает маску (сторона изображения не меньше диаметра маски); максимальный — утроенный минимальный; исходник меньше маски растягивается до покрытия с предупреждением о возможной потере четкости (загрузка не блокируется). Виджет MUST показывать предпросмотр результата в реальном времени — ровно то, что станет аватаром (FR-51). Подтверждение — кнопкой «Применить»: аватар заменяется выбранной областью, изменения сразу видны в кружке сайдбара/профиле/tooltip'е по кеш-бастингу `?v=avatar_updated_at` (FR-52, ОГР-23; на сервер передается только итоговый квадрат — NFR-11, FR-54). Отмена (кнопка «Отмена», закрытие виджета, уход со страницы без «Применить») MUST оставлять прежний аватар без изменений — никаких частично примененных состояний и запросов на сервер (FR-53). Виджет работает только при новой загрузке файла; уже сохраненные аватары не перекадрируются (ОГР-21).

#### Scenario: Фото под маской, drag
- **GIVEN** пользователь выбрал png/jpg ≤2 МБ в карточке профиля
- **WHEN** открылся кроп-виджет и пользователь перетаскивает фото мышью
- **THEN** фото смещается под круглой маской — под маской оказывается другой участок изображения; фото всегда полностью закрывает маску (FR-49, FR-50, СЦ-1)

#### Scenario: Зум слайдером и колесом
- **GIVEN** кроп-виджет открыт
- **WHEN** пользователь двигает слайдер зума или прокручивает колесо мыши над фото
- **THEN** фото плавно увеличивается/уменьшается обоими способами в пределах минимального (покрытие маски) и максимального (×3) масштабов; «дыр» под маской нет ни в одном положении (FR-50, ОВ-СА-4, СЦ-2)

#### Scenario: Мелкий исходник растягивается с предупреждением
- **GIVEN** пользователь выбрал изображение меньше маски (например, 64×64)
- **WHEN** открылся кроп-виджет
- **THEN** фото растянуто до полного покрытия маски, виджет показывает предупреждение о возможной потере четкости; загрузка не блокируется (ОВ-СА-4)

#### Scenario: Предпросмотр = итог
- **GIVEN** пользователь кадрировал фото смещением и зумом
- **WHEN** пользователь сравнивает предпросмотр в виджете с аватаром после применения
- **THEN** кружок сайдбара/профиля/tooltip'а визуально идентичен предпросмотру до применения (FR-51, СЦ-3)

#### Scenario: Применение заменяет аватар выбранной областью
- **GIVEN** пользователь кадрировал область с лицом, смещенным от центра
- **WHEN** пользователь нажимает «Применить»
- **THEN** аватар заменен выбранной областью (не center-crop); кружок сайдбара/профиль/tooltip обновились без ручного сброса кеша — `?v=` в URL изменился; на сервер передан только итоговый квадрат (FR-52, NFR-11, СЦ-4)

#### Scenario: Отмена оставляет прежний аватар
- **GIVEN** пользователь начал загрузку нового фото, кадрировал его
- **WHEN** пользователь нажимает «Отмена» (или закрывает виджет / уходит со страницы без «Применить»)
- **THEN** прежний аватар без изменений во всех местах отображения; запросов на сервер не было — файл на сервере не перезаписан, `?v=` не изменился (FR-53, СЦ-5)

#### Scenario: Виджет только при новой загрузке
- **GIVEN** у пользователя есть аватар, загруженный ранее
- **WHEN** пользователь открывает страницу настроек, не выбирая новый файл
- **THEN** кроп-виджет не открывается, текущий аватар отображается как есть — перекадрирование сохраненного аватара недоступно (ОГР-21, СЦ-13)

### Requirement: Тач-жесты и доступность кроп-виджета

Кроп-виджет MUST поддерживать тач-жесты: перемещение фото пальцем (touch-drag) и зум pinch-жестом; слайдер зума MUST быть работоспособен на таче (NFR-13); тач-взаимодействие с виджетом MUST NOT ломать скролл страницы вне виджета. Доступность (NFR-15): слайдер зума MUST управляться с клавиатуры (фокусируемый input, стрелки меняют масштаб); drag-перемещение MUST иметь клавиатурный аналог (фокус на виджете, стрелки двигают фото); виджет MUST нести aria-атрибуты (роль, подпись «выбор области аватара», значение зума для скринридера). При prefers-reduced-motion анимации виджета MUST быть отключены (ОГР-17). При недоступности canvas/JS (старый браузер, отключен JS) кроп-виджет MUST NOT показываться, загрузка аватара остается работоспособной как в Релизе 4 (простая загрузка с серверным center-crop), ошибки клиентского кода MUST NOT нарушать работоспособность страницы профиля (NFR-14).

#### Scenario: Тач-drag и pinch
- **GIVEN** кроп-виджет открыт на тач-устройстве (или в эмуляции)
- **WHEN** пользователь перемещает фото пальцем и зумирует pinch-жестом (или слайдером)
- **THEN** drag пальцем работает, зум доступен pinch-ом и слайдером; скролл страницы вне виджета не нарушен (NFR-13, СЦ-9)

#### Scenario: Клавиатурное управление и aria
- **GIVEN** кроп-виджет открыт
- **WHEN** пользователь проходит виджет с клавиатуры (фокус на слайдере — стрелки меняют зум; фокус на виджете — стрелки двигают фото) и проверяет aria
- **THEN** зум и перемещение управляются с клавиатуры; скринридер озвучивает виджет («выбор области аватара») и значение зума; при prefers-reduced-motion анимаций нет (NFR-15, СЦ-12)

#### Scenario: Лимит исходника — как в Релизе 4
- **GIVEN** пользователь выбирает файл более 2 МБ или неподдерживаемого типа
- **WHEN** файл проверяется виджетом/страницей
- **THEN** отклонение с понятной ошибкой (клиентская проверка теми же правилами, что серверная); поведение не ухудшилось относительно Релиза 4 (NFR-12, СЦ-10)

#### Scenario: Fallback без canvas
- **GIVEN** окружение без JS-canvas (старый браузер, JS отключен)
- **WHEN** пользователь загружает файл аватара
- **THEN** кроп-виджет не показывается, простая загрузка работает «как сейчас» (серверный center-crop); страница профиля функциональна, ошибок JS нет (NFR-14, СЦ-11)
