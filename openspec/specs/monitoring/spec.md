# monitoring Specification

## Purpose

Мониторинг — наблюдаемость прод-контура ekotov-wiki через Netdata (контейнер
в матрице, без агентов на хосте): метрики системы и контейнеров доступны
Заказчику через дашборд `/netdata/` на прод-порту 10443. Доступ защищен
nginx basic auth (htpasswd вне репозитория, отдельный пароль — FR-76);
netdata не публикует порты наружу — только через nginx-прокси с вырезанием
префикса (официальный паттерн Netdata subpath). Ссылка «Мониторинг» в
сайдбаре видна owner (роль Product manager) — дельта navigation.

## Requirements

### Requirement: Метрики собираются сервисом Netdata без агентов на хосте

Метрики железа хоста (CPU, RAM, диски, сеть) и контейнеров прод-стека MUST
собираться контейнером `netdata` (образ `netdata/netdata`) в составе
compose-проекта (FR-75). Контейнер MUST читать хостовые источники только
через read-only маунты `/proc` и `/sys`; метрики контейнеров MUST собираться
через `/var/run/docker.sock` в режиме read-only (только чтение метрик,
управление контейнерами НЕ выполняется). Схема БД wiki и данные пользователей
MUST NOT изменяться пакетом.

#### Scenario: Метрики железа доступны в дашборде

- **GIVEN** прод-стек поднят с сервисом netdata
- **WHEN** owner открывает дашборд мониторинга
- **THEN** видны показатели CPU, RAM, дисков (HDD) и сети хоста — собраны
  через ro-маунты `/proc` и `/sys` (FR-77)

#### Scenario: Метрики контейнеров стека доступны в дашборде

- **GIVEN** прод-стек поднят (app, frontend, search, backup, netdata)
- **WHEN** owner открывает раздел контейнеров дашборда
- **THEN** каждый контейнер стека виден по имени с показателями CPU/RAM/IO —
  собраны через docker-сокет в режиме ro (FR-77)

#### Scenario: docker-сокет подключен только на чтение

- **GIVEN** контейнер netdata запущен
- **WHEN** конфигурация контейнера инспектируется
- **THEN** `/var/run/docker.sock` смонтирован с флагом `:ro` — попытки записи
  через сокет невозможны на уровне ФС (урок R6, FR-75)

### Requirement: Netdata не публикуется наружу напрямую

Контейнер `netdata` MUST NOT публиковать порты наружу; доступ к его дашборду
MUST выполняться только через nginx-контейнер по пути `/netdata/` на
существующем публичном порте 10443 (преемственность deploy: «Наружу открыт
только nginx»). Локации `/netdata` и `/netdata/...` MUST обрабатываться
парами точной и префиксной nginx-локаций по образцу search-семейства; запрос
без завершающего слэша MUST перенаправляться на `/netdata/`.

#### Scenario: Порт netdata закрыт снаружи

- **GIVEN** прод-стек поднят на VPS
- **WHEN** клиент снаружи обращается к порту 19999 хоста
- **THEN** соединение отклоняется — порт контейнера netdata не опубликован
  (FR-75)

#### Scenario: Дашборд доступен по под-пути nginx

- **GIVEN** owner открыл дашборд по `https://<host>:10443/netdata/`
- **WHEN** дашборд загружается
- **THEN** страница и её ресурсы (assets, API-вызовы) обслуживаются через
  nginx-прокси на netdata без ошибок сборки страницы (FR-77)

#### Scenario: Запрос без слэша перенаправляется

- **GIVEN** клиент запрашивает `/netdata` без завершающего слэша
- **WHEN** nginx обрабатывает запрос
- **THEN** клиент перенаправляется на `/netdata/` (301) и дашборд открывается

### Requirement: Доступ к дашборду — только учетка owner через nginx

Доступ к `/netdata/` MUST требовать HTTP Basic-аутентификацию на уровне
nginx (парная проверка на точной и префиксной локациях) ДО проксирования
запроса в netdata (ОВ-2, FR-76). Файл htpasswd MUST храниться вне
репозитория и монтироваться в контейнер frontend в режиме read-only; пароль
basic auth MUST быть отдельным от пароля учетки owner в wiki. Пользователи
без валидных кредов MUST получать 401. Скрытие ссылки в сайдбаре для не-owner
MUST NOT являться механизмом защиты — границей доступа является basic auth
nginx.

#### Scenario: Owner входит по кредам basic auth

- **GIVEN** htpasswd с кредами owner сгенерирован и смонтирован в frontend
- **WHEN** owner открывает `/netdata/` и вводит креды basic auth
- **THEN** дашборд открывается (200) — повторный ввод не требуется, пока
  браузер держит креды (FR-76)

#### Scenario: Негативный: без кредов доступ закрыт

- **GIVEN** прод-стек поднят, htpasswd смонтирован
- **WHEN** клиент (в т.ч. пользователь PE и неавторизованный) запрашивает
  `/netdata/` без basic-кредов
- **THEN** nginx отвечает 401 ДО любого обращения к netdata (ОВ-2, FR-76)

#### Scenario: Негативный: htpasswd вне репозитория

- **GIVEN** файл htpasswd создан на VPS
- **WHEN** репозиторий инспектируется
- **THEN** файла/хеша в git нет (`.gitignore` покрывает артефакт; FR-76)

### Requirement: Дашборд покрывает показатели Заказчика

Дашборд мониторинга MUST отображать вживую (real-time) показатели: CPU, RAM
и диски (HDD) хоста, а также показатели каждого контейнера прод-стека
(FR-77). Дополнительные компоненты мониторинга (exporters, отдельные
хранилища метрик) для этого MUST NOT требоваться.

#### Scenario: Критерий приемки Заказчика

- **GIVEN** прод-выкатка выполнена, owner открыл дашборд
- **WHEN** Заказчик смотрит показатели вживую (генерируется нагрузка —
  запросы к wiki)
- **THEN** на дашборде видны изменения CPU/RAM хоста и контейнеров, диски
  хоста присутствуют в списках метрик — критерий приемки выполнен без
  дополнительных компонентов (FR-77)

### Requirement: Ресурсы мониторинга ограничены

Контейнер `netdata` MUST иметь лимит памяти 256m и стандартную ротацию логов
(json-file, 10m×3) — паритет остальному стеку (NFR-19). Суммарные лимиты
стека с netdata MUST сохранять резерв памяти хосту ≥ 2 GB (преемственность
deploy: «Лимиты памяти контейнеров»). Сервис netdata MUST иметь healthcheck,
чтобы оркестрация compose отражала его живость.

#### Scenario: Лимит netdata применен

- **GIVEN** полный стек с netdata поднят
- **WHEN** `docker stats --no-stream` выполняется
- **THEN** netdata работает в пределах 256m, суммарные лимиты стека —
  1.41 GB, резерв хосту ≥ 2 GB (NFR-19)

#### Scenario: Фактическое потребление измерено до прод-выкатки

- **GIVEN** стенд с netdata поднят (задачи пакета)
- **WHEN** фактическое потребление RAM netdata измеряется после прогрева
- **THEN** значение зафиксировано в отчете задачи; стабильное превышение
  лимита блокирует прод-выкатку до решения Заказчика (урок PLAN-R7 «вес
  меряем по факту», NFR-19)
