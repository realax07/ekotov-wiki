# categories Specification

## Purpose
Справочник категорий: задаваемый пользователем список категорий проекта; выбор категории только из справочника, жесткая валидация (UI и API), миграция существующих значений 1:1 без потери данных.


## Requirements

### Requirement: Справочник категорий

В системе MUST существовать справочник категорий — задаваемый пользователем список категорий проекта (FR-19). Категория задачи MUST быть значением из справочника, а не свободным текстом; поле категории во всех местах ввода (создание, редактирование, фильтр) MUST работать как выбор из списка значений справочника.

#### Scenario: Поле категории предлагает только значения справочника

- **GIVEN** пользователь авторизован и в справочнике заведены категории «home», «work»
- **WHEN** пользователь открывает поле категории в форме создания задачи
- **THEN** поле предлагает выбор только из значений справочника («home», «work») и не допускает ввод произвольного текста

#### Scenario: Поле категории в фильтре работает от справочника

- **GIVEN** пользователь авторизован, в справочнике заведены категории «home», «work»
- **WHEN** пользователь открывает фильтр-конструктор поиска и раскрывает поле «Категория»
- **THEN** поле предлагает выбор только из значений справочника

#### Scenario: Негативный: категория вне справочника не доступна для выбора

- **GIVEN** пользователь авторизован, в справочнике заведены категории «home», «work»; значение «old-project» в справочнике отсутствует
- **WHEN** пользователь пытается указать категорию «old-project» в любом месте ввода (создание, редактирование, фильтр)
- **THEN** значение «old-project» не может быть выбрано/сохранено — выбор ограничен списком справочника

### Requirement: Управление справочником категорий

Пользователь MUST иметь возможность в настройках создавать, переименовывать и удалять категории справочника (FR-20). Переименование категории MUST применяться ко всем задачам, у которых стоит эта категория. Удаление категории, используемой хотя бы одной задачей, MUST блокироваться до перевода этих задач на другие категории (Д-1).

#### Scenario: Создание категории в настройках

- **GIVEN** пользователь авторизован и находится на странице настроек
- **WHEN** пользователь создает категорию с названием «home»
- **THEN** категория «home» появляется в справочнике и доступна для выбора в поле категории

#### Scenario: Переименование применяется ко всем задачам

- **GIVEN** в справочнике есть категория «home», и хотя бы одна задача имеет категорию «home»
- **WHEN** пользователь переименовывает категорию «home» в «дом»
- **THEN** в справочнике отображается «дом» и все задачи, имевшие категорию «home», отображают категорию «дом» (значение заменено у всех)

#### Scenario: Негативный: удаление используемой категории блокируется

- **GIVEN** в справочнике есть категория «work», используемая хотя бы одной задачей
- **WHEN** пользователь пытается удалить категорию «work»
- **THEN** удаление отклоняется с сообщением о том, что категория используется задачами и должна быть освобождена (переводом задач на другие категории); категория остается в справочнике

#### Scenario: Удаление неиспользуемой категории

- **GIVEN** в справочнике есть категория «temp», не используемая ни одной задачей
- **WHEN** пользователь удаляет категорию «temp»
- **THEN** категория удаляется из справочника и исчезает из списков выбора

#### Scenario: Негативный: создание категории с пустым названием

- **GIVEN** пользователь авторизован и находится на странице настроек
- **WHEN** пользователь пытается создать категорию с пустым названием (или только из пробелов)
- **THEN** создание отклоняется с сообщением об ошибке; категория в справочнике не появляется

### Requirement: Жесткая валидация категории задачи

Задачу MUST быть нельзя сохранить с непустой категорией, отсутствующей в справочнике (FR-21, решение Заказчика «Жесткая»). Валидация MUST действовать и при создании, и при редактировании: в интерфейсе (форма не позволяет отправить значение вне списка) и на уровне API/хранения (запрос с невалидной категорией отклоняется ошибкой; обойти валидацию через API MUST быть нельзя).

#### Scenario: Негативный: создание задачи с категорией вне справочника через API

- **GIVEN** вызывающий авторизован; категория «ghost» в справочнике отсутствует
- **WHEN** вызывающий отправляет API-запрос создания задачи с категорией «ghost»
- **THEN** API отклоняет запрос ошибкой валидации; задача не создается

#### Scenario: Негативный: редактирование задачи с категорией вне справочника через API

- **GIVEN** вызывающий авторизован и существует задача с валидной категорией; категория «ghost» в справочнике отсутствует
- **WHEN** вызывающий отправляет API-запрос редактирования этой задачи с категорией «ghost»
- **THEN** API отклоняет запрос ошибкой валидации; категория задачи не изменяется

#### Scenario: Валидация следует за справочником

- **GIVEN** категория «work» есть в справочнике
- **WHEN** пользователь удаляет категорию «work» из справочника (после перевода всех задач) и пытается сохранить задачу с категорией «work»
- **THEN** сохранение отклоняется — категория более не входит в справочник

#### Scenario: Пустая категория жесткой валидацией не запрещена

- **GIVEN** пользователь авторизован, категория задачи не выбрана (пустая)
- **WHEN** пользователь сохраняет задачу без категории
- **THEN** задача сохраняется успешно (жесткая валидация FR-21 действует на непустые значения; пустое значение допустимо моделью данных)

### Requirement: Миграция существующих категорий в справочник

При внедрении справочника существующие текстовые значения category задач MUST быть перенесены в справочник (FR-22, решение Заказчика «Мапь в справочник»). Правило маппинга (Д-2): каждое уникальное непустое значение category MUST стать отдельной категорией справочника 1:1; пустые значения MUST НЕ создавать записей справочника; ни одна задача MUST НЕ потерять значение своей категории. Ручное слияние «синонимов» (опечатки, регистр) при миграции MUST НЕ выполняться — слияние выполняется после миграции средствами переименования (ОГР-9). После миграции каждая задача MUST ссылаться на категорию справочника (не на отдельный текст).

#### Scenario: Уникальные значения становятся категориями 1:1

- **GIVEN** до миграции в системе есть задачи с категориями «home», «Home», «work» (три уникальных непустых значения, включая различие по регистру)
- **WHEN** выполняется миграция
- **THEN** справочник содержит ровно три категории: «home», «Home», «work» (без ручного слияния синонимов)

#### Scenario: Задачи сохраняют значения категорий

- **GIVEN** до миграции существует задача с категорией «work»
- **WHEN** выполняется миграция
- **THEN** эта задача имеет категорию «work», и она является категорией справочника (значение не потеряно и не изменено)

#### Scenario: Пустые значения не создают записей справочника

- **GIVEN** до миграции существуют задачи с пустой категорией и хотя бы одна задача с непустой категорией «home»
- **WHEN** выполняется миграция
- **THEN** справочник не содержит пустой категории; задачи с пустой категорией остаются без категории; задача с «home» — со своей

#### Scenario: После миграции все непустые категории задач валидны

- **GIVEN** миграция выполнена
- **WHEN** выполняется автоматическая сверка значений category всех задач со справочником
- **THEN** каждое непустое значение category каждой задачи присутствует в справочнике (жесткая валидация FR-21 не нарушена ни для одной существующей задачи)

### Requirement: Миграция без потери данных

Миграция категорий MUST NOT терять данные (NFR-8): после миграции каждая существующая задача сохраняет свою категорию — 0 задач с потерянным или измененным (без переименования) значением; число категорий в справочнике после миграции MUST равняться числу уникальных непустых значений category до миграции. Проверка MUST выполняться автоматической сверкой состояния до и после миграции.

#### Scenario: Автосверка до/после подтверждает ноль потерь

- **GIVEN** до миграции зафиксирован снимок: список уникальных непустых значений category и категории каждой задачи
- **WHEN** миграция выполнена и запущена автоматическая сверка
- **THEN** сверка показывает: (а) каждая задача имеет то же значение категории, что в снимке; (б) число категорий справочника равно числу уникальных непустых значений снимка; расхождений нет

#### Scenario: Негативный: расхождение сверки останавливает внедрение

- **GIVEN** выполнена миграция, автоматическая сверка обнаружила задачу, значение категории которой отсутствует в справочнике
- **WHEN** сверка завершается
- **THEN** сверка фиксирует расхождение как провал проверки NFR-8; внедрение справочника не считается завершенным до устранения расхождения
