# services Specification

## Purpose

Возможность `services` выделяет stateful-вынос частей монолита в отдельные
контейнерные сервисы за общим nginx. Первый сервис — `search`: простой и
advanced поиск и подсказки (`/api/search*`, `/api/suggestions`) обслуживаются
отдельным контейнером; ядро не содержит этих маршрутов. Контракт сервиса
замораживается (`contracts/openapi-search.json`) до выделения и проверяется
гейтом «экспорт = файл». Сервис читает БД в read-only профиле (запись —
только ядро), маршрутизируется nginx с заголовком `X-Service: search`,
деградирует управляемым 503 (JSON + Retry-After) при недоступности.

## Requirements

### Requirement: Поиск работает отдельным сервисом

Поиск (простой и advanced) и подсказки (`/api/suggestions`) MUST обслуживаться
отдельным контейнером `search`; ядро (`app`) MUST NOT содержать этих маршрутов.
Для клиента URL не меняются — маршрутизацию выполняет nginx.

#### Scenario: Маршрутизация nginx

- **Когда** запрос `/api/search?…` приходит через nginx
- **то** он проксируется сервису `search` (заголовок `X-Service: search` в ответе),
  а запрос `/api/tasks` — сервису `app`.

#### Scenario: Ядро без маршрутов поиска

- **Когда** запрос `/api/search` приходит напрямую контейнеру `app` внутри сети
- **то** ответ 404/405 — маршрутов поиска в ядре нет.

#### Scenario: Деградация при отказе search

- **Когда** контейнер `search` остановлен
- **то** nginx отвечает 503 быстро (не таймаут), остальные маршруты работают.

### Requirement: Search читает данные read-only

Сервис `search` MUST монтировать том данных в режиме только-чтение и MUST NOT иметь
прав записи; схема БД MUST NOT меняться сервисом.

#### Scenario: RO-маунт

- **Когда** сервис `search` смонтирован
- **то** том `wiki-data` подключен `:ro`; попытка записи невозможна на уровне ФС.

#### Scenario: Схема не мигрирует

- **Когда** деплойится новый релиз search-сервиса
- **то** миграционные шаги не выполняются (схема одна, владелец — ядро).

### Requirement: Контракт поиска зафиксирован до выделения

Схема OpenAPI маршрутов `/api/search*` и `/api/suggestions` MUST быть экспортирована в
`contracts/openapi-search.json` до переноса кода; CI MUST проверять «экспорт =
зафиксированный файл».

#### Scenario: Экспорт = файл

- **Когда** CI выполняет экспорт схемы search-сервиса
- **то** git-дифф `contracts/openapi-search.json` пустой.

### Requirement: Бэкап тома — sidecar по расписанию

Контейнер `backup` MUST снимать консистентную копию БД и аватаров в
`/var/backups/ekotov-wiki` по расписанию; релизный бэкап перед деплоем
MUST сохраняться в `deploy.sh` (не дублируясь кодом).

#### Scenario: Sidecar создает бэкап

- **Когда** проходит интервал расписания
- **то** в каталоге бэкапов появляется непустой .db (integrity ok) и tar аватаров.

#### Scenario: Релизный бэкап сохранен

- **Когда** выполняется деплой
- **то** шаг бэкапа в deploy.sh срабатывает как раньше (до матрицы up).

### Requirement: Деплой матрицей сервисов

`deploy.sh` MUST управлять всеми сервисами единым RELEASE_TAG: build каждого,
порядок (бэкап → миграция ядра → up app → up читателей), healthcheck-матрица
до смоука; откат MUST быть тегом каждого сервиса.

#### Scenario: Порядок подъема

- **Когда** деплой выполняется
- **то** app поднимается и становится healthy до подъема search/backup.

#### Scenario: Откат одного сервиса

- **Когда** search-сервис дефектен после релиза
- **то** `docker compose up -d search` с предыдущим тегом восстанавливает
  работу без пересоздания app.

### Requirement: Лимиты памяти полного стека

Сумма mem_limit сервисов (app 512m, frontend 64m, search 512m, backup 64m)
MUST оставлять хосту резерв ≥ 2 GB (VPS 3.9 GB).

#### Scenario: Резерв хоста

- **Когда** полный стек работает
- **то** `free -m` available ≥ 2000.

### Requirement: Сервис images пишет в общую БД

Сервис `images` MUST работать с общей БД в **read-write профиле своей
схемы**: создает/читает/пишет только таблицы галереи (изображения,
категории галереи, теги, реакции, комментарии) и MUST NOT изменять схему
и данные существующих таблиц ядра (users — только чтение). Схему таблиц
галереи MUST создавать ядро миграцией (один владелец миграций —
преемственность deploy: «Миграции БД — one-shot до подъема нового app»);
сам сервис images миграций НЕ выполняет. Файлы изображений MUST храниться
в именованном томе `images-data` (не в общем томе wiki-data, не в БД).

#### Scenario: RW-маунт общей БД

- **GIVEN** сервис images смонтирован
- **WHEN** конфигурация контейнера инспектируется
- **THEN** том `wiki-data` подключен в режиме RW (в отличие от search:
  images пишет реакции/комментарии/метаданные в свои таблицы)

#### Scenario: Границы записи — только таблицы галереи

- **GIVEN** сервис images работает, пользователь ставит лайк и комментирует
- **WHEN** инспектируются записи БД
- **THEN** изменены только таблицы галереи (реакции, комментарии,
  метаданные изображений); таблицы ядра (tasks, comments, categories,
  sessions) не изменены; users — только читался

#### Scenario: Схему создает ядро, сервис не мигрирует

- **GIVEN** деплой нового релиза с галереей
- **WHEN** контейнер images стартует
- **THEN** миграционные шаги images не выполняются — таблицы галереи
  созданы one-shot-миграцией ядра до подъема (паритет search: схема —
  зона ядра)

#### Scenario: Данные изображений в отдельном томе

- **GIVEN** изображения загружены
- **WHEN** тома инспектируются
- **THEN** файлы изображений находятся в томе `images-data`; том
  `wiki-data` содержит только БД и аватары — как прежде
