# services/ — микросервисы (монорепо, план P11)

> Статус: ЗАГОТОВКА (ничего не реализовано) | Источник: `docs/ba/architecture-services-plan.md` (P11, ЧЕРНОВИК на решение Заказчика) | Границы сервисов определит архитектор-сабагент при старте работ.

Каталог под будущие сервисы в рамках перехода на контейнеры (план P11):

- **ЭТАП 1** — контейнеризация монолита как есть: `app` (uvicorn) + `frontend` (nginx) + общий том данных; код монолита (`backend/app/`, тесты, статика) переезжает сюда без изменения логики.
- **ЭТАП 2** — выделение сервисов **по одному**, по мере надобности; первый кандидат — `search` (код изолирован, доступ к БД только RO). `auth` выделению **не рекомендован** (сетевой хоп на каждый запрос через middleware, сессии в общей БД, выигрыша при 2 пользователях нет).

## Структура

Каждый сервис — свой подкаталог:

```
services/<name>/
├── app/          # код сервиса
├── tests/        # юнит/контрактные тесты сервиса
├── openapi.yaml  # контракт (экспорт схемы, §3 плана)
├── mocks/        # макеты/заглушки для локальной разработки
└── docs/         # доки сервиса
```

## Правила (из плана P11)

- Контракт сервиса фиксируется в OpenAPI **до** выделения кода; несовместимый дифф схемы = breaking → блок merge.
- В ЭТАПЕ 2 — только сервисы с read-only или изолированным профилем записи к общей SQLite (инварианты монолита держатся транзакциями одного процесса).
- Никогда два изменения инфраструктуры в одном шаге; границы и состав — решение архитектора по плану, не «потому что можно».
