# services/backup — сервис резервного копирования (sidecar)

> Статус: **в работе, ЭТАП B** (каркас — задача 0.2; код/образ/compose — задачи 1.2, 1.4 пакета `add-microservices-full`) | Источники: `docs/ba/architecture-services-plan.md` §1.2, design пакета §5.

## Назначение

Выделение бэкапа из деплоя в sidecar-сервис: вместо бэкапа только в момент релиза (deploy.sh) — периодический cron-цикл между релизами. Релизный бэкап при этом остается в деплое (задача 1.4).

## Режим работы

- **sidecar**: живет рядом с `app`, не в цепочке запросов; падение бэкапа не деградирует продукт (сценарий stop-backup — задача 2.2).
- **cron-цикл**: периодическое копирование БД внутри контейнера (шедулер в цикле python, без системного cron).
- Ресурсы: mem_limit 64m (задача 1.2).

## Данные

- Том: bind **`/var/backups/ekotov-wiki`** (host) → каталог бэкапов в контейнере.
- Доступ к данным: том данных **ro** — сервис только читает SQLite и копирует; ничего не пишет в общую БД (безопасный профиль данных, plan §1.2 — НЕ механический разрез с общим RW SQLite).
- В образе данных нет.

## Структура (план, задача 1.2)

```
services/backup/
├── Dockerfile     # python-slim, USER non-root, healthcheck
└── backup.py      # cron-цикл копирования (ЭТАП B)
```
