## 1. Стек и обоснование

Ограничение ОГР-1: легковесность («веб движок (можно nginx)», «lite DB» — SQLite по слову Заказчика, вне репозитория). ОГР-4: ограничений по ресурсам VPS нет. Масштаб: 2 пользователя, до 1 000+ задач (NFR-2).

| Слой | Выбор | Обоснование в рамках легковесности |
|---|---|---|
| Front-proxy | **nginx** (reverse-proxy, TLS/Let's Encrypt, раздача статики) | Прямое пожелание Заказчика (п. В-1). Проверенное решение, нулевая стоимость лицензии, конфиг ~десяток строк |
| Backend-фреймворк | **Python + FastAPI** (ASGI, uvicorn) | Микрофреймворк: маршруты + валидация схем (pydantic) + middleware сессий из коробки; нет «энтерпрайз»-обвязки. REST API (ОГР-2) выражается напрямую. Альтернатива Flask — равно легковесна, FastAPI предпочтительнее готовыми контрактами OpenAPI |
| БД | **SQLite** (WAL-режим), файл вне репозитория | Прямое пожелание Заказчика (ОГР-1, NFR-5). Для 2 пользователей и 1 000 задач серверная БД (PostgreSQL) — лишняя эксплуатационная сущность; SQLite WAL покрывает конкурентность двух пользователей с запасом. Ноль демонов, бэкап = копия файла |
| Пароли | bcrypt (passlib) или argon2 | NFR-7: не хранить в открытом виде; оба алгоритма — стандарт, доступны pip-пакетом |
| Веб-морда | Серверные шаблоны (Jinja2) + минимальный ванильный JS (fetch к API) | Без SPA-фреймворков (React и т.п.) — несоразмерно личному проекту на 2 пользователей; ОГР-2 соблюдается: UI — клиент REST API, не лезет в БД |
| Развертывание | systemd-юнит, VPS, HTTPS | NFR-6 |

Отклонение от пожеланий: нет. nginx и SQLite приняты; фреймворк — решение СА в рамках «легковесности» (ОГР-1 делегирует выбор системному анализу).

## 2. Компоненты

```
Браузер ──HTTPS──> nginx ──> FastAPI (uvicorn, systemd)
                              ├── auth middleware (сессии/куки)
                              ├── REST API (/api/*)
                              │     ├── auth (login/logout)
                              │     ├── tasks CRUD + move + comments
                              │     ├── categories (справочник, CRUD)
                              │     ├── board
                              │     └── search (builder + advanced)
                              ├── Jinja2 шаблоны (страницы: login, доска, поиск, настройки)
                              └── SQLite (WAL) ── файл вне репозитория (NFR-5)
```

- **Auth middleware** — единая точка проверки сессии для страниц и API.
- **API-слой** — вся бизнес-логика: инвариант fast line (серверная проверка, не UI), жесткая валидация категории по справочнику (FR-21), priority-lock fast-задач (FR-27).
- **Модуль категорий** — CRUD справочника `/api/categories*` + серверная валидация задач + миграционный скрипт внедрения (`backend/app/migrate_categories.py`).
- **Фильтр-конвейер поиска** — builder→text→parse→параметризованный SQL (см. design.md §6).

## 3. API-контракты (REST, JSON)

Общее: префикс `/api`; все запросы, кроме exempt-списка авторизации, требуют валидную сессионную куку, иначе **401** `{"error": "unauthorized"}`.

**Exempt-список авторизации** (запросы без сессии не отклоняются 401; соответствует дельте auth, Requirement «Авторизация обязательна для API», и tasks 2.2):

| Путь | Причина exempt |
|---|---|
| `POST /api/auth/login` | Сам вход: сессии еще нет, получить ее можно только здесь |
| `GET /api/health` | Health-check для мониторинга и deploy: проверка живости до и без участия пользователей |

Все прочие `/api/*` — 401 без сессии. Страницы (не `/api`) exempts не являются и покрыты правилом §3.6: защищенные страницы без сессии — редирект на `/login`; сама страница `/login` и статика — доступны без сессии по необходимости (форма входа должна быть достижима). Ошибки валидации — **422** `{"error": "<сообщение>", "details": {...}}`. Конфликт — **409**. Не найдено — **404**.

### 3.1 Auth

| Метод/путь | Описание |
|---|---|
| `POST /api/auth/login` | Вход |
| `POST /api/auth/logout` | Выход (удаляет сессию и куку) |

**POST /api/auth/login**
- Запрос: `{"login": "string", "password": "string"}`
- Ответ 200: `{"ok": true, "user": "string"}` + `Set-Cookie: session=<token>; HttpOnly; SameSite=Lax; Secure`
- Ошибки: `401 {"error": "invalid credentials"}` — единый текст и для неверного логина, и для неверного пароля (не раскрывать существование логина, NFR-7).

**POST /api/auth/logout** — Ответ 200: `{"ok": true}`; сессия удалена, кука сброшена.

### 3.1a Health

| Метод/путь | Описание |
|---|---|
| `GET /api/health` | Health-check для мониторинга и deploy |

- Ответ 200: `{"status": "ok"}` — каркас и процесс приложения живы.
- Без авторизации (входит в exempt-список выше): проверка живости выполняется до входа пользователей, монитором и деплой-скриптом.
- Ошибок нет: тело фиксировано, БД не трогает.

### 3.2 Задачи (CRUD)

| Метод/путь | Описание |
|---|---|
| `POST /api/tasks` | Создать задачу |
| `GET /api/tasks/{id}` | Карточка задачи со всеми признаками и комментариями |
| `PATCH /api/tasks/{id}` | Редактировать признаки |
| `DELETE /api/tasks/{id}` | Удалить задачу |
| `POST /api/tasks/{id}/move` | Перевести в другой столбец (в т.ч. в «Выполнено» = архив) |
| `POST /api/tasks/{id}/comments` | Добавить комментарий |

Объект Task:
```json
{
  "id": 1,
  "title": "string (обязательно)",
  "description": "string|null",
  "priority": "low|medium|high|null",
  "category": "string|null",
  "due_date": "YYYY-MM-DD|null",
  "tags": ["string"],
  "is_fast": false,
  "status": "todo|in_progress|done",
  "done_at": "ISO-datetime|null",
  "archived_at": "ISO-datetime|null"
}
```

`done_at` — момент перевода задачи в «Выполнено» (новое требование Заказчика, FR-4 в редакции «архивация через день»): проставляется при move в done, снимается при обратном переводе; точка отсчета календарной границы автоархивации. `archived_at` проставляется НЕ при move, а ленивой автоархивацией при чтении доски (§3.3) после смены календарного дня по МСК.

**POST /api/tasks**
- Запрос: поля Task; обязателен `title`; `is_fast` — опциональный флаг fast line (только при создании — ручное назначение, ОГР-5).
- Валидации: непустая `category` вне справочника → **422** `{"error": "validation", "details": {"category": "not in categories"}}` (FR-21, §3.7); priority-lock (FR-27, ОГР-10): `is_fast=true` с явно переданным `priority ≠ "high"` (включая явный `null`) → **422** `{"error": "validation", "details": {"priority": "fast requires high"}}` — отклонение, а не молчаливая правка.
- Ответ 201: Task; при `is_fast=true` приоритет — `high` (устанавливается сервером автоматически, инвариант `is_fast ⇒ priority='high'`).
- Ошибки: `422` — нет названия или сработала валидация выше; `409 {"error": "fast line occupied"}` — is_fast=true при наличии активной (todo/in_progress) fast-задачи. Порядок проверок: валидации тела (категория, priority) — до проверки занятости fast line.

**PATCH /api/tasks/{id}** — Ответ 200: Task. Та же жесткая валидация категории (FR-21). `is_fast` при PATCH не входит (fast назначается только при создании, ОГР-5); изменение `priority` существующей fast-задачи на значение ≠ high (включая `null`) → **422** `{"error": "validation", "details": {"priority": "fast requires high"}}` — инвариант `is_fast ⇒ priority='high'` соблюдается при любом изменении. Ошибки: `404`, `422`.

**POST /api/tasks/{id}/move**
- Запрос: `{"status": "todo|in_progress|done"}`
- Ответ 200: Task (при `done` — проставлен `done_at`, задача ОСТАЕТСЯ на доске в столбце «Выполнено»; `archived_at` НЕ проставляется — автоархивация лениво при GET /api/board, §3.3; при обратном переводе из done снимаются оба: `done_at = NULL`, `archived_at = NULL`).
- Ошибки: `404`, `422` (недопустимый статус).

### 3.3 Доска

| Метод/путь | Описание |
|---|---|
| `GET /api/board` | Задачи, сгруппированные по столбцам |

- Перед формированием ответа выполняется **ленивая автоархивация** (FR-4, новая редакция): все done-задачи, момент перевода которых (`done_at`) приходится на предыдущий или более ранний календарный день по МСК, архивируются (`archived_at = now`). Механика — design.md §5.
- Ответ 200: `{"columns": {"todo": [Task], "in_progress": [Task], "done": [Task]}}` — только не архивные задачи. Столбец `done` содержит done-задачи, у которых `done_at` приходится на текущий календарный день по МСК (UTC+3); архив в ответ не попадает. Внутри столбцов: fast-задача выделена и отсортирована по приоритету.
- Ошибки: только 401.

**Часовой пояс (зафиксировано):** календарная граница «сегодня» — МСК, UTC+3, фиксировано и независимо от локального времени сервера (сервер и/или контейнер могут иметь любой TZ; расчеты границ дня и `done_at`-сравнение выполняются в UTC+3).

### 3.4 Fast line

Отдельного endpoint нет: fast line — проекция `is_fast` + активные статусы в `GET /api/board` и ограничение при `POST /api/tasks` (409). См. design.md §4.

**Priority-lock (FR-27, ОГР-10):** fast и приоритет не независимы — инвариант `is_fast ⇒ priority='high'`. Fast-задача при создании получает `high` автоматически; явно переданный приоритет ≠ high отклоняется 422 (§3.2); изменение приоритета существующей fast-задачи через PATCH — тот же 422. В UI поле приоритета fast-задачи заблокировано значением «высокий» — серверная валидация остается страховкой от подделанных клиентских запросов. Ограничение действует только на fast-задачи: обычная задача принимает low/medium/high/null без ограничений.

### 3.5 Поиск

| Метод/путь | Описание |
|---|---|
| `GET /api/search` | Поиск по признакам |
| `POST /api/search/advanced` | Поиск по SQL-подобному тексту фильтра |

**GET /api/search**
- Query-параметры (все опциональны; пустой набор = все задачи): `priority`, `category`, `tag` (повторяемый), `due_before`, `due_after`, `archived=true|false|all` (по умолчанию `all`).
- Ответ 200: `{"results": [Task]}` — каждый Task содержит признак архивности.
- Ошибки: `422` (невозможное значение параметра).

**POST /api/search/advanced**
- Запрос: `{"query": "priority = \"high\" AND tag IN (\"home\")"}`
- Ответ 200: `{"results": [Task], "normalized_query": "…"}` (normalized — сериализация распарсенного фильтра обратно, для UI).
- Ошибки: `400 {"error": "filter syntax: <позиция/причина>"}` — синтаксическая ошибка; запрос не выполняется.

### 3.6 Страницы (не API)

`GET /login`, `GET /board`, `GET /search`, `GET /wiki` (заглушка с todo), `GET /settings` (настройки: управление справочником категорий — единственный состав настроек, FR-25; настройки общие для обоих пользователей, FR-24/ОГР-11 — без пер-пользовательских списков и разграничения прав). Все, кроме `/login` и раздаваемой nginx'ом статики, — редирект на `/login` без сессии (страница входа и статика должны быть доступны без сессии, иначе вход невозможен; exemption страниц — не часть exempt-списка API-авторизации выше). Раздел «Настройки» в сайдбаре — внизу слева, рядом с кнопкой выхода.

Селект-поля (категория в форме задачи и в фильтре-конструкторе) заполняются из фактических данных: категории — из `GET /api/categories` (справочник), теги/подсказки — из `GET /api/suggestions` (заведенные значения); статические списки значений не используются (FR-30, DEF-001 закрыт).

### 3.7 Категории (справочник)

Справочник категорий (FR-19) — задаваемый пользователем список категорий проекта; категория задачи — значение из справочника, не свободный текст. Справочник един для системы (ОГР-7), состояние — общие таблицы БД без user_id. Управление (создание/переименование/удаление) — через страницу настроек (§3.6) и API:

| Метод/путь | Описание | Ответы |
|---|---|---|
| `GET /api/categories` | Список справочника (источник select-полей формы и фильтра) | 200 `{"categories": [{"id": 1, "name": "home"}, ...]}` — отсортировано по name |
| `POST /api/categories` | Создать категорию | 201 `{"id": ..., "name": ...}` |
| `PATCH /api/categories/{id}` | Переименовать (применяется ко всем задачам со старым значением) | 200 `{"id": ..., "name": ...}` |
| `DELETE /api/categories/{id}` | Удалить | 200 `{"ok": true}` |

**POST /api/categories** — Запрос: `{"name": "string"}`. Ошибки: `422` — пустое/пробельное имя (после trim); `409 {"error": "category already exists"}` — дубль имени (уникальность — на уровне БД; «home» и «Home» — разные записи, слияние «синонимов» не автоматизируется, Д-2).

**PATCH /api/categories/{id}** — Запрос: `{"name": "string"}`. Переименование применяется ко всем задачам (FR-20): задачи ссылаются на категорию по значению (TEXT, §4), поэтому в одной транзакции выполняются `UPDATE categories` и `UPDATE tasks SET category = ?` — значение переносится у всех задач-ссылок атомарно. Ошибки: `404`, `422` (пустое имя), `409` (дубль имени).

**DELETE /api/categories/{id}** — Удаление блокируется, если категория используется хотя бы одной задачей (Д-1): порядок «проверить использование → удалить»; ошибка `409 {"error": "category in use", "details": {"tasks": N}}` — перевести задачи на другие категории и повторить. Ошибка: `404`.

**Жесткая валидация категории задачи (FR-21):** при POST /api/tasks и PATCH /api/tasks/{id} непустая `category` сверяется со справочником (`SELECT 1 FROM categories WHERE name = ?`); отсутствует → **422** `{"error": "validation", "details": {"category": "not in categories"}}`. Точка проверки — API-слой: обойти валидацию через API нельзя; UI не позволяет отправить значение вне списка (select из справочника), серверная проверка — страховка. Пустая категория (NULL/пустая строка) проходит валидацию — nullable-модель данных сохраняется; валидация следует за справочником: удаленная из справочника категория более не принимается.

**GET /api/suggestions** — без изменений (set() из тегов и категорий существующих задач); переиспользуется формой задачи как источник подсказок тегов с правом создания нового значения (в отличие от поиска). Категории — из справочника, не из suggestions.

**Миграция при внедрении (FR-22, NFR-8, ОГР-9):** одноразовый идемпотентный скрипт `backend/app/migrate_categories.py` (запуск: `python -m app.migrate_categories` из каталога `backend/`). Шаги: (1) снимок «до» — уникальные непустые значения `tasks.category` + категории каждой задачи; (2) `INSERT OR IGNORE INTO categories SELECT DISTINCT` непустых значений — маппинг 1:1, пустые значения записей не создают, повторный запуск не создает дублей; слияние «синонимов» (регистр, опечатки) НЕ выполняется — корректировка после миграции средствами переименования; (3) задачи не трогаются — их значения уже совпадают с созданными записями; (4) приведение fast-задач к инварианту FR-27 (`UPDATE tasks SET priority='high' WHERE is_fast=1 AND priority != 'high'`); (5) автосверка «после» (NFR-8): (а) каждое непустое значение category каждой задачи присутствует в справочнике, (б) `COUNT(categories)` = числу уникальных непустых значений «до», (в) значения категорий каждой задачи = снимку. Шаги 2 и 4 — одна транзакция (частично мигрированная БД исключена). Расхождение сверки → exit 1, внедрение не считается завершенным; сверка зеленая → exit 0, отчет в stdout.


## 4. Модель данных (SQLite)

Файл БД — вне репозитория (NFR-5: `*.db`, `*.sqlite*` в `.gitignore`; путь — конфиг развертывания).

```sql
users (
  id            INTEGER PK,
  login         TEXT UNIQUE NOT NULL,
  password_hash TEXT NOT NULL            -- bcrypt/argon2, не открытый пароль (NFR-7)
)

sessions (
  token       TEXT PK,                   -- криптостойкий случайный
  user_id     INTEGER NOT NULL FK -> users.id,
  created_at  TEXT NOT NULL,
  expires_at  TEXT NOT NULL              -- скользящий TTL
)

tasks (
  id          INTEGER PK,
  title       TEXT NOT NULL,             -- обязательно (FR-5)
  description TEXT,
  priority    TEXT CHECK(priority IN ('low','medium','high') OR priority IS NULL),
  category    TEXT,
  due_date    TEXT,                      -- YYYY-MM-DD
  is_fast     INTEGER NOT NULL DEFAULT 0,-- fast line (FR-3)
  status      TEXT NOT NULL DEFAULT 'todo'
              CHECK(status IN ('todo','in_progress','done')),  -- Ожидает/В работе/Выполнено (ОГР-3)
  done_at     TEXT,                      -- момент перевода в done; NULL <=> не в done (FR-4, новая редакция)
  archived_at TEXT,                      -- NOT NULL <=> в архиве; ставится ленивой автоархивацией (FR-4), НЕ при move
  created_at  TEXT NOT NULL,
  updated_at  TEXT NOT NULL
)

Инвариант (FR-4, новая редакция): `status = 'done' AND archived_at IS NULL` ⇒ `done_at IS NOT NULL` —
задача видима в столбце «Выполнено» до конца текущего МСК-дня; ленивая автоархивация при
GET /api/board переводит такие задачи в архив по смене календарного дня по МСК (UTC+3,
фиксировано — независимо от локального TZ сервера).
```

- `tasks.category` — TEXT (nullable), ссылка **по значению** на `categories.name`; FK не вводится: хранение по значению делает переименование категории переносом значения у всех задач-ссылок одним UPDATE (§3.7), а целостность «непустая category существует в справочнике» обеспечивает серверная валидация API (FR-21) — nullable-поле её схемой не выразить.
- Инвариант priority-lock (FR-27): `is_fast = 1 ⇒ priority = 'high'` — поддержан серверной валидацией POST/PATCH (§3.2, §3.4) и приведением существующих fast-задач при миграции (§3.7); CHECK-ограничением в схеме не выражается (зависимость между двумя колонками).

Индексы: `tasks(status, is_fast)`, `tasks(archived_at)`, `tasks(priority)`, `task_tags(tag_id)`, `comments(task_id)`, `tasks(done_at)` (фильтр ленивой автоархивации и столбца done, §3.3), `tasks(category)` (проверка использования при удалении категории — Д-1, и сверка миграции — NFR-8).
