# PLAN: Аудит потребления железа сервисами (hw-audit)

**Дата:** 2026-10-26 · **Инициатор:** Заказчик · **Флоу:** 4 (обслуживание, ops) — только сбор фактов и отчет, прод-код и конфиги не трогаем. Любые оптимизации — отдельным пакетом по решению Заказчика после отчета.

## Цель

Карта потребления железа всеми сервисами хоста: кто сколько ест (CPU/RAM/disk), где нет лимитов, что можно ужать без риска. Выход — отчет с оценкой экономии по каждому пункту.

## Состав работ

1. **Инвентаризация хоста** — CPU/RAM/swap/disk (nproc, free -h, df -h), версии docker/compose.
2. **Снимки потребления** — docker stats (3 среза с интервалом), per-container CPU%/MEM%/NET/IO; сравнение с memory-лимитами из compose.
3. **Диск:** docker system df (образы/тома/кэш), размеры логов контейнеров (json-file без ротации?), volumes, journald.
4. **Периметр:** стек ekotov-wiki-par (7), game-portal, 3x-ui (только чтение — НЕ трогать!), netdata/прочее.
5. **Анализ:** контейнеры без лимитов; завышенные/заниженные лимиты; дублирование функций (search vs app?); count воркеров/тредов vs ядра; периодические джобы (backup — пики); image-size vs distroless-альтернативы.
6. **Отчет** — `docs/ops/hw-audit-2026-10-26.md`: таблица сервис → CPU/RAM (пик/среднее) → лимит → вердикт; топ-рекомендации с оценкой экономии (RAM X MB, disk Y GB); что НЕ трогаем и почему.

## Роли

- **devops** (сабагент): сбор фактов по разделам 1–4, сырые данные в артефакт.
- **ПМ**: анализ (раздел 5), отчет, доклад Заказчику.

## Запреты

- Никаких рестартов/stop/prune на живом проде (включая 3x-ui и game-portal).
- Read-only диагностика; docker system prune — только рекомендация в отчет, не действие.

## Критерий приемки

Отчет с таблицей по каждому контейнеру и ≥3 конкретными рекомендациями с количественной оценкой экономии.
