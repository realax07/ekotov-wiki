## Пакет 1: add-netdata-monitoring (Флоу 1)

**Цель:** мониторинг железа/контейнеров/сервисов в Netdata; ссылка в UI wiki
в нижнем левом углу сайдбара; доступ — только учетка owner.

**Состав:**
- 0.1 SA: requirements + design + дельта (новая capability monitoring):
  Netdata-контейнер в compose (health, RAM-лимит), авторизация перед
  Netdata (basic auth на nginx-локации /netdata — owner-креды), ссылка в
  сайдбаре (рендер по роли: только owner — серверная проверка)
- 1.1 Dev: Netdata в compose (образ netdata/netdata, ~150–300 MB RAM,
  host-метрики через маунты /proc,/sys + docker.sock ro для контейнеров),
  nginx-локация /netdata/ (proxy_pass + basic-auth owner), ссылка
  «Мониторинг» в сайдбаре (только owner; PE/аноним — скрыта и 403)
- 1.2 QA: смоук (Netdata UI под owner отвечает, PE/аноним — нет), регресс
  web сайдбара
- 1.3 [ops] Devops + Заказчик: прод-выкатка, приемка (дашборд CPU/RAM/HDD/
  контейнеры глазами Заказчика)

**Риски/уроки:** docker.sock в контейнер — ro, только чтение метрик; вес
контейнера меряем после подъема (RAM-лимит по факту).

## Пакет 2: add-gallery-service (Флоу 1)

**Цель:** ЧЕТВЕРТЫЙ раздел сайдбара «Галерея» — сервис изображений с
категориями и тегами; просмотр «как в галлерее»: клик по превью → модальное
окно на весь экран с листанием (←/→), лайк/дизлайк, скачивание, комментарии.
Связь с трекером — только общий фронт сайдбара (без ссылок на задачи).
Доступ общий (оба пользователя, без разделения прав).

**Состав:**
- 0.1 SA: requirements + design + дельты (новая capability gallery): схема
  (images: id, filename, original_name, mime, size, uploaded_by, created_at;
  categories — справочник галереи; image_tags — переиспользовать механизм
  тегов — решает СА; reactions: image_id, user_id, value(+1/−1);
  image_comments: image_id, user_id, body, created_at), API-контракт
  (/api/images upload/list/get, /api/images/{id}/like, /comments), UI-флоу
  (сетка превью → full-screen модалка с листанием ←/→, панель:
  лайк/дизлайк, скачать, комментарии)
- 1.1 Dev: services/images (FastAPI по образцу search: upload (multipart),
  list с фильтрами категории/тега, get, like/unlike, comments CRUD; том
  images-data; файлы НЕ в БД — БД только метаданные; превью-генерация —
  решает СА: Pillow на upload или on-the-fly)
- 1.2 Dev: фронт «Галерея» (4-й пункт сайдбара, страница /gallery: сетка
  превью, фильтры категория/тег, загрузка; full-screen модалка с листанием,
  лайк/дизлайк, скачивание, комментарии) — общий фронт сайдбара, без связей
  с задачами
- 1.3 Devops: nginx-маршрутизация /api/images* (пара `=` + `^~`, по образцу
  search) + отдача файлов /images/ (отдельный том), образ images, compose
  (RAM-лимит)
- 2.1 QA: юниты images (upload/list/like/comments), api на стенде, web
  регресс (галерея + сайдбар не сломал трекер)
- 2.2 [ops] Devops + Заказчик: прод-выкатка (миграция ядра: таблицы gallery —
  one-shot с репетицией на копии), приемка Заказчика (загрузка, просмотр,
  лайк, комментарий)

**Открытое на этапе СА:** thumb-генерация (Pillow на upload vs on-the-fly),
удаление изображений (кто), лимит размера файла, хранение оригинал+превью.
