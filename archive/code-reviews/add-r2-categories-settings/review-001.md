## Известная эскалация (design.md §1.4 vs реализация)

Действительно: design.md §1.4 утверждает, что при переименовании «задачи обновляются автоматически» (следствие хранения по значению) — **это неверно**: UPDATE имени в `categories` сам по себе не трогает `tasks.category`. Реализация компенсирует явным `UPDATE tasks SET category = ? WHERE category = ?` в той же транзакции (`categories.py:166–169`), и наблюдаемое поведение **соответствует Scenario спеки FR-20** («все задачи … отображают категорию „дом"») — подтверждено смоком каскада. Вывод: обход корректен, дефект — только в тексте design.md. **Эскалация оркестратору** (дефект спеки/дизайна, не задачи): поправить §1.4 design.md в пакете, чтобы документ не расходился с реализацией.

## Best practices (второй круг)

- SQL только параметризованный (categories.py, tasks.py, migrate_categories.py) — инъекций нет.
- Секретов в диффе нет; конфиг через env (DB_PATH, SECRET_KEY обязательны).
- Ошибки не глотаются: IntegrityError → 409 + rollback; соединения закрываются в `finally`.
- Тела ошибок в формате sdd (`{error, details}`); коды совпадают с sdd r2 §3.1 дословно.
- `extra="forbid"` на pydantic-моделях — лишние поля тела отклоняются.
- Данных в git нет: БД вне репозитория (копия боевой БД использовалась только в /tmp).

## Integration-точки (третий круг)

- `main.py`: роутер подключен до search/board — порядок не влияет (prefix-ы разные).
