## Решения по вопросам dev

**1) Текст 401: «unauthorized» (формулировка задачи) vs «invalid credentials» (реализовано).** Решение dev — обосновано. Приоритет API-контракта sdd.md r4 §3.1 дословен: `401 {"error": "invalid credentials"} — единый текст и для неверного логина, и для неверного пароля (не раскрывать существование логина, NFR-7)`. Слово «unauthorized» из tasks.md — общий 401-код из формулировки задачи, а не контрактный текст ошибки; sdd — арбитр контракта (правило «спека — арбитр»). Формулировка задачи 2.1 («единый текст без раскрытия причины») реализованным текстом соблюдена. Расхождение задач формулировки и sdd, если оно вообще имеет значение, — не дефект задачи. ✅ принято.

**2) Logout отсутствует в коде.** Решение dev — правомерно. Logout (`POST /api/auth/logout`) в tasks.md отнесен к задаче 2.2 («TTL со скольжением и продлением; logout … удаляет сессию и куку») и к 2.3 (страница выхода). Наличие logout-контракта в sdd §3.1 не требует его реализации в 2.1; намеренное отсутствие задокументировано в докстринге `auth.py`. Нарушения трассировки нет — обратное было бы выходом за scope задачи. ✅ принято.

## Факт-чек ревьюера (воспроизведено лично, TestClient, чистая тестовая БД)

| Проверка | Результат |
|---|---|
| Валидный логин → 200 + кука | `200 {"ok": true, "user": "owner"}`; `Set-Cookie: session=…; HttpOnly; Max-Age=2592000; Path=/; SameSite=lax; Secure` — все три флага на месте, путь `/`. ✅ |
| Неверный пароль vs несуществующий логин | Оба → `401`, тела байт-в-байт идентичны (`bodies_identical: true`), заголовки ответов идентичны (content-length 31, content-type). ✅ |
| Timing-защита (чтение кода) | `auth.py`: на пути несуществующего логина `row is None` → `stored_hash = _DUMMY_PASSWORD_HASH` (bcrypt-хеш той же стоимости, генерируется на импорте модуля, не на запросе) → `bcrypt.checkpw` выполняется всегда. Защита реальна, не заявлена. ✅ |
| Timing-защита (замер) | 3 прогона на каждый класс: неверный пароль 0.377 с, несуществующий логин 0.393 с, отношение 1.04 — в пределах шума bcrypt. ✅ |
| SQL | Оба запроса (`SELECT … WHERE login = ?`, `INSERT INTO sessions …`) параметризованы; конкатенации нет. ✅ |
| Токен | `secrets.token_urlsafe(32)` = 256 бит энтропии ≥ 128 (design §2). Повторный логин создает вторую запись (PK уникален), коллизий нет. ✅ |
| Хранение токена в БД | Токен хранится в БД в открытом виде и совпадает с токеном в куке (сверено посимвольно). Это **соответствует sdd §4**: `sessions.token TEXT PK — криптостойкий случайный`; хеш токена в модели данных не предусмотрен. Расхождений с sdd нет. ✅ |
| TTL в БД vs Max-Age куки | created_at `2026-09-17T12:07:03` → expires_at `2026-10-17T12:07:03` = ровно 30 дней; Max-Age `2592000` с = 30 дней. Консистентны, источник единый (`SESSION_TTL`). ✅ |
| Нет раскрытия версий/стека | `docs_url/redoc_url/openapi_url = None` (main.py); тела 401/422 без стека и версий; длинный ввод (5000 симв.) → корректный 401. ✅ |
| Соседние сценарии (круг 3) | `GET /api/health` отвечает 200 без сессии (exempt из дельты auth соблюден); logout отсутствует — `404 {"detail":"Not Found"}` (ожидаемо до 2.2); схема sessions в БД соответствует sdd §4. ✅ |

## Проверенные Scenario (specs/auth/spec.md)

- «Успешный вход существующего пользователя» — HTTP-уровень подтвержден (200 + сессия в БД); UI-часть формы — вне scope 2.1 (задача 2.3).
- «Неверный пароль» — 401, доступ не предоставлен. ✅
- «Несуществующий пользователь» — 401, единый текст, причина не раскрыта (байт-в-байт идентичность + тайминг). ✅
- «Посторонний не может войти» — покрыт проверкой несуществующего логина. ✅
- «Проверка хранимых учетных данных» — в БД только bcrypt-хеш (seed 1.3, схема `password_hash`); открытых паролей нет. ✅
- «Повторное открытие приложения в рамках действующей сессии» / «Истечение сессии» / API-сценарии без сессии и с просроченной сессией — это middleware (задача 2.2), в scope 2.1 не входят; проверен только смежный смоук (health exempt).

## Что НЕ проверено (честно)

- Реальный HTTPS-прогон через nginx (флаг `Secure` проверен на уровне заголовка Set-Cookie; поведение браузера с не-HTTPS в dev — вне скоупа).
- Скользящее продление TTL и инвалидация по expires_at — кода проверки сессии еще нет (задача 2.2), проверять нечего.
- Страница /login и редиректы — задача 2.3/3.2.
- Долговременный статистически значимый тайминг-анализ (100+ замеров) — трехзамерный смоук достаточно для подтверждения наличия dummy-проверки, которая доказана чтением кода.
