### Гонка (параллельные POST is_fast, 8 потоков × 3 прогона)

| Прогон | 201 | 409 | Активных fast в БД |
|---|---|---|---|
| 1 | ровно 1 | 7 | 1 |
| 2 | ровно 1 | 7 | 1 |
| 3 | ровно 1 | 7 | 1 |

Тело 409 во всех случаях дословно `{"error": "fast line occupied"}`.

Дополнительно ревьюер воспроизвел базовое утверждение dev на копии схемы tasks
(20 прогонов × 2 потока, check-then-insert): **без** BEGIN IMMEDIATE обе-201 в
11/20 прогонов (утверждение dev подтверждено); **с** BEGIN IMMEDIATE — 0/20,
ровно одна запись во всех прогонах. Fix не «плацебо».

### Unarchive-дыра (сценарий из review-4.4-001)

| Шаг | Результат |
|---|---|
| Создание fast-A → 201; создание fast-B при занятой линии | 409 (досл.) |
| fast-A → done; создание fast-B | 201 |
| unarchive fast-A (done → todo) при активной fast-B | **409** `{"error": "fast line occupied"}` |
| БД после этого 409 | fast-A осталась `status=done`, `archived_at` проставлен (мутации нет) |
| fast-B → done; unarchive fast-A при свободной линии | **200**, `archived_at` снят, `is_fast` сохранен |
| unarchive **обычной** archived-задачи при занятой fast line | 200 (не задета) |
| move fast todo → in_progress (без смены архивности) | 200 (инвариант не срабатывает на не-unarchive пути) |

### Rollback при 409

- 409 POST с tags: COUNT строк в `tasks` до/после одинаков (3 = 3); тег
  `ghosttag` в `tags` не создан — rollback откатывает и вставки тегов пути.
- Пустой title при is_fast → 422 (валидация до транзакции).

### Регрессия CRUD (обычные задачи)

POST 201 (title+priority+tags) / GET 200 (все поля по схеме) / PATCH 200 —
только переданные поля, tags заменен целиком / move 200 / DELETE 204 → GET 404.
404 на move несуществующего id, 422 без title, `GET /api/board` 200.
Сценарии спеки: «Повторная попытка после отказа» (обычная после 409 — 201),
«Освобождение» (fast → done → новая fast — 201), «Обычная задача не блокирует
fast line» (активные обычные не мешают созданию fast) — все подтверждены.

## Круг 1 — спека как закон

- Все 6 Scenario дельты fastline покрыты (включая оба негативных: UI и API).
- 409-тело дословно sdd §3.2: `{"error": "fast line occupied"}` — совпадает
  посимвольно, включая unarchive-ветку.
- COUNT-проверка ровно по инварианту: `is_fast = 1 AND status IN ('todo','in_progress')`
  (ОГР-3 активные; done = архив, линию не занимает — design §4 «Освобождение»).
- Параметры SQL — только `?`-плейсхолдеры (в т.ч. `ACTIVE_STATUSES` распакован
  в параметры, не в строку SQL).
- Расширение сверх спеки (unarchive-ветка в move): правомерно, см. ниже.

## Круг 2 — best practices

- BEGIN IMMEDIATE — корректный механизм для SQLite/WAL: захват writer-lock
  до проверочного SELECT; `_fast_line_busy` внутри той же транзакции. Без него
  check-then-insert атомарным не является (воспроизведено: см. таблицу гонки).
- 409-выход — через `conn.rollback()` → `finally: conn.close()`; мусорных
  строк нет (проверено чтением БД).
- SQL параметризован; секретов нет; БД/логи не в git; ошибки не глотаются
  (IntegrityError-страховка сохранена).
- Читаемость: `ACTIVE_STATUSES`, `_fast_line_busy`, `FAST_LINE_OCCUPIED_BODY` —
  имена по домену; докстринги честно фиксируют расширение и его источник.

## Круг 3 — integration-точки

- Регрессия CRUD обычных задач — без изменений (смоук выше).
- board/comments/tags не задеты: диф не трогает их пути; смоук /api/board 200.
- PATCH по-прежнему не принимает `status`/`is_fast` (задача 4.1/4.2) — обходных
  путей перевода задачи в fast, кроме создания и unarchive, нет; оба закрыты.
- Схема БД не менялась (миграций не требуется).

## Решение по расширению сверх спеки

Unarchive-ветка (move done → todo/in_progress для fast-задачи) в спеке fastline
сценарием не прописана — там только создание. Правомерность подтверждена:
ADDED Requirement «Не более одной fast-задачи в активных статусах» сформулирован
как инвариант уровня системы (MUST), а не только сценарий создания; unarchive —
фактически «назначение второй fast-задачи» в обход создания, и без проверки он
ломает инвариант (подтверждено в review-4.4-001 живым смоуком). По духу
покрывается и design §4 («Место проверки: … и при любых попытках перевода в fast»).

**Рекомендация ПМ:** при архивации change-пакета (контракт 7, слияние дельт в
master-spec) добавить в fastline-спеку сценарий «Возврат архивной fast-задачи при
занятой линии → 409» (и позитивный «при свободной → 200»), чтобы дельта и код
сошлись дословно. До этого момента — задокументированное расхождение, не дефект.
