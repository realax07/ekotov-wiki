## Оси ревью

- **Соответствие design/sdd/FR:** `GET /api/profile` — 200 ровно
  `{login, display_name, role, bio, avatar_url}` (sdd §3.1a-кватер дословно);
  `avatar_url` null при avatar_path NULL — URL не строится (B-3 ревью-001,
  design §2). `PUT` — 200 с обновленным профилем; только пользователь сессии
  (JOIN sessions→users по токену куки, FR-39); avatar_* от клиента не
  принимаются (верно — зона 2.3). `me` расширен составом профиля, ключ
  `user` сохранен (обратная совместимость, design §3) — MODIFIED-дельта
  реализована и согласована с правками me-тестов Р3.
- **Валидация роли по справочнику (ОВ-21):** `VALID_ROLES = ('Product
  manager', 'Product engineer')` — фиксированный список ровно из двух
  значений; вне списка → 422 `{"error": "validation error",
  "details": {"role": "not in directory"}}` в форме sdd §3. Роль null не
  валидируется и сбрасывается в NULL — соответствует «пустые значения —
  null» (sdd §3.1a-кватер); подтверждено живым прогоном (role="" → 422,
  role=null → 200 с role:null).
- **Д-10:** пустая строка display_name/bio нормализуется в None
  (field_validator) — единое «пустые значения — null», fallback на логин
  остается на клиенте. Тест TC-profile-007 проверяет именно null (не «»),
  верно по контракту.
- **Д-11 (пароль, захваченный из 2.2):** bcrypt.checkpw(current) →
  bcrypt.hashpw(new, gensalt); UPDATE/DELETE по sessions отсутствуют —
  подтверждено тестом TC-passwd-004 на уровне записи (token/user_id не
  тронуты, expires_at корректно исключен из сравнения из-за скользящего
  TTL). 422 единый текст «invalid current password», пароль при ошибке не
  меняется; 422 пустой новый. Хранится только хеш (NFR-7).
- **401 middleware:** все три эндпоинта вне EXEMPT_API (список в
  middleware.py не расширялся — правок middleware нет в диффе);
  независимый прогон: GET/PUT/password без сессии → 401
  `{"error": "unauthorized"}` (TC-profile-003 проходит).
- **Качество тестов (13):** дельта покрыта: 2x GET-сценарий (owner + второй
  пользователь), негатив 401 (все 3 эндпоинта), CRUD-цикл PUT→GET→me,
  негатив ОВ-21 с проверкой НЕИЗМЕНЕННОСТИ профиля (в т.ч. DB-direct),
  негатив типа полей, Д-10 пустое имя, Д-11 успех (старый пароль отклонен,
  новый работает, сессия жива), неверный текущий (пароль не изменен),
  пустой новый, запись sessions не тронута, расширенный состав me, дефолты
  null при незаполненном. Гигиена: teardown восстанавливает профиль и
  пароль owner (роль owner = «Product manager» — иначе повторный
  migrate_r4 даст exit 1; guard-фикстура возвращает seed-пароль bcrypt-хешем
  даже при падении теста) — повторные прогоны безопасны, проверено двумя
  полными прогонами.
- **Зона записи (7 файлов):** profile.py (новый), auth.py (расширение me —
  в ТЗ 2.1), main.py (роутер), tasks.md (чекбокс 2.1), test_profile_r4.py
  (новый), test_auth_me.py + test_authme_r3.py (точное тело → ключ user —
  обязательная адаптация под MODIFIED-дельту, не самодеятельность).
  Служебный SESSION.md в worktree НЕ закоммичен (untracked) — чисто.
- **Регресс:** подтверждено независимо — 144 passed / 9 skipped / 2 xfailed
  / 0 failed; профильный сьют 13/13 passed; все 9 skip — унаследованные
  ручные НФТ-процедуры и UI-скоуп, не связанные с 2.1 (ни один не «нужен
  env»); `openspec validate --strict`: change valid. Негативный допуск
  role="" → 422, role=null → 200/NULL, пароль без политики сложности
  (спека не требует — верно, вводить запрещено) — проверены живыми
  запросами сверх сьюта.

  только усложнит конвейер без выигрыша в качестве. Требование: чекбокс 2.2

  появится третья ветка с кодом пароля. Профильный роутер монтируется

  страница настроек (3.1) должна отправлять все три поля разом.
- **minor m-2 (без действия):** 404 `{"error": "not found"}` при живой
  сессии с удаленным пользователем — ветвь вне спеки (достижима только
  ручной правкой БД), выбор кода соответствует §3 «Не найдено — 404».
