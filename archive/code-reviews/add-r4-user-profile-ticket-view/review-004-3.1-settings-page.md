## Оси ревью (по пунктам ТЗ ревью)

- **Соответствие design §4/§6 и дельтам:** страница `GET /settings/profile` в pages.py — состав ровно по design: форма профиля (display_name — text, role — select ровно с двумя значениями ОВ-21, bio — textarea), блок смены пароля (текущий+новый), загрузка аватара (file, png/jpg) с показом ошибок; кнопки сохранения — отдельные на каждый блок. Справочника категорий на странице нет (ОГР-20, тестом TC-setp-202: `#category-list` count=0, текста «Категории» нет); общий `/settings` не изменен. Роут не дублирует редирект — авторизация страниц middleware'ом (Scenario «Негативный: неавторизованный доступ» покрыт TC-setp-201, редирект на /login подтвержден прогоном).
- **API-контракты (потребление 2.1–2.3):** предзаполнение — GET /api/profile при загрузке с сигналом готовности `data-loaded` (автожидание тестов, конвенция #board); пустые поля → пусто, роль NULL → дефолт select (не ошибка). PUT — ровно по M-1 review-003: уходят ВСЕ ТРИ поля (display_name/bio с emptyToNull — Д-10; role всегда) — подтверждено тестом фактом в БД (`row == (name, role, bio)`). 422-тексты: password — «invalid current password»→«Неверный текущий пароль», «empty new password»→«Новый пароль не может быть пустым»; avatar — «file too large»/«invalid file type» смаплены (m-1); role 422 различается по `details.role`. Multipart — FormData c полем `file`, превью по `avatar_url` из ответа (с `?v=`). 401 между загрузкой и действием → переход на /login (паттерн settings.js).
- **Клик-профиль (Д-10, navigation MODIFIED):** подпись = display_name или логин (тесты TC-setp-204/206 с reload), аватар вместо кружка при avatar_url, fallback кружок с буквой (TC-ava-102: `img.profile-avatar` есть, `.profile-badge` count=0). Клик открывает /settings/profile, НЕ /settings (TC-nav-201). aria-label = «Профиль: <имя>» — сознательно не начинается с «Настройки», чтобы не ловить strict-violation в TC-nav-006…008: подтверждено прогоном — 3/3 settings_link-тестов зеленые на новой разметке.
- **XSS-гигиена:** все пользовательские строки (display_name, bio, логин) — только `textContent`/`setAttribute` (profile.js и profile-settings.js, включая showMessage/showSuccess); URL аватара — через свойство `src`, не разметку. `innerHTML`/`insertAdjacentHTML` в диффе отсутствуют. Инъекция через display_name в aria-label безопасна (setAttribute не парсит HTML).
- **Правки conftest (законность/минимальность):** три правки, все в зоне фикстур запуска и минимальные: (1) seed ролей owner→«Product manager», wife→«Product engineer» (ОВ-21) — законно: web-стенд миграцию не запускает, дефолт обязан быть воспроизведен на уровне seed, иначе предзаполнение роли недетерминировано; (2) AVATARS_DIR стенда → tmp + экспорт EKOTOV_WIKI_AVATARS_DIR с очисткой в teardown — законно и обязательно (blocker C-1: никаких записей в продовый /var/lib/ekotov-wiki/avatars — проверено, тесты читают каталог через env и удаляют файл в гигиене); (3) `page.route` → `page.context.route` для /static — необходимо: тесты задачи открывают вторые страницы того же контекста (сессии wife/fresh), на page.route правило не действует. Изоляция от прода соблюдена (tmp TemporaryDirectory на сессию).
- **static_v не тронут:** pages.py `static_v = "r3.2"` — без изменений (единый финальный бамп в 6.3, C-5 review-001, design §6). Тесты от кеша не зависят: web-стенд поднимается свежим на каждый прогон, статики в кеше нет; новые файлы (profile-settings.*) в кеше прод-пользователей отсутствуют по определению, а измененный profile.js попадает под финальный бамп до деплоя — риска релиза нет.
- **Качество web-тестов (11):** покрытие трассировано в docstring'ах (TC-setp-201…206, TC-passwd-101/102, TC-ava-101/102, TC-nav-201): негатив не пропущен — неавторизованный редирект, неверный текущий пароль (+проверка что вход со старым работает), txt-файл отклонен (+БД не изменена). Позитив с проверкой факта на сервере (SQLite-direct), сценарий «только свои данные» через вторую сессию wife. Автожидание везде expect-ами с таймаутами, sleep нет. Гигиена: profile_hygiene (профиль + файл аватара + avatar_path NULL) и owner_password_guard (bcrypt-возврат seed-пароля) — teardown независимо от исхода; повторные прогоны безопасны (проверено тремя прогонами сьюта). Пароли в файлах — только тестовые значения (NFR-7 не нарушен).
