# requirements.md — ТЗ change-пакета add-containerization (ЭТАП 0+1 плана P11)

> Статус: УТВЕРЖДЕН r1 (Заказчик, Telegram 2026-10-03: «Утверждаю») | Автор: ba_agent | История: r1

## 1. Общее описание

Легкий БА-проход change-пакета `add-containerization`: **внешнее поведение продукта не меняется**. Система переводится с systemd-деплоя (rsync + uvicorn :8377 + хостовой nginx :10443) на контейнерную топологию ЭТАПА 1 плана P11: `app` (uvicorn) + `nginx` (статика + reverse proxy) + именованный том данных, управление — `docker compose`. Решения Заказчика ОВ-1…ОВ-4 зафиксированы (все рекомендации ПМ приняты) — `docs/ba/architecture-services-plan.md` §8 и `decisions/2026-10-03-p11-containerization.md` (ЕДИНЫЙ ИСТОЧНИК требований). ЭТАП 2 (выделение сервисов, первый кандидат — `search`) в скоуп данного ТЗ не входит.

Нормативный план: `docs/ba/architecture-services-plan.md` §8 (решения Заказчика + факты VPS). Запись журнала решений: `decisions/2026-10-03-p11-containerization.md` (decision_id `2026-10-03-p11-containerization`).

## 2. Аудитория

Конечные пользователи — без изменений: два пользователя (владелец и жена), доступ через браузер по HTTPS :10443 (TLS self-signed, ошибки игнорируются — штатный режим). Исполнители change-пакета: SA (главный проектировщик), devops-сабагент (deploy-активности), dev, QA — см. решение `2026-10-03-p11-containerization`.

## 3. Функциональные требования (FR)

Нумерация продолжает сквозную (FR-1…FR-63 — история git прошлых циклов; см. указатель в истории этого файла, r1 указателя сохранен в git до перезаписи).

- **FR-64** (Must): Монолит `app` (текущий `backend/app`, uvicorn, 1 воркер) работает как контейнер без изменения кода: все существующие маршруты `/api/*` и страницы Jinja2 отвечают идентично systemd-проду.
- **FR-65** (Must): Контейнер `nginx` (frontend): статика `/static/*` и `/avatars/*`, reverse proxy на `app:8377`, security-заголовки, gzip; наружу публикуется только nginx (published `10443:10443`), контейнер `app` портов наружу не публикует (паритет с текущим localhost-only :8377).
- **FR-66** (Must): Данные SQLite (`wiki.db`) и `avatars/` живут в именованном томе `wiki-data`; контейнер `app` имеет к тому доступ RW.
- **FR-67** (Must): `deploy/compose.yaml` (прод-топология) и `deploy/compose.test.yaml` (стенд: временный том БД, seeded-юзер, другой порт); dev/prod паритет — один и тот же образ, различаются env/тома.
- **FR-68** (Must): Машинный контракт API: `openapi_url="/openapi.json"` включен в `main.py`, схема не раскрывается публично — без сессии редирект на login (302) или 401 (по существующему middleware, без его изменения); `docs`/`redoc` остаются выключенными; зафиксированный `openapi.json` хранится в `contracts/`.
- **FR-69** (Must): e2e-сьют в `e2e/` монорепо против compose-стенда (та же база playwright, что `tests/web`): закрывает риск расхождения «web-стенд эмулирует nginx через http.server» — заголовки кеша, gzip, security-заголовки проверяются тестом, а не только прод-смоуком.
- **FR-70** (Must): Миграции БД — one-shot запуск из того же образа до подъема нового `app`; идемпотентность обязательна; перед выкаткой — репетиция на копии прод-БД со старой схемой (урок инцидента Р4 2026-09-30).
- **FR-71** (Must): Бэкап тома (`sqlite3 .backup` + копия аватаров) выполняется до каждого деплоя, без остановки сервиса.
- **FR-72** (Must): Откат — предыдущим тегом образа `ekotov-wiki/app:<release>` (тег `latest` запрещен); при несовместимой схеме — возврат БД из пред-деплойного бэкапа (пара «код+БД»).
- **FR-73** (Must): Лимиты памяти контейнеров: `mem_limit` nginx 64m, app 512m (факт VPS: 3.9 GB total).
- **FR-74** (Must): TLS self-signed (`/etc/nginx/ssl/ekotov-wiki.{crt,key}`, срок до 2028-12-22) монтируется в контейнерный nginx томом; валидация цепочки доверия не требуется ни на одном контуре — клиенты ходят с игнором ошибок TLS (штатный режим, CA-инфраструктура не строится — решение Заказчика).

## 4. Нефункциональные требования (NFR)

- **NFR-9** (Must): Простой продакшена минимизируется: первый контейнерный деплой запускается параллельно с живым systemd-стеком (другой порт на время проверки), переключение — одна операция (reload/перенацеливание nginx); откат на systemd возможен за минуты (юнит остановлен, но не удален).
- **NFR-10** (Must): Dev/prod паритет: стенд и прод используют один и тот же образ; топология стенда воспроизводит прод-топологию (nginx → app → SQLite-том).
- **NFR-11** (Should): Ротация логов контейнеров: `json-file` с `max-size: 10m`, `max-file: 3` на контейнер.

## 6. Ограничения

- Одиночный VPS: RAM 3.9 GB total / 2.7 GB available, диск 49G (37% занято) — лимиты FR-73 сходятся, образы и тома помещаются (факты §8 плана, проверено 2026-10-03).
- Без k8s и оркестраторов: только `docker compose`.
- Docker на VPS сейчас НЕ установлен — установка входит в ЭТАП 0 change-пакета (см. §7).
- SQLite на томе, 2 пользователя, 1 разработчик + LLM-агенты.
- TLS: только self-signed до 2028-12-22, без CA (решение Заказчика).
- Правило плана: никогда два изменения инфры в одном шаге; каждая выкатка начинается бэкапом и заканчивается смоуком; RUNBOOK обновляется тем же change-пакетом.

## 7. Открытые вопросы

Открытых вопросов Заказчику нет (легкий проход, раундов БА не требуется — источники полны: ОВ-1…ОВ-4 решены, §8 плана). За пределами скоупа, но требующие учета при планировании:

- Установка Docker/compose на VPS — отдельная задача devops (ЭТАП 0), не продуктовое требование данного ТЗ.
- ЭТАП 2 (выделение `search` и далее) — отдельный БА-цикл после паузы эксплуатации 1–2 недели (ОВ-1 = (а)).
