## 3. Обработка ошибок / set -euo pipefail

- `set -euo pipefail` (строка 38) — есть. Все шаги-мутации: `run ...`/`|| fail`/if-else с `fail`. Упавший build, миграция, up, wait_healthy, бэкап, smoke_static — каждый роняет скрипт с внятным сообщением. ✓
- Смоук ловится: каждый `curl`-код проверяется case'ом/`[ = ]` c `fail`; `|| true` стоит только на захвате кода ответа (иначе set -e убил бы скрипт до проверки) — ложного PASS не создает: код `000` (connection fail) не проходит ни один case. health search — if/else с fail. ✓
- bash-квантильные ловушки проверены: `for f in ...wiki-daily-*.db; do [ -e ] && mv ...` при пустом gloбе НЕ роняет set -e (эмпирически: проваленная левая часть AND-списка errexit не триггерит) — цикл безопасен. ✓
- 6.7 «502=0» — только WARN, деплой не валит (унаследовано от v2), но печатается и безусловный ok — см. 1.4-b.

## 4. FR-72 (latest запрещен, теги) — воспроизведено

`case ""|latest|Latest|LATEST|:latest)` → fail; charset-фильтр `*[!A-Za-z0-9._-]*` → fail (инъекция `p12 r1;rm` отвергнута — проверено живым прогоном). Смешанный регистр `lAtEsT` проходит валидацию, но это **различный** docker-тег, а не `latest` — спека (spec deploy: «тег `latest` MUST NOT использоваться») не нарушена. ## 5. Бэкап: один код с sidecar (design §5) — и найденная major

- Дубля SQL-кода нет: скрипт копирует `services/backup/backup.py` в контейнер app и вызывает `from backup import run_backup; run_backup()` — ТОТ ЖЕ модуль, что cron sidecar (сверено с backup.py:107–139). ✓
- Релизные имена vs retention: `prune_old_backups` (backup.py:87–104) удаляет только `wiki-daily-*`/`avatars-daily-*`; `wiki-pre-*`/`avatars-pre-*` не трогает — заявление о «релизный бэкап остается» верно. ✓
- **Но (1.4-a, major):** mv-циклы (deploy.sh:182–187) гоняют по gloбу **всех** `wiki-daily-*.db`/`avatars-daily-*.tar` в `${BACKUP_DIR}` — а sidecar-контейнер (compose.yaml: `BACKUP_DIR: /backups`, bind `/var/backups/ekotov-wiki:/backups`) пишет свои суточные файлы **в тот же каталог хоста** с теми же именами. Каждый деплой заберет всю суточную историю (до 14 файлов по retention) и по очереди `mv -f` в ОДНО релизное имя: история sidecar уничтожается, содержимое релизного файла — «последний по сортировке», т.е. свежий (UTC-штампы сортируемы) — но корректность держится на неявной сортируемости, без проверки. Подробности и рекомендация — в таблице находок.

## 6. Смоук: X-Service и ложные PASS

- Поиск через nginx проверяет не только код: `_search_smoke` отдельно тянет заголовки и требует `X-Service: search` (awk-матч `x-service:` — проверено на живом образце заголовка), иначе fail. 200/401/422 — все «ответил search» (без сессии/без q); 502/503/000 — fail. Соответствует design §4 и механике search-headers.inc (задача 1.3). ✓
- 502-счетчик: WARN-only + ложный ok-сообщение (1.4-b). Не регрессия v2 (там так же), но против заявленного «502=0» в матрице слабее.
- Прочие PASS не ложные: все ветки завершаются `fail` при отказе; smoke_static — if/else fail. Единственный мягкий пункт — 6.7 (см. 1.4-b).

## 7. DRY_RUN — воспроизведено

Греп прямых мутаций вне `run()`/DRY_RUN-гардов: все `${COMPOSE} exec/up/build` либо под `run`, либо в `else`-ветках не-dry; идемпотентные чтения (git rev-parse, docker info, compose version/ps) — безвредны. `.env`-проверка в dry-run пропущена (корректно — up не будет). Ничего не изменено — подтверждено. ✓
