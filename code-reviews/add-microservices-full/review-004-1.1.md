## 3. Тесты — собственный прогон и дискриминационная сила (требование «(в)»)

Собственный прогон: `cd services/search && /home/openclaw/venvs/wiki/bin/python -m pytest tests/ -v` → **12 passed** (без стенда, TestClient + tmp sqlite). Все 9 тестов f0e5a37 + 3 теста 41ffe87 зеленые. Но:

### 1.1-a (major) — fallback `immutable=1` не покрыт ни одним тестом; TC-212 идет не той веткой

`services/search/tests/test_search_service.py:283-299` (`test_readonly_dir_without_wal`).

Spy на `sqlite3.connect` при прогоне TC-212/213/214: во всех соединениях сработал только **`mode=ro`** — ветка `immutable=1` (главный риск фикса: осознанный компромисс несвежести данных) ни разу не выполнялась. Причина: фикстура создает БД `sqlite3.connect()` без WAL — в заголовке journal=delete, probe `SELECT count(*) FROM sqlite_master` по `mode=ro` в ro-каталоге **успешен** (проверено моей репликой: «mode=ro probe OK without wal → fallback NOT triggered»). Дефект из ревью 1.2 воспроизводится только на БД с WAL-заголовком (мой негативный эксперимент: та же реплика на WAL-БД → «attempt to write a readonly database» → fallback). Т.е. TC-212 зеленым был бы и без fallback-ветки, а сама ветка — непокрытый код в самом тонком месте фикса. Обоснование major: требование ревью (в) «тесты покрывают оба поведения» не выполнено для поведения (а) наполовину; регресс (случайное удаление fallback) тесты не поймают. Лечение: фикстуре задать `PRAGMA journal_mode=WAL` (и/или удалить `-wal` после закрытия писателя) — тогда probe падает и тест реально идет через `immutable=1`.

### 1.1-b (major) — TC-214 не дискриминирует исходный дефект (заявлен как регресс, им не является)

`services/search/tests/test_search_service.py:313-329` (`test_expired_session_select_only`).

Негативный эксперимент: я подменял в middleware `_is_valid` на исходную версию ядра (с `DELETE FROM sessions` + `commit()`) и прогонял TC-214 — **тест зеленый** (rc=0). Причина: в тестовом окружении БД записываемая, DELETE истекшей сессии успешен, `_is_valid` возвращает False → 401, как и у исправленной версии. Т.е. тест проверяет «истекшая → 401» (полезно), но НЕ «без попытки записи», хотя докстринг заявляет «Регресс ревью задачи 1.2 … 500 вместо 401». На ro-маунте старый код дал бы 500 — тест этого не воспроизводит. Обоснование major: то же требование (в) для поведения (б) — регресс-защита заявлена, но отсутствует. Лечение: в тесте переводить каталог БД в ro (как TC-212) или ставить spy на `conn.execute`, запрещающий не-SELECT — тогда старый вариант валится (500 / запрещенная запись).

### 1.1-c (minor) — 422-handler в main.py без `jsonable_encoder` (ядро оборачивает)

`services/search/app/main.py:50` vs `backend/app/tasks.py:706` (`install_error_handlers`).

Локальный обработчик пишет `"details": exc.errors()` напрямую; ядро — `jsonable_encoder(exc.errors())`. Для pydantic v2 `exc.errors()` может содержать не-JSON-сериализуемые объекты в `ctx` → `JSONResponse` упадет уже на этапе ответа (500 вместо 422) на невалидных входах вне протестированного набора (TC-207 покрывает три случая — они сериализуемы). Отклонение не прописано в комментарии (сказано лишь «минимальная локальная копия») — по правилам трассировки отклонений следовало назвать явно. Лечение: `jsonable_encoder(exc.errors())` (импорт уже есть в search.py — не в main.py) или явный комментарий-обоснование.

### 1.1-d (minor) — мертвый `SESSION_TTL` и устаревший комментарий в middleware

`services/search/app/middleware.py:28-31`.

Комментарий «SESSION_TTL используется скользящим продлением ниже» после SELECT-only фикса неверен — скользящего продления больше нет, константа нигде не используется (grep: только определение). Это артефакт дословного переноса, оставленный после удаления `_slide_ttl`, — вводит в заблуждение при следующей правке. Лечение: удалить константу и поправить комментарий (или указать «скопировано про запас, не используется — см. SELECT-only»).

### 1.1-e (nit) — `_open_readonly`: не-OperationalError и спецсимволы пути

`services/search/app/db.py:39-53` (в diff 41ffe87).

(1) Fallback ловит только `sqlite3.OperationalError`; `sqlite3.DatabaseError` (поврежденный файл) уйдет наверх 500 — возможно, осознанно, но не оговорено. (2) `urllib.parse.quote(path)` с дефолтным `safe='/'` не экранирует `?` и `#` — путь из env с такими символами сломает URI (сейчас пути контролируемые: env/дефолт). Не блокирует; на усмотрение.
