## Замечания

| # | Файл:строки | Severity | Замечание | Рекомендация |

| 1 | deploy/deploy.sh:155 | **major** | Шаг миграции: `${COMPOSE} run --rm … app` вызывается БЕЗ `APP_IMAGE` в окружении (в скрипте нет `export`; на up env передается явно, str.166 — на run нет). Дефект спящий (до 2.1 `MIGRATE_MODULE` пуст), но именно к 2.1 должен быть закрыт. | Симметрично up: `env APP_IMAGE="${APP_IMAGE}" FRONTEND_IMAGE="${FRONTEND_IMAGE}" ${COMPOSE} run --rm --no-deps …` на str.155; проверить live-пробой миграции на стенде в рамках 2.1 (вместе с уже открытым вопросом run-vs-exec). |
| 2 | deploy/deploy.sh:118–120 vs 125–140 | minor | Dry-run печатает УПРОЩЕННЫЕ команды бэкапа (`python -c … /tmp/backup.db`, без cp/rm/проверок), тогда как реальная ветка исполняет другое (`<<PYEOF` heredoc, `/tmp/.deploy-backup.db`, `rm`, fallback tar). ТЗ требует dry-run нового метода до боевой выкатки — оператор ревьюит не в точности то, что исполнится. | Печатать в dry-run дословные команды реальной ветки (или вынести оба варианта в одну функцию). |
| 3 | deploy/deploy.sh:236 | minor | `docker image prune -f` (7/7) без `|| fail`/`|| true`: под `set -e` отказ prune (редкий, но возможен при занятых слоях) даст exit≠0 ПОСЛЕ успешного деплоя и смоука — оператор увидит «упавший» деплой при живом новом релизе. | Явно `run docker image prune -f \|\| ok "prune не критичен"` (или фиксировать warning без смены exit-кода). |
