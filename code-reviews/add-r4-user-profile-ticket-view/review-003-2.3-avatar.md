## Проверено (спека как закон)

- **Соответствие design §2 / §9, sdd §4, tasks 2.3, FR-42, NFR-10, ОГР-16, Д-8, ОВ-22:**
  контракт эндпоинта дословно (multipart `file`; 200 `{"ok", "avatar_url"}`;
  422 `invalid file type` / `file too large`; 401 middleware-текст). Путь/тексты
  ошибок — байт-в-байт с design §2 и дельтой auth.
- **Безопасность:** валидация содержимого Pillow-декодированием (не расширением;
  битый png с png-расширением → 422 — есть отдельный тест);
  двойной фильтр типов — декларация (content-type ИЛИ расширение) и фактический
  формат после декода (`_ALLOWED_PILLOW_FORMATS`); имя файла генерирует сервер
  (`<user_id>.png`, пользовательский ввод в путь не попадает — NFR-7);
  хранение `AVATARS_DIR` (env, дефолт `/var/lib/ekotov-wiki/avatars/`) — вне
  rsync-корня прода, blocker C-1/ОГР-16 соблюден; пользователь — только из сессии
  (JOIN sessions→users; эндпоинт вне exempt — проверено по middleware.py, 401 тест есть).
- **Лимит 2 МБ ДО декодирования (NFR-10/ОВ-22):** `file.read(MAX+1)` — память
  ограничена независимо от размера присланного тела; oversize-тест на реальном
  ~27 МБ png проходит, аватар на диске не изменяется.
- **Автосжатие (Д-8):** center-crop до квадрата + resize 256×256 LANCZOS; формат
  содержимого приводится к PNG; тест проверяет сохраненный файл на диске
  (256×256, PNG) и center-crop по цветам краев — детальнее, чем сценарий спеки.
- **avatar_updated_at (minor B-3, кеш-бастинг):** dedicated-колонка обновляется при
  сохранении; `avatar_url = /avatars/<id>.png?v=<avatar_updated_at>`; тест
  инверсии кеша (повторная загрузка → `?v=` строго растет) есть.
- **Атомарная запись:** tmp + `os.replace`; отказы до записи файл не создают и
  состояние users не меняют (проверено тестами reject_*: mtime/row до == после).
- **Не-сделанное честно:** DELETE аватара спекой не предусмотрен — не реализован
  (верно, дельта auth предусматривает только загрузку). Отдача `location /avatars/`
  в nginx — явный шаг деплоя релиза (design §2/§9), в задачу 2.3 не входит.
