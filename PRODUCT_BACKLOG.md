## Блок P: Продуктовые улучшения (черновики)

### P1. Карточка/форма задачи — детальная проработка UX

**Заметки Заказчика:**
- Категории заранее задаются в настройках проекта (см. P5) — в форме выбор из списка, не свободный текст.
- Крестик закрытия модального окна — в верхний правый угол (сейчас расположение неудобно); проработать графику/визуал формы в целом.
- Теги подтягиваются из уже имеющихся (автодополнение, как в Jira): начинаешь вводить — показывает существующие теги проекта, можно выбрать или создать новый.
- Приоритеты — с цветом и иконкой (визуальное различение low/medium/high в форме и на карточке).
- Fast line: при создании fast-задачи приоритет автоматически «высокий», без возможности смены (быстрая задача = всегда высокая важность; снимает вопрос рассинхрона fast × priority).

**Доработка ПМ (интерпретация, требует подтверждения):**
- Автоподстановка priority=high для is_fast — это изменение спеки fastline (сейчас fast и priority независимы; CHECK в БД и sdd §3.2 допускают fast с любым приоритетом). Потребует дельты ADDED/MODIFIED в fastline + задачи в backend (валидация) и frontend (UI-lock поля).
- Автодополнение тегов — нужен API-эндпоинт «список существующих тегов проекта» (сейчас теги живут только внутри задач; GET /api/tags отсутствует).
- Иконки приоритетов — минимально: без внешних библиотек (inline SVG), чтобы не тянуть зависимости.

### P2. Раздел «Настройки» в сайдбаре

**Заметки Заказчика:** добавить раздел настроек, внизу слева, рядом с кнопкой выхода.

**Доработка ПМ:**
- Пока не определен состав настроек. Кандидаты из других пунктов: управление категориями проекта (P1/P5), возможно управление тегами. Требует решения Заказчика: какие настройки входят в первый релиз.
- Навигация: новый раздел = пункт сайдбара + страница — затрагивает домен navigation (спека: сайдбар, редиректы). Ленивая автоархивация не затрагивается.
- Открытый вопрос: настройки — общие (оба пользователя видят и меняют) или только для owner? Связано с моделью «общая доска» без разграничения прав — скорее общие, но подтвердить.

### P3. Профиль пользователя внизу сайдбара

**Заметки Заказчика:** отображать внизу слева имя пользователя и аватарку, настройки пользователя.

**Доработка ПМ:**
- Имя: сейчас у пользователей только login (owner/wife). Понадобится поле display_name (миграция схемы + API) или захардкоженные подписи («Владелец» / «Жена») — решить.
- Аватарка: внешний сервис (типа Gravatar) или загрузка файла? Загрузка = хранение файлов, новые NFR (размер, типы), новый эндпоинт. Минимум для первого шага: цветной кружок с первой буквой логина (без хранения файлов).
- «Настройки пользователя»: смена пароля — вероятный кандидат (сейчас пароли только через seed). Смена логина — вряд ли нужна (логины фиксированы по sdd).
- GET /api/auth/me — понадобится в любом случае (сейчас UI не знает, кто залогинен).

### P4. Подсказки в поиске (для полей теги/категории)

**Заметки Заказчика:** в поиске добавить подсказку для некоторых полей — теги, категории.

**Доработка ПМ:**
- Тот же механизм, что автодополнение в P1 (список существующих тегов/категорий) — реализовать один API и переиспользовать в двух местах (форма задачи + панель поиска).
- Для advanced-режима (SQL-подобный синтаксис) подсказки — отдельная история: dropdown с примерами синтаксиса или отложить.

### P5. Категории — справочник, задаваемый в настройках

**Заметки Заказчика:** категории — это выбор из списка; список задается в настройках проекта (см. P2).

**Доработка ПМ:**
- Новая сущность «категория проекта»: таблица categories, CRUD настроек, валидация задачи по справочнику (сейчас category — свободная строка в БД). Это изменение схемы + контрактов + спеки tasks (MODIFIED) — заметный change-пакет, самый крупный в списке.
- Миграция: существующие значения category в задачах (свободный текст) — маппить в справочник или оставить «как есть» с пометкой.
- Открытый вопрос: жесткая валидация (задача не создается с категорией вне справочника) или мягкая (предупреждение)?

### P6. Архитектурное разбиение крупных разделов на модули

**Заметки Заказчика:** разбить крупные разделы (строки из сайдбара) на модули в репозитории.

**Доработка ПМ:**
- Трактовка: сейчас frontend/templates/ и static/js/ — плоские файлы (board.html+board.js — самый крупный, ~600 строк JS). «Разбить на модули» = по разделу сайдбара (board / search / wiki) — своя папка: templates/board/, static/js/board/ (index, card, comment, modal...).
- Связано с G6/G9 из конвейерного бэклога (ветки, жизненный цикл артефактов): рефакторинг удобнее делать в ветке.
- Требование обратной совместимости: URL статики (/static/js/board.js) используются в шаблонах — при разбиении обновить пути; дымовой прогон после.
- Кандидат на первый шаг: board.js → модули (карточка, модалка формы, карточка детали/комментарии, фильтры). Без сборщика (ES-модули или конкатенация в том же порядке) — решить при проработке; сборщик (bundler) тянет Node-инфраструктуру, для двух пользователей избыточен.

## Приоритизация (предложение ПМ, не решение)

Естественная зависимость: **P5 (справочник категорий) → P1 (форма)** и **P5 → P2 (настройки)** — справочник нужен обоим. **P3 (профиль)** и **P4 (подсказки)** — независимы. **P6 (рефакторинг)** — выгодно сделать до P1/P2/P4, чтобы новые UI-фичи сразу писать в модульной структуре, а не переписывать.

Возможный порядок: P6 (рефакторинг) → P5+P2 (категории + настройки) → P1 (форма) → P3 → P4.
