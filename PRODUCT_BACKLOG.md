### P7. Drag-and-drop плиток на доске

**Статус:** РЕАЛИЗОВАНО (Релиз 3).

**Заметки Заказчика:** перетаскивание плиток по колонкам: при зажатии плитка прикрепляется к курсору и исчезает с доски; при отпускании — падает в зону столбца; при отсутствии зоны — возвращается на место.

**Доработка ПМ:**
- Эквивалентно move через селект (задача 4.4) — тот же API `POST /api/tasks/{id}/move`, новое только UI-представление. Дельта спеки не нужна (поведение то же, новое средство).
- Технология: HTML5 Drag and Drop API (нативно, без библиотек) — плитка `dragstart`, колонка `dragover` (подсветка зоны-приемника), `drop` (move + refresh). «Прикрепляется к курсору» — через `setDragImage` или CSS-клон; «исчезает с доски» — opacity/dispay при dragstart.
- Fallback: перенос недоступен на touch-устройствах без библиотеки — для двух пользователей (десктоп) приемлемо, зафиксировать как ограничение.
- Взаимодействие с fast line: drop в активную фазу при существующем fast — 409 (инвариант сохраняется), показать ошибку и вернуть плитку.
- Тесты: Playwright `drag_and_drop` + проверка 409-инварианта; E2E-сценарий в критический путь.
- Зависимость: после P6-рефакторинга (карточки в cards.js — добавлять DnD туда же).

### P10. Оптимизация qa_automation-сабагента: расход токенов и скорость (аудит)

**Статус:** черновик (2026-09-27, Заказчик).
**Наблюдение:** qa_automation — самая дорогая роль QA-контура. Текущий прогон Р3 (32 кейса): >45 мин живой сессии, транскрипт >115 КБ, api_calls ~100+; на больших пакетах линейно растет.
**Гипотезы расхода:** (а) playwright-отладка — каждый прогон стенда тянет циклы «запустил→упал→читал traceback→правил» (основная масса токенов); (б) контекст тащит полные тексты кейсов + спеки + логи прогонов; (в) стенд поднимается/сеется с нуля в каждой сессии; (г) повторы зависимых фикстур.
**Направления анализа:** замер по транскриптам session-archive (распределение токенов по типам tool-вызовов: bash/exec vs file-операции); готовые фикстуры стенда (поднятый стенд + seeded БД как артефакт до делегации); партиционирование кейсов на несколько автоматизаторов (экспресс-конвейер); вынесение playwright-прогонов в отдельный дешевый шаг (модель без reasoning) с передачей только ошибок.
**Выход:** отчет с числами (токены/этап, мин/кейс) + решение: фикстуры, партиционирование, смена модели или acceptance as-is.
**Связь:** J8 (общий анализ токенов), J13 (QA = отдельные роли).

### Обновление приоритизации

Визуальный блок (P7/P8/P9) естественно идет после P6-рефакторинга и вместе с P1: drag-and-drop в cards.js, редизайн формы в task-form.js, общий стиль P8 связывает. Предлагаемая цепочка: **P6 → P7+P8+P9+P1 (визуально-функциональный релиз) → P5+P2 (справочники/настройки) → P3 → P4**. Альтернатива: визуал (P7/P8/P9) отдельным быстрым релизом сразу после P6 — даст быстрый видимый эффект Заказчику.

Естественная зависимость: **P5 (справочник категорий) → P1 (форма)** и **P5 → P2 (настройки)** — справочник нужен обоим. **P3 (профиль)** и **P4 (подсказки)** — независимы. **P6 (рефакторинг)** — выгодно сделать до P1/P2/P4, чтобы новые UI-фичи сразу писать в модульной структуре, а не переписывать.

Возможный порядок: P6 (рефакторинг) → P5+P2 (категории + настройки) → P1 (форма) → P3 → P4.

### P11. Переход на сервисы в контейнерах + контракты между ними

**Статус:** черновик (2026-10-01, Заказчик).
**Цель:** сайт работает из контейнеров (как минимум backend/app + nginx; БД — на решение проработки), а не из rsync-каталога на хосте.
**Объём проработки (до реализации — Флоу 1):**
1. **Топология:** какие сервисы (app/uvicorn, nginx, опционально db); что остаётся на хосте — том с `wiki.db` и `avatars/` вне контейнера (урок rsync-инцидента C-1: данные не в образе).
2. **Контракты между сервисами:** внутренние порты/сети, healthcheck (уже есть `/api/health` — формализовать), переменные среды (SECRET_KEY, DB_PATH, AVATARS_DIR), монтируемые тома, обратная совместимость с текущим deploy.sh (постепенный переход, не big bang).
3. **Деплой-процедура:** docker compose vs systemd-юниты; откат (предыдущий образ/тег); миграции БД в контейнерной схеме (кто исполняет migrate_rN, идемпотентность — урок прод-инцидента 2026-09-30: репетиция миграции на копии прода обязательна); smoke после подъёма.
4. **Dev/prod паритет:** локальный стенд тестов на том же compose-файле.
5. **Observability:** логи, ротация.
**Ограничения:** одиночный VPS, минимум operational complexity (без k8s), простои при переходе минимальны (сайт живой).
**Выход проработки:** ADR/дизайн-док + план миграции с чекпоинтами отката; реализация — отдельным релизом (не смешивать с фичевыми пакетами).
**Связь:** devops-сабагент (все deploy-активности через него, J26 фабрики), nginx-avatars (5b/6 Р4), прод-инциденты миграции Р4.

**Дополнение Заказчика (2026-10-01, при выводе из обсуждения):**
- Каждый сервис — в отдельном контейнере (фундамент под сервисы, не монолит в контейнере).
- Растет роль архитектурной карты (architecture/map.md — обновить «как есть» → «как будет») и devops-роли.

Кандидаты: контрактные тесты по OpenAPI-схеме (провайдер/потребитель), gate в CI «сломал контракт → блок», e2e на compose-стенде.

**Открытый вопрос Заказчика (2026-10-01):** отдельные репозитории под каждый сервис/контейнер или монорепозиторий? Позиция: «кучу реп создавать не хочу, но и жить в одной как будто не хорошо» — ответа пока нет, решить в проработке. Кандидаты-аргументы: монорепо (атомарные изменения контрактов, один CI, сквозные тесты из одного места, простота для 1 разработчика + агентов) vs полирепо (чистые границы собственности сервисов, независимые версии/деплои, но оверхед синхронизации контрактов и N деплоев); гибрид — монорепо + жёсткие границы каталогов-сервисов с отдельными конвейерами.
