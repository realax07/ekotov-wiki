# Тест-кейсы: домен auth (change add-kanban-core)

Источник: `test-model/checklists/add-kanban-core.md` (CHK-1…CHK-17).
Спека: `openspec/changes/add-kanban-core/specs/auth/spec.md`; контракт API — `sdd.md` §3, §3.1, §3.1a.

**Общие предусловия для всех кейсов файла:**
- Приложение развернуто и запущено; `GET {BASE_URL}/api/health` без сессии → 200 `{"status": "ok"}`.
- Пользователи заведены seed-скриптом (`python -m app.seed_users`, идемпотентен): `owner`, `wife`. Пароли вводятся исполнителем при seed и нигде не логируются; далее по тексту `<pwd_owner>` — пароль owner, `<pwd_wife>` — пароль wife (конкретные значения известны исполнителю, в артефакты не попадают — NFR-7).
- `BASE_URL` — корень развернутого приложения (локальный прогон: `http://localhost:8080`; VPS: домен из deploy/README.md).
- API-запросы выполняются `curl -i` (видны код и заголовки); сохранение куки — `-c cookies.txt`, отправка — `-b cookies.txt`.

## TC-auth-001 — API-запрос без сессии отклоняется 401
- **CHK:** CHK-1
- **Источник:** auth: «Авторизация обязательна для API» (NFR-7, FR-8) / Scenario: API-запрос без сессии
- **Тип:** негативный | **Приоритет:** Must
- **Предусловия:** общие; на доске есть ≥1 задача (создана заранее, id известен, напр. id=1).
- **Шаги:**
  1. `curl -s -i {BASE_URL}/api/board` (без куки).
  2. `curl -s -i -X POST {BASE_URL}/api/tasks -H "Content-Type: application/json" -d '{"title":"Тест без сессии"}'`.
  3. `curl -s -i -X PATCH {BASE_URL}/api/tasks/1 -H "Content-Type: application/json" -d '{"priority":"high"}'` (без куки).
  4. `curl -s -i -X DELETE {BASE_URL}/api/tasks/1` (без куки).
  5. `curl -s -i {BASE_URL}/api/search?priority=high` (без куки).
- **Ожидаемый результат:** каждый ответ — HTTP **401**, тело точно `{"error": "unauthorized"}`; данных задач в теле нет; `GET /api/board` не возвращает `columns`; задача id=1 после шага 3–4 не изменена и не удалена (проверка после входа: `GET /api/tasks/1` с валидной сессией — поля без изменений).
- **Тестовые данные:** title=`Тест без сессии`; priority=`high`; id=1.

## TC-auth-002 — API-запрос с просроченной сессией → 401
- **CHK:** CHK-2
- **Источник:** auth: «Авторизация обязательна для API» / Scenario: API-запрос с просроченной сессией (NFR-7, FR-8)
- **Тип:** негативный | **Приоритет:** Must
- **Предусловия:** общие. Способ искусственно истечь сессию: строка `sessions` с `expires_at` в прошлом (обновить напрямую в SQLite: `UPDATE sessions SET expires_at = '2020-01-01T00:00:00+00:00' WHERE token = '<token>';`), БД-путь — из конфига развертывания.
- **Шаги:**
  1. `curl -s -i -X POST {BASE_URL}/api/auth/login -H "Content-Type: application/json" -d '{"login":"owner","password":"<pwd_owner>"}' -c cookies.txt` → 200.
  2. Обновить `expires_at` сессии из cookies.txt в прошлое (см. предусловие).
  3. `curl -s -i -b cookies.txt {BASE_URL}/api/board`.
- **Ожидаемый результат:** шаг 1 — 200 + `Set-Cookie: session=…`; шаг 3 — HTTP **401**, тело `{"error": "unauthorized"}`; запись сессии отсутствует/невалидна (просроченная сессия не принимается).
- **Тестовые данные:** login=`owner`, password=`<pwd_owner>`; expires_at=`2020-01-01T00:00:00+00:00`.

## TC-auth-017 — Пароли не хранятся в открытом виде (НФТ, осмотр БД)
- **CHK:** CHK-17
- **Источник:** auth: «Пароли не хранятся в открытом виде» (NFR-7) / Scenario: Проверка хранимых учетных данных
- **Тип:** НФТ | **Приоритет:** Must
- **Метрика:** в `users.password_hash` нет открытых паролей; только необратимые bcrypt-представления (sdd §4, seed_users.py).
- **Предусловия:** общие; известны точные значения `<pwd_owner>`, `<pwd_wife>` (введены при seed); путь БД — из конфига развертывания.
- **Шаги:**
  1. `sqlite3 $DB_PATH "SELECT login, password_hash FROM users;"`.
  2. Для каждой строки проверить: значение начинается с `$2b$` (bcrypt) и длина ≥ 60 символов.
  3. `grep -c "<pwd_owner>" $DB_PATH` и `grep -c "<pwd_wife>" $DB_PATH` — поиск открытых паролей в файле БД (двоичный grep: `grep -ac`).
  4. Проверить вход: `POST /api/auth/login` с `owner`/`<pwd_owner>` → 200 (хеш рабочий, т.е. это действительно представление пароля).
- **Ожидаемый результат (порог):** 0 вхождений открытых паролей в файле БД; все `password_hash` вида `$2b$…`; вход по исходному паролю работает. Файл БД вне репозитория (побочно: `git -C <repo> check-ignore <DB_PATH>` — проигнорирован).
- **Тестовые данные:** БД `$DB_PATH`; сравниваемые строки `<pwd_owner>`, `<pwd_wife>`.
