# TC-profile-r4-101 — GET /api/profile и /api/auth/me при роли вне справочника в БД (рассинхрон, ОВ-21 × миграция)

- **CHK:** CHK-R4-103
- **Change:** add-r4-user-profile-ticket-view
- **Источник:** auth: «Профиль пользователя — просмотр и редактирование» (ОВ-21 «роль — только из справочника», Д-10-подобное поведение me при незаполненных полях); СЦ «Негативный: роль вне справочника отклоняется» (PUT-ветка уже покрыта TC-profile-005 — здесь ЧИТАЮЩАЯ ветка: БД-значение, попавшее мимо валидации); impact «рассинхрон роли» (TC-me4-002 проверяет только role=NULL, произвольная строка не проверена)
- **Тип:** гран. (негатив по состоянию данных) | **Приоритет:** Should
- **Маркер:** api (сьют tests/api; requires db-крюк `EKOTOV_WIKI_DB_PATH` — как TC-passwd-004/TC-me4-002, skip без env)
- **Среда/предусловия:** тестовый стенд tests/api; сессия owner (conftest); прямой доступ к БД стенда (conftest db_update/db_select_one); teardown обязателен — БД-правка откатывается, иначе повторный `migrate_r4` упадет на сверке (задокументировано в impact §4.1 и test_profile_r4).
- **Шаги:**
  1. Войти owner; зафиксировать baseline: `GET /api/profile` → 200, `role` = «Product manager» (значение после миграции, ОВ-21).
  2. Прямой БД-крюк: `UPDATE users SET role = 'SuperAdmin' WHERE login = 'owner'` — рассинхрон: значение в БД вне справочника VALID_ROLES (попадает мимо PUT-валидации — например ручная правка/сбой миграции).
  3. `GET /api/profile` в той же сессии → статус, тело.
  4. `GET /api/auth/me` в той же сессии → статус, тело.
  5. Контроль отсутствия каскада: `GET /api/board` → 200 (авторизация/права не зависят от role — NFR-4); `POST /api/tasks` с `{"title": "QAT-s103-проба"}` → 201, затем delete (роль — чисто отображаемое поле).
  6. **Поведение PUT при рассинхроне:** `PUT /api/profile` с валидным телом (display_name без изменений, role = «Product engineer») → 200; read-back `GET /api/profile` → role = «Product engineer» — корректный PUT «вылечивает» рассинхрон (эндпоинт не отказывается работать из-за текущего невалидного значения).
  7. Teardown (fixture-финализатор): восстановить `role = 'Product manager'` (или дефолт), сверить `SELECT role FROM users WHERE login='owner'`; удалить пробную задачу.
- **Ожидаемый результат:** шаги 3–4 — НЕ 5xx: `GET /api/profile` отвечает 200 и возвращает `role` как есть в БД (`"SuperAdmin"` — read-only зеркало данных; 500/исключение сериализации = дефект); `GET /api/auth/me` отвечает 200 с 5 ключами, `role` — значение БД-строки без нормализации (end-to-end SELECT без валидации, auth.py me: `role: row[2]` — если реализация когда-либо вернет null, это расхождение факта с контрактом «как в БД» фиксируется как дефект, а не легальный исход; контракт стабилен). Шаг 5 — доска и создание задач работают (роль не влияет на права, ОВ-21/NFR-4). Шаг 6 — PUT с валидной ролью → 200, рассинхрон устранен. Ни один шаг не дает 500.
- **Тестовые данные:** БД-роль-инъекция `'SuperAdmin'` (вне VALID_ROLES); валидные роли «Product manager»/«Product engineer»; логин owner; задача `QAT-s103-проба` (cleanup).
