# TC-weather-025 — NFR: отзывчивость при отказе провайдера — /api/weather ≤ ~11 с, стек не деградирует

- **Change:** weather-service
- **Источник:** weather-service: «Отзывчивость при недоступности провайдера (NFR)» / Scenario: Замер отзывчивости при отказе провайдера
- **Тип:** НФТ | **Приоритет:** Must
- **Среда/предусловия:** поднятый стенд (`GET {BASE_URL}/api/health` → 200); owner `owner/QaOwner_Pass_1!`, второй пользователь `pe/QaPe_Pass_1!` (seed); Playwright (Python): `page`, `expect`, `api_request_context`; unit/integration-уровень: `services/weather` pytest с httpx.MockTransport; e2e-имитация отказа провайдера — блокировка egress к api.open-meteo.com (сетевая политика стенда) либо остановка резолва DNS
- **Шаги:**
  1. Обеспечить пустой кэш и недоступный Open-Meteo.
  2. Выполнить `GET /api/weather` (под сессией), замерить полное время (2 попытки × 5 с + пауза).
  3. Параллельно (в момент ожидания таймаутов) открывать `/board`, `/search`, `/gallery`, `/video` и замерять их времена.
- **Ожидаемый результат:** `/api/weather` завершается управляемой ошибкой (503) не дольше ~11 с; при наличии кэша — быстрее (стало/устарело из кэша без вызова провайдера); параллельные разделы отвечают без деградации (в пределах обычных для стенда времен); UI не блокируется (индикатор загрузки).
- **Тестовые данные:** блокировка egress; секундомер; пустой и, вторым прогоном, устаревший кэш.
