## 2. Дыры покрытия

1. **E2E «поиск → карточка → редактирование» — НЕ покрыто.** TC-UI-017
   останавливается на открытии карточки (view: бейдж + признаки). Редактирование
   из модалки, открытой с /search (кнопки формы карточки, submit, закрытие) —
   не протестировано: search.js получает собственную копию renderCard-механики
   (комментарий в коде: «та же механика, что в board.js»), рассинхрон копий
   регрессом не ловится. Рекомендация: 1 TC-UI в следующий QA-контур.
2. **Поведение при отключенном JS / без поддержки ES-модулей — не покрыто и
   не специфицировано.** `type="module"` без JS оставляет доску пустой, без
   `noscript`-заглушки; graceful degradation нигде не заявлена (спека молчит).
   Для wiki на 2 учетки риск принятый, но решение должно быть зафиксировано
   (NFR в master-spec), а не молчанием.
3. **ES-модули верифицированы только в chromium** (headless Playwright).
   firefox/webkit-контексты не гоняются; старые браузеры без module-поддержки
   покажут пустую доску без сообщения. Связано с п.2.
4. **CI не запускает pytest-сьюты.** flow.yml: openspec validate, flow_check,
   ruff, eslint, pr_validate — регресс существует только в локальных прогонах.
   Рантайм-проверка модульной загрузки доски (п.2) в gates не попадает;
   зеленый CI ≠ зеленый регресс. Для деплоя компенсируется ручным прогоном
   (выполнен, см. шапку); системно — кандидат в бэклог (CI job pytest).
5. **Флейк TC-UI-017 без политики обработки.** Известен: дубль данных →
   strict mode violation на локаторе карточки в полном прогоне; изолированно
   проходит. Политики «падение флейка → перезапуск изолированно → вердикт»
   в манифесте регресса нет — на релизном прогоне это дает ложный NO-GO риск.
