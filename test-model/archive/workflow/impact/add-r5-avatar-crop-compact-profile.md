## 3. Новые тестовые требования дельты (вход для чеклиста → кейсов)

По сверке 27 сценариев с существующим набором — пробелы (не покрыты перечисленным):

1. **Граница лимита NFR-12** (сценарии «Негативный: исходник больше 2 МБ»,
   «Лимит исходника — как в Релизе 4», СЦ-10): TC-ava-005 проверяет файл ~27 МБ
   (много больше), web TC-r5crop (oversize) — 2 МБ + 1 байт мусора ДО виджета.
   Гэп: граница «ровно 2 МБ» (должен быть ПРИНЯТ — спека отклоняет «более 2 МБ»)
   и серверный отказ «2 МБ + 1 байт» (422 file too large — размер проверяется до
   декодирования). Кроп-путь blob 256×256 заведомо < 2 МБ — граница актуальна
   для прямого POST (fallback/подмененный клиент).
2. **Нормализация jpg-входа** (сценарий «Серверная нормализация…» — в спеке
   пример png): TC-ava-r5-101 — только png. Гэп: валидный JPEG не-квадратной
   геометрии → 256×256 PNG (нормализация не должна зависеть от исходного формата).
3. **Backward-compat ОГР-21 / СЦ-13** (сценарий «Backward-compat существующих
   аватаров»): web-покрытие частичное (виджет закрыт без выбора файла —
   TC-r5crop-401). Гэп API-уровня: файл аватара, сохраненный ДО релиза
   (center-crop Р4), остается байт-в-байт после открытия профиля/страницы —
   никакой перекраски/миграции.
4. **Изоляция пользователей** (сценарий «Успешная загрузка png» + хвост
   CHK-R4-25 Р4 «покрыт косвенно»): загрузка аватара одним пользователем не
   затрагивает файл другого (wife.png создается, owner.png байт-в-байт).
5. **EXIF-портрет с телефона** (design §7 «Риски», главный кейс пользователей):
   jpg с EXIF-ориентацией (портрет) не отклоняется сервером; сервер не обязан
   вращать (вращает браузер при декодировании), но обязан принять и нормализовать.

Не-пробелы (проверять не нужно сверх существующего): 401 без сессии (TC-ava-006
+ TC-setp-201), контракт/`?v=` (TC-ava-001/007), тип-содержимое (TC-ava-004b/c),
fallback-страница (TC-r5crop-415), blob 256×256/NFR-11 (TC-r5crop-406/407).
