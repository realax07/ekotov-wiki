## 1. Согласованность с sdd r8 и architecture/map.md

**Допущения карты — пакет не нарушает ни одного:**

- **Д-а (статика через nginx, приложение без StaticFiles)** — соблюдено. Пакет не вводит `StaticFiles`/`mount` (проверено: в дельтах нет серверной статики; единственный новый маршрут `GET /api/auth/me` идет через `proxy_pass`, как весь `/api/*`). Все визуальные изменения доставляются через `/static/` (nginx alias) с бампом `static_v` — ровно тот механизм, что появился из уроков DEF-002/DEF-003 (карта §5, решение о кеш-бастинге). Единственный недочет — неполнота применения урока в tasks, см. З-2.
- **Д-ж (SECRET_KEY фактически не используется, токены сессий — `secrets.token_urlsafe`)** — соблюдено. Пакет не вводит ни подписи, ни криптографии: `/api/auth/me` резолвит логин из таблицы `sessions` по токену куки — тот же механизм, что и весь API. Пакет не закрывает и не консервирует задел Д-ж — нейтрально.
- Д-б/Д-в/Д-е/Д-з — не затрагиваются: нагрузки не растут (NFR-1 обоснован в design §6), схема/сессии/процессы без изменений.
- Расхождение карты с sdd (§4, примечание к Д-в про формулировку NFR-3 в sdd) пакетом не усугубляется.

**Согласованность с sdd r8:** контракт §3.1-бис дословно совпадает с design §3 и дельтой auth (200 `{"user": "<login>"}`, 401 вне exempt, read-only). exempt-список middleware (`EXEMPT_API` в `middleware.py` — проверен) не расширяется — дельта auth это прямо требует, корректно. §2 примечание (DnD/эффекты — клиентские) соответствует design §1–2. Матрица трассировки §6 дополнена FR-31…FR-35.

**Фактическая ошибка в design.md (З-1, исправить формулировку, не блокирует):** design §3 утверждает «middleware уже резолвит user_id → login». Проверено по коду: `_is_valid` в `middleware.py` проверяет только `expires_at` и продлевает TTL — user_id он **не** резолвит; `users.login` из токена сессии не извлекается нигде (login в ответе `/api/auth/login` берется из тела запроса). Следствие: `/api/auth/me` потребует собственного `SELECT u.login FROM sessions s JOIN users u ON u.id = s.user_id WHERE s.token = ?` в auth-роутере. Тривиально, но dev-задача 1.1 не должна строиться на неверной посылке «данные уже в request.state».

## 2. Техдолг: не добавляет ли пакет нового

**Инвариант DnD 409 — сервер уже возвращает. Проверено по коду `tasks.py::move_task`:** проверка «fast-задача возвращается из done в активный статус при занятой линии → 409 `{"error": "fast line occupied"}`» в move **существует** (расширение из review-4.4-001). Д-6 сценарий «drop fast-карточки в активную фазу при занятой line» достижим ровно одним путем — done → todo/in_progress (перевод fast между двумя активными статусами инвариант не меняет и 409 не порождает; не-fast карточка 409 в move не дает вообще). Дельта board и tasks 2.2 описывают именно этот случай, клиентская ветка — чистый потребитель существующего контракта. **Новый техдолг не создается.**

**Client-side ветка не ломает существующий move:** эквивалентность ОГР-14 выдержана архитектурно — drop вызывает тот же `POST /api/tasks/{id}/move`, тот же pydantic `TaskMove`, те же коды 200/404/422/409. Существующие web-тесты fastline (`test_fastline_ui.py`) гоняют прежний элемент перевода, который не удаляется — регрессия маловероятна.

**Новый принимаемый техдолг (фиксирую, не задача):**
- Возврат плитки при 409 — клиентское состояние «исходная позиция до подтверждения»: если между dragstart и ответом другой пользователь перевел эту же задачу, возврат на «исходное» место может отрисовать устаревшее состояние. На практике (2 пользователя) ничтожно; перерисовка после ответа API частично гасит. Принимаю как следствие тонкого клиента.
- FLIP-анимация (задача 3.2) — самый сложный клиентский код релиза, синхронизация с `refreshBoard()` (пересоздание DOM-узлов после ответа). Риск флэша/скачка назван в design §7 и закрыт web-тестом — корректно.

## 3. Точки расширения: пресеты P8

**Механизм в пакете не зафиксирован (З-3 — указать в задаче 3.2 до старта).** Design §2 говорит «чистый CSS поверх токенов», но не говорит, КАК переключается пресет. Рекомендация архитектора: пресет = один атрибут/класс на корне доски (`data-fx="preset-N"` или класс на контейнере столбцов), все правила пресета скоупятся под этот атрибут, базовый обязательный минимум (3.1) — вне скоупа. Это дает: (а) переключение пресета без правки селекторов; (б) будущую смену темы — новые токены в `:root` + переопределение значений под тем же скоупом; (в) дешевое A/B для Заказчика (мокапы ОВ-20 могут быть живыми пресетами — это буквально предусмотрено вводными). Обязать dev не могу (зона СА), но в задачу 3.2 формулировка механизма должна попасть — иначе получится россыпь нескоупленных селекторов, которая при следующей теме умрет.

**prefers-reduced-motion — риск реализации (З-4):** `@media (prefers-reduced-motion: reduce)` покрывает только CSS-анимации. FLIP при drop может быть реализован и на JS (Web Animations API/цикл) — research §4 такой вариант не исключает. Если анимация уйдет в JS, CSS-media ее не отключит. Требование к задаче 3.2: либо FLIP строго на CSS-transitions (media сработает), либо явная проверка `matchMedia('(prefers-reduced-motion: reduce)')` в JS. Сценарий дельты («анимации отключены, функциональность сохранена») сформулирован верно и тестируем (Playwright `emulateMedia({ reducedMotion: 'reduce' })`).
