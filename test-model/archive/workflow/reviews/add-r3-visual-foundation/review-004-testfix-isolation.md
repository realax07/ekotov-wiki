## Ось 1. Изоляция и cleanup (порядок-независимость)

**TC-UI-018 (`test_final_path_autoarchive_and_fast_release`).** Регистрация `new_card` id в `web_cleanup_created` перенесена ДО ассертов «fast line занята»/`task-card-fast`. Корректно: `web_cleanup_created` (tests/web/conftest.py:257) — фабрика с teardown-DELETE, регистрация до ассертов гарантирует удаление fast-задачи даже при падении ассерта; setup TC-dnd-103/106 в совместном прогоне больше не зависит от исхода этого теста. Новых межтестовых зависимостей фикс не вносит — наоборот, устраняет. Без замечаний (блокирующих).

**TC-arch-008 (`test_archived_task_found_by_search_card_opens`).** Категория «Дом» (session-seed) заменена на свою `QAT-арх-категория` через фикстуру `category_directory` (tests/api/conftest.py:467; teardown = `cleanup_tracked()`). Seed больше не трогается — порядокозависимость устранена.

Ключевой порядок-независимый момент — **алфавит teardown'ов**: при алфавитной финализации фикстур `category_directory` teardown выполняется РАНЬШЕ `cleanup_task` teardown, т.е. на момент `cleanup_tracked()` задача-носитель еще жива → DELETE категории вернул бы 409 → `assert False` в teardown (conftest.py:416). Автор это осознал и вынес cleanup категории в тело теста ЯВНО: снять категорию с задачи (`api.patch(task_id, category="")`), DELETE категории, `untrack`. Проверено по продукту:
- пустая `category` в PATCH проходит жесткую валидацию FR-21 (`_category_not_in_directory_422`: `if not category: return None`, tasks.py:233 — nullable-модель, Д-2) → 200 реалистичен, assert стоит;
- архивность задачи PATCH не блокирует (`update_task` не проверяет archived_at);
- DELETE категории после снятия носителя: `in_use = 0` → 200 (categories.py:186+);
- `untrack` перед `cleanup_tracked` — двойного DELETE нет; `untrack` идемпотентен.

Инвариант «0 забытых QAT-категорий» (TC-env-002 шаг 4) сохранен: при падении теста до явного cleanup teardown `cleanup_tracked` даст 409-assert — утечка видима, не глотается. Замечание Minor №3 (см. таблицу) — не блокирующее.

**TC-vis-105.** Изоляцию не меняет (таска уже трекалась до фикса).

## Ось 3. Детерминизм (фикс гонки TC-vis-105)

Проверено по frontend (`frontend/static/js/board/cards.js`):
- `dragInProgress` — module-переменная, в `window` недоступна (type="module") — комментарий в тесте верен, прямого поллинга флага нет и быть не может.
- `onDragStart` при `dragInProgress=true` делает `preventDefault` и не ставит ghost (cards.js:220–227) — гонка реальна, описание дефекта корректно.
- Синхронизация через **expect-поллинг** (`.to_be_visible()` карточки QAT-vis-rm в «В работе»), не sleep — соответствует G8. Обоснование валидно: `moveTask` onOk → `refreshBoard(); dragInProgress=false` (cards.js:213–215) — `refreshBoard` асинхронен, `dragInProgress=false` выполняется синхронно сразу после запуска; следовательно факт появления карточки в «В работе» (renderBoard отработал) гарантирует `dragInProgress=false` к моменту следующего evaluate. Ожидание именно наблюдаемого следствия завершения move — корректная синхронизация без доступа к внутреннему состоянию.
- Селектор карточки взят по фактическому местоположению (in_progress), слепой «первая карточка todo» убран — устраняет null/чужая-карточка после перерисовки. Остаточный нюанс — Minor №1.
- `time.sleep` в диффе отсутствует; rAF-promise для чтения класса ghost — как в dnd_helpers, корректно.
