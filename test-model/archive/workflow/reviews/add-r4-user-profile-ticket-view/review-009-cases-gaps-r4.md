## Спец-проверка TC-search-r4-101 (объект-сравнение против класса 8225bbf)

**Покрывает класс дефекта корректно.** Дефект 8225bbf был `_load_search_tags(conn, row[10])` — row-индекс после JOIN 5.2 давал логин creator вместо id задачи → tags=[] в КАЖДОЙ строке. Механизм кейса (полное объект-сравнение строки выдачи с эталоном E: множество ключей + значения всех 13 полей + tags как точный массив) ловит ОБА поломанных состояния: и «ключ/tags пуст» (факт 8225bbf), и любой будущий сдвиг проекции (перепутанное поле — не только tags: сравнение ПОБИТОВО, каждое поле эталона отлично от прочих — title/description/priority/category/due_date уникальны в эталонной задаче, сдвиг row[x] проявится в любом из них). Граничный шаг 6 (`tags == []` ровно list для задачи без тегов) закрепляет семантику пустого списка. Advanced-ветка шага 5 валидна: обе выдачи идут через ту же `_row_to_task_with_users`. Дефект формулировки (исправлен на месте): шаг 5 использовал `tag = "..."` — грамматика advanced допускает для tag ТОЛЬКО `IN (...)` (search.py: «tag supports only IN (...)» → 400), кейс падал бы на 400, а не на объект-сравнение. Исправлено на `tag IN ("...")`.

## Спец-проверка TC-assignu-201 (stale-гвард hotfix 71729ed)

**Механизм route-перехвата воспроизводим, ожидаемый результат верен.** Проверено по коду task-form.js: select наполняется только из ответа GET /api/users (loadAssignedOptions); assignedLoaded поднимается ТОЛЬКО в success-колбэке (onError флаг не поднимает); collectTaskForm включает `assigned_to_id` в payload ТОЛЬКО при `assignedLoaded === true`; assignedLoadGen инкрементится на каждое открытие и отсекает stale (`if (gen !== assignedLoadGen) return`). Отсюда: вариант А (route.abort → ключ отсутствует в PATCH, не `null`) — точная модель горячего пути hotfix; серверная сторона подтверждена (PATCH без ключа не трогает колонку — model_fields_set, комментарий collectTaskForm). Ожидание «assigned не очищается» (карточка = wife, GET /api/tasks → assigned = wife) — верное наблюдаемое. Сильная сторона кейса: вариант В корректно разводит легальную очистку ПОЛЬЗОВАТЕЛЕМ (загруженный список, «Не назначено» → явный null — легально) от системной (незагруженный → ключа нет) — это ровно граница, на которой был сделан major review-008. Детерминизм соблюден: гонка моделируется deferred-fulfill колбэком, ожидания — expect(), sleep нет. Паттерн route-перехвата в web-сьюте прецедирован (test_view_modal_r4.py:230–243, test_r3_dnd_ui.py:265). В кейс добавлено примечание о механизме (по коду) для автоматизатора.
