## 3. Эскалация на спеку/чеклист (не замечание кейсу — решение по поручению)

**TC-UI-013: молчаливый guard vs «понятное сообщение» в CHK-E-13.** По спеке: master-spec board (FR-6, «Перемещение задач между столбцами») путь «перенос без выбранной карточки» не определяет вообще — ни требования сообщения, ни требования молчания; арбитра в спеке нет. По чеклисту CHK-E-13 сформулирован «показано понятное сообщение об ошибке», но фактически (фикс 79ceb7b) guard в `moveCurrentTask` — тихий `return`; при этом после исправления дефекта (a) путь недостижим пользователем (оверлей скрыт, селект в скрытой модалке), поэтому сообщение не имеет наблюдателя в UI. Кейс задает проверяемый критерий «запрос не уходит, доска не ломается» и прямо фиксирует расхождение с формулировкой чеклиста.

**Решение ревьюера:** кейс принимается — критерий объективен, воспроизводит продовый путь дословно (`POST /api/tasks/null/move`, 422 `int_parsing`) и проверяет суть регрессии; требование сообщения из CHK-E-13 при недостижимости пути пользователем — оверспецификация чеклиста, не дефект кейса. Формулировка CHK-E-13 и допустимость «молчаливого» guard для недостижимых путей — кандидат в «Дефекты спеки» чеклиста; эскалация ПМ (право решать — за Заказчиком). Кейс TC-UI-015 в эскалации не нуждается: guard комментария сообщение показывает, кейс проверяет его дословно (текст совпадает с board.js посимвольно).

## 4. Наблюдение для ПМ (прогноз, не замечание)

TC-UI-017 шаг 7 («клик по карточке архивной задачи в результатах поиска открывает карточку с признаками») с высокой вероятностью вскроет продуктовый дефект: в текущей реализации `renderCard` в search.js не вешает click-обработчик на карточки результатов (в отличие от board.js), детальной карточки на странице поиска нет. ПМ: будьте готовы к баг-репорту по этому шагу при прогоне.

- **Трассировка:** программная сверка 18 TC ↔ 18 CHK-E (1:1, порядок, источники); канон ID в телах; ворота `flow_check.py` + `openspec validate --all --strict` — зеленные.
- **Соответствие спеке:** ожидания сверены с master-specs и фактическим поведением кода: текст ошибки входа `Неверный логин или пароль` (login.html, role=alert, статичен — NFR-7 «логин не раскрывается»), редирект 302 на `/login` (middleware.py), сообщение 409→`fast line занята` (board.js), UI-валидация названия, текст guard комментария дословно, сортировка fast первыми (`ORDER BY is_fast DESC`), ленивая архивация при GET доски и граница 00:00 UTC+3 (board.py: лексикографическое сравнение done_at формата `+03:00`).
- **Regression E-6/E-13/E-15:** дословность прод-дефектов сверена с кодом ДО фикса (диф 79ceb7b): видимость оверлеев поверх `hidden`, `POST /api/tasks/null/comments`, `POST /api/tasks/null/move` → 422 `int_parsing`; механика крюков проверена против board.js: `change`-листенер на `#task-move-select`, `submit`-листенер на `#comment-form` (requestSubmit проходит нативную валидацию — поле заполнено, событие сработает), guard-ветки и тексты совпадают с кейсами. TC-UI-006 корректно объясняет отсутствие отдельных DOM-модалок редактирования/удаления (редактирование = та же обертка; удаление = `window.confirm`).
- **Селекторы:** рольные/семантические — основной инструмент (get_by_role/get_by_label по фактической разметке: label-обертки, nav, h1/h2/h3, role=alert); ID-локаторы обоснованы в соглашениях (скрытые модалки без ARIA-роли; секции-скоупы там, где два одинаковых «Найти»); data-* (`data-status`, `data-cards`, `data-loaded`) существуют в шаблонах. Запрещенные паттерны (XPath, стилевые классы, цепочки div>) в шагах отсутствуют — упомянуты только в списке запретов; два класса-исключения (`task-card-fast`/`has-fast` — факт разметки, цвет спекой не зафиксирован, Дефект спеки №3) и `.task-fast-badge` (замечание №3). `sleep` — только две оговоренные паузы 1 с (замечание №4).
- **Сквозность:** все 18 кейсов ведут путь пользователя через UI (формы, модалки, клики, сайдбар, поиск); перехват сети — только для негативных утверждений «запрос не ушел»; API — только очистка данных после сюита. Дублирования API-сюита нет (доменные проверки — коды/тела — в кейсы не перенесены).
- **E-18 / механика DB-крюка (вариант Б):** формат `'${D-1}T15:00:00+03:00'` совместим с лексикографическим сравнением board.py и способом записи done_at приложением; смещение done_at при status=done запускает ленивую архивацию при первом чтении доски (page.reload) — соответствует спеке archive («WHEN наступает следующий день и доска открывается/обновляется»); skip без `EKOTOV_WIKI_DB_PATH` согласован с tests/api/conftest.py (DB_PATH_ENV, тот же паттерн). Проверка освобождения fast line после архивации соответствует ACTIVE_STATUSES. **Но** предусловие «fast line свободна» в цепочке сюита не обеспечено — major №1.
- **Данные:** конкретные значения во всех 18 кейсах (титулы, приоритеты, даты, фильтры); изоляция — уникальные фиксированные названия, очистка через DELETE по списку ID.
- **Негативные:** у всех 7 негативных кейсов явный проверяемый исход (нет POST + сообщение/состояние; редирект; 409-отказ; отсутствие карточки).

**Не проверено (за пределами процедуры ревью кейсов):** живой прогон кейсов в браузере не выполнялся — ревью статическое (тексты кейсов ↔ спеки ↔ код/разметка); исполнимость и флейкоустойчивость на реальном окружении подтвердит автоматизация (следующий этап конвейера).
