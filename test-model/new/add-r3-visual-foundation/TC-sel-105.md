# TC-sel-105 — Изменение справочника отражается в обоих селект-полях

- **CHK:** CHK-176
- **Change:** add-r3-visual-foundation
- **Источник:** search (MODIFIED): «Селект-поля…из фактических данных» (FR-35); Сценарий «Изменение данных отражается в селект-полях»
- **Тип:** поз. | **Приоритет:** Must
- **Среда/предусловия:** web-стенд tests/web; вход owner; в справочнике есть категория «Дом» (seed); API-сессия для управления справочником. **Прогон в одиночной сессии** (не в параллельном наборе): шаг 4 удаляет категорию — параллельный кейс, создавший на ней задачу, сломал бы DELETE. Категория `QAT-sel-новая` — узкая QAT-префиксная, задачи на ней кейсом не создаются.
- **Шаги:**
  1. Через API создать категорию `QAT-sel-новая` (DELETE в teardown; задача на ней не создается — удаление свободной категории разрешено).
  2. Открыть форму задачи: `#task-category` содержит `QAT-sel-новая`.
  3. Открыть /search: `#search-category` содержит `QAT-sel-новая`.
  4. Через API удалить `QAT-sel-новая`; переоткрыть оба поля — категория исчезла из обоих. (Проверка удаления — **дополнение автора кейса** сверх CHK-176/дельты, которые требуют только появления; ожидание шага сохранено.)
- **Ожидаемый результат:** оба селекта следуют за фактическим содержимым справочника (появление и удаление отражаются в форме и в фильтре; опции перезагружаются при каждом открытии — селект следует за данными, не за статикой).
- **Тестовые данные:** категория `QAT-sel-новая` (POST /api/categories → DELETE в teardown).
