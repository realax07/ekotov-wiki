## 3. Заявленное отклонение: служебная колонка tasks.r4_backfill

**Оценка решения (вопрос оркестратора):**

- **Законность — да, в рамках задачи 1.1.** Спека недоопределяет сверку (г) для повторных прогонов: формула design §1 «COUNT(assigned IS NULL) = числу задач, созданных ПОСЛЕ миграции (0 на момент накатки)» невычислима при повторном прогоне после того, как приложение начало создавать задачи с NULL assigned (FR-37). Без маркера-границы повторный прогон после жизни релиза дает ложный FAIL. Альтернативы (сверка только по снимку текущего запуска) задачу не решают — в снимок попадают и послерелизные задачи. Механизм «метка первого наката» — минимальное корректное решение; семантика реализована правильно (первый прогон: все задачи «существующие», метка всем; повторный: метки нет → не бэкфиллится; NULL creator у немаркированных → сверка (в) → exit 1 — аномалия вне прикладного слоя ловится, как и заявлено).
- **Не сверху ли скоупа — нет.** Колонка нужна именно идемпотентности/сверке задачи 1.1; в контракты API не входит; задач 5.1+ не касается (сервер просто не трогает колонку).
- **Риски — приемлемые, но назвать:** (а) окно между шагом 4b (миграция) и шагом 5 (рестарт): старый код еще жив и может создать задачу без creator и без метки → последующий повторный прогон даст exit 1 (безопасный отказ с восстановлением из бэкапа, не порча данных; окно секунды); (б) лексикографическое сравнение `created_at <= r4_backfill` при разных смещениях TZ (created_at UTC+00:00, метка МСК+03:00) недостоверно — но терм избыточен (все маркированные задачи созданы до метки, немаркированные отсечены IS NOT NULL) — см. R-3; (в) сравнение строковых снимков задач по id — при конкурентной вставке в окне снимок→BEGIN IMMEDIATE возможен ложный FAIL (R-4).
- **Должно ли быть в sdd — ДА, обязательно** → **R-1 (major):** `tasks.r4_backfill TEXT` — постоянная колонка схемы, отсутствует в sdd §4 (модель данных) и design §1. В этом проекте sdd — контракт: последующие задачи Р4 (1.2, 5.1, поиск FR-46) и финальное сведение пакета читают §4; колонка, живущая только в docstring кода (к тому же с неверной атрибуцией «tasks.md 1.1» — в tasks.md ее нет), — рассинхрон кода и спеки. Прецедент дисциплины: «расхождение RUNBOOK и deploy.sh недопустимо» — тот же принцип для схемы.
  **Рекомендация:** внести в sdd §4 в блок tasks: `r4_backfill TEXT -- служебная метка первого наката migrate_r4 (граница «существующие на момент накатки»); вне API-контрактов; не создается SCHEMA_SQL` + одним предложением в design §1 рядом со сверкой (г) описать механизм границы; поправить атрибуцию в docstring migrate_r4.py. Вопрос о форме записи в спеку (дефект недоопределенности design §1) — эскалация СА вместе с этим ревью: design §1 следует дополнить формулой сверки для повторных прогонов.
