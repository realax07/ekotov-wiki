## Вердикт: **ВЕРНУТЬ** (СА, до dev-волн)

Пакет архитектурно состоятелен по замыслу (двухслойная защита «гейт =
поверхность маршрутов, схемные тесты = payloads», экспорт из живого кода,
порядок волн по ОВ-4), FR-покрытие полное, `openspec validate --strict`
зеленый, content_when-механика гейта реализуема на фактическом коде (все
эндпойнты всех сервисов действительно объявлены декораторами `@router/@app`
— см. §«Подтверждено»). Но **гейт дрейфа в текущем виде немержибелен**:
два существующих правила (IR-07, IR-01) дают НЕУСТРАНИМЫЕ ложные DENY на
штатные PR пакета — доказано симуляцией. Плюс два значимых дефекта фактов
(числа маршрутов, health в search-контракте). Возврат СА на точечные
правки design/tasks/specs — код и замысел не пересматриваются.

## Дефекты

### Блокирующие (ложные DENY гейта — доказаны прогоном)

**Д-Б1. IR-07 в текущей формулировке несовместим с пакетом.** Существующее
правило IR-07 (`when: ^contracts/` + content_when по «/api/…|"paths"|$ref»
→ require ядерного `contracts/openapi.json` в диффе) DENY-ит:

- **волны 2–4** — любой PR заморозки: новый файл
  `contracts/openapi-video.json` матчится, content-regex совпадает,
  ядерного контракта в диффе нет;
- **все будущие ОГР-31 PR** — правка кода сервиса + перегенерация
  контракта того же сервиса: ядерный контракт по-прежнему не в диффе.

Симуляция (check_impact_rules на клоне main 7cf5b6a, staged-дифф):

```
Кейс «новый contracts/openapi-video.json»            → DENY (IR-07)
Кейс «services/video/app/videos.py + контракт video» → DENY (IR-07)
```

Требование неустранимо по построению: перегенерация ядра при неизменном
ядре дает пустой дифф, а пустой дифф требование не засчитывает — это сам
пакет фиксирует в research Р-4. Design §5 при этом явно сохраняет IR-07
(«правка чужого контракта-файла по-прежнему требует ядерный переген») —
внутреннее противоречие пакета. **Фикс:** сузить `when[].path` IR-07 до
`^contracts/openapi\.json$` (ядерный контракт — по образцу сужения IR-01
из design §5) как обязательное сопутствующее изменение волны 7.

**Д-Б2. Сужение IR-01 запланировано в волну 7, а нужно ДО первой волны с
якорем.** Существующий IR-01 (`when: ^services/[^/]+/openapi`) уже на main
DENY-ит новый якорь: симуляция «новый services/video/openapi.yaml» →
`DENY (IR-01): …но в диффе нет contracts/openapi.json`. Якоря добавляются
в волнах 2–4, правка IR-01 — в волне 7 (tasks 7.1, design §5
«обязательное сопутствующее изменение») → волны 2–4 немержибельны в CI.
**Фикс:** перенести сужение IR-01 (`^services/[^/]+/openapi\.json$`) в
волну 2 (первую, добавляющую якорь) или отдельной «волной 0»; design/tasks
поправить соответственно.

### Значимые (факты пакета расходятся с кодом)

**Д-З1. Числа маршрутов video/images не совпадают с кодом.** Фактические
декораторы (grep по main 7cf5b6a):

| Сервис | @router/@app-маршруты | Пакет утверждает |
|---|---|---|
| video | **14 операций** (videos.py 7 + social.py 6 + `@app.get /api/health`); живой /openapi.json = 10 path-items | **15** везде (FR-135, design §1 assert «video: 15», tasks 2.1/2.2 «якорь содержит все 15 путей», spec-сценарий «15 маршрутов») |
| images | **11 операций** (gallery.py 10 + health) | «11 маршрутов gallery **+ /api/health**» = 12 (FR-134, design §1 assert «images: 11 + /api/health», tasks 3.1) |

Числа захардкожены в ассерты design §1 («расхождение = RuntimeError») —
упадут в волнах 2–3 и потребуют правки ТЗ-фактов на лету; «15 путей» для
якоря невыполнимо в принципе (путей 10, операций 14). **Фикс:** снять
числа с кода (14/11 операций либо формулировка «все маршруты живого
/openapi.json, сверка множеством path-items»), поправить FR-134/135,
design §1, tasks 2.1–3.1, сценарии specs.

**Д-З2. Требование «exempt — только /api/health и authcheck» для КАЖДОГО
контракта не выполняется для search.** Факт: замороженный
`contracts/openapi-search.json` содержит **4 пути** (это монолитный экспорт
`export_openapi_search.py` с фильтрацией по префиксам /api/search*,
/api/suggestions*; ассерт TC-openapi-201 «ровно 4 пути»), а живой
`/openapi.json` **сервиса** search отдает **5 путей** — включая
`/api/health` (ассерт TC-openapi-205). FR-137 и Requirement «Единый формат
и место контрактов сервисов» требуют, чтобы каждый контракт фиксировал
пути и модель auth с exempt `/api/health` — для search-контракта это
несамосогласовано; паттерн волн 2–4 «замороженная спека = живой
/openapi.json 1:1» на search не выполняется (4 ≠ 5). **Фикс (на выбор
СА/ПМ):** либо явно оговорить в FR-137/specs, что search-контракт —
отфильтрованное подмножество (health-исключение — особенность эталона,
наследие монолитного экспорта), либо включить `/api/health` в
search-контракт волной 1 с синхронной правкой TC-openapi-201/якоря
(меняет замороженный «эталон» — требует отдельного решения, ОГР-29 не
нарушает: поведение не меняется).

### Замечания (не блокирующие)

- **Н-1.** content_when в design §5 / tasks 7.2 задан только регэкспом;
  по схеме impact_rules.json это список `{path, regex}` (образцы — IR-06/07).
  Вписать в design path-компонент (`services/<svc>/app/`, `backend/app/`),
  чтобы dev не собирал форму по аналогии.
- **Н-2.** Живой FastAPI-экспорт не содержит схем 4xx (ошибки сервисов идут
  через кастомный exception handler, в auto-схему не попадают) — Error-схема
  и 401/404/409/422 попадут в контракт только пост-аннотацией экспорт-скрипта.
  Design §2 это предусматривает («post-export шаг»), но формулировку
  «источник истины — живой код» стоит дополнить: «контракт = детерминированный
  экспорт + аннотация ошибок скриптом», иначе «повторный экспорт стабилен»
  выглядит противоречащим ручным правкам.
- **Н-3.** Кейс позитива tasks 7.3 («тот же дифф + строка в
  contracts/openapi-video.json → green») в текущем виде не пройдет из-за
  Д-Б1; после фикса IR-07 станет верным — проверить при code_review.
- **Н-4.** Именование: политика arch-review называет файл
  `review-NNN-architecture.md`; путь `arch-review-001.md` задан брифом ПМ —
  допустимое отклонение, зафиксировано здесь.

## Подтверждено (сверка с кодом/механикой, main 7cf5b6a)

- **FR-покрытие полное:** FR-133…FR-141 — все 9 покрыты дельтами capability
  `contracts` (ADDED-only) с трассировкой в тексте; NFR-45/46, ОГР-29…31,
  ОВ-1…ОВ-9, Д-16/17 отражены в requirements/design/tasks/specs.
- **content_when реализуем и точен:** механизм штатный — `pr_validate.py`
  check_impact_rules читает content_when по git-патчу (~L887–950),
  `flow_preflight.py` — тот же фильтр (L361); используются IR-06/07.
  **Все эндпойнты всех 4 сервисов объявлены декораторами** `@router.*` /
  `@app.get`: images gallery.py ×10 + main.py health; video videos.py ×7 +
  social.py ×6 + main.py health; search search.py ×2 + suggestions.py ×2 +
  main.py health; weather routes.py ×1 + main.py health; `add_api_route`,
  `api_route`, mount-маршруты не используются; `include_router` — только
  существующих роутеров. Регэксп `\+\s*@(router|app)\.(get|post|put|patch|
  delete|api_route)` их ловит; правки без новых декораторов (static_v-бампы
  `pages.py`, миграции) — не триггерят. Ложных DENY от самих IR-08…IR-12
  ожидаемо нет (слепое пятно «дрейф payload без декоратора» осознанно
  закрыто вторым уровнем — волна 5).
- **IR-08…IR-12 свободны**; шаг pr_validate в flow.yml подтвержден
  (~L110); IR-01 триггер `^services/[^/]+/openapi` подтвержден (матчит
  якоря — обоснование сужения верно, см. Д-Б2 о сроках).
- **nginx-тест реализуем на HEAD:** все семейства design §6 существуют в
  `services/frontend/nginx/ekotov-wiki.conf` — пары «= точный + ^~ префикс»
  для search/suggestions/images/videos/weather, `/videos/` (authcheck через
  `= /_video_auth`), named-локации `@search_down/@images_down/@videos_down/
  @weather_down`; /games/ — прокси, вне скоупа (ОВ-9).
- **Порядок волн корректен** по замыслу: search (эталон) → video → images →
  weather → схемная валидация → карта/nginx-тест → гейт последней волной
  (ОВ-4, ТЗ §10.3); дельты волн не пересекаются; гейт не может быть включен
  раньше заморозки — impact §4 это фиксирует. Нарушение только в сроках
  правки IR-01 (Д-Б2).
- **Артефакты-предпосылки существуют:** contracts/openapi.json,
  contracts/openapi-search.json, services/search/openapi.yaml (якорь,
  образец), scripts/export_openapi_search.py, architecture/map.md.
- **Формат/валидность:** `openspec validate add-p20-contracts --strict` —
  valid; helper §3 `Path(__file__).resolve().parents[2]/..` — корректный
  путь к корню репо из services/<svc>/tests/.
