## Отклонения от design §6/§5 (осознанные)

1. **Путь выноса бэкапа**: design §5 не фиксирует механику «из контейнера
   наружу». v2 использовала `docker compose cp`; v3 использует tar-поток
   (`exec tar -cf - | tar -xf -` на хосте) — модуль пишет во временный
   каталог контейнера (BACKUP_DIR=/tmp/.deploy-bk), откуда поток выносится
   без docker cp. Причина: единый код с sidecar (требование ТЗ) означает
   файлы с именами модуля (wiki-daily-*) и на стороне контейнера; tar-поток
   переносит их одним шагом, `mv` на хосте дает релизные имена. Метод
   документирован в шапке скрипта и RUNBOOK §7.6.
2. **wait_healthy для nginx добавлен отдельным шагом**: design §6 формулирует
   «up app → healthy → up search/backup → healthy → смоук»; фактически
   nginx (frontend) тоже поднимается до смоука и ждет healthy — иначе смоук
   гоняет по еще не готовому TLS-фронту. Это не новый сервис в матрице —
   frontend-образ и так был (в v2), изменился только порядок/ожидание.
3. **Коды смоука поиска: 200/401/422 вместо только 200**: на пустом стенде
   без сессии search отвечает 401 (middleware), без `q` — 422. Оба = «ответил
   search» (502/503 = провал); маршрутность доказывает X-Service. На проде
   с браузерной сессией будет 200 (проверено на стенде с сессией).
4. **COMPOSE_EXTRA** — новая env-переменная (в design не описана): минимальный
   механизм для тестовых прогонов с override-файлами (self-signed серты).
   В бою не используется (пустая).

## Нерешенные вопросы / наблюдения

1. **Права тома на свежем стенде** (не прод-дефект, но зафиксировать):
   именованный том при первом создании принадлежит root:root 755 — app

   `chown 10001` тома (один раз, вручную или шагом первого деплоя).
   На стены деплоя НЕ влияет (том не пересоздается), но задачи 2.3/2.4
   (прод-параллель на :10444 — там тоже НОВЫЙ том проекта) споткнутся.
   Рекомендация: включить однократный chown тома в первый деплой нового
   проекта или в RUNBOOK §7.3/7.6 чеклист (решение — за владельцем задач 2.3+).
2. **backups-test на диске стенда**: bind deploy/backups-test должен быть
   доступен uid 10001 (на этом стенде поправлен chown'ом через docker-run;
   на проде bind /var/backups/ekotov-wiki уже wiki:wiki). См. также п.1.
3. **Успешный health search на пустом томе** — наблюдение, не дефект:
   /api/health exempt БД, search healthy даже без схемы; первый реальный

### Что закрыто

- **1.4-a (major) — staging для релизного бэкапа.** mv-циклы больше не гоняют по
  gloбу всего `BACKUP_DIR` (где лежит суточная история sidecar). Новый
  staging-подкаталог `${BACKUP_DIR}/release-staging/` (env-оверрайд
  `RELEASE_STAGING`): tar-вынос из контейнера → staging → mv в релизные имена
  `wiki-pre-*`/`avatars-pre-*` → `rmdir` staging. Суточная история sidecar
  `wiki-daily-*`/`avatars-daily-*` НЕ затрагивается — страховой слой design §5
  («sidecar страхует между релизами») восстановлен. Retention-маска
  (`backup.py:prune_old_backups`, префиксы `wiki-daily-`/`avatars-daily-`)
  staging-каталог не затрагивает: он не читает подкаталоги вовсе
  (`os.listdir` + `os.remove`, не `rglob`); после `rmdir` каталог вообще
  отсутствует. Добавлен явный guard `[ ${moved} -eq 1 ]` — mv-цикл
  проваливается, если свежевынесенный файл не найден ровно один (ранее
  корректность держалась на неявной сортируемости штампов).
- **1.4-b (minor) — смоук 6.7.** `[OK] 502 не обнаружено` теперь печатается
  только при `NGINX_502 = 0`; при 502>0 — `fail` с контекстом (деплой
  прерывается, взаимоисключающий WARN+OK исчез). Критерий 502=0 из
  tasks.md/design §6 теперь enforced, а не WARN-only; оговорка про 503
  search-деградации (управляемый error_page, не 502) — в тексте fail и RUNBOOK.
- **1.4-c (minor) — cleanup контейнера.** `rm -rf /tmp/.deploy-bk /tmp/backup.py`
  получил `|| ok "cleanup ... не удался (не критично)"` — сбой cleanup после
  успешного бэкапа больше не роняет скрипт по `set -e`.
- **1.4-d (nit) — закрыт фиксом** (тривиально): ограничение не-квоченного
  `${COMPOSE}` (разбиение по словам; пути с пробелами не поддерживаются)
  зафиксировано комментарием в шапке у определения `COMPOSE`.
- **1.4-e (nit) — закрыт фиксом** (тривиально): магическое `36500`
  прокомментировано (~100 лет — чтобы prune внутри временного /tmp/.deploy-bk
  контейнера ничего не удалил; retention на хосте ведет sidecar).
