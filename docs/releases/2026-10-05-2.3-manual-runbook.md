# Инструкция 2.3: прод-параллель на :10444 (исполняет Заказчик под sudo)

Пакет add-microservices-full, задача 2.3. Текущее состояние кода: коммит
`28a6dc39` (ветка `add-microservices-full`, содержит все задачи 0.x–2.2).
Прода и systemd **не трогаются** на всем протяжении 2.3. Откат = см. §5.

> Порт 10444 и проект параллели изолированы от прода: compose-проект
> `ekotov-wiki-par` (свой префикс контейнеров и СВОЙ том `wiki-data`),
> публикация только `10444`. Прод на 10443 (systemd + его nginx) не
> участвует ни в одной команде ниже.

---

## 0. Предусловия (2 минуты)

```bash
# 0.1 Клон/обновление рабочего клона до целевого коммита (SRC_DIR скрипта):
sudo git -C /opt/ekotov-wiki fetch origin 2>/dev/null
# Если клона нет — склонируй репозиторий в /opt/ekotov-wiki и checkout ветки:
#   sudo git clone <url> /opt/ekotov-wiki
#   sudo -C /opt/ekotov-wiki checkout add-microservices-full
sudo git -C /opt/ekotov-wiki checkout add-microservices-full 2>/dev/null || true
sudo git -C /opt/ekotov-wiki pull --ff-only 2>/dev/null || true
sudo git -C /opt/ekotov-wiki log --oneline -1   # ожида: 28a6dc39 (или новее)

# 0.2 Порт 10444 свободен (пусто = ок):
ss -tln | grep 10444

# 0.3 Свободная память ≥ 2 GB:
free -m | awk '/Mem:/{print "available MB:", $7}'

# 0.4 deploy/.env с SECRET_KEY (один раз; не коммитится):
sudo test -f /opt/ekotov-wiki/deploy/.env && echo ".env есть" || {
  echo "SECRET_KEY=$(sudo grep -oP '(?<=^SECRET_KEY=).*' /opt/ekotov-wiki/.env)" | \
    sudo tee /opt/ekotov-wiki/deploy/.env >/dev/null
  sudo chmod 600 /opt/ekotov-wiki/deploy/.env
}
```

## 1. DRY_RUN — печать плана (ничего не меняет)

```bash
cd /opt/ekotov-wiki
sudo -E DRY_RUN=1 PROJECT=ekotov-wiki-par \
  SMOKE_URL=https://127.0.0.1:10444 \
  NGINX_PORT=10444 \
  RELEASE_TAG=p12-rc1 \
  bash deploy/deploy.sh
```
Ожидаю: EXIT=0, печать шагов (бэкап-пропуск на пустом каталоге — норм,
build, миграция, up app → search/backup → nginx, смоук-матрица).
При ошибке — остановись, пришли вывод, шаг не исполняй.

## 2. Сборка образов и подъем стека (боевой прогон)

```bash
cd /opt/ekotov-wiki
sudo -E PROJECT=ekotov-wiki-par \
  SMOKE_URL=https://127.0.0.1:10444 \
  NGINX_PORT=10444 \
  RELEASE_TAG=p12-rc1 \
  bash deploy/deploy.sh
```
Скрипт сам: pre-backup → build 4 образов (app/frontend/search/backup,
тег p12-rc1) → one-shot миграция ядра → up app → healthy → up search
backup → healthy → up nginx → healthy → смоук-матрица (health ×2,
поиск + X-Service через nginx, статика, аватары, 502=0, теги образов =
релизные) → image prune. Останов на первой ошибке (set -euo pipefail).

## 3. Наполнение параллельного тома данными прода (ОДНОКРАТНО)

Параллельный стек поднят с ПУСТЫМ томом `ekotov-wiki-par_wiki-data`.
Переносим копию прода (контейнеры параллели остановить на время):

```bash
cd /opt/ekotov-wiki/deploy
sudo -E PROJECT=ekotov-wiki-par docker compose stop

# 3.1 Консистентная копия живой БД прода (.backup — онлайн-безопасно):
sudo sqlite3 /var/lib/ekotov-wiki/wiki.db ".backup '/tmp/wiki-seed.db'"

# 3.2 БД → в том параллели:
sudo docker run --rm -v ekotov-wiki-par_wiki-data:/data -v /tmp:/seed \
  ekotov-wiki/app:p12-rc1 cp /seed/wiki-seed.db /data/wiki.db

# 3.3 Аватары (на этой VPS каталог пуст — шаг можно пропустить, но тогда
# все равно выполни проверку тома в 3.4):
sudo tar -C /var/lib/ekotov-wiki -cf /tmp/avatars-seed.tar avatars 2>/dev/null || \
  echo "avatars отсутствует — пропускаю tar (норма для этой VPS)"
sudo docker run --rm -v ekotov-wiki-par_wiki-data:/data -v /tmp:/seed \
  ekotov-wiki/app:p12-rc1 tar -C /data -xf /seed/avatars-seed.tar 2>/dev/null || true
sudo rm -f /tmp/wiki-seed.db /tmp/avatars-seed.tar

# 3.4 Проверка тома (внутри контейнера: файл + целостность):
sudo docker run --rm -v ekotov-wiki-par_wiki-data:/data \
  ekotov-wiki/app:p12-rc1 sh -c 'ls -la /data && sqlite3 /data/wiki.db "PRAGMA integrity_check; SELECT count(*) FROM tasks;"'

# 3.5 Подъем параллели с данными:
sudo -E PROJECT=ekotov-wiki-par NGINX_PORT=10444 docker compose up -d
sudo -E PROJECT=ekotov-wiki-par docker compose ps   # все 4 healthy
```

## 4. Смоук + приемка браузером (то, что ждет 2.3 по спеке)

```bash
# 4.1 health обоих сервисов через nginx:
curl -sk https://127.0.0.1:10444/api/health
curl -sk https://127.0.0.1:10444/api/search/health 2>/dev/null || true
# (поисковый health: https://127.0.0.1:10444/api/health от search — смотри REPORT-matrix-22 §1 за точным путем)

# 4.2 Поиск с заголовком сервиса:
curl -sk -D - -o /dev/null 'https://127.0.0.1:10444/api/search?q=test' | grep -i 'HTTP\|x-service'
# ожида: HTTP/2 200 и x-service: search

# 4.3 Статика:
curl -sk -o /dev/null -w '%{http_code}\n' https://127.0.0.1:10444/login        # 200
curl -sk -o /dev/null -w '%{http_code}\n' https://127.0.0.1:10444/static/css/app.css  # 200

# 4.4 Прод жив (контрольная точка НЕИЗМЕННОСТИ):
curl -sk -o /dev/null -w '%{http_code}\n' https://127.0.0.1:10443/login        # 200
systemctl is-active ekotov-wiki                                                # active
```

**Приемка браузером (Ваш шаг по спеке 2.3):** открой
`https://194.58.34.122:10444` — логин (продовые креды из перенесенной БД),
доска открывается, поиск находит задачу, **создай задачу** (смоук записи —
урок 2.3 контейнеризации), загрузи/обнови аватар. Результат — «ок» в чат.

## 5. Откат параллели (в любой момент, прод не затрагивает)

```bash
cd /opt/ekotov-wiki/deploy
sudo -E PROJECT=ekotov-wiki-par docker compose down -v   # стек + ТОЛЬКО том параллели
sudo docker image prune -f
```
