# План перехода на сервисы в контейнерах + гарантия контрактов (P11)

**Статус: ЧЕРНОВИК на решение Заказчика.** Проработка П11 (PRODUCT_BACKLOG.md), 2026-10-01. Ничего не реализовано — это документ-план: целевая декомпозиция, структура репозитория, механизм контрактов, e2e, devops-процедуры, план миграции с откатом и открытые вопросы (ОВ).

**Контекст и ограничения:** сайт живой (простой минимизировать), одиночный VPS 4 GB RAM, без k8s, 1 разработчик + LLM-агенты, SQLite на хосте, деплой сегодня — rsync + systemd. Позиция Заказчика по репозиториям: «кучу реп создавать не хочу, но и жить в одной как будто не хорошо» — решается в §2.

**Фактура сверена с кодом и RUNBOOK (grep/read, main `eae7bfc`):** FastAPI-монолит `backend/app/` — 11 роутеров, ~27 HTTP-маршрутов под префиксами `/api/{auth,profile,board,categories,tasks,search,suggestions,users}` + страницы Jinja2; крупнейшие модули — `search.py` (805 стр.) и `tasks.py` (708 стр.); весь продуктовый код + frontend ≈ 10 500 строк, 432 файла в git, 333 коммита. `main.py`: `openapi_url=None, docs_url=None` — **схема OpenAPI сейчас выключена** (существенно для §3). Прод: nginx :10443 (TLS self-signed до 2028-12-22, хост) → uvicorn :8377 (systemd, 1 воркер) → SQLite `/var/lib/ekotov-wiki/wiki.db` + `avatars/` (вне rsync-корня). CI `flow.yml` (43 строки) — только ворота артефактов (openspec validate, flow_check, pr_validate); тесты (~196 api + ~150 web) и линтеры гоняются локально, в CI их нет.

## 1. Целевая декомпозиция

### 1.1. Принцип этапности (главная рекомендация)

Текущий монолит — 11 роутеров с **общей БД и общими транзакциями** (короткие sqlite3-транзакции с commit в роутере, инварианты fast line и валидация категории держатся в одном процессе). Разнесение роутеров по контейнерам при общей SQLite дает границы **без транзакционности**: инвариант «fast line + priority-lock» (сейчас одна транзакция в `tasks.py`) превращается в распределенную проверку без атомарности; WAL выдержит два процесса на одном хосте, но каждая новая пара «сервис–БД» — это новая точка отказа и новая схема бэкапа. Поэтому:

- **ЭТАП 1 — контейнеризация монолита как есть.** Цель П11 «сайт работает из контейнеров» достигается без изменения кода: `app` (uvicorn) + `nginx` (статика + reverse proxy) + именованный том данных. Деплой rsync → `docker compose up` с тегированными образами.
- **ЭТАП 2 — выделение сервисов по одному, по мере надобности.** Каждый сервис — отдельный контейнер (требование Заказчика соблюдено), выделяется только когда есть **операционная причина** (ресурсы, частые релизы изолированно, изоляция отказов), не «потому что можно».

### 1.2. Кандидаты сервисов

| Сервис | Ответственность | Граница контракта | Данные | Сложность выделения | Когда оправдан |
|---|---|---|---|---|---|
| `app` (ядро) | auth, tasks, board, categories, comments, profile, users, suggestions, страницы Jinja2 | Весь `/api/*` (OpenAPI, §3) + HTML-маршруты | SQLite RW (том `wiki-data`) | — (это база ЭТАПА 1) | Всегда |
| `frontend` (nginx) | Статика (`expires 7d`, кеш-бастинг `?v=` без изменений — URL те же), reverse proxy на `app`, security-заголовки, gzip; TLS — ОВ-3 | HTTP: `/static/*`, `/avatars/*`, proxy `/ → app:8377`. Контракт — compose-сеть и порт, не API | Без томов (статика в образе) | S: конфиг `deploy/nginx-*.conf` переносится в образ почти как есть | Всегда (ЭТАП 1) |
| `search` | `search.py` (805 стр.): простой + advanced-поиск | Выделенные маршруты `/api/search*`, `/api/suggestions` — уходят из `app`, контракт фиксируется в OpenAPI до выделения | SQLite **RO** (тот же том, mount ro) | **M**: код изолирован (один файл, 18 функций, свои роутеры), но: общая БД → границы без транзакционности (поиск только читает — риск низкий); UI-фронт `search.js` продолжает звать те же URL — проксирует nginx, для браузера ничего не меняется | Первым в ЭТАПЕ 2, если поиск начнет тормозить доску или его будут дорабатывать часто (P4-направления) |
| `auth` | `auth.py` + `middleware.py` | `/api/auth/*`; проверка сессии на `app` превращается в вызов auth — **либо**auth остается в ядре | SQLite RW (sessions) | **L**: middleware вызывается каждым запросом → сетевой хоп на каждый маршрут; сессии в общей БД; выигрыша нет при 2 пользователях | **Не рекомендован** в обозримом горизонте |
| `exporter/backup` | sidecar/cron: `sqlite3 .backup` + копия аватаров, выкладка в `/var/backups` | Без HTTP; контракт — тома (`wiki-data` ro) и каталог бэкапов | Том RO + volume для бэкапов | S | Вместе с ЭТАПОМ 1 или сразу после (снимает ручной шаг из deploy.sh) |

Честная оценка «разнесение при общей SQLite»: сейчас **все** инварианты держатся транзакциями одного процесса. Каждый выделенный сервис с доступом RW к общей БД — это отказ от атомарности (прецедент инвариантов fast line), синхронизация миграций между N процессами и деградация WAL-конкурентности. Поэтому в ЭТАПЕ 2 — только сервисы с read-only или изолированным профилем записи; `search` (RO) — единственный дешевый кандидат.

### 1.3. События

Событийной шины нет и не предлагается: при 2 пользователях вся интеграция — синхронный HTTP JSON. Если когда-нибудь появится асинхронность (например, экспорт), это будет отдельная проработка.

## 2. Структура репозитория: монорепо vs полирепо vs гибрид

### 2.1. Аргументы цифрами (контекст: 1 разработчик + LLM-агенты + 1 VPS)

| Метрика | Монорепо | Полирепо (3 репы: app, frontend, contracts) |
|---|---|---|
| Изменение контракта (добавили поле в API) | **1 коммит**: схема + провайдер + потребитель + тесты атомарно | 3 PR в 3 репах, последовательность: contracts → app → frontend; рассинхрон между мержами = сломанный main где-то одного |
| CI-прогон на PR | 1 прогон (~3–5 мин с e2e на compose) | 3 прогона + отдельный механизм «прогнать e2e по трем репам вместе» (его еще надо построить — runner с checkout нескольких реп) |
| Онбординг LLM-агента на задачу | 1 clone, весь контекст в одном дереве (агент видит потребителя и провайдера) | Агенту для сквозной задачи нужно 2–3 клона и знание, какие версии совместимы |
| Синхронизация версий | не нужна (main = истина) | версии контрактов/образов, changelog, git tags на каждый релиз каждого сервиса |
| Стоимость репо-инфраструктуры | 0 | N × (защита веток, secrets CI, шаблон ревью — в этом проекте ревью-ворота `code-reviews/<id>/` привязаны к репе) |
| Размер (сегодня) | 432 файла, ~10.5k строк, .git 16 MB | те же, размазаны по 3+ репам |

Вывод: при 1 разработчике полирепо дает чистые границы собственности (некому делить) ценой синхронизации контрактов (главная боль, которую П11 как раз лечит) и невозможности атомарных сквозных изменений. Позиция Заказчика «кучу реп не хочу» подтверждается цифрами.

### 2.2. Рекомендация: монорепо с жесткими границами каталогов-сервисов (гибрид по смыслу)

Это ответ на «но и в одной нехорошо»: границы проводятся **каталогами и контрактами**, а не репозиториями. Сервис физически не может залезть в чужое — CI-gate (§3) ловит сломанный контракт, а ревью-ворота конвейера — чужие правки в чужом каталоге.

```
ekotov-wiki/
├── services/
│   ├── app/                  # ядро (ЭТАП 1 — весь текущий backend/app)
│   │   ├── app/              # пакет
│   │   ├── tests/            # api-сьют перезжает сюда (ЭТАП 1)
│   │   ├── Dockerfile
│   │   └── openapi.yaml      # экспорт схемы (§3) — или генерируется в CI
│   ├── frontend/             # nginx-образ: конфиг + статика (ЭТАП 1)
│   │   ├── nginx/            # из deploy/nginx-*.conf
│   │   ├── static/  templates/
│   │   └── Dockerfile
│   └── search/               # появляется в ЭТАПЕ 2 (выделение search.py)
│       ├── app/  tests/  Dockerfile  openapi.yaml
├── contracts/                # OpenAPI-схемы всех сервисов + правила диффа (§3)
├── e2e/                      # сквозные сьюты против compose-стенда (§4)
├── deploy/                   # compose.yaml (прод), compose.test.yaml (стенд), RUNBOOK.md
├── openspec/  docs/  design/ scripts/   # без изменений
└── .github/workflows/flow.yml           # + контрактный gate и e2e (§3–4)
```

Перенос в `services/` — механический (пути + CI + RUNBOOK), делается в ЭТАПЕ 1 одним change-пакетом; можно начать и с плоской структуры, оставив каталогизацию на ЭТАП 2, — но лучше один раз, до появления второго сервиса.

## 3. Гарантия контрактов

Проблема Заказчика: «при изменениях в разных сервисах API-вызовы не должны ломаться». Сегодня гарантия фактически одна — 196 api-тестов против монолита; контракты описаны в sdd §3 прозой, машинной схемы нет (`openapi_url=None`).

### Вариант А — OpenAPI-схема как контракт + CI-gate на дифф *(рекомендация)*

1. Включить схему: `openapi_url="/openapi.json"` в `main.py` (docs/redoc оставить выключенными). Нюанс безопасности: middleware сейчас пропускает только login/health — `/openapi.json` будет за 401 (сессия), для CI — fetch под тестовой сессией; публичной раскрывать не нужно. FastAPI строит схему из pydantic-моделей бесплатно, вручную описывать нечего.
2. Контракт = зафиксированный `openapi.json` в `contracts/`. Изменение схемы, несовместимое с прошлой (удалено поле/эндпоинт, сужен тип, новый обязательный параметр) = **breaking** → блок merge, пока не помечен `BREAKING:` с миграционной заметкой (потребитель обновлен тем же коммитом — плюс монорепо).
3. Контрактные тесты потребителя: schemathesis против стенда (property-based по схеме) + точечные тесты «потребитель читает ровно те поля, что объявлены» — в `services/<consumer>/tests/`.
- **Плюсы:** дешево (FastAPI отдает схему из кода; gate — ~50 строк в CI), точный машинный дифф, совместимо с агентами-исполнителями (агент видит схему как спецификацию и не может «немного» изменить ответ без срабатывания gate). **Минусы:** схема описывает форму, не семантику (409-инварианты все равно проверяют функциональные тесты).

### Вариант Б — pact-подобные потребительские контракты

Каждый потребитель (frontend, search) фиксирует ожидания, провайдер верифицирует. **Не рекомендован сейчас:** полный объем (pact-python + брокер или подобие) при ≤2 сервисах и одном потребителе-браузере; выигрывает при 5+ независимых командах — не наш случай. Может быть добавлен точечно позже, если появится второй реальный потребитель API.

### Вариант В — только e2e на compose

**Не достаточен как единственный:** ловит поломку поздно (полный прогон ~5+ мин), не говорит *что* именно сломано в контракте, ломается по любому.UI-дефекту. Оставляется как **страховочный слой** (§4), а не gate.

**Рекомендация: А + В.** А — быстрый gate в CI на каждый PR; В — сквозной прогон перед деплоем. Для агентов-исполнителей это лучшая комбинация: gate объективен (дифф JSON-схемы), не требует вкусовых ревью и ловит ошибку агента до ревьюера.

## 4. Сквозные тесты (e2e)

- **Где живут:** `e2e/` в монорепо (та же база playwright, что `tests/web` — переиспользование хелперов, `dnd_helpers`, фикстур).
- **Против чего:** compose-стенд (`deploy/compose.test.yaml`) — та же топология, что прод: nginx-контейнер → app-контейнер → временный том SQLite. Это закрывает многолетний риск «web-стенд эмулирует nginx через `http.server`» (architecture/map.md §6.1): заголовки кеша, gzip, security-заголовки впервые проверяются тестом, а не только прод-смоуком (класс DEF-002/003).
- **Кто гоняет:** CI — на каждый PR (после контрактного gate); локально — та же команда `docker compose -f deploy/compose.test.yaml up --build` + `pytest e2e/`.
- **Прод-смоук:** остается как есть (RUNBOOK §4.4): `/api/health` + `/login` + статика через прод-URL + `scripts/smoke_static.py` + один проход браузером. e2e прод не заменяет — прод-смоук проверяет живой TLS, кеш и конфиг хоста, которых в стенде нет.

## 5. DevOps-процедуры

| Область | Решение (рекомендация) |
|---|---|
| compose-файлы | Один `deploy/compose.yaml` (прод-топология) + `deploy/compose.test.yaml` (стенд: tmp-том БД, seeded-юзеры, другой порт). Dev/prod паритет = один и тот же образ, разные env/тома |
| Сеть | Внутренняя compose-сеть; наружу — только nginx (published `10443:10443`); `app` портов наружу не публикует (сегодня 8377 слушает только localhost — паритет сохраняется) |
| Миграции | One-shot: `docker compose run --rm app python -m app.migrate_rN` **до** `up` нового app, из того же образа (исполняет — deploy-скрипт/Заказчик). Идемпотентность обязательна (урок инцидента Р4 2026-09-30): миграция = новый шаг конвейера со свойствами текущего шага 4b — падение прерывает деплой, **репетиция на копии прод-БД со старой схемой** (три конфигурации: старая / смигрированная / свежая, включая «данные, измененные пользователем») до выкатки |
| Бэкапы | До каждого деплоя — `sqlite3 .backup` (как сейчас, без остановки); регулярный бэкап — cron на хосте или sidecar `exporter` (§1.2): том `wiki-data` ro + выкладка в `/var/backups/ekotov-wiki/`; аватары — в тот же контур (урок Р4) |
| Откат | Теги образов `ekotov-wiki/app:<release>` (не `latest`); откат = `docker compose up -d` с предыдущим тегом + при несовместимой схеме — возврат БД из пред-деплойного бэкапа (пара «код+БД», как сегодня). Прежний откат rsync-снапшотом исчезает как класс |
| Лимиты памяти (4 GB total!) | `mem_limit`: nginx 64m, app 512m, search (когда появится) 512m, резерв хосту ≥ 2 GB (systemd, бэкапы, кеши). Uvicorn 1 воркер как сейчас — незачем больше |
| Логи | `logging: json-file` с `max-size: 10m, max-file: 3` на контейнер; просмотр `docker compose logs`; journald-привычки RUNBOOK переносятся 1:1 |
| deploy.sh | Эволюция, не rewrite: шаги rsync/pip/схема заменяются на `docker compose pull/build/up`; бэкап БД, миграция-шаг, смоук — остаются. Обратная совместимость перехода: первый контейнерный деплой запускается **параллельно** с живым systemd (другой порт на время проверки), переключение — один reload nginx (минимальный простой, см. §6) |

(ЭТАП 2) Выделение search** | search.py → `services/search/` (контракт `/api/search*` заморожен в OpenAPI **до** выделения), nginx проксирует, том ro; e2e тот же | e2e+api зеленые; контрактные тесты потребителя зеленые; дифф схемы = пусто | `docker compose up` без сервиса search + возврат app-образа дообъединенной версии (маршруты убираются из app отдельным коммитом — откат одного тега) | M |
